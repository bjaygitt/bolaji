## 17.1 From certificate to trust decision

When a client receives a certificate chain, it must answer one question: should I trust that this public key belongs to this name, for this purpose, right now? Answering takes two steps:

1. **Path building:** find a chain from the leaf certificate to a root in the trust store.
2. **Path validation:** check every certificate in that chain against a long list of rules.

## 17.2 Path building

Servers are supposed to send the leaf plus its intermediates, in order. In reality, chains arrive incomplete, out of order, with extra certificates, or with expired cross-signs. Because several valid paths can exist (cross-signing, Chapter 15), clients must search:

- Match each certificate's **Issuer** name and **Authority Key Identifier** against candidate issuers.
- Look for candidates in the certificates the server sent, in a local cache, in the trust store, and, in some clients, by downloading from the **Authority Information Access (AIA)** URL in the certificate.
- If a path fails (for example, it ends at an expired root), backtrack and try another.

Good path builders, as in modern browsers and current versions of major libraries, search all possibilities. Simpler ones take the first path and fail if it is bad, which caused the 2020 and 2021 root expiry outages described in Chapter 15. This difference is why the same server can work in a browser and fail in a mobile app or a Java service.

## 17.3 Path validation

Once a candidate path exists, the client checks it using the algorithm in RFC 5280, section 6. For each certificate, from the root down to the leaf:

| Check | What fails it |
| --- | --- |
| Signature verifies with the issuer's public key | A forged or corrupted certificate |
| Current time is within Not Before and Not After | An expired or not-yet-valid certificate, or a wrong system clock |
| Issuer is allowed to be a CA (Basic Constraints CA:TRUE) | A leaf certificate pretending to be a CA |
| Path length constraints are respected | Too many CAs below a constrained intermediate |
| Name constraints are respected | An internal CA issuing for a domain outside its permitted space |
| Key usage permits certificate signing for CAs | Misused keys |
| Not revoked | A compromised or withdrawn certificate (sections 17.4 to 17.7) |
| Policy constraints are met | Rare outside government PKIs |

Then, for the leaf only:

- The **hostname** must match a SAN entry.
- The **Extended Key Usage** must allow the purpose, such as serverAuth.
- For public TLS, browsers also check **Certificate Transparency** proofs (Chapter 16).

> **Watch out.** Writing your own certificate validation is one of the most reliably dangerous things a developer can do. A 2012 study titled "The Most Dangerous Code in the World" found that many non-browser applications, including payment SDKs and cloud clients, disabled or broke validation, often through a single misused library option. Use your platform's validation, and never ship code that turns verification off "temporarily".

## 17.4 Revocation: the hard part

Sometimes a certificate must stop being trusted before it expires, usually because its private key was exposed or it was issued wrongly. **Revocation** is how the CA announces this. It has three classic mechanisms, and all of them have serious problems.

### Certificate Revocation Lists (CRLs)

A **CRL** is a signed list of the serial numbers of revoked, unexpired certificates, published by the CA at the URL in the certificate's CRL Distribution Points extension and refreshed on a schedule (for example, every few days).

- **Strengths:** simple, cacheable, and private: downloading the whole list does not reveal which site you are visiting.
- **Weaknesses:** lists can grow to megabytes, so downloading them on every connection is impractical; and a newly revoked certificate stays trusted until clients fetch the next list.

### OCSP

The **Online Certificate Status Protocol** (RFC 6960) lets a client ask the CA's responder about one certificate and receive a signed "good", "revoked" or "unknown" answer.

- **Strengths:** small, current answers.
- **Weaknesses:** an extra network request on every new connection, slowing page loads; a **privacy leak**, because the CA learns which sites each user visits; and a single point of failure, because if the responder is down, clients must decide what to do.

### OCSP stapling

With **OCSP stapling**, the server fetches its own OCSP response periodically and attaches ("staples") it to the TLS handshake. The client gets fresh, signed status without contacting the CA. It fixes the speed and privacy problems, but only if every server enables it, and an attacker with a stolen key can simply not staple. The **Must-Staple** certificate extension was designed to require stapling, but it saw little adoption.

## 17.5 Soft-fail: why revocation rarely protects anyone

What should a browser do if it cannot reach the OCSP responder? If it refuses the connection (**hard-fail**), every responder outage breaks large parts of the web. So browsers **soft-fail**: if the check fails, they proceed as if the certificate were good.

Now consider the attacker. Someone able to intercept your connection with a stolen certificate is, by definition, in a position to block your OCSP request too. Soft-fail therefore protects you only from attackers who are not able to carry out the attack. Security researcher Adam Langley summarised it in 2014: soft-fail revocation checking is like a seat belt that snaps when you crash.

This is why Chrome stopped doing online OCSP checks for most certificates years ago.

## 17.6 What browsers do instead

Browsers moved revocation from the network moment to a push model:

- **CRLSets (Chrome)** and **disallowed lists (other platforms)** are curated lists of high-priority revocations, such as compromised intermediates and major incidents, pushed to browsers through their update mechanism.
- **CRLite (Firefox)** compresses the revocation status of all publicly trusted certificates, gathered from CRLs and CT logs, into a compact data structure (originally cascading Bloom filters, and since 2025 a newer filter design called Clubcards), and pushes small updates to browsers several times a day. Firefox can then check revocation locally, privately and with hard-fail semantics.
- **Short-lived certificates** make revocation less necessary: if a certificate lives a few days, a leaked key is useful only briefly.

> **Current development.** The industry is retiring OCSP. In 2023 the CA/Browser Forum made OCSP optional for public CAs and required CRLs instead (Ballot SC-063). Let's Encrypt, the largest CA, ended its OCSP service in August 2025 and now publishes revocation only through CRLs. Combined with lifetimes falling to 47 days, revocation for the public web is becoming a matter of CRLs aggregated by browsers, plus short validity, rather than live per-connection checks.

## 17.7 Revocation inside organisations

Inside private PKIs (Chapter 18), the picture is different and often better:

- You control both the CA and the clients, so you can configure **hard-fail** checks where they matter, such as for VPN or mTLS clients.
- CRLs for a private CA are usually small and can be cached and refreshed predictably.
- You can use very short lifetimes (hours or days) for workloads and devices, which is the most robust approach of all.

Whatever the mechanism, operations matter: CRL and OCSP endpoints must be highly available, CRLs must be re-signed before their **Next Update** time even if nothing changed, and the CA's revocation signing must be monitored. An expired CRL can cause hard-failing clients to reject every certificate the CA ever issued.

## 17.8 The right order for revocation

Revoking a certificate that is still installed takes the service down for every client that checks. The safe order is always:

1. **Replace** the certificate on every installation, with a new key.
2. **Verify** each installation now serves the replacement.
3. **Revoke** the old certificate, with the correct reason code (key compromise, superseded, cessation of operation, affiliation changed).

With a key compromise, follow the same order, only faster. This is one of many reasons an accurate inventory of where every certificate is installed (Chapter 19) is essential.

## Lab: validate chains and check revocation

**1. Validate a chain manually.** Save a server's certificates (as in Chapter 15's lab) into `leaf.pem` and `intermediate.pem`, then:

```bash
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt -untrusted intermediate.pem leaf.pem
```

Remove `-untrusted intermediate.pem` and observe the failure: this is what a client sees from a server with an incomplete chain.

**2. Fetch and read a CRL.**

```bash
openssl x509 -in leaf.pem -noout -ext crlDistributionPoints
curl -s -o ca.crl <URL-from-the-output>
openssl crl -in ca.crl -inform DER -noout -text | head -30
```

Note the **This Update** and **Next Update** times and count the revoked entries.

**3. Query OCSP, where still offered.** Many CAs still run OCSP responders for now:

```bash
openssl x509 -in leaf.pem -noout -ocsp_uri
openssl ocsp -issuer intermediate.pem -cert leaf.pem -url <OCSP-URI> -resp_text | head -20
```

**4. Test hostname and time failures.** Use `openssl verify` with `-verify_hostname wrong.example` and with `-attime` set to a date after expiry, and read the errors. These are the two most common real-world validation failures.

## Failure story: the most dangerous code in the world

In 2012, researchers from Stanford and the University of Texas published "The Most Dangerous Code in the World: Validating SSL Certificates in Non-Browser Software". They tested widely used software that made TLS connections outside browsers: payment gateway libraries from major merchants, cloud storage clients, popular HTTP libraries, and mobile app frameworks.

They found that certificate validation was broken in a striking number of them. Some libraries checked the chain but not the hostname, so any valid certificate for any site was accepted. Others had confusing APIs where a parameter that looked like "verify hostname = true" actually meant something else. Many applications had simply disabled validation, often with a code comment about getting tests to pass. In every case, an attacker on the network could intercept supposedly secure connections, including payment traffic, with a self-made certificate.

The cryptography was sound; the checks around it were missing. The paper drove fixes across many libraries and is still a useful checklist: verify the chain, verify the hostname, never disable verification, and test that your code rejects bad certificates, not only that it accepts good ones.

## Chapter summary

- Trust decisions require path building, which may need backtracking, and path validation against RFC 5280 rules, plus hostname and purpose checks.
- CRLs are private but slow to update; OCSP is current but slow, leaky and fragile; stapling helps but is optional.
- Browsers soft-fail on revocation, which protects little, so they moved to pushed lists (CRLSets, CRLite) and rely on short lifetimes.
- OCSP is being retired from the public web; CRLs plus short-lived certificates are the future.
- Private PKIs can use hard-fail and very short lifetimes. Always replace before revoking.
