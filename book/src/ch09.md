## 9.1 What a signature guarantees

A **digital signature** scheme has three operations:

```
keypair   = KeyGen()
signature = Sign(private_key, message)
valid     = Verify(public_key, message, signature)   # true or false
```

A valid signature proves three things:

1. **Authenticity.** It was produced by someone holding the private key.
2. **Integrity.** The message has not changed since it was signed. Changing a single bit makes verification fail.
3. **Non-repudiation.** Because only the private key holder could have produced it, the signer cannot plausibly deny it later, assuming the key was properly protected.

Signatures differ from MACs (Chapter 6) in one crucial way. A MAC uses a shared secret, so either party could have created the tag. A signature uses a private key held by one party, and anyone with the public key can verify it. This makes signatures suitable for publishing: one signature on a software update can be verified by a billion devices that hold only the public key.

### What a signature does not guarantee

- **That the public key belongs to who you think.** A signature proves that the holder of *some* key signed. Linking that key to an identity requires a certificate or another trusted source (Part V).
- **That the signer understood or intended the content.** Signing systems that show users one thing and sign another have been abused.
- **When the signature was made.** Without a trusted timestamp, a signature does not prove it was created before a key was compromised or expired. Long-lived signatures, such as code signing, use **timestamping authorities** for this.
- **Confidentiality.** Signed messages are readable by anyone.

## 9.2 Hash-then-sign

Signature algorithms work on short, fixed-size values. Every practical scheme first hashes the message, then signs the hash. Two consequences follow:

- The signature is only as strong as the hash. If an attacker can find two messages with the same hash, a signature on one is a signature on the other. This is exactly how MD5 collisions produced a rogue CA certificate (Chapter 6).
- Large files can be signed cheaply. Signing a 4-gigabyte disk image costs the same as signing a sentence, plus the time to hash it.

## 9.3 RSA signatures

Chapter 7 covered RSA signatures: pad the hash with PKCS#1 v1.5 or PSS, then exponentiate with the private key. RSA signatures are large (384 bytes for a 3072-bit key), slow to create, but very fast to verify, which suits certificates verified many times. They remain the most common signature in the web PKI and in code signing, but are scheduled for retirement with the rest of classical public-key cryptography.

## 9.4 ECDSA

The **Elliptic Curve Digital Signature Algorithm (ECDSA)** is the elliptic curve version of the older DSA standard. It gives 128-bit security with 64-byte signatures on P-256, and is used in TLS certificates, code signing, smart cards, cryptocurrency and countless devices.

Signing works like this, with private key d and public key Q = dG:

1. Hash the message to get z.
2. Choose a secret, single-use random number k, called the **nonce**.
3. Compute the point kG and take its x-coordinate, mod the curve order, as r.
4. Compute `s = k^(−1)(z + r·d) mod n`.
5. The signature is the pair (r, s).

Step 2 is the dangerous one. The nonce k must be:

- **Secret.** If k is ever revealed, the private key follows immediately: `d = (s·k − z)/r`.
- **Never repeated.** If the same k signs two different messages, the two equations can be solved together to find k, and then d. This is how the PlayStation 3 master key was recovered (Chapter 3).
- **Unbiased.** Even if a few bits of k are predictable, or leak through timing, lattice techniques combine many signatures to recover the key. The 2019 **Minerva** and **TPM-Fail** attacks recovered keys from smart cards and trusted platform modules this way, using timing leaks of just a few bits per signature.

> **Watch out.** ECDSA is unusual among cryptographic tools in that a small flaw in one signature, not in the key, can reveal the long-term private key. Any ECDSA implementation that draws k from a random number generator inherits that generator's every weakness.

### Deterministic ECDSA

**RFC 6979** removes the dependence on randomness by deriving k from the private key and the message hash using HMAC. The same message always gives the same signature, k is unpredictable to anyone without the private key, and a broken random number generator can no longer leak the key. Many libraries now use deterministic or "hedged" nonces (deterministic plus some fresh randomness, which also helps against fault attacks).

## 9.5 EdDSA and Ed25519

**EdDSA**, and its most common instance **Ed25519** (RFC 8032), was designed to avoid ECDSA's sharp edges:

- **Deterministic by design.** The nonce is derived from a hash of a secret key component and the message. There is no random number to get wrong.
- **Complete, constant-time formulas** on Edwards curves, with no special cases for an attacker to trigger.
- **Fast and small:** 32-byte public keys, 64-byte signatures, and verification fast enough to check thousands of signatures per second per core.

Ed25519 is the default for SSH keys, is used by Signal, Tor, WireGuard and many software signing systems, and was added to FIPS 186-5 in 2023, making it acceptable in US federal systems.

| Scheme | Signature size | Security | Nonce risk | Typical use |
| --- | --- | --- | --- | --- |
| RSA-3072 PSS | 384 bytes | 128 bits | None (PSS randomness is not key-critical) | Certificates, code signing, legacy |
| ECDSA P-256 | 64 bytes | 128 bits | Severe unless deterministic | TLS certificates, smart cards, devices |
| Ed25519 | 64 bytes | About 128 bits | None by design | SSH, modern protocols, software signing |
| ML-DSA-65 | 3,309 bytes | Category 3 (post-quantum) | Hedged by design | Post-quantum signatures (Chapter 26) |

## 9.6 Signatures in the real world

### Software and code signing

Operating systems and package managers verify signatures before installing software. Code signing keys are among the most valuable keys any organisation holds: a stolen code signing key lets malware run as trusted software. The 2020 compromise of a network monitoring vendor's build system, which inserted a backdoor into signed updates delivered to about 18,000 customers, showed that the signature only proves what the build system produced, not that the build was clean. Modern supply-chain practice adds **reproducible builds**, signed build provenance, and transparency logs.

**Sigstore**, an open-source project launched in 2021, popularised **keyless signing**: a developer proves their identity through an existing login, receives a certificate valid for about ten minutes, signs, and the signature is recorded in a public transparency log. There is no long-lived signing key to steal. Major open-source package ecosystems have adopted it for publishing provenance.

### Documents and long-term signatures

Signed contracts and records may need to be verified decades later, long after the signing certificate expired and perhaps after the algorithm weakened. Standards such as PAdES (for PDFs) solve this with trusted timestamps and by periodically adding fresh timestamps over the old signatures, so that the evidence chain is always protected by a current algorithm.

### Protocols

In TLS 1.3, the server signs a hash of the entire handshake transcript with its certificate key, proving it holds the private key and binding the key exchange to its identity. In SSH, the server signs the exchange with its host key. These signatures are created millions of times per second across the internet, which is why fast schemes like ECDSA and Ed25519 dominate there.

## 9.7 Operating signature keys

Signature keys need different handling from encryption keys:

- **Value scales with what trusts them.** A root CA key, a firmware signing key or a package repository key may be trusted by millions of devices. Protect such keys in hardware security modules, with multi-person controls (Chapter 23).
- **Separate keys by purpose.** Never use one key for both signing and encryption, and never reuse a TLS server key for code signing.
- **Plan for rotation.** Devices that trust a single hard-coded signing key cannot be fixed if that key leaks. Ship devices with the ability to trust new keys, signed by the old ones.
- **Log every use.** For high-value keys, every signature should be recorded and reviewable, so a misuse is detected.
- **Use timestamps** for signatures that must outlive the signing certificate.

## Lab: sign, verify and break ECDSA

**1. Ed25519 and ECDSA with OpenSSL.**

```bash
openssl genpkey -algorithm ED25519 -out ed.key
openssl pkey -in ed.key -pubout -out ed.pub
echo "firmware v7" > fw.bin
openssl pkeyutl -sign -inkey ed.key -rawin -in fw.bin -out fw.sig
openssl pkeyutl -verify -pubin -inkey ed.pub -rawin -in fw.bin -sigfile fw.sig
```

**2. Recover an ECDSA key from a repeated nonce** (Python, with the `ecdsa` package: `pip install ecdsa`):

```python
from ecdsa import SigningKey, NIST256p
from ecdsa.util import sigdecode_string
import hashlib
sk = SigningKey.generate(curve=NIST256p); n = NIST256p.order
k = 123456789                                    # the fatal mistake: a fixed nonce
def sign(m):
    sig = sk.sign(m, k=k, hashfunc=hashlib.sha256)
    return sigdecode_string(sig, n), int.from_bytes(hashlib.sha256(m).digest(), "big")
(r, s1), z1 = sign(b"message one")
(_, s2), z2 = sign(b"message two")
k_found = ((z1 - z2) * pow(s1 - s2, -1, n)) % n
d = ((s1 * k_found - z1) * pow(r, -1, n)) % n
print(d == sk.privkey.secret_multiplier)          # True: private key recovered
```

Two signatures, a few lines of algebra, and the private key is gone. This is why deterministic nonces matter.

## Failure story: a stolen signing key and a crash dump

In July 2023, Microsoft disclosed that a threat actor it named Storm-0558 had accessed the email accounts of about 25 organisations, including US government agencies. The attackers forged authentication tokens accepted by Microsoft's cloud email service. They could do this because they had obtained a **consumer account signing key**, created in 2016, that should only have been able to sign tokens for personal accounts.

Two failures combined. First, the private signing key left its protected environment: Microsoft's investigation suggested it ended up in a crash dump that was moved into a less-protected debugging environment and later reached a compromised engineer's account, although Microsoft later said it could not confirm this path with certainty. Second, a validation flaw meant enterprise email systems accepted tokens signed by the consumer key, so one key could forge access far beyond its intended scope.

The US Cyber Safety Review Board's 2024 report called the intrusion preventable and criticised the long-lived key, which should have been rotated years earlier. The lessons map directly onto this chapter: keep signing keys in hardware where they cannot be copied into dumps, scope keys narrowly and verify scope strictly, rotate keys on a schedule, and keep an inventory of which keys are trusted by what.

## Chapter summary

- Signatures provide authenticity, integrity and non-repudiation, verifiable by anyone with the public key. They do not provide confidentiality, identity binding or timing on their own.
- All practical schemes hash then sign, so signatures are only as strong as their hash.
- ECDSA leaks its private key if a nonce is repeated, revealed or slightly biased. Use deterministic nonces (RFC 6979) or Ed25519.
- Ed25519 is fast, compact and safe by design, and is now FIPS-approved.
- Signing keys are among the most valuable secrets an organisation holds: protect them in hardware, scope them narrowly, rotate them and log their use.
