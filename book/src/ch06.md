## 6.1 What a hash function is

A **cryptographic hash function** takes input of any length and produces a fixed-length output, called a **digest** or **hash**. SHA-256, for example, always produces 256 bits (32 bytes), whether you hash one letter or a 10-gigabyte file.

```
SHA-256("hello")  = 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
SHA-256("hello.") = 0b0a0e4a7c2a4f2b... (completely different)
```

A tiny change to the input changes about half of the output bits unpredictably. This is called the **avalanche effect**. There is no key: anyone can compute a hash. That makes hashes ideal for checking whether data has changed, but useless on their own for proving who created it.

## 6.2 The three security properties

A cryptographic hash must resist three kinds of attack. Learn them in order of difficulty for the attacker:

| Property | The attacker's task | Generic cost for an n-bit hash | Why it matters |
| --- | --- | --- | --- |
| **Preimage resistance** | Given a hash, find any input that produces it | 2^n | Hashes of secrets must not reveal the secret |
| **Second-preimage resistance** | Given an input, find a different input with the same hash | 2^n | Nobody can swap a signed file for a malicious one with the same hash |
| **Collision resistance** | Find any two inputs with the same hash | 2^(n/2), by the birthday bound | Signatures and certificates sign hashes; a collision lets one signature cover two documents |

Collision resistance is the hardest property to keep, because the attacker gets to choose both inputs. It is also the first property to fall when a hash function weakens.

## 6.3 The fall of MD5 and SHA-1

**MD5** (1992) and **SHA-1** (1995) were the standard hashes for two decades. Their histories are a lesson in how cryptographic deprecation works.

- **2004:** researchers found practical MD5 collisions.
- **2008:** a team used MD5 collisions to create a rogue certificate authority certificate that browsers trusted, by getting a real CA to sign a harmless-looking certificate whose MD5 hash collided with a malicious one.
- **2012:** the Flame malware used an MD5 collision to forge a Microsoft code-signing certificate and spread through Windows Update.
- **2017:** Google and CWI Amsterdam announced **SHAttered**, the first real SHA-1 collision: two different PDF files with the same SHA-1 hash, computed with about 2^63 operations.
- **2020:** the **Shambles** attack made chosen-prefix SHA-1 collisions cost about 45,000 US dollars of cloud computing, and demonstrated an impersonation attack on PGP keys.

Between the first theoretical weakness and practical exploitation, systems had over a decade of warning. Many still did not migrate in time. Today, MD5 and SHA-1 must not be used for signatures, certificates, or any purpose that needs collision resistance. NIST plans to withdraw SHA-1 entirely by 2030.

> **In practice.** You will still find MD5 and SHA-1 used as non-security checksums (for example, to detect accidental file corruption) and in Git's original object IDs. Accidental corruption cannot exploit collisions, so those uses are tolerable, although Git is moving to SHA-256. Any use where an attacker could choose the input is not.

## 6.4 How hash functions are built

### Merkle-Damgård: SHA-2

**SHA-2** (SHA-224, SHA-256, SHA-384, SHA-512) uses the **Merkle-Damgård** construction. The message is padded and split into blocks. A compression function absorbs one block at a time into an internal state, and the final state is the hash.

This design has one surprising flaw: the **length extension attack**. Because the hash output *is* the final internal state, anyone who knows `SHA-256(secret || message)` and the length of the secret can compute `SHA-256(secret || message || padding || extra)` without knowing the secret. They simply resume hashing from the published state.

This breaks naive authentication schemes such as `tag = SHA-256(key || message)`, which some APIs used in the 2000s. An attacker could append parameters like `&admin=true` to a signed request and compute a valid tag. The fix is HMAC (section 6.5), or a hash immune to extension: SHA-512/256 (a truncated SHA-512) or SHA-3.

### Sponges: SHA-3

**SHA-3** was chosen through another NIST public competition and standardised in 2015 (FIPS 202). It uses a completely different design called a **sponge**: data is "absorbed" into a large internal state, which is then "squeezed" to produce output. Only part of the state is ever output, so length extension is impossible.

SHA-3 also provides **SHAKE128** and **SHAKE256**, called extendable-output functions (XOFs), which can produce output of any length. The post-quantum standards ML-KEM and ML-DSA use SHAKE heavily (Chapter 26).

| Hash | Output | Collision security | Length extension | Notes |
| --- | --- | --- | --- | --- |
| SHA-256 | 256 bits | 128 bits | Vulnerable | The default for most uses |
| SHA-384 | 384 bits | 192 bits | Resistant (truncated) | Required by some high-assurance profiles such as CNSA 2.0 |
| SHA-512 | 512 bits | 256 bits | Vulnerable | Faster than SHA-256 on 64-bit CPUs |
| SHA3-256 | 256 bits | 128 bits | Resistant | Different design; a hedge if SHA-2 ever weakens |
| BLAKE2 / BLAKE3 | Variable | 128 bits or more | Resistant | Very fast; common in software, not FIPS-approved |

## 6.5 Message authentication codes

A **message authentication code (MAC)** is like a hash that requires a key. Only someone holding the key can create a valid tag, and only someone holding the key can check it. MACs provide integrity and authentication between parties who share a secret.

```
tag = MAC(key, message)
verify: MAC(key, received_message) == received_tag
```

### HMAC

**HMAC** (RFC 2104, FIPS 198-1) builds a MAC from any hash function by hashing twice with the key mixed in differently each time:

```
HMAC(K, m) = H( (K XOR opad) || H( (K XOR ipad) || m ) )
```

The nested structure defeats length extension, and HMAC remains secure even with hash functions whose collision resistance has weakened. HMAC-SHA256 is the most widely used MAC in the world: it signs API requests, protects session cookies and JWTs (Chapter 14), and forms the core of the TLS 1.3 key schedule.

Other MACs you will meet: **CMAC** (built from AES, common in payment and smart card systems), **GMAC** (the authenticator inside GCM), and **Poly1305** (paired with ChaCha20).

### Compare tags in constant time

When verifying a MAC, never compare the received tag with the expected tag using ordinary string comparison. Ordinary comparison stops at the first mismatched byte, so the time it takes reveals how many leading bytes were correct. An attacker can discover a valid tag byte by byte by measuring response times. Every language offers a constant-time comparison: `hmac.compare_digest` in Python, `MessageDigest.isEqual` in Java, `crypto.timingSafeEqual` in Node.js, `subtle.ConstantTimeCompare` in Go.

## 6.6 Key derivation functions

A **key derivation function (KDF)** turns some input secret into one or more cryptographic keys. There are two very different kinds, and confusing them is a common mistake.

### KDFs for high-entropy secrets: HKDF

When the input is already a strong secret, such as the shared value from a Diffie-Hellman exchange or a master key, you use a fast KDF. The standard is **HKDF** (RFC 5869), built from HMAC in two steps:

1. **Extract:** condense the input, which may have uneven randomness, into a uniform pseudo-random key.
2. **Expand:** produce as many keys as needed, each bound to a distinct **context label**.

```
prk      = HKDF-Extract(salt, shared_secret)
enc_key  = HKDF-Expand(prk, "app v1 encryption key", 32)
mac_key  = HKDF-Expand(prk, "app v1 MAC key", 32)
```

The labels guarantee that keys for different purposes are independent: knowing one reveals nothing about the others. This **key separation** principle is central to key management (Chapter 20). TLS 1.3 derives all of its traffic keys with HKDF and labels such as "c hs traffic" and "s ap traffic".

### KDFs for passwords: deliberately slow

Passwords are the opposite of high-entropy secrets. Humans choose them, and attackers can guess billions per second using graphics cards. If you store `SHA-256(password)`, an attacker who steals the database can test every common password against every account almost instantly.

**Password hashing functions** defend against this in three ways:

1. A unique random **salt** per password, so identical passwords produce different hashes and precomputed tables are useless.
2. A tunable **work factor**, so each guess costs real time.
3. **Memory hardness**, so each guess also needs a lot of memory, which blunts the advantage of graphics cards and custom chips.

| Function | Memory-hard | Status | Guidance |
| --- | --- | --- | --- |
| **Argon2id** | Yes | Winner of the 2015 Password Hashing Competition; RFC 9106 | First choice for new systems |
| **scrypt** | Yes | Widely available | Good choice |
| **bcrypt** | Partly | Mature and common | Acceptable; limited to 72-byte passwords |
| **PBKDF2-HMAC-SHA256** | No | FIPS-approved | Use when FIPS is required, with a high iteration count (OWASP suggests 600,000) |
| Plain or salted SHA-256 | No | Unsuitable | Never use for passwords |

## 6.7 Where you will see these tools

| Task | Tool |
| --- | --- |
| Check a download was not altered | SHA-256 digest, published over a trusted channel or signed |
| Sign a certificate or document | Hash with SHA-256 or SHA-384, then sign the hash (Chapter 9) |
| Authenticate API requests or webhooks | HMAC-SHA256 with a shared secret |
| Store user passwords | Argon2id, scrypt or bcrypt |
| Turn a shared secret into session keys | HKDF |
| Derive per-tenant or per-object keys from a master key | HKDF with distinct labels |
| Build tamper-evident logs and transparency logs | Hash chains and Merkle trees (Chapter 16) |

## Lab: hashes, MACs and passwords

**1. The avalanche effect.**

```bash
echo -n "hello"  | openssl dgst -sha256
echo -n "hello." | openssl dgst -sha256
```

**2. A length extension attack, safely.** The open-source tool `hash_extender` (or the Python package `hashpumpy`) demonstrates it: given `SHA-256(secret || "user=alice")` and the secret's length, it produces a valid hash for `"user=alice" + padding + "&admin=true"`. Then confirm that HMAC is immune:

```python
import hmac, hashlib
key = b"server-secret"
tag = hmac.new(key, b"user=alice", hashlib.sha256).hexdigest()
# No extension trick produces a valid HMAC for "user=alice...&admin=true"
```

**3. Feel the cost of password hashing.**

```python
import hashlib, time, os
salt = os.urandom(16)
t = time.time(); hashlib.sha256(b"Summer2026!").digest(); print("sha256", time.time()-t)
t = time.time(); hashlib.scrypt(b"Summer2026!", salt=salt, n=2**15, r=8, p=1); print("scrypt", time.time()-t)
```

SHA-256 finishes in microseconds; scrypt takes tens of milliseconds and uses 32 MB of memory. A user logging in will not notice the difference. An attacker trying a billion guesses certainly will.

## Failure story: the hash that forged a CA

In December 2008, at the Chaos Communication Congress, a team of researchers revealed that they had created a certificate authority certificate trusted by every major browser, without the CA's permission.

They exploited three things. A commercial CA still signed certificates using MD5. Its certificates had predictable serial numbers and validity dates. And MD5 was vulnerable to chosen-prefix collisions. The team prepared two certificates with the same MD5 hash: an ordinary website certificate, and a CA certificate with powers to sign any website. They bought the ordinary certificate. The CA's signature on it was equally valid for the colliding CA certificate. Computing the collision took a cluster of 200 PlayStation 3 consoles a few days.

The researchers deliberately set their rogue certificate to expire in the past so it could not be abused, and worked with browsers before disclosure. Within weeks, CAs stopped issuing MD5-signed certificates and began using random serial numbers, a defence that the CA/Browser Forum later made mandatory. Every certificate you see today contains at least 64 bits of randomness in its serial number because of this attack.

## Chapter summary

- Hash functions produce fixed-size fingerprints and must resist preimages, second preimages and collisions. Collision resistance is only half the output size.
- MD5 and SHA-1 are broken for collision resistance. Use SHA-256, SHA-384, or SHA-3.
- SHA-2 is vulnerable to length extension; never use `hash(key || message)` as a MAC. Use HMAC.
- MACs need shared keys and constant-time tag comparison.
- Use HKDF with distinct labels to derive keys from strong secrets, and Argon2id, scrypt or bcrypt for passwords.
