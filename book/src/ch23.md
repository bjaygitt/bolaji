## 23.1 Why hardware

A key stored in a file or in application memory can be copied by anyone who gains administrator access, reads a backup, captures a crash dump (as in the Storm-0558 case, Chapter 9), or exploits a memory-disclosure bug (Heartbleed, Chapter 12). Once copied, it can be used anywhere, forever, without leaving a trace.

A **hardware security module (HSM)** is a hardened device that generates, stores and uses keys inside a tamper-resistant boundary. Applications send requests ("sign this", "unwrap that"); the HSM performs the operation and returns the result. **The key never leaves the boundary in usable form.** An attacker who fully compromises the server attached to an HSM can misuse it while they have access, but cannot take the key away. Remove the attacker and the key is safe again.

## 23.2 Inside an HSM

| Component | Purpose |
| --- | --- |
| **Tamper-resistant enclosure** | Sensors detect drilling, opening, voltage or temperature attacks and erase (zeroise) secrets |
| **Secure cryptographic processor** | Performs operations with side-channel countermeasures |
| **True random number generator** | Physical entropy source for key generation |
| **Internal key hierarchy** | A master key protects all stored keys; keys stored outside the HSM are wrapped under it |
| **Partitions (or slots, domains)** | Isolated logical HSMs for different applications or tenants, each with its own keys and credentials |
| **Role-based access** | Separate security officer, crypto officer and crypto user roles |
| **Quorum (M-of-N) authentication** | Sensitive actions require several people with separate credentials, often smart cards |
| **Audit log** | Tamper-evident record of administrative and key operations |

HSMs come in several forms: network-attached appliances shared by many servers, PCIe cards inside a single server, USB devices for small CAs and offline roots, and cloud HSM services where the provider hosts dedicated or multi-tenant HSMs that you control.

### Key attributes matter

When a key is created in an HSM, its **attributes** decide what anyone can ever do with it. In PKCS#11 terms:

- `CKA_SENSITIVE = true`: the key value cannot be read in the clear.
- `CKA_EXTRACTABLE = false`: the key cannot be exported at all, even wrapped.
- `CKA_SIGN`, `CKA_DECRYPT`, `CKA_WRAP`: which operations are allowed.

A key created as extractable can later be exported, which defeats much of the point. Review attributes during key creation ceremonies.

## 23.3 Certification: FIPS 140-3 and Common Criteria

Buyers rely on independent certification to know an HSM does what it claims.

### FIPS 140-3

**FIPS 140-3** is the US and Canadian standard for cryptographic modules, administered by NIST's **Cryptographic Module Validation Program (CMVP)** and aligned with ISO/IEC 19790. It has four security levels:

| Level | Physical security requirement | Typical products |
| --- | --- | --- |
| 1 | No physical protection beyond production-grade components | Software cryptographic libraries |
| 2 | Tamper evidence (seals, coatings) and role-based authentication | Some USB tokens, smart cards |
| 3 | Tamper resistance with active zeroisation; identity-based authentication; separation of key entry | Most network HSMs and cloud HSMs |
| 4 | Complete envelope protection against environmental and physical attacks | Specialised high-assurance modules |

A FIPS certificate covers a specific module version, configuration and set of approved algorithms. Running the module outside its validated configuration, such as with non-approved algorithms enabled, means you are not operating a validated module.

> **Current development.** The older FIPS 140-2 standard reached its end: on 21 September 2026, all remaining FIPS 140-2 validation certificates moved to the CMVP's Historical list. Historical modules may continue in existing deployments, but US federal agencies should not include them in new procurements. Check that any HSM, library or appliance you buy now holds an active FIPS 140-3 certificate, and ask vendors when their post-quantum algorithms (ML-KEM, ML-DSA, SLH-DSA) will appear in a validated configuration.

### Common Criteria

**Common Criteria** (ISO/IEC 15408) is an international certification framework. Products are evaluated against **Protection Profiles** to an assurance level (EAL). In Europe, HSMs used for qualified electronic signatures under eIDAS must be certified against specific Common Criteria protection profiles. Common Criteria certificates name exact versions and configurations too.

### Payment HSMs

Payment networks use specialised **payment HSMs** for PIN processing, card verification and key exchange with card schemes, certified under **PCI PTS HSM**. Their key management follows payment-specific standards such as ANSI X9.24 (including TR-31 key blocks), with strict dual control and split knowledge.

## 23.4 Operating HSMs

Owning an HSM is easy; operating one well takes discipline.

**Key ceremonies.** Generating and using the most sensitive keys, such as root CAs, follows a scripted, witnessed, recorded ceremony (Chapter 18), with quorum smart cards held by different people.

**Backup and recovery.** Keys inside an HSM die with it unless backed up. HSM vendors provide secure backup: keys exported only in encrypted form to another HSM of the same family or to backup devices, protected by the HSM's domain key. Test restoration regularly. An HSM key that cannot be recovered after a hardware failure can be as damaging as one that was stolen.

**High availability.** Production HSMs run in clusters, with keys replicated between devices and sites, and clients that fail over automatically. Plan capacity for peak operations per second, especially for signing-heavy workloads such as TLS termination or token issuance.

**Firmware and lifecycle.** HSM firmware updates fix vulnerabilities and add algorithms, but can change the validated configuration. Plan updates as projects, not patches. Track hardware end-of-support dates years ahead; migrating keys between HSM generations is a significant project.

**Monitoring.** Forward HSM audit logs to your security monitoring. Alert on administrative logins, partition changes, failed authentications, and unusual operation volumes.

## 23.5 TPMs and secure elements

A **Trusted Platform Module (TPM)** is a small security chip, or firmware equivalent, present in almost every modern PC and server. TPM 2.0 provides:

- **Protected key storage:** keys created in the TPM can be made non-exportable and bound to that machine.
- **Measured boot:** each stage of the boot process records a hash of the next stage in **Platform Configuration Registers (PCRs)**. Keys can be **sealed** so they are released only if the PCRs match an expected, trusted state.
- **Remote attestation:** the TPM signs a statement of the PCR values, letting a remote service verify what software the machine booted.

Practical uses: full-disk encryption keys sealed to measured boot (BitLocker and Linux equivalents), device identity certificates for network access, protected storage for credentials such as Windows Hello keys, and host attestation in data centres.

Phones and laptops have similar dedicated **secure elements** and **secure enclaves** that protect biometric templates, payment credentials and passkeys (Chapter 14). They are why a passkey's private key cannot be copied off a device.

> **Watch out.** TPMs are not HSMs. They are inexpensive, slow, and certified to modest levels. Some have had serious flaws: ROCA (Chapter 7) affected TPMs, and TPM-Fail (2019) extracted ECDSA keys through timing. Use TPMs for device-bound keys and attestation, not as a substitute for an HSM for CA or high-value signing keys.

## 23.6 Confidential computing

Encryption protects data at rest and in transit, but data must be decrypted to be processed, and then it is exposed to the operating system, the hypervisor, and whoever runs the infrastructure. **Confidential computing** protects data **in use** by running workloads in hardware-isolated **trusted execution environments (TEEs)**:

| Technology | What it isolates |
| --- | --- |
| Intel SGX | Small application enclaves inside a process |
| Intel TDX | Whole virtual machines from the hypervisor |
| AMD SEV-SNP | Whole virtual machines, with memory encryption and integrity |
| Arm CCA | Realms isolated from the hypervisor on Arm servers |
| Confidential GPUs | AI and data processing on accelerators, with encrypted transfers |

Memory inside a TEE is encrypted with keys held by the processor, so even a malicious administrator or cloud operator cannot read it. **Remote attestation** lets a relying party verify, before sending data or releasing keys, that a workload is running inside a genuine TEE with the expected code. A common pattern ties this to key management: the KMS releases a decryption key only to a workload that presents a valid attestation report.

Confidential computing is growing quickly, particularly for processing sensitive data in shared clouds and for protecting AI models and their inputs. Its limits are real, though: researchers have published many side-channel and fault attacks against TEEs, particularly SGX, and the security of the whole depends on trusting the processor vendor's design and attestation keys. Treat it as an extra layer that significantly raises the bar, not as an absolute guarantee.

## Lab: a software HSM with PKCS#11

**SoftHSM2** is a free software implementation of a PKCS#11 token, ideal for learning the interfaces real HSMs use. It provides no hardware protection.

```bash
sudo apt-get install softhsm2 opensc
softhsm2-util --init-token --slot 0 --label "lab" --so-pin 12345678 --pin 1234
MOD=/usr/lib/softhsm/libsofthsm2.so
pkcs11-tool --module $MOD --login --pin 1234 --keypairgen --key-type EC:prime256v1 \
  --label signing-key --id 01
pkcs11-tool --module $MOD --login --pin 1234 --list-objects
```

Note the key attributes printed (sensitive, never extractable). Now sign data without the key ever leaving the token:

```bash
echo "release 1.0" > data.txt
pkcs11-tool --module $MOD --login --pin 1234 --sign --id 01 -m ECDSA-SHA256 \
  --input-file data.txt --output-file data.sig
```

Try to export the private key with `--read-object --type privkey`. It is refused. Then explore using the token from OpenSSL 3 through a PKCS#11 provider, the same way a CA or web server would use a real HSM.

## Failure story: the cloud key in a crash dump

The Storm-0558 incident (Chapter 9) is, at its heart, an HSM story. The stolen consumer signing key had been created in 2016 and was used in a way that allowed it to appear in process memory. Microsoft's investigation suggested a crash dump containing the key was moved from a highly isolated production environment into a debugging environment, where the attacker later found it, although the company later said it could not confirm this sequence with certainty.

If the key had been generated and used exclusively inside an HSM with non-extractable attributes, no crash dump could have contained it. In its response, Microsoft announced that it had moved consumer and enterprise signing keys into HSM-backed key storage with automatic rotation. The US Cyber Safety Review Board recommended that cloud providers protect identity signing keys with hardware and rotate them regularly. The lesson for every organisation: the keys that can mint identities, sign software or issue certificates belong inside hardware, where memory bugs and operational accidents cannot reach them.

## Chapter summary

- HSMs keep keys inside a tamper-resistant boundary; attackers can at most misuse them while present, never take them away.
- Key attributes such as non-extractable are set at creation and decide what can ever be done with a key.
- FIPS 140-3 levels and Common Criteria certify modules; FIPS 140-2 certificates moved to Historical status in September 2026.
- Operating HSMs means ceremonies, tested backups, high availability, planned firmware updates and monitored logs.
- TPMs and secure enclaves bring hardware key protection and attestation to every device; confidential computing protects data in use, with real but bounded assurance.
