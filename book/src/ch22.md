## 22.1 What counts as a secret

A **secret** is any value that grants access or capability if someone else learns it:

- Passwords for databases, service accounts and administrators.
- API keys and access tokens for internal and third-party services.
- Cloud access keys.
- Private keys for TLS, SSH, signing and encryption.
- Webhook signing secrets, HMAC keys and session encryption keys.
- Connection strings that embed any of the above.

Keys managed in a KMS or HSM (Chapter 21) are a special case: they never leave their protected boundary. Most other secrets must be delivered to the software that uses them, which is where the trouble starts.

## 22.2 Secret sprawl

Secrets spread because copying them is easy and every copy feels harmless:

- Hard-coded in source code "temporarily".
- Committed in configuration files and `.env` files.
- Baked into container images and virtual machine templates.
- Pasted into chat messages, tickets and wiki pages.
- Stored as long-lived variables in CI/CD systems.
- Printed in logs and error messages.

Once in a Git repository, a secret is effectively permanent: deleting the file does not remove it from history, forks or clones. Attackers scan public repositories continuously, and leaked cloud keys are typically abused within minutes of being pushed. Industry studies by secret-scanning vendors have counted tens of millions of secrets leaked to public repositories in a single year, with a large share still valid years later.

> **In practice.** Treat any secret that has appeared in a repository, image, ticket or log as compromised. Revoke and replace it first; clean up history second.

## 22.3 Central secrets management

A **secrets manager** is a hardened service that stores secrets encrypted (usually with envelope encryption under a KMS or HSM key), controls access to them by identity and policy, audits every read, and supports rotation. Examples include the secrets services of every major cloud, open-source systems such as **OpenBao**, Kubernetes secret operators that sync from them, and commercial privileged access management products.

Core features to look for:

| Feature | Why it matters |
| --- | --- |
| Encryption at rest under a KMS/HSM key | Storage compromise does not reveal secrets |
| Identity-based access policies | Each workload reads only its own secrets |
| Audit log of every read and change | You can answer "who accessed this?" |
| Versioning and rotation | Change a secret without breaking consumers |
| Leases and expiry | Secrets that expire on their own |
| Dynamic secrets | Credentials created on demand, per consumer (section 22.5) |
| High availability | The secrets manager becomes a dependency of every service |

### Getting secrets to applications

Storing secrets centrally solves half the problem. Delivery is the other half:

- **Read at start-up through an API or agent**, keeping the secret only in memory. Preferred.
- **Mounted files** written by an agent or sidecar into a memory-backed filesystem, refreshed when rotated.
- **Environment variables.** Common but weaker: they leak into crash reports, child processes and debugging tools.
- **Kubernetes Secrets.** By default only base64-encoded in etcd. Enable encryption at rest with a KMS provider, restrict RBAC tightly, or sync from an external secrets manager.

For configuration stored in Git (GitOps), tools such as **SOPS** and **Sealed Secrets** encrypt secret values so the encrypted file can live in the repository and be decrypted only by authorised deployment systems.

### The bootstrap problem

To read secrets, an application must authenticate to the secrets manager, which seems to need a secret of its own: the "secret zero". The answer is to authenticate with something the platform already proves about the workload, such as its cloud instance identity, its Kubernetes service account token, or its SPIFFE identity (section 22.6). Those identities are issued and rotated by the platform, so no human-handled secret is needed.

## 22.4 Rotation

Every static secret should have an owner, a rotation schedule and a tested rotation procedure. Rotation without downtime usually follows a **two-phase** pattern:

1. Create the new secret and make it valid **alongside** the old one (for example, a database user with two valid passwords, or an API with two active keys).
2. Update every consumer to use the new secret, and verify.
3. Revoke the old secret.

Systems that allow only one valid credential at a time force a risky switch-over and are a common reason rotation is postponed forever. Prefer systems that support overlapping credentials.

## 22.5 Dynamic secrets and short-lived credentials

The strongest way to reduce secret risk is to stop having long-lived secrets at all.

**Dynamic secrets** are created on demand for one consumer and expire automatically. When an application starts, it asks the secrets manager for database credentials; the secrets manager creates a new database user with exactly the needed permissions and a lease of, say, one hour, renews it while the application runs, and deletes it when the lease ends. Benefits:

- Every credential is unique, so the audit trail shows exactly which instance did what.
- A leaked credential expires on its own, usually before anyone could use it.
- There is nothing to rotate, because nothing lives long enough.

The same principle appears throughout this book: SSH certificates valid for hours (Chapter 13), TLS certificates valid for days (Chapter 19), OAuth access tokens valid for minutes (Chapter 14). **Short lifetimes are the most reliable revocation mechanism ever invented.**

## 22.6 Workload identity: replacing secrets with identity

Modern platforms can prove a workload's identity cryptographically, without any stored secret. The workload then exchanges that proof for short-lived credentials.

### Cloud workload identity and OIDC federation

Cloud platforms give each virtual machine, function or container an identity, and issue short-lived credentials for it automatically. Across platforms, **OIDC federation** connects them: a CI/CD system or a Kubernetes cluster issues a signed OIDC token (Chapter 14) describing the workload, such as "repository X, branch main, workflow deploy", and the cloud provider exchanges that token for temporary cloud credentials, after checking a trust policy.

Federation has removed long-lived cloud keys from many CI/CD pipelines. The trust policy is now the security boundary: it must check the token's issuer, audience and the specific subject claims (repository, branch, environment), or any workflow from any repository on the same CI platform could assume the role.

### SPIFFE and SPIRE

**SPIFFE** (Secure Production Identity Framework for Everyone), a graduated Cloud Native Computing Foundation project, standardises workload identity across platforms:

- Every workload gets a **SPIFFE ID**, a URI such as `spiffe://example.org/payments/api`.
- The identity is delivered as an **SVID** (SPIFFE Verifiable Identity Document): a short-lived X.509 certificate for mTLS, or a JWT.
- **SPIRE**, the reference implementation, **attests** each workload, checking evidence such as the node it runs on and its process or container properties, before issuing an SVID, and rotates SVIDs automatically, typically every hour or less.

Service meshes use the same idea: each workload gets an automatically rotated certificate, and services authenticate each other with mTLS, with no passwords or API keys between them.

## 22.7 Detecting and responding to leaks

Even with good practices, secrets leak. Layer detection:

- **Pre-commit and CI scanning** for secret patterns before code is pushed.
- **Repository and image scanning** across history and registries.
- **Platform push protection**: major code-hosting platforms block pushes containing recognised secrets and notify issuers, many of whom revoke leaked keys automatically.
- **Honeytokens**: fake credentials placed where attackers look, which alert when used.
- **Anomaly detection** on secrets manager and cloud audit logs.

And prepare the response before you need it: for each class of secret, a runbook that says how to revoke, replace and verify, who owns it, and how to find every place it was used.

## Lab: from static secret to dynamic credentials

Use OpenBao in development mode (or any secrets manager you have access to) and a PostgreSQL container.

1. **Static secret.** Store a database password in the key-value engine, read it with a token, and note the audit log entry.
2. **Dynamic secret.** Enable the database secrets engine, configure it with an administrative connection to PostgreSQL, and define a role that creates users with read-only access and a one-hour time to live. Request credentials twice and observe two different usernames. Connect with one.
3. **Expiry.** Revoke the lease, or wait for it to expire, and confirm the database user no longer exists.
4. **Scan for leaks.** Run an open-source secret scanner such as `gitleaks` against a test repository where you have committed a fake key, and then against its history after "deleting" the file.

## Failure story: the CI pipeline with keys to everything

In 2022, a ride-sharing company suffered a breach that began with social engineering: an attacker bought a contractor's stolen password and repeatedly sent multi-factor approval requests until the contractor accepted one. Once inside the network, the attacker found a network share containing PowerShell scripts. One script contained hard-coded administrator credentials for the company's privileged access management system, the very system meant to protect secrets. With those, the attacker obtained access to cloud consoles, internal tools and the security team's own systems.

The pattern is common: a single long-lived secret, stored in a place many people could read, unlocks the vault that holds every other secret. The defences are the ones in this chapter: no secrets in scripts or shares; scanning to find the ones that slip through; strong, phishing-resistant authentication for people (Chapter 14); and workload identity and short-lived credentials so that the most powerful access is never a static string someone can copy.

## Chapter summary

- Secrets sprawl into code, images, CI systems, logs and chat; leaked secrets are exploited within minutes.
- Store secrets centrally, encrypted under KMS keys, with identity-based access and audit; deliver them in memory, not in images or repositories.
- Rotate with overlapping credentials; prefer systems that allow two valid secrets at once.
- Dynamic secrets and short-lived credentials remove the need for rotation and limit damage from leaks.
- Workload identity (cloud identity, OIDC federation, SPIFFE) replaces stored secrets with platform-attested identity; scan for and rehearse responses to leaks.
