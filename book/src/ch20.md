## 20.1 Why key management is the real work

Kerckhoffs's principle (Chapter 1) says security should rest only on the key. The flip side is that **every weakness in how keys are handled becomes a weakness in the system.** Real breaches rarely break AES. They find keys:

- in source code repositories and container images,
- in configuration files, environment variables and logs,
- in memory and crash dumps,
- in backups stored next to the data they protect,
- with administrators and services that should never have had them,
- long after they should have been rotated or destroyed.

NIST's **SP 800-57** (Recommendation for Key Management) is the most widely used reference for the discipline. This chapter follows its concepts in plain language.

## 20.2 Types of keys

Keys are classified by algorithm family and by purpose. Purpose matters most, because **each key should have exactly one purpose.**

| Key type | Purpose | Example |
| --- | --- | --- |
| **Data encryption key (DEK)** | Encrypts application data | A per-file AES-256 key |
| **Key encryption key (KEK)** | Encrypts (wraps) other keys | A master key in a key management service |
| **Signing key** | Creates digital signatures | Code signing, token signing, CA keys |
| **Verification key** | Checks signatures | Public keys in trust stores and JWKS |
| **Key agreement key** | Establishes shared secrets | Static or ephemeral ECDH, ML-KEM keys |
| **MAC key** | Creates and checks MACs | HMAC keys for API signing |
| **Key derivation key** | Derives other keys | An HKDF master secret |

Using one key for two purposes, for example signing and encryption, or two different protocols, has repeatedly enabled cross-protocol attacks, as DROWN showed (Chapter 11). Separate keys are cheap; untangling shared ones after an incident is not.

| Stage | What happens | Controls that matter |
| --- | --- | --- |
| **Generation** | The key is created | Approved algorithm and size; strong randomness (Chapter 3); generated inside the system that will protect it (an HSM or KMS) |
| **Registration and distribution** | The key is recorded, given metadata, and delivered to users | Inventory entry with owner, purpose and expiry; keys delivered wrapped, never in plain text |
| **Storage** | The key rests | Hardware protection for high-value keys; wrapped by a KEK otherwise; never alongside the data it protects |
| **Use** | The key performs its purpose | Access control per operation; logging; usage limits (for example, GCM message counts) |
| **Rotation** | A new key replaces it for new data | Scheduled cryptoperiods and event-driven rotation |
| **Archival and backup** | Copies kept for recovery | Encrypted, split or HSM-protected backups in a separate location; tested restores |
| **Deactivation** | The key stops protecting new data but may decrypt or verify old data | Enforced by the key system, not by convention |
| **Destruction** | All copies are removed | Including backups and caches; destruction recorded; data under the key becomes unrecoverable (crypto-shredding) |

**Crypto-shredding** deserves a note: destroying a key makes everything encrypted under it permanently unreadable. Organisations use it to delete data from backups that cannot be edited, or to satisfy data-deletion requirements, by giving each customer or dataset its own key and destroying the key when the data must go.

## 20.4 Key hierarchies and envelope encryption

Encrypting large amounts of data directly with a master key in an HSM would be slow, and would expose the master key to heavy use. Instead, systems use **envelope encryption**:

1. Generate a fresh **data encryption key (DEK)** for each object (file, record, disk, backup).
2. Encrypt the data locally with the DEK, using AEAD.
3. Send the DEK to the key management system to be **wrapped** (encrypted) under a **key encryption key (KEK)** that never leaves the KMS or HSM.
4. Store the wrapped DEK next to the encrypted data, and discard the plain DEK from memory.

To decrypt, send the wrapped DEK to the KMS, receive the plain DEK (if authorised), and decrypt the data locally.

The benefits are large:

- **Performance:** bulk encryption happens locally at full speed; the KMS handles only tiny wrapping operations.
- **Containment:** each object has its own DEK, so a leaked DEK exposes one object.
- **Cheap rotation:** rotating a KEK means re-wrapping DEKs, not re-encrypting the data.
- **Access control and audit:** every unwrap is an authorised, logged KMS call, so you can see who decrypted what and revoke access centrally.
- **Separation of duties:** storage administrators hold encrypted data; KMS administrators hold keys; neither alone can read the data.

### Derived keys

An alternative to storing many DEKs is to **derive** them with HKDF from a master key and a context label such as a tenant ID or object ID (Chapter 6). Derivation avoids storing wrapped keys but makes rotation of the master key harder, because every derived key changes. Many systems combine the approaches: a wrapped per-tenant key from which per-object keys are derived.

## 20.5 Cryptoperiods and rotation

A **cryptoperiod** is the time a key is allowed to be used. Limiting it limits how much data any one key protects, how long a stolen key stays useful, and how much material an attacker can gather against one key.

SP 800-57 suggests cryptoperiods by key type. Typical practice:

| Key | Typical cryptoperiod |
| --- | --- |
| Symmetric data encryption key | Up to 2 years for protecting; can decrypt longer |
| Key encryption key | 1 to 2 years |
| TLS server key | Lifetime of its certificate; new key every renewal |
| Code signing key | 1 to 3 years, with timestamps extending signature validity |
| CA keys | Root 10 to 20 years; issuing CA 2 to 5 years |
| API secrets and tokens | Days to months; ideally replaced with short-lived credentials |

Rotation comes in two kinds:

- **Scheduled rotation** at the end of each cryptoperiod. Fully automated in a good system: new data uses the new key version, old versions remain available for decryption.
- **Event-driven rotation** after a suspected compromise, a staff departure with access, or a vulnerability. This is the one that tests whether your systems can actually rotate. If rotation has never been practised, it will fail when you need it most.

> **Watch out.** Rotation of a KEK protects new data immediately but does not re-protect data wrapped under the old version. If an old KEK is believed compromised, you must re-wrap (or re-encrypt) everything it protected, then destroy it.

## 20.6 The key inventory

You cannot manage keys you do not know about. A **key inventory** records, for every key:

- An identifier and version.
- Algorithm, size and purpose.
- Where it lives (which HSM, KMS, application or file) and whether it can be exported.
- Owner (a team) and the systems that use it.
- Creation date, cryptoperiod, and next rotation date.
- What it protects (data classification, regulatory scope).
- Its current lifecycle state.

The inventory is also the foundation for the post-quantum migration. A **cryptographic bill of materials (CBOM)** extends the idea to every use of cryptography in an application, including algorithms in libraries and protocols, not only managed keys (Chapter 27).

## 20.7 Key management policy and roles

A short written policy, approved by security leadership, should state at least: approved algorithms and sizes; where each class of key must be stored; cryptoperiods; who may create, use, export, rotate and destroy keys; logging and review; backup and recovery; and how compromise is handled.

Separate the roles. The people who administer the key management system should not be the people who own the data, and destroying or exporting high-value keys should require two people. This **separation of duties** and **dual control** is a requirement in standards such as PCI DSS for payment keys.

## Lab: envelope encryption in practice

This Python lab simulates a KMS with a local master key. Replace the "KMS" functions with calls to a real key management service later.

```python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.keywrap import aes_key_wrap, aes_key_unwrap

KEK = AESGCM.generate_key(bit_length=256)       # lives in the KMS in real life
def kms_wrap(dek):   return aes_key_wrap(KEK, dek)
def kms_unwrap(wdek): return aes_key_unwrap(KEK, wdek)

def encrypt_object(data, object_id):
    dek = AESGCM.generate_key(bit_length=256)
    nonce = os.urandom(12)
    ct = AESGCM(dek).encrypt(nonce, data, object_id)   # object ID as associated data
    return {"wdek": kms_wrap(dek), "nonce": nonce, "ct": ct, "id": object_id}

def decrypt_object(blob):
    dek = kms_unwrap(blob["wdek"])
    return AESGCM(dek).decrypt(blob["nonce"], blob["ct"], blob["id"])

b = encrypt_object(b"customer record 42", b"rec-42")
print(decrypt_object(b))
```

Now extend it:

1. **Rotate the KEK.** Create a new KEK, unwrap each stored DEK with the old one, re-wrap with the new one, and confirm decryption still works. Note that the data ciphertext never changed.
2. **Crypto-shred.** Delete one object's wrapped DEK and show its data is unrecoverable.
3. **Context binding.** Try decrypting `rec-42`'s ciphertext with the ID `rec-43` and observe the failure: associated data stops records being swapped.

## Failure story: the keys in the repository

In January 2023, a widely used continuous integration service disclosed that an attacker had stolen customer secrets: environment variables, tokens and keys that customers had stored for their build pipelines. The intrusion began with malware on one engineer's laptop that stole a session token, giving the attacker access to production systems, including the data and the encryption keys needed to decrypt it. The service told all customers to rotate every secret they had ever stored with it.

The incident showed two things. Encryption at rest helped little, because the attacker reached a place where keys and data were both accessible. And many customers discovered they could not rotate quickly: secrets had been copied into dozens of places, had no recorded owner, or were long-lived cloud credentials used by systems nobody remembered. Organisations with an inventory, short-lived credentials and practised rotation recovered in hours; others took weeks.

Envelope encryption with keys in a separate, access-controlled KMS, short-lived credentials instead of stored secrets (Chapter 22), and a live inventory are the direct answers.

## Chapter summary

- Breaches find keys more often than they break algorithms. Key management is the core of applied cryptography.
- Give every key one purpose, and manage it through generation, storage, use, rotation, backup, deactivation and destruction.
- Envelope encryption gives speed, containment, cheap rotation, central access control and audit.
- Set cryptoperiods; automate scheduled rotation and practise event-driven rotation.
- Keep a key inventory with owners and states; it is also the foundation of post-quantum migration.
