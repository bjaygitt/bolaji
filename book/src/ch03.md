## 3.1 Why randomness is the foundation

A 128-bit key is strong only if an attacker has to try all 2^128 possibilities. If the key was generated by a process that can only produce a million different values, the attacker only has to try a million, and the 128 bits on paper mean nothing. The Debian incident in Chapter 1 is exactly this: keys that looked long but came from a pool of about 32,000 values.

Cryptography consumes randomness in several roles:

| Item | What it is | What goes wrong if it is predictable |
| --- | --- | --- |
| **Key** | The secret that protects everything | Attacker guesses the key |
| **Nonce** ("number used once") | A value that must never repeat under the same key | Encryption leaks data; signatures leak the private key |
| **Initialisation vector (IV)** | A starting value for some encryption modes | Patterns in data become visible |
| **Salt** | A random value mixed into password hashing | Precomputed tables crack many passwords at once |
| **Session ID or token** | An identifier that grants access | Attacker guesses a valid session and takes it over |

## 3.2 Entropy: measuring unpredictability

**Entropy** is the measure of how unpredictable something is, counted in bits. A fair coin flip has 1 bit of entropy. A fair six-sided die has about 2.6 bits. A truly random 128-bit key has 128 bits.

Two traps catch people:

- **Length is not entropy.** A 20-character password made from a dictionary word plus a year, such as "Summer2026!", has far less entropy than its length suggests, because attackers guess common patterns first.
- **Average is not worst case.** Cryptographers care about **min-entropy**: how likely the single most likely value is. A source that produces a fixed value 1 percent of the time is dangerous even if its other outputs look random, because an attacker simply guesses the common value first.

## 3.3 Where computers get randomness

Computers are built to be predictable, so randomness has to be harvested from the physical world and then stretched.

1. **Entropy sources.** Unpredictable physical events: timing jitter between hardware interrupts, electrical noise inside dedicated hardware random number generators (such as the RDRAND and RDSEED instructions in modern processors), and similar sources.
2. **The operating system's pool.** The kernel mixes many sources together, so that one weak or compromised source cannot ruin the result.
3. **A cryptographically secure pseudo-random number generator (CSPRNG).** A deterministic algorithm, seeded from the pool, that produces an endless stream of output that nobody can predict without knowing the seed.

A CSPRNG differs from an ordinary pseudo-random generator in one crucial property: even an attacker who sees millions of outputs cannot predict the next one or work out earlier ones. Ordinary generators, such as those used for simulations and games, do not have this property. Their output can often be predicted after seeing a few values.

### The rule: always use the operating system's CSPRNG

In almost every situation, the correct answer is to ask the operating system or your language's dedicated cryptographic API:

| Language or platform | Use this | Never use this for secrets |
| --- | --- | --- |
| Linux | `getrandom()` system call, or `/dev/urandom` | Custom generators |
| Windows | `BCryptGenRandom` | `rand()` |
| Python | `secrets` module, `os.urandom` | `random` module |
| Java | `java.security.SecureRandom` | `java.util.Random` |
| JavaScript (browser and Node.js) | `crypto.getRandomValues`, `crypto.randomBytes` | `Math.random()` |
| Go | `crypto/rand` | `math/rand` |

A widely repeated myth says `/dev/random` is better than `/dev/urandom` on Linux because it "blocks when entropy runs out". On modern Linux kernels, both are fed by the same CSPRNG, and `/dev/urandom` is the right choice once the system has been seeded at boot. The `getrandom()` call handles the one genuinely risky moment, very early boot before seeding, by waiting until the pool is ready.

> **In practice.** The riskiest places for randomness today are not laptops and servers but freshly booted virtual machines, cloned VM images, containers started from snapshots, and small embedded devices. A cloned VM can start with the same random state as its siblings. Make sure images are reseeded on first boot, and generate long-term keys after boot, never inside the image.

## 3.4 Probability that every engineer should know: the birthday bound

How many people must be in a room before there is a 50 percent chance that two share a birthday? Most people guess around 180. The answer is 23.

This **birthday paradox** happens because you are not comparing everyone with one person; you are comparing every pair, and the number of pairs grows much faster than the number of people. The general rule, called the **birthday bound**, is:

> If values are drawn at random from N possibilities, a repeat becomes likely after about the square root of N draws.

For bit strings, the square root of 2^n is 2^(n/2). So among random 64-bit values, you expect a repeat after about 2^32, roughly 4 billion, draws. That sounds like a lot until you remember that a busy service can generate 4 billion values in days.

The birthday bound sets the safe size of many things:

| Item | Size | Repeat expected after about | Consequence |
| --- | --- | --- | --- |
| Random 64-bit IDs | 64 bits | 4 billion | Too small for large systems |
| AES-GCM random nonces | 96 bits | 2^48 messages | NIST limits random-nonce use to 2^32 messages per key, for a large safety margin |
| Block cipher output blocks | 128 bits (AES block) | 2^64 blocks | Rekey well before this; old 64-bit block ciphers fell to attacks like Sweet32 |
| Hash outputs | 256 bits (SHA-256) | 2^128 hashes | Collisions infeasible: this is why hash security is "half the output size" |
| UUID version 4 | 122 random bits | 2^61 | Fine as an identifier; not a substitute for a secret token |

The last row of the hash line explains a rule you saw in Chapter 1: a hash function with an n-bit output gives only n/2 bits of security against collisions. SHA-256 gives 128-bit collision resistance.

## 3.5 What "hard" means

Security claims say things like "breaking this requires solving a hard problem". In cryptography, **hard** has a specific meaning: no algorithm running in a practical amount of time succeeds with more than a tiny probability.

Three terms make this precise:

- **Polynomial time** describes algorithms whose running time grows reasonably with input size, such as doubling when the input doubles. Honest users must be able to do their part in polynomial time.
- **Superpolynomial or exponential time** describes algorithms whose running time explodes, such as doubling every time the input grows by one bit. Attackers should face this.
- **Negligible** describes a success probability so small that it shrinks faster than any polynomial. In practice, below about one in 2^80 to 2^128.

Two cautions keep these claims honest:

1. **Hardness is believed, not proved.** No one has proved that factoring or lattice problems are hard. Confidence comes from decades of failed attacks.
2. **Hardness is relative to a computer model.** Factoring is hard for classical computers and easy for large quantum ones. A problem's hardness can change when technology changes, which is exactly what is happening now.

## 3.6 Security in practice: work factors

Engineers translate abstract hardness into concrete **work factors**, the expected number of operations to break a system. Some reference points help calibrate:

| Operations | Roughly equals |
| --- | --- |
| 2^40 | A laptop for a few hours |
| 2^64 | A large cluster for months; feasible for well-funded attackers (SHA-1 collisions were found with about 2^63) |
| 2^80 | Beyond any single organisation today; considered the old minimum |
| 2^112 | NIST's current minimum security level |
| 2^128 | The standard target; far beyond all computing on Earth |
| 2^256 | Exceeds the number of atoms in the observable universe (about 2^266) |

Choose 128-bit security for almost everything. Choose 256-bit symmetric keys where data must stay secret for decades, as a margin against both unknown advances and quantum search (Chapter 25).

## Lab: see weak randomness fail

This lab uses Python 3.

**1. Predicting a non-cryptographic generator.** Python's `random` module uses the Mersenne Twister. After observing 624 consecutive 32-bit outputs, its internal state can be completely reconstructed. You do not need to do the reconstruction to see the danger: seed it with a time value and watch it repeat.

```python
import random, time
seed = int(time.time())
random.seed(seed); a = [random.getrandbits(32) for _ in range(3)]
random.seed(seed); b = [random.getrandbits(32) for _ in range(3)]
print(a == b)   # True: same seed, same "random" numbers
```

An attacker who knows roughly when a token was created can try every second in that window.

**2. The right way.**

```python
import secrets
print(secrets.token_hex(32))     # 256 bits, suitable for keys and tokens
print(secrets.token_urlsafe(32)) # for URLs and reset links
```

**3. The birthday bound in action.** Draw random 24-bit values until one repeats:

```python
import secrets
seen, n = set(), 0
while True:
    v = secrets.randbits(24); n += 1
    if v in seen: break
    seen.add(v)
print(n)   # usually a few thousand, near the square root of 2^24 = 4096
```

Run it several times. The answer clusters around a few thousand, not millions. Scale the same intuition up to 64-bit identifiers and 96-bit nonces.

## Failure story: the console that signed with a constant

In 2010, a group of researchers presented a complete break of the code-signing system protecting the PlayStation 3. The console accepted only software signed with the manufacturer's private key, using the ECDSA signature algorithm (Chapter 9). ECDSA requires a fresh random number for every signature. The implementation used the **same** number every time.

With two signatures made using the same random value, simple algebra reveals the private key. The researchers recovered the master signing key, and from then on anyone could sign software the console would trust. The key could not be changed in devices already sold.

Nothing was wrong with ECDSA or with the curve. One value that had to be random was constant. Modern implementations avoid this whole class of failure by deriving the per-signature value deterministically from the key and message (RFC 6979, and the design of EdDSA), so a broken random generator cannot leak the key.

## Chapter summary

- Every key, nonce, IV, salt and token depends on unpredictable randomness. Predictable randomness silently destroys security.
- Entropy measures unpredictability; length and appearance do not. Min-entropy is what attackers exploit.
- Always use the operating system's CSPRNG through your language's cryptographic API. Watch cloned VMs, containers and embedded devices.
- The birthday bound says repeats become likely after about the square root of the number of possibilities. It sets safe sizes for nonces, identifiers and hash outputs.
- "Hard" means infeasible for practical computers, as far as we know, and can change with technology.
