## 7.1 The idea

In 1977, Ron Rivest, Adi Shamir and Leonard Adleman published a system in which anyone could encrypt a message using a public key, but only the holder of the matching private key could decrypt it. The security rests on the factoring problem from Chapter 2: multiplying two large primes is easy, but recovering them from their product is not.

RSA works with ordinary modular exponentiation. A message, represented as a number m, is encrypted by raising it to a public power and decrypted by raising the result to a private power:

```
encrypt:  c = m^e mod n
decrypt:  m = c^d mod n
```

The magic is that e and d are chosen so that the two powers cancel each other out mod n, and computing d from e requires knowing the factors of n.

## 7.2 Generating a key pair

1. Choose two large random primes, p and q, each half the desired key size. For a 3072-bit key, each is 1536 bits.
2. Compute the **modulus** `n = p × q`. This is public.
3. Compute `φ(n) = (p − 1)(q − 1)`. This must stay secret, because it reveals the factors.
4. Choose the **public exponent** e. Almost everyone uses `e = 65537`, which makes encryption and signature verification fast.
5. Compute the **private exponent** `d = e^(−1) mod φ(n)`, using the extended Euclidean algorithm.

The **public key** is (n, e). The **private key** is d, usually stored with p, q and a few precomputed values that speed up decryption using the Chinese Remainder Theorem (CRT), roughly four times faster.

Anyone who factors n can repeat step 5 and obtain d. That is why key size is everything.

## 7.3 Textbook RSA is broken

The formulas above, used directly, are called **textbook RSA**, and they are insecure in several ways:

- **Deterministic.** Encrypting the same message twice gives the same ciphertext. An attacker can guess likely messages ("yes", "no", "approve") and check by encrypting them with the public key.
- **Malleable.** Multiplying a ciphertext by `2^e mod n` produces a valid encryption of `2m`. An attacker can transform encrypted values without decrypting them.
- **Small messages leak.** If m is small and e is small, `m^e` may be smaller than n, so no modular wrap-around happens and the attacker simply takes an ordinary e-th root.
- **Signatures can be forged.** With textbook signatures (`s = m^d mod n`), multiplying two valid signatures gives a valid signature on the product of their messages.

The solution to all of these is **padding**: a structured, randomised encoding applied to the message before exponentiation. Padding is not optional decoration. It is half of the security of RSA.

## 7.4 Padding for encryption: PKCS#1 v1.5 and OAEP

**PKCS#1 v1.5 encryption padding** (1993) wraps the message as `00 02 [random non-zero bytes] 00 [message]`. It adds randomness but has a fatal flaw, discovered by Daniel Bleichenbacher in 1998: if a server reveals, by error message or timing, whether a decrypted ciphertext had valid padding, an attacker can decrypt any ciphertext by sending a series of carefully chosen variations. This is the same pattern as the padding oracle in Chapter 5, with a different mathematical engine.

The attack has returned again and again: in 2012 against hardware tokens, in 2017 as **ROBOT** (Return Of Bleichenbacher's Oracle Threat), which affected TLS implementations from major vendors and some of the largest websites in the world, and in 2023 as the **Marvin** attack, which found timing variants in many libraries.

**OAEP** (Optimal Asymmetric Encryption Padding), standardised in PKCS#1 v2, mixes the message with randomness using hash-based masks in a way that comes with a security proof. Use **RSA-OAEP with SHA-256** whenever RSA encryption is unavoidable.

> **In practice.** Modern protocols have largely stopped using RSA for encryption at all. TLS 1.3 removed RSA key transport entirely; RSA now appears in TLS only to sign the handshake. If a design proposes RSA encryption for new data, ask why it is not using ECDH or ML-KEM key exchange with symmetric encryption (Chapters 8 and 26).

## 7.5 Padding for signatures: PKCS#1 v1.5 and PSS

An RSA signature is created by hashing the message, padding the hash, and raising it to the private exponent:

```
s = pad(hash(m))^d mod n         verify: s^e mod n == pad(hash(m))
```

- **PKCS#1 v1.5 signature padding** is deterministic and, unlike its encryption counterpart, has no practical attack when verified strictly. It remains the most common RSA signature format in certificates. Loose verification has caused forgeries: in 2006, Bleichenbacher showed that verifiers which did not check the padding fully could be fooled with forged signatures when `e = 3`.
- **RSA-PSS** (Probabilistic Signature Scheme) adds randomness and has a strong security proof. It is required in TLS 1.3 for RSA handshake signatures and is the better choice for new designs.

## 7.6 Key sizes and lifetime

| RSA modulus | Security level | Status |
| --- | --- | --- |
| 1024 bits | About 80 bits | Broken in practice for well-funded attackers; disallowed |
| 2048 bits | 112 bits | Today's minimum; acceptable until about 2030 under NIST guidance |
| 3072 bits | 128 bits | Recommended for new keys with long lifetimes |
| 4096 bits | About 140 bits | Common for root CAs; slower |

The largest RSA number publicly factored by classical computers is 829 bits (RSA-250, in 2020), which took about 2,700 core-years of computation. 2048-bit RSA is far beyond classical reach. It is not, however, beyond the reach of a large, error-corrected quantum computer running Shor's algorithm (Chapter 25). Estimates of the quantum resources needed keep falling: a 2025 analysis by Google researchers estimated that 2048-bit RSA could be factored in under a week with fewer than one million noisy qubits, a twentyfold reduction from their 2019 estimate. No such machine exists, but the trend is why governments now set retirement dates for RSA.

> **Current development.** NIST's draft transition plan proposes that 2048-bit RSA be deprecated after 2030 and all RSA be disallowed after 2035 for federal use. Larger RSA keys do not help against quantum attackers; the replacement is ML-DSA for signatures and ML-KEM for key establishment (Chapter 26).

## 7.7 Implementation pitfalls

Correct mathematics is not enough. RSA implementations have failed in these ways:

- **Weak prime generation.** In 2012, two research teams scanned the internet's public keys and found that tens of thousands of devices, mostly routers and firewalls generating keys at first boot with poor randomness, shared a prime factor with another device. A simple gcd computation between pairs of keys factored them instantly.
- **Structured primes.** The **ROCA** vulnerability (2017) found that a widely used security chip generated primes with a special structure that made factoring feasible, affecting keys in a very large number of national ID cards, laptops' trusted platform modules and hardware tokens. Estonia had to replace the keys on 760,000 national ID cards.
- **Timing and fault attacks.** Decryption time can leak bits of d; a single computing error during CRT decryption can reveal p. Libraries use blinding and verify results before releasing them.
- **Small or shared exponents.** Never use a small private exponent d, and never share a modulus n between users.

The rules for you are short: generate RSA keys only with mature libraries or certified hardware, use OAEP for encryption and PSS (or strictly verified PKCS#1 v1.5) for signatures, use at least 3072 bits for anything long-lived, and plan RSA's replacement.

## Lab: RSA by hand, then RSA done right

**1. Toy RSA and its weaknesses** (Python):

```python
p, q, e = 1009, 1013, 65537
n, phi = p*q, (p-1)*(q-1)
d = pow(e, -1, phi)
m = 42
c = pow(m, e, n); print(pow(c, d, n))        # 42
# Malleability: double the plaintext without the key
c2 = (c * pow(2, e, n)) % n; print(pow(c2, d, n))  # 84
# Determinism: guess-and-check a "secret" vote
print(pow(1, e, n) == pow(1, e, n))          # same ciphertext every time
```

**2. Generate and inspect a real key with OpenSSL.**

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out rsa.key
openssl pkey -in rsa.key -text -noout | head -20   # modulus, exponent, primes
openssl pkey -in rsa.key -pubout -out rsa.pub
```

**3. Sign with PSS and verify.**

```bash
echo "release v2.4.1" > release.txt
openssl dgst -sha256 -sigopt rsa_padding_mode:pss -sign rsa.key -out release.sig release.txt
openssl dgst -sha256 -sigopt rsa_padding_mode:pss -verify rsa.pub -signature release.sig release.txt
```

Change one character in `release.txt` and verify again. Verification fails.

**4. The shared-prime attack in miniature.**

```python
from math import gcd
n1, n2 = 1009*1013, 1009*1019   # two "devices" that shared a prime
print(gcd(n1, n2))               # 1009: both keys factored instantly
```

## Failure story: ROCA and the national ID cards

In October 2017, researchers from Masaryk University in the Czech Republic published **ROCA**. A cryptographic library built into chips from a major manufacturer generated RSA primes using a shortcut that made them faster to find. The shortcut left a hidden structure: every key generated by the chip could be recognised by a quick test, and its modulus factored using a specialised method. A 2048-bit key could be factored for an estimated 20,000 to 40,000 US dollars of cloud computing, and 1024-bit keys in hours.

The chip was certified to high security standards and used in national identity cards, trusted platform modules in business laptops, hardware security keys and smart cards. The library's design had never been published, so nobody outside the manufacturer could review it. Kerckhoffs's principle from Chapter 1 is not only about algorithms: secret implementation shortcuts can be just as dangerous as secret algorithms.

Recovery was expensive. Estonia suspended the certificates of 760,000 ID cards and asked citizens to update their keys. Laptop makers shipped firmware updates, and every key generated by an affected chip had to be replaced. The episode is a powerful argument for crypto agility and for knowing exactly which keys came from which hardware.

## Chapter summary

- RSA security rests on factoring. The private exponent d can be computed by anyone who knows the factors of n.
- Textbook RSA is deterministic and malleable. Padding is mandatory: OAEP for encryption, PSS or strictly verified PKCS#1 v1.5 for signatures.
- Bleichenbacher-style padding oracles have recurred for 25 years. Modern protocols avoid RSA encryption altogether.
- Use 3072-bit keys for long-lived uses; 2048-bit is the minimum and is scheduled for deprecation after 2030.
- Bad randomness and secret implementation shortcuts (shared primes, ROCA) have broken millions of RSA keys.
