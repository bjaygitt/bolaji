## 12.1 The goal: a boring, modern configuration

A good TLS configuration is boring. It offers a small set of modern options, has no legacy fallbacks, and changes rarely. Most organisations should adopt a published profile rather than invent their own. The Mozilla Server Side TLS guidelines are the most widely used, with three levels:

| Profile | Protocols | Who it serves | When to use |
| --- | --- | --- | --- |
| **Modern** | TLS 1.3 only | Clients from roughly the last five years | New services, APIs, internal systems |
| **Intermediate** | TLS 1.2 and 1.3, AEAD ciphers with forward secrecy | Almost all clients | The default for public websites |
| **Old** | Down to TLS 1.0 | Very old clients | Only with a documented, time-limited exception |

## 12.2 Protocol and cipher choices

For the intermediate profile, the TLS 1.2 cipher suites should all:

- Use **ephemeral key exchange** (ECDHE), for forward secrecy.
- Use **AEAD** (AES-GCM or ChaCha20-Poly1305), never CBC.
- Avoid RSA key transport, static DH, 3DES, RC4, export suites, and NULL or anonymous suites.

A representative TLS 1.2 list:

```
ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:
ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:
ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305
```

TLS 1.3 suites need no tuning; all of them are good. Two settings deserve attention:

- **Key exchange groups.** Offer `X25519MLKEM768` first where your software supports it (OpenSSL 3.5 and later, recent BoringSSL, Go 1.24 and later, and others), then `X25519`, `secp256r1`, `secp384r1`.
- **Server cipher preference.** Letting the server choose the order is no longer critical with an all-strong list, but it prevents clients from picking a weaker option if any slip in.

### An example configuration

For nginx, an intermediate profile looks like this:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
ssl_ecdh_curve X25519MLKEM768:X25519:prime256v1:secp384r1;
ssl_session_tickets off;      # or rotate ticket keys frequently
ssl_certificate     /etc/tls/fullchain.pem;   # leaf + intermediates
ssl_certificate_key /etc/tls/privkey.pem;
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
```

Session tickets are disabled here because their encryption keys, if never rotated, can undermine forward secrecy: anyone who steals the ticket key can decrypt resumed sessions. If you enable tickets, rotate their keys at least daily across all servers.

## 12.3 Certificates on the server

Many TLS failures are certificate failures. Know the four classic ones.

### 1. The incomplete chain

A server must send its own certificate **and** the intermediate CA certificates that link it to a trusted root (Chapter 15). Browsers sometimes cope with a missing intermediate by fetching it or using a cache, which hides the problem during testing. Mobile apps, API clients, IoT devices and older systems do not, and fail with "unable to get local issuer certificate". Always configure the **full chain** (leaf plus intermediates, not the root).

### 2. The name mismatch

The hostname the client connects to must appear in the certificate's **Subject Alternative Name** list. Connecting by IP address, an internal alias, or a new subdomain not in the list fails. Wildcards cover one label only: `*.example.com` covers `shop.example.com` but not `example.com` or `eu.shop.example.com`.

### 3. The expired certificate

Covered at length in Chapter 19. The fix is automation, monitoring and early renewal, not calendar reminders.

### 4. The wrong key type for the client

Some old clients only accept RSA certificates. Servers can hold both an ECDSA and an RSA certificate for the same names and choose per client. ECDSA P-256 is the better default: smaller, faster handshakes.

## 12.4 HTTPS beyond the handshake

TLS protects the connection, but web applications can still undo that protection. Four mechanisms matter.

**HTTP Strict Transport Security (HSTS).** A response header that tells the browser to use only HTTPS for this site for a set period. It stops **SSL stripping** attacks, where an attacker on the network intercepts the first plain-HTTP request and keeps the user on HTTP. With `includeSubDomains` and a long `max-age`, a site can apply to be **preloaded** into browsers, so even the first visit is protected. Roll it out carefully: once preloaded, every subdomain must support HTTPS, and removal takes months.

**Secure cookies.** Session cookies must carry the `Secure` flag (sent only over HTTPS), `HttpOnly` (unreadable by JavaScript) and an appropriate `SameSite` value. The `__Host-` name prefix enforces these properties.

**Mixed content.** An HTTPS page that loads scripts or styles over plain HTTP gives an attacker a way to inject code. Modern browsers block active mixed content and upgrade many passive resources automatically. The `Content-Security-Policy: upgrade-insecure-requests` header helps migrate old pages.

**Certificate Authority Authorization (CAA).** A DNS record listing which CAs may issue certificates for your domain (Chapter 16). It is a cheap, valuable protection against mis-issuance.

## 12.5 A history of TLS attacks, and the rule each one taught

| Year | Attack | What it exploited | Rule it taught |
| --- | --- | --- | --- |
| 2009 | SSL stripping | First request over plain HTTP | Use HSTS and preloading |
| 2011 | BEAST | Predictable CBC IVs in TLS 1.0 | Retire TLS 1.0; prefer AEAD |
| 2012 | CRIME, later BREACH | Compression leaking secret lengths | Disable TLS compression; be careful compressing secrets in HTTP |
| 2013 | Lucky Thirteen | Timing in MAC-then-encrypt CBC | Use AEAD only |
| 2014 | Heartbleed | A memory-read bug in OpenSSL's heartbeat feature | Patch fast; rotate keys after memory disclosure |
| 2014 | POODLE | SSL 3.0 padding | Disable SSL 3.0 everywhere |
| 2015 | FREAK, Logjam | Downgrade to export-grade crypto | Remove legacy options entirely |
| 2016 | Sweet32 | 64-bit block ciphers (3DES) | Remove 3DES |
| 2016 | DROWN | SSLv2 on any service sharing a key | Never share keys across services |
| 2017 | ROBOT | Bleichenbacher oracles in RSA key exchange | Remove RSA key transport |

Notice the pattern: almost every attack exploited an option that was kept "for compatibility". The single best rule in TLS deployment is to **remove what you do not need**.

## 12.6 Testing and monitoring

Test every public endpoint when it is built and continuously afterwards.

| Tool | What it does |
| --- | --- |
| Qualys SSL Labs Server Test | Free web-based grading (A+ to F) of public servers; the best known external check |
| testssl.sh | Open-source command-line scanner; works on internal hosts and in pipelines |
| sslyze | Python scanner suited to automation |
| openssl s_client | Manual inspection of handshakes and chains |
| Certificate Transparency monitors | Alert when certificates are issued for your domains (Chapter 16) |

Integrate a scanner into your deployment pipeline so that a configuration regression fails the build, and run scheduled external scans so drift is caught.

### Getting an A+ on SSL Labs

The SSL Labs grade is a useful, widely recognised benchmark. An A+ typically requires: TLS 1.2 and 1.3 only, forward-secret AEAD suites only, a complete chain from a trusted CA, a key of adequate size, no known vulnerabilities, and HSTS with a long `max-age`. Treat the grade as a floor, not a finish line: it does not see your internal services, client-side behaviour or certificate operations.

> **In practice.** TLS often terminates not on the application server but on a load balancer, reverse proxy, CDN or service mesh. Every termination point needs its own configuration review, and traffic between the terminator and the backend needs its own protection. "We use TLS" should always be followed by "where does it terminate, and what protects the next hop?"

## Lab: grade and fix a server

**1. Scan a public site.** Run `testssl.sh` (from testssl.sh on GitHub) against a site you own or are permitted to test:

```bash
./testssl.sh --fast https://your-site.example
```

Read the sections on protocols, cipher order, forward secrecy, HSTS, and vulnerabilities.

**2. Build a deliberately weak local server and fix it.** Using Docker and nginx, start with a configuration that allows TLS 1.0, CBC ciphers and no HSTS, scan it with testssl.sh, then apply the configuration in section 12.2 and scan again. Record each finding that disappears.

**3. Break and fix a chain.** Configure the server with only the leaf certificate, then connect with:

```bash
openssl s_client -connect localhost:443 -servername localhost </dev/null | grep -i verify
```

Observe the verification error, add the intermediate to `fullchain.pem`, and confirm `Verify return code: 0 (ok)`.

## Failure story: Heartbleed

In April 2014, a flaw named **Heartbleed** was disclosed in OpenSSL, the library behind a large share of the web's HTTPS servers. The TLS heartbeat extension let one side send a message and ask for it to be echoed back, stating the message's length. OpenSSL trusted the stated length without checking it against the actual message. An attacker could send one byte and claim 64 kilobytes, and the server would return 64 kilobytes of whatever happened to be in its memory: session cookies, passwords, and in some cases the server's private TLS key.

The cryptography was never involved. A missing bounds check in a rarely used feature exposed everything the cryptography protected, and the attack left no trace in normal logs. Recovery required patching, then **replacing private keys and certificates** on hundreds of thousands of servers, because nobody could prove their keys had not been read. Many organisations discovered they had no inventory of where their certificates were installed, which turned a patch into months of work.

Heartbleed also exposed how underfunded critical open-source infrastructure was: OpenSSL had a handful of part-time maintainers. The response led to the Core Infrastructure Initiative, later the Open Source Security Foundation, and to new TLS libraries such as BoringSSL and LibreSSL.

## Chapter summary

- Adopt a published profile (Mozilla intermediate or modern) instead of inventing your own. Offer TLS 1.2 and 1.3 with forward-secret AEAD suites only, and hybrid post-quantum groups where supported.
- Configure full chains, correct names, and automated renewal. Prefer ECDSA certificates.
- Protect the web layer with HSTS, secure cookies, mixed-content controls and CAA.
- Nearly every historical TLS attack exploited a legacy option kept for compatibility. Remove what you do not need.
- Test in pipelines and continuously, and remember every TLS termination point.
