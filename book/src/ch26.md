## 26.1 How the standards were chosen

In 2016, NIST launched an open competition for post-quantum public-key algorithms, modelled on the AES and SHA-3 competitions. Researchers worldwide submitted 82 proposals. Over three rounds and six years, the community attacked them publicly; several were broken outright, including one finalist, SIKE, which fell in 2022 to an attack that ran in about an hour on a single laptop core. That break is a reminder of why open competitions and conservative choices matter.

In August 2024, NIST published three standards:

| Standard | Algorithm (original name) | Type | Mathematical basis |
| --- | --- | --- | --- |
| **FIPS 203** | **ML-KEM** (CRYSTALS-Kyber) | Key encapsulation | Module lattices (Module-LWE) |
| **FIPS 204** | **ML-DSA** (CRYSTALS-Dilithium) | Signature | Module lattices |
| **FIPS 205** | **SLH-DSA** (SPHINCS+) | Signature | Hash functions only |

Two more are in progress:

- **FN-DSA** (Falcon), a compact lattice signature, as FIPS 206. The draft was submitted for approval in 2025; final publication is expected around the end of 2026 or in 2027.
- **HQC**, a code-based KEM selected in March 2025 as a backup to ML-KEM with different mathematics; a draft standard is expected first, with a final version around 2027.

NIST also runs an "on-ramp" competition for additional signature schemes with different trade-offs, so more options will follow later in the decade.

## 26.2 Lattices in one page

Recall the idea from Chapter 2: **Learning With Errors (LWE)**. Take a secret vector s. Publish many random linear equations in s, each with a small random error added. Without the errors, ordinary algebra recovers s instantly. With the errors, recovering s means solving a hard lattice problem, believed hard for both classical and quantum computers.

**Module-LWE**, used by ML-KEM and ML-DSA, organises the numbers into small polynomials to make keys compact and arithmetic fast, using a technique called the **Number Theoretic Transform (NTT)**, a cousin of the fast Fourier transform.

### How ML-KEM works, intuitively

1. **Key generation.** Bob's public key is a matrix A and a vector `t = A·s + e`, where s is his secret and e a small error. Recovering s from t is the LWE problem.
2. **Encapsulation.** Alice picks her own small random values, computes a ciphertext from Bob's public key that hides a random message, and derives a shared key from that message.
3. **Decapsulation.** Bob uses s to remove most of the noise and recover the message, then derives the same shared key.

The small errors mean Bob's recovery is approximate, with a tiny chance of failure (below 2^-138 for ML-KEM-768). ML-KEM wraps this in the **Fujisaki-Okamoto transform**: Bob re-encrypts the recovered message and checks it matches, rejecting any manipulated ciphertext with a pseudo-random key. That is what makes ML-KEM IND-CCA2 secure (Chapter 10), and safe to use with long-lived keys.

### A KEM is not Diffie-Hellman

ML-KEM is a **key encapsulation mechanism**, not a Diffie-Hellman replacement in every respect:

- DH is symmetric: both sides contribute and compute. A KEM is asymmetric: one side encapsulates to the other's public key.
- Protocols built on DH's special properties (for example, combining static and ephemeral keys in Signal's X3DH) needed redesign, which is why PQXDH and similar protocols took effort.
- For ephemeral key exchange, as in TLS, the KEM interface fits naturally: the client sends a public key, the server returns a ciphertext.

## 26.3 The algorithms, compared

### ML-KEM (FIPS 203)

| Parameter set | Security category | Public key | Ciphertext | Shared secret |
| --- | --- | --- | --- | --- |
| ML-KEM-512 | 1 (about AES-128) | 800 bytes | 768 bytes | 32 bytes |
| **ML-KEM-768** | 3 (about AES-192) | 1,184 bytes | 1,088 bytes | 32 bytes |
| ML-KEM-1024 | 5 (about AES-256) | 1,568 bytes | 1,568 bytes | 32 bytes |

For comparison, an X25519 public key is 32 bytes. ML-KEM is very fast, often faster than X25519, but much larger. **ML-KEM-768** is the default choice; it is what X25519MLKEM768 uses in TLS. CNSA 2.0 requires ML-KEM-1024 for US national security systems.

### ML-DSA (FIPS 204)

| Parameter set | Security category | Public key | Signature |
| --- | --- | --- | --- |
| ML-DSA-44 | 2 | 1,312 bytes | 2,420 bytes |
| **ML-DSA-65** | 3 | 1,952 bytes | 3,309 bytes |
| ML-DSA-87 | 5 | 2,592 bytes | 4,627 bytes |

ML-DSA is the general-purpose post-quantum signature: fast to sign and verify, with no secret state and "hedged" randomness by default. Its cost is size: an ECDSA P-256 signature is 64 bytes and its public key 64 bytes. A TLS certificate chain with ML-DSA keys and signatures grows by roughly 10 to 15 kilobytes, which matters for handshake performance and constrained devices.

### SLH-DSA (FIPS 205)

SLH-DSA is built **only from hash functions**, so its security rests on the most conservative assumption in cryptography: that SHA-2 or SHAKE behave as expected. No lattice mathematics is involved. The price is large, slow signatures:

| Parameter set | Public key | Signature | Signing speed |
| --- | --- | --- | --- |
| SLH-DSA-128s ("small") | 32 bytes | 7,856 bytes | Slow |
| SLH-DSA-128f ("fast") | 32 bytes | 17,088 bytes | Faster, larger |
| SLH-DSA-256s | 64 bytes | 29,792 bytes | Slow |

SLH-DSA suits uses where signatures are created rarely and must be trusted for a very long time, and where a second mathematical basis is valuable: root CA certificates, firmware roots of trust, and long-term archives.

### FN-DSA (draft FIPS 206)

FN-DSA (Falcon) offers the smallest lattice signatures: about 666 bytes with an 897-byte public key at the lower security level. It is attractive where size matters, such as certificate chains. Its signing uses floating-point arithmetic and is notoriously hard to implement in constant time, so expect it mainly for verification-heavy uses and in well-reviewed libraries.

### HQC (selected 2025)

HQC is a KEM based on error-correcting codes rather than lattices. It is larger and slower than ML-KEM, but provides a fallback with independent mathematics in case a breakthrough against lattices emerges.

### Stateful hash-based signatures: LMS and XMSS

**LMS** (RFC 8554) and **XMSS** (RFC 8391), approved by NIST in SP 800-208 in 2020, are hash-based signatures that have been available longer than the FIPS 203 to 205 standards. They are compact and fast to verify, but **stateful**: each one-time key inside them must be used only once, and the signer must reliably track which have been used. Reusing state, for example by restoring a backup or cloning a VM, can destroy security.

That makes them unsuitable for general use but well suited to **firmware and software signing**, where signatures are created rarely, in controlled HSM-based environments. CNSA 2.0 requires LMS or XMSS for firmware signing, and many device makers are already using them.

## 26.4 Choosing an algorithm

| Use case | Recommended choice |
| --- | --- |
| Key exchange in TLS, SSH, VPNs | Hybrid X25519 (or P-256) with ML-KEM-768; ML-KEM-1024 for CNSA 2.0 systems |
| Encrypting data to a public key (HPKE, key wrapping) | ML-KEM-768 or 1024, in hybrid during transition |
| General signatures: TLS certificates, tokens, documents | ML-DSA-65 (ML-DSA-87 for CNSA 2.0); FN-DSA where size is critical, once standardised |
| Root CAs and long-lived trust anchors | ML-DSA-87, or SLH-DSA for maximum conservatism |
| Firmware and boot signing | LMS or XMSS in an HSM; SLH-DSA or ML-DSA as alternatives |
| Symmetric encryption and hashing | Keep AES-256, SHA-384 or SHA-3; no change of algorithm needed |

## 26.5 Hybrid and composite designs

During the transition, most deployments combine a classical algorithm with a post-quantum one, so that security holds if **either** survives. This protects against a quantum computer (if the classical part breaks) and against an undiscovered flaw in the new algorithms or their implementations (if the post-quantum part breaks).

- **Hybrid key exchange** feeds both shared secrets into the key derivation function. X25519MLKEM768 in TLS 1.3, mlkem768x25519-sha256 in SSH, and PQXDH in Signal all work this way.
- **Composite signatures** pair a classical and a post-quantum signature in a single certificate or signature object, valid only if both verify. The IETF LAMPS working group has specified composite ML-DSA formats for X.509, alongside "pure" ML-DSA certificates.
- **Dual certificates or chains** are an alternative: issue a classical and a post-quantum certificate, and let each relying party use what it supports.

Some agencies, notably the NSA for national security systems, prefer moving directly to pure post-quantum algorithms rather than hybrids for signatures; others, including Germany's BSI and France's ANSSI, recommend hybrids during the transition. Follow your sector's guidance.

## 26.6 Implementation risks

New algorithms bring new implementation pitfalls:

- **Side channels.** In early 2024, researchers found **KyberSlash**: several implementations of Kyber used a division step whose timing depended on secret data, allowing key recovery. Mature libraries fixed it; immature ones may not have.
- **Decapsulation failures and validation.** ML-KEM implementations must perform the re-encryption check exactly as specified, and validate input sizes.
- **Randomness.** As always, key generation needs a strong random source (Chapter 3).
- **State for LMS and XMSS.** Lose or duplicate state and security is gone.
- **Size assumptions.** Protocol fields, database columns, HSM buffers, certificate size limits, and network packets sized for 64-byte signatures will break.

Use well-maintained libraries that implement the final FIPS versions: recent releases of OpenSSL (3.5 and later include ML-KEM, ML-DSA and SLH-DSA), BoringSSL and AWS-LC, the Go standard library, Bouncy Castle for Java, and the Open Quantum Safe project's liboqs for experimentation. Prefer FIPS-validated modules where compliance requires it, as vendors add post-quantum algorithms to their validated configurations.

## Lab: post-quantum cryptography with OpenSSL

You need OpenSSL 3.5 or later (`openssl version`).

**1. List the algorithms.**

```bash
openssl list -kem-algorithms | grep -i ml-kem
openssl list -signature-algorithms | grep -iE "ml-dsa|slh-dsa"
```

**2. Generate and compare key sizes.**

```bash
openssl genpkey -algorithm ML-DSA-65 -out mldsa.key
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ec.key
openssl pkey -in mldsa.key -pubout -outform DER | wc -c
openssl pkey -in ec.key -pubout -outform DER | wc -c
```

**3. Sign and verify with ML-DSA.**

```bash
echo "post-quantum hello" > msg.txt
openssl pkeyutl -sign -inkey mldsa.key -in msg.txt -rawin -out msg.sig
wc -c msg.sig                                # about 3,309 bytes
openssl pkeyutl -verify -inkey mldsa.key -in msg.txt -rawin -sigfile msg.sig
```

**4. Encapsulate and decapsulate with ML-KEM.**

```bash
openssl genpkey -algorithm ML-KEM-768 -out kem.key
openssl pkey -in kem.key -pubout -out kem.pub
openssl pkeyutl -encap -inkey kem.pub -pubin -out ct.bin -secret ss_sender.bin
openssl pkeyutl -decap -inkey kem.key -in ct.bin -secret ss_receiver.bin
cmp ss_sender.bin ss_receiver.bin && echo "shared secrets match"
```

**5. Make a post-quantum certificate.** Create a self-signed ML-DSA-65 certificate with `openssl req -x509 -newkey ML-DSA-65 ...` and inspect it. Compare its size with an ECDSA certificate.

## Failure story: SIKE, broken in an hour

**SIKE** (Supersingular Isogeny Key Encapsulation) was one of the most elegant candidates in NIST's competition. It had the smallest keys of any post-quantum KEM, it had survived years of analysis, and it was selected in 2022 as a fourth-round candidate for possible standardisation. Major technology companies had experimented with it in TLS.

In July 2022, Wouter Castryck and Thomas Decru published an attack, building on a 25-year-old mathematical result, that recovered SIKE's secret key in about an hour on a single classical computer core for the lowest security level, and in about a day for the highest. The scheme was withdrawn.

Nobody was harmed, because SIKE had only been used experimentally and always in hybrid with classical key exchange. The episode is the strongest argument for three practices in this chapter: prefer algorithms with long and broad analysis (ML-KEM, ML-DSA, SLH-DSA), use hybrid designs during the transition, and keep systems agile enough to swap algorithms when the unexpected happens.

## Chapter summary

- NIST standardised ML-KEM (FIPS 203), ML-DSA (FIPS 204) and SLH-DSA (FIPS 205) in 2024; FN-DSA and HQC are coming.
- ML-KEM and ML-DSA rest on Module-LWE lattices: fast, but with keys and signatures tens of times larger than today's.
- SLH-DSA relies only on hashes: very conservative, with large signatures; LMS and XMSS are compact stateful hash signatures suited to firmware.
- Use ML-KEM-768 in hybrid for key exchange, ML-DSA-65 for general signatures, and stronger sets or SLH-DSA for long-lived roots.
- Hybrid and composite designs hedge against both quantum attacks and new-algorithm flaws; implementation risks include side channels, state handling and size assumptions.
