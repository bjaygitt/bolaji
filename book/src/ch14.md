## 14.1 Authentication, authorisation and federation

Three words are often mixed up:

- **Authentication** answers "who are you?" (logging in).
- **Authorisation** answers "what may you do?" (permissions).
- **Federation** lets one system trust another's answer, so a user who logged in once can use many services (single sign-on).

Identity protocols carry these answers between systems as **signed tokens**. The signature is what lets a service trust a token without calling back to the issuer every time. That makes the issuer's signing key one of the most powerful keys in any organisation: anyone who holds it can mint any identity.

## 14.2 OAuth 2.0: delegated authorisation

**OAuth 2.0** (RFC 6749) lets a user grant an application limited access to their resources without giving it their password. The roles:

| Role | Example |
| --- | --- |
| **Resource owner** | The user |
| **Client** | The application that wants access |
| **Authorisation server** | The system that authenticates the user and issues tokens |
| **Resource server** | The API holding the data |

The recommended flow for most applications is the **authorisation code flow with PKCE**:

1. The client sends the user to the authorisation server with a random **code challenge** (a hash of a secret **code verifier**).
2. The user logs in and approves access.
3. The authorisation server redirects back with a short-lived **authorisation code**.
4. The client exchanges the code, plus the original code verifier, for an **access token** (and often a **refresh token**).

**PKCE** (Proof Key for Code Exchange, RFC 7636) ensures that a stolen authorisation code is useless without the verifier, which never left the client. It is now required for all clients in the OAuth 2.1 consolidation of best practices.

**Access tokens** are usually **bearer tokens**: whoever presents one gets access, like cash. That makes them valuable to steal. Defences include short lifetimes (minutes), narrow **scopes**, and **sender-constrained tokens** that are bound to a key the client holds, using mTLS (RFC 8705) or **DPoP** (RFC 9449), where the client signs each request with a private key, so a stolen token alone is not enough.

## 14.3 OpenID Connect: authentication on top of OAuth

OAuth on its own is about access, not identity. **OpenID Connect (OIDC)** adds an **ID token**: a signed statement from the identity provider saying "this user authenticated, at this time, for this client". Enterprise single sign-on, "Sign in with..." buttons, and workload identity in cloud platforms all use OIDC.

The identity provider publishes its signing public keys at a well-known URL as a **JSON Web Key Set (JWKS)**. Relying services fetch the JWKS, cache it, and verify ID token signatures locally. Each key has a **key ID (kid)**, and tokens name which key signed them, which makes rotation possible: the provider publishes a new key, starts signing with it, and later removes the old one once all tokens signed by it have expired.

## 14.4 JSON Web Tokens

Both access tokens and ID tokens are commonly **JSON Web Tokens (JWT)**, RFC 7519. A JWT has three base64url-encoded parts separated by dots:

```
header.payload.signature
{"alg":"ES256","kid":"2026-09"} . {"iss":"https://id.example","sub":"u123","aud":"api","exp":1791500000} . <signature>
```

The **header** names the signing algorithm and key. The **payload** holds **claims**: issuer (`iss`), subject (`sub`), audience (`aud`), expiry (`exp`) and others. The **signature** covers the header and payload. A JWT is signed, not encrypted: anyone can read the payload. (Encrypted JWTs, called JWE, exist but are less common.)

### How to validate a JWT

Every check matters. Missing any one has caused real breaches.

1. **Fix the algorithm on your side.** Accept only the algorithm you expect for this issuer, such as ES256 or RS256. Never let the token's header choose.
2. **Verify the signature** with the issuer's key, selected by `kid` from a JWKS you fetched over TLS from a configured URL.
3. **Check the issuer** (`iss`) is the one you trust.
4. **Check the audience** (`aud`) is your service. Otherwise a token issued for another service can be replayed against yours.
5. **Check time claims** (`exp`, `nbf`, `iat`) with a small allowance for clock skew.
6. **Check token type and purpose**, so an ID token is not accepted as an access token.

### Classic JWT attacks

| Attack | How it works | Prevention |
| --- | --- | --- |
| `alg: none` | Attacker sets the algorithm to "none" and removes the signature; naive libraries accept it | Reject "none"; fix the algorithm (check 1) |
| Algorithm confusion | Attacker changes RS256 to HS256 and signs with the server's **public** key as an HMAC secret; a library that picks the algorithm from the header verifies it | Bind each key to one algorithm |
| `kid` or `jku` injection | Attacker points the header at a key they control, or injects paths into `kid` | Only use keys from configured JWKS URLs |
| Missing audience check | Token for service A accepted by service B | Always check `aud` |
| Weak HMAC secret | Short shared secrets for HS256 brute-forced offline | Use asymmetric signatures, or 256-bit random secrets |

> **In practice.** Prefer asymmetric signing (ES256 or EdDSA) for tokens consumed by multiple services. With HMAC (HS256), every service that verifies tokens holds the secret and can therefore also mint them.

## 14.5 SAML

**SAML 2.0** is the older, XML-based federation standard, still common for enterprise single sign-on. The identity provider signs XML assertions with **XML Digital Signature**. XML signatures are notoriously tricky: **signature wrapping attacks** move signed elements around in the document so that the signature still verifies but the application reads a different, unsigned element. Several major SAML libraries have had such flaws. If you must accept SAML, use a mature, well-maintained library and keep it patched.

## 14.6 Protecting identity signing keys

Whoever holds an identity provider's signing key can impersonate any user to every federated service, often without triggering normal login alerts. Two incidents make the point:

- In the **2020 software supply-chain intrusion** that affected many US agencies and companies, attackers who reached on-premises federation servers stole token-signing certificates and forged SAML assertions, a technique researchers named **Golden SAML**. Forged tokens gave access to cloud email and documents while bypassing multi-factor authentication.
- In the **2023 Storm-0558** incident (Chapter 9), a stolen consumer signing key, combined with a validation flaw, let attackers forge tokens for enterprise mailboxes.

Treat identity signing keys like root CA keys: keep them in HSMs or managed key services where they cannot be exported, rotate them on a schedule, publish only what verifiers need, scope keys tightly by tenant and purpose, and monitor for tokens that do not match normal issuance patterns.

## 14.7 Passkeys: public-key cryptography for everyone

Passwords are phishable: a convincing fake login page collects them, and many forms of multi-factor authentication (codes by text message or authenticator apps) can be phished in real time too. **FIDO2** and its web API, **WebAuthn**, replace passwords with public-key cryptography, and **passkeys** are the consumer-friendly form of FIDO2 credentials.

How it works:

1. **Registration.** Your device creates a new key pair for this specific website. The public key goes to the website; the private key stays on your device or in your platform's password manager, protected by the device's secure hardware and unlocked with your fingerprint, face or PIN.
2. **Login.** The website sends a random challenge. Your device signs it, together with the website's origin (its exact domain), and the site verifies the signature with the stored public key.

Two properties make passkeys **phishing-resistant**:

- The signature includes the origin. A key created for `bank.example` will never sign for `bank-example.login.site`. The browser enforces this, not the user.
- There is no shared secret to steal from the server. A breached website loses only public keys.

> **Current development.** Passkeys are now supported by all major operating systems, browsers and password managers, and can sync across a user's devices. Large consumer platforms report that passkey sign-ins are both faster and far more successful than passwords, and many organisations now require phishing-resistant authentication, such as FIDO2 security keys or passkeys, for administrators. US federal guidance has required phishing-resistant multi-factor authentication for agency staff since 2022.

## Lab: build and break a JWT

**1. Create and verify a signed JWT** (Python, `pip install pyjwt cryptography`):

```python
import jwt, time
from cryptography.hazmat.primitives.asymmetric import ec
key = ec.generate_private_key(ec.SECP256R1())
tok = jwt.encode({"iss": "https://id.lab", "aud": "api", "sub": "u1",
                  "exp": int(time.time()) + 300}, key, algorithm="ES256",
                 headers={"kid": "lab-1"})
print(jwt.decode(tok, key.public_key(), algorithms=["ES256"],
                 audience="api", issuer="https://id.lab"))
```

**2. Try the "none" attack.** Edit the token: change the header to `{"alg":"none"}`, change `sub` to `admin`, and drop the signature (keep the trailing dot). Pass it to `jwt.decode` with `algorithms=["ES256"]`. It is rejected, because the algorithm is fixed by the verifier, not the token.

**3. Try the audience attack.** Encode a token with `aud: "other-service"` and decode with `audience="api"`. It is rejected. Now remove the `audience` argument and see the library refuse to skip the check silently: good libraries force you to make the decision explicitly.

**4. Inspect a JWKS.** Fetch a real identity provider's public keys, for example `https://www.googleapis.com/oauth2/v3/certs`, and note the `kid`, `alg` and key parameters. Fetch it again weeks later to observe rotation.

## Failure story: the token that trusted its own header

In 2015, security researcher Tim McLean reviewed popular JWT libraries across several languages and found two critical flaws in many of them. Some libraries accepted tokens with `"alg": "none"` as valid, even when the application expected signed tokens, so anyone could forge any identity by deleting the signature. Others allowed **algorithm confusion**: when a server expected RSA signatures, an attacker could change the header to HS256 and create an HMAC using the server's **public** RSA key, which the library then used as the HMAC secret and accepted.

The underlying mistake was the same in both: the library let attacker-controlled data, the token header, decide how the token would be verified. Libraries were patched to require callers to specify allowed algorithms, and the JWT best-practice RFC 8725 was published in 2020 to codify the lessons. Variants still appear in new libraries and custom code, which is why "fix the algorithm on your side" is the first rule of token validation.

## Chapter summary

- Identity protocols carry authentication and authorisation as signed tokens; the issuer's signing key can mint any identity.
- OAuth 2.0 delegates access; use the authorisation code flow with PKCE, short-lived scoped tokens, and sender-constrained tokens where possible. OIDC adds signed ID tokens and publishes keys via JWKS.
- Validate JWTs completely: fixed algorithm, signature, issuer, audience, time and type. Never let the token's header choose the verification method.
- Identity signing keys deserve root-CA-level protection, as Golden SAML and Storm-0558 showed.
- Passkeys apply public-key signatures bound to the website's origin, making login phishing-resistant and server breaches far less damaging.
