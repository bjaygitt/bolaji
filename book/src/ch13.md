## 13.1 SSH: secure remote access

**SSH** (Secure Shell) gives administrators encrypted remote access to servers, and moves files and automation traffic. It runs over TCP port 22 and, like TLS, combines an ephemeral key exchange, server authentication, and symmetric encryption. Its trust model is very different, though.

### Host keys and trust on first use

Every SSH server has a **host key**. The first time you connect, your client shows the key's fingerprint and asks whether to trust it. If you accept, the key is saved in `~/.ssh/known_hosts`, and future connections warn loudly if it changes. This model is called **trust on first use (TOFU)**.

TOFU is convenient but weak in practice. Almost nobody checks the fingerprint on first connection, and in large fleets where servers are rebuilt often, users learn to click through "host key changed" warnings, which are exactly the warnings that should stop a man-in-the-middle.

### User authentication with keys

Users usually authenticate with a key pair: the public key is placed in `~/.ssh/authorized_keys` on each server, and the client proves possession of the private key. Ed25519 is the recommended key type.

At organisational scale, static SSH keys become a serious problem:

- Keys are copied to many servers and never removed when people leave.
- Private keys sit unencrypted on laptops and build servers.
- Nobody can answer "who has access to this server?" because the answer is scattered across thousands of `authorized_keys` files.

Studies of large enterprises have repeatedly found more SSH keys than employees, many granting root access, many orphaned.

### SSH certificates: the scalable answer

OpenSSH supports its own simple **certificates** (not X.509). An organisation runs an **SSH certificate authority**:

- Servers trust the CA's public key for user logins (`TrustedUserCAKeys`), instead of listing individual user keys.
- Users authenticate to an identity system (with single sign-on and multi-factor authentication) and receive a **short-lived certificate**, often valid for 8 to 16 hours, stating their username and allowed principals.
- Likewise, hosts receive host certificates, and clients trust the host CA, which eliminates TOFU prompts.

When someone leaves, their certificates simply expire. There are no keys to hunt down. This is the same pattern as short-lived X.509 certificates (Chapter 19), and the same principle runs through this book: **short lifetimes replace revocation.**

> **Current development.** OpenSSH added hybrid post-quantum key exchange in 2022 (sntrup761x25519-sha512, default from version 9.0), and version 10.0 in April 2025 made **mlkem768x25519-sha256** the default. Recent versions warn when a connection uses a key exchange that is not post-quantum. SSH sessions are therefore already protected against harvest-now-decrypt-later on up-to-date systems. Host and user signature keys are a separate, later migration.

## 13.2 IPsec: network-layer protection

**IPsec** protects traffic at the IP layer, so every application benefits without changes. It is the long-standing standard for site-to-site VPNs between offices and clouds, and is built into most routers and firewalls.

IPsec has two parts:

- **IKEv2** (Internet Key Exchange, RFC 7296) authenticates the peers, with certificates or pre-shared keys, and negotiates keys using Diffie-Hellman.
- **ESP** (Encapsulating Security Payload) encrypts and authenticates the packets, today usually with AES-GCM.

IPsec is powerful but notoriously complex: many options, many negotiable algorithms, and configuration that must match on both ends. Interoperability between vendors often forces administrators to enable weaker options, and pre-shared keys, which are easy to set up, are often weak and shared across many tunnels.

> **In practice.** Review IPsec tunnels like TLS endpoints: IKEv2 only (not IKEv1), AES-GCM, DH groups of at least 2048-bit finite field or P-256 and above, certificates instead of shared keys for anything important, and lifetimes that force regular rekeying. RFC 9370 defines how IKEv2 adds post-quantum KEMs alongside the classic exchange, and vendors are rolling it out.

## 13.3 WireGuard: radical simplicity

**WireGuard**, created by Jason Donenfeld and merged into the Linux kernel in 2020, takes the opposite approach to IPsec. It has about 4,000 lines of code, compared with hundreds of thousands for typical IPsec stacks, and **no algorithm negotiation at all**. It uses one fixed set of modern primitives:

| Purpose | WireGuard uses |
| --- | --- |
| Key exchange | X25519 |
| Encryption | ChaCha20-Poly1305 |
| Hashing | BLAKE2s |
| Handshake framework | The Noise protocol framework (Noise_IK) |

Peers are identified purely by their public keys, which are configured in advance, much like SSH `authorized_keys`. The handshake gives forward secrecy and rekeys every two minutes.

The lack of negotiation is both a strength and a weakness. There is nothing to downgrade, and the small code base has been formally verified. But if one of its primitives were ever broken, every deployment would need a new protocol version rather than a configuration change. This is a deliberate rejection of algorithm agility in favour of simplicity, and it is a useful design to compare with the agility requirements of Chapter 24. WireGuard also offers an optional pre-shared symmetric key, mixed into the handshake, which some deployments use as a stop-gap protection against future quantum attacks on X25519.

## 13.4 End-to-end encrypted messaging: the Signal protocol

In TLS, the server can read your data: encryption stops at the server. **End-to-end encryption (E2EE)** means only the communicating users can read messages; the service that relays them cannot. The **Signal protocol**, developed by Moxie Marlinspike and Trevor Perrin, is the foundation of E2EE in Signal, WhatsApp, Google Messages and others, protecting several billion users.

Messaging has a hard problem that TLS does not: the other person may be offline when you start a conversation, and conversations last for years on devices that may be stolen or compromised. Signal solves this with two components.

### X3DH, now PQXDH: starting a conversation offline

Each user uploads a bundle of public keys to the server: a long-term identity key, a signed medium-term "prekey", and a batch of one-time prekeys. To start a conversation, Alice downloads Bob's bundle and combines several Diffie-Hellman exchanges between her keys and his to derive a shared secret, without Bob being online. This is **X3DH** (Extended Triple Diffie-Hellman).

In 2023, Signal upgraded this to **PQXDH**, which adds an ML-KEM encapsulation to the exchange, so that new conversations are protected against harvest-now-decrypt-later.

### The Double Ratchet: healing after compromise

Once a conversation starts, the **Double Ratchet** derives a new key for every message:

- A **symmetric ratchet** runs each key through a KDF to produce the next. Old keys are deleted, so stealing today's key does not reveal yesterday's messages (**forward secrecy**).
- A **Diffie-Hellman ratchet** mixes in a fresh DH exchange whenever the conversation changes direction. Even if an attacker steals a device's current keys, the next fresh DH exchange, which the attacker did not observe, locks them out again. This is called **post-compromise security** or "self-healing".

> **Current development.** In October 2025, Signal announced a "triple ratchet" design that adds a post-quantum ratchet (named SPQR) alongside the Double Ratchet, so ongoing conversations, not only their start, gain quantum resistance. Apple's iMessage moved to a comparable post-quantum design, PQ3, in 2024.

### What E2EE does not protect

E2EE protects message content in transit and on the server. It does not hide **metadata** (who talks to whom, when, how often) unless the service takes extra steps, it does not protect messages on a compromised phone, and it depends on users verifying each other's keys (the "safety number") to rule out a server inserting itself as a man-in-the-middle. **Key transparency** systems, now deployed by several large messaging services, publish users' public keys in auditable logs so that such substitution would be detected automatically.

## 13.5 Group messaging: MLS

Signal's pairwise design becomes expensive for large groups: a message to 1,000 members means 1,000 encryptions. **Messaging Layer Security (MLS)**, standardised as RFC 9420 in 2023, solves this with a tree of keys (TreeKEM) so that adding, removing or updating a member costs work proportional to the logarithm of the group size. MLS keeps forward secrecy and post-compromise security for groups of up to tens of thousands of members, and is being adopted by enterprise messaging platforms and by the mobile industry's RCS standard.

## 13.6 Comparing the protocols

| Protocol | Who is trusted to vouch for keys | Algorithm agility | Forward secrecy | Post-quantum status (2026) |
| --- | --- | --- | --- | --- |
| TLS 1.3 | Certificate authorities | Negotiated | Yes | Hybrid key exchange deployed widely |
| SSH | TOFU, or an SSH CA | Negotiated | Yes | Hybrid ML-KEM default in OpenSSH 10 |
| IPsec / IKEv2 | Certificates or pre-shared keys | Negotiated | Yes, if configured | Standard defined (RFC 9370); rolling out |
| WireGuard | Pre-configured peer keys | None | Yes | Optional PSK as stop-gap |
| Signal | The service, verified by safety numbers or key transparency | Versioned | Yes, plus self-healing | PQXDH and post-quantum ratchet deployed |
| MLS | Credentials from an identity service | Cipher suites | Yes, plus self-healing | Post-quantum cipher suites in development |

## Lab: an SSH certificate authority

**1. Create a user CA and sign a short-lived certificate.**

```bash
ssh-keygen -t ed25519 -f user_ca -C "lab user CA" -N ""
ssh-keygen -t ed25519 -f alice -N ""
ssh-keygen -s user_ca -I alice@lab -n alice -V +8h alice.pub
ssh-keygen -L -f alice-cert.pub      # shows principals and the 8-hour validity
```

**2. Trust the CA on a test server** (a container or VM you control):

```
# /etc/ssh/sshd_config
TrustedUserCAKeys /etc/ssh/user_ca.pub
```

Restart `sshd`, then connect with `ssh -i alice alice@server`. No `authorized_keys` entry is needed. Wait for the certificate to expire, or issue one with `-V +1m`, and watch access end on its own.

**3. Check your post-quantum key exchange.**

```bash
ssh -v user@server 2>&1 | grep "kex: algorithm"
```

On OpenSSH 10 at both ends, you should see `mlkem768x25519-sha256`.

## Failure story: the SSH keys nobody owned

Beginning around 2013, the inventor of SSH, Tatu Ylönen, and other researchers published findings from key audits at large banks, governments and enterprises. The pattern was consistent: organisations held hundreds of thousands to millions of SSH keys, the large majority unused or of unknown purpose, and a significant share granting privileged access, including keys belonging to people who had long left. Nobody had ever designed this sprawl. It accumulated one convenient copy at a time.

Attackers exploit exactly this. Malware families and intrusion groups routinely harvest SSH private keys from compromised machines and use the `known_hosts` and `authorized_keys` files as maps to move laterally through networks. Unlike passwords, stolen SSH keys usually bypass multi-factor authentication and are rarely rotated.

The remedy is the one in the lab: replace scattered static keys with short-lived certificates issued after strong authentication, and treat any remaining static keys as inventoried, owned credentials with expiry dates, just like the certificates and secrets in Parts V and VI.

## Chapter summary

- SSH uses trust on first use and static keys by default, which scale badly. SSH certificates with short lifetimes fix both, and OpenSSH now uses hybrid post-quantum key exchange by default.
- IPsec is powerful and complex; configure IKEv2 with AEAD, strong groups and certificates. WireGuard trades agility for simplicity and verifiability.
- The Signal protocol combines an asynchronous start (now PQXDH) with the Double Ratchet for forward secrecy and post-compromise security, and has added a post-quantum ratchet.
- MLS brings these properties efficiently to large groups.
- End-to-end encryption does not hide metadata or protect compromised devices; key verification and key transparency close the man-in-the-middle gap.
