## 11.1 What a secure channel must provide

A **secure channel** gives two parties, usually a client and a server, three things over an untrusted network:

1. **Confidentiality:** nobody else can read the data.
2. **Integrity:** nobody can change, reorder, drop or replay records without detection.
3. **Authentication:** at least the server, and optionally the client, proves its identity.

TLS provides all three by combining the tools from Parts II and III: ephemeral (EC)DH for key agreement, signatures and certificates for authentication, HKDF for key derivation, and AEAD for protecting data.

TLS has two layers:

- The **handshake protocol** negotiates parameters, authenticates the server (and optionally the client), and establishes shared keys.
- The **record protocol** splits application data into records and protects each one with AEAD, using a sequence number as part of the nonce so that records cannot be reordered or replayed.

## 11.2 A short history of TLS

| Version | Year | Status |
| --- | --- | --- |
| SSL 2.0 and 3.0 | 1995 to 1996 | Broken (POODLE, DROWN); prohibited |
| TLS 1.0 and 1.1 | 1999, 2006 | Deprecated by RFC 8996 in 2021; removed from browsers in 2020 |
| TLS 1.2 | 2008 | Still widely supported; secure only with modern settings |
| TLS 1.3 | 2018 (RFC 8446) | The current standard; used by the large majority of web traffic |

TLS 1.3 was designed after two decades of attacks on earlier versions. Its designers removed everything that had caused trouble: RSA key transport (no forward secrecy, Bleichenbacher attacks), CBC mode and MAC-then-encrypt (padding oracles, Lucky Thirteen), static DH, compression (CRIME), renegotiation, weak hashes, and custom DH groups (Logjam). What remains is small enough to analyse formally, and TLS 1.3 was the first major protocol to be designed alongside machine-checked security proofs.

**ClientHello.** The client sends a random value, the TLS versions and cipher suites it supports, and, crucially, one or more **key shares**: ephemeral public keys for the key exchange groups it guesses the server will accept. It also sends extensions, including **Server Name Indication (SNI)** naming the website it wants, and **ALPN**, which names the application protocol (such as HTTP/2).

**ServerHello.** The server picks a cipher suite and one of the client's key shares, and replies with its own ephemeral key share. At this moment, both sides can compute the shared secret, and everything that follows is encrypted.

**EncryptedExtensions, Certificate, CertificateVerify.** The server sends its certificate chain, then a **CertificateVerify** message: a signature, using its certificate's private key, over a hash of every handshake message so far. This proves the server holds the private key and binds its identity to this exact key exchange, defeating man-in-the-middle attacks.

**Finished.** Each side sends a MAC over the whole transcript using a key derived from the handshake secret. This confirms that both sides saw identical messages, so an attacker cannot have silently removed or altered anything, such as downgrading the offered algorithms.

If the server does not support any of the groups the client guessed, it sends a **HelloRetryRequest** naming a group it does support, and the client tries again, costing an extra round trip.

### Cipher suites in TLS 1.3

TLS 1.3 cipher suites name only the AEAD and the hash; key exchange and signatures are negotiated separately. There are just five, and three are used in practice:

| Cipher suite | Use |
| --- | --- |
| TLS_AES_128_GCM_SHA256 | Mandatory; most common |
| TLS_AES_256_GCM_SHA384 | Where AES-256 is required |
| TLS_CHACHA20_POLY1305_SHA256 | Devices without AES hardware |

## 11.4 The key schedule

TLS 1.3 derives every key from the shared secret through a **key schedule** built entirely on HKDF (Chapter 6). It runs in three stages, each mixing in more secret material and the transcript hash so far:

1. **Early secret.** From a pre-shared key if resuming a session, otherwise from zeros.
2. **Handshake secret.** Mixes in the (EC)DH or KEM shared secret. Produces keys that encrypt the rest of the handshake.
3. **Master secret.** Produces the **application traffic keys**, separate for each direction.

Each key is derived with a distinct label ("c hs traffic", "s ap traffic", "exp master" and so on) and the transcript hash, so keys for different purposes and different connections are independent. Keys can also be **updated** during long connections with a KeyUpdate message, limiting how much data any single key protects.

> **In practice.** For debugging, most TLS libraries can write the derived secrets to a **key log file** (the `SSLKEYLOGFILE` environment variable in browsers and curl). Wireshark uses it to decrypt captured traffic. Never enable this on production systems: anyone with the file can read the traffic.

## 11.5 Resumption and 0-RTT

Full handshakes cost public-key operations and a round trip. TLS 1.3 lets clients **resume** a previous session:

- After a handshake, the server sends one or more **session tickets** containing a pre-shared key (PSK) for future connections.
- On reconnection, the client presents the ticket. The server can skip certificate verification, and the handshake can still include a fresh ECDH exchange to preserve forward secrecy (the recommended "psk_dhe_ke" mode).

### 0-RTT early data and replay

TLS 1.3 also allows a resuming client to send application data in its very first message, before the handshake completes. This **0-RTT** (zero round trip) data makes repeat visits faster, but it has a serious weakness: **it can be replayed.** An attacker who captures the client's first flight can send it to the server again, and the server may process the request twice.

The rule is simple: **only allow 0-RTT for requests that are safe to repeat**, such as fetching a public page. Never accept 0-RTT for payments, state changes or anything non-idempotent. Many servers disable 0-RTT entirely, and that is a sensible default.

## 11.6 Hiding the server name: Encrypted Client Hello

Even with TLS 1.3, one important piece of information remains visible to network observers: the **SNI**, which names the website the user is visiting. Network operators, censors and attackers can see it.

**Encrypted Client Hello (ECH)** fixes this. The server publishes an ECH public key in DNS (in an HTTPS resource record). The client encrypts its real ClientHello, including the SNI, using HPKE (Chapter 8), and wraps it inside an outer ClientHello that names only a shared front-end, such as a content delivery network. Observers see that you connected to the CDN, not which of its thousands of sites you visited.

> **Current development.** ECH was published as RFC 9849 in March 2026, after years of drafts. Major browsers have supported it since 2023 and 2024, and large CDNs enable it for hosted sites. It depends on encrypted DNS: if DNS lookups are visible, the site name leaks there instead.

## 11.7 Post-quantum key exchange in TLS

The ephemeral ECDH exchange in TLS is vulnerable to "harvest now, decrypt later": an attacker who records traffic today could decrypt it once a large quantum computer exists. TLS 1.3's design makes the fix straightforward, because the key exchange is just a named group carried in the key share.

The new group **X25519MLKEM768** combines classical X25519 with the post-quantum KEM ML-KEM-768 (Chapter 26). Both shared secrets are concatenated and fed into the key schedule, so the connection is secure as long as **either** algorithm holds. This **hybrid** design protects against quantum attackers while hedging against any undiscovered weakness in the newer algorithm.

> **Current development.** X25519MLKEM768 has been the default key exchange in Chrome and Edge since version 131 and in Firefox since version 132 (late 2024). Apple added it across iOS 26 and macOS in 2025. By early 2026, major CDNs reported that around two-thirds of human web traffic reaching them was protected by hybrid post-quantum key exchange. Server-side and internal adoption lag far behind, which is the migration challenge Chapter 27 addresses.

The hybrid key share is larger: about 1,216 bytes from the client instead of 32. This occasionally breaks old middleboxes that cannot handle a ClientHello spanning more than one network packet, a class of bug called **protocol ossification**.

## 11.8 Mutual TLS

By default only the server authenticates. In **mutual TLS (mTLS)**, the server also requests a certificate from the client, and the client proves possession of its private key with its own CertificateVerify message. mTLS is widely used between services inside organisations, in service meshes, for device authentication and for high-security API access. It requires a way to issue and rotate client certificates at scale, usually from a private CA (Chapter 18).

> **Watch out.** Public certificate authorities have been removing the client authentication purpose from public TLS certificates, following browser root program rules that public TLS hierarchies serve websites only. Systems that use public certificates as client certificates must move to private PKI. Check your CA's current timeline.

## Lab: watch a TLS 1.3 handshake

**1. Inspect a live handshake.**

```bash
openssl s_client -connect example.com:443 -servername example.com -tls1_3 </dev/null 2>/dev/null \
  | grep -E "Protocol|Cipher|Server Temp Key|Peer signature|Verification"
```

You will see the protocol version, the AEAD cipher suite, the key exchange group, and the signature algorithm.

**2. Request post-quantum key exchange.** OpenSSL 3.5 and later support ML-KEM:

```bash
openssl s_client -connect cloudflare.com:443 -groups X25519MLKEM768 </dev/null 2>/dev/null | grep -i "temp key\|group"
```

**3. Decrypt your own traffic.** Set a key log file, make a request, and open the capture in Wireshark:

```bash
export SSLKEYLOGFILE=$HOME/tlskeys.log
curl -s https://example.com > /dev/null
```

In Wireshark, set Preferences, Protocols, TLS, "(Pre)-Master-Secret log filename" to that file while capturing. The encrypted records become readable, and you can match every message in Figure 11.1. Delete the key log afterwards.

## Failure story: the downgrade that TLS 1.3 was built to stop

In 2016, researchers published **DROWN**. Many servers that supported only modern TLS for their websites still had **SSLv2**, a protocol from 1995, enabled on another service sharing the same RSA key, such as an old mail server configuration. SSLv2's weaknesses let an attacker use that server as a Bleichenbacher oracle (Chapter 7) to decrypt recorded *modern TLS* connections that used RSA key exchange with the same key. At disclosure, about a third of HTTPS servers were vulnerable, including many large sites.

DROWN combined three things TLS 1.3 removed by design: RSA key transport (no forward secrecy and an oracle target), the reuse of one key across protocols, and support for ancient protocol versions. TLS 1.3 also signs the full transcript and includes special values in the server random that let clients detect downgrade attempts. Its lesson for operators remains: disable old protocols everywhere a key is used, not only on the main website, and never share keys across services.

## Chapter summary

- TLS provides confidentiality, integrity and authentication through a handshake protocol and an AEAD record protocol.
- TLS 1.3 completes a full handshake in one round trip, encrypts everything after the ServerHello, signs the whole transcript, and removes the legacy features behind two decades of attacks.
- An HKDF key schedule derives independent, labelled keys at each stage.
- Session resumption speeds reconnection; 0-RTT data can be replayed and must be limited to safe requests.
- ECH hides the destination site; hybrid X25519MLKEM768 key exchange protects against harvest-now-decrypt-later and is already the browser default.
