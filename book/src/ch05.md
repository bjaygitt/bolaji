## 5.1 Why modes exist

Chapter 4 ended with the encrypted penguin: encrypting each block independently (**ECB mode**) leaks every repetition in the data. A **mode of operation** is a recipe for using a block cipher on data of any length so that patterns disappear. Every mode does this by mixing in something that changes: a previous ciphertext block, a counter, or a random starting value.

That changing input has two names you must know:

- **Initialisation vector (IV):** a starting value for the mode. Some modes need it to be unpredictable.
- **Nonce:** short for "number used once". A value that must never repeat under the same key. It does not have to be secret or random, only unique.

Getting the IV or nonce wrong is the single most common way modes fail in practice.

## 5.2 CBC: chaining blocks together

**Cipher Block Chaining (CBC)** mode XORs each plaintext block with the previous ciphertext block before encrypting it. The first block is XOR-ed with the IV.

```
C1 = Encrypt(K, P1 XOR IV)
C2 = Encrypt(K, P2 XOR C1)
C3 = Encrypt(K, P3 XOR C2) ...
```

Because each ciphertext block depends on all previous blocks, identical plaintext blocks now produce different ciphertext. CBC was the default for TLS and disk encryption for many years.

CBC has two requirements and three weaknesses:

- The IV must be **unpredictable** for each message. Predictable IVs enabled the BEAST attack on TLS 1.0 in 2011.
- The plaintext must be **padded** to a multiple of 16 bytes, usually with PKCS#7 padding, where the last bytes all equal the number of padding bytes added.
- Encryption cannot run in parallel, because each block needs the previous one.
- **CBC provides no integrity.** Flipping a bit in ciphertext block C1 scrambles P1 but flips the same bit in P2. An attacker can make controlled changes without the key.
- Its padding becomes an attack surface, as the next section shows.

### The padding oracle attack

Imagine a server that decrypts CBC data and responds differently when the padding is wrong ("padding error") versus when the content is wrong ("invalid request"). That small difference is an **oracle**: a yes-or-no answer about a secret. In 2002, Serge Vaudenay showed that an attacker can use it to decrypt any ciphertext, one byte at a time, by submitting about 128 carefully altered versions per byte and watching which ones produce a valid padding response. No key is ever recovered; the server decrypts the data for the attacker.

Padding oracles appeared in web frameworks, in TLS (the Lucky Thirteen attack in 2013 used timing differences instead of error messages, and POODLE in 2014 broke SSL 3.0), and in countless custom applications. The deeper lesson: **any encryption that can be modified without detection will eventually leak through the way systems react to the modified data.** The fix is not better error messages. It is integrity protection.

## 5.3 CTR: turning a block cipher into a stream cipher

**Counter (CTR)** mode encrypts a sequence of counter values and XORs the results with the plaintext:

```
keystream block i = Encrypt(K, nonce || counter_i)
Ci = Pi XOR keystream block i
```

CTR has attractive properties. It needs no padding, it runs in parallel, and encryption and decryption are the same operation. Its one rule is absolute:

> **Never reuse a nonce with the same key.** If two messages are encrypted with the same key and nonce, they share the same keystream. XOR-ing the two ciphertexts cancels the keystream and gives the XOR of the two plaintexts, which is usually enough to recover both.

Like CBC, CTR alone provides no integrity, and it is even easier to tamper with: flipping a ciphertext bit flips exactly the same plaintext bit. An attacker who knows a message says "pay 100" can change it to "pay 900" without knowing the key.

## 5.4 Authenticated encryption: confidentiality plus integrity

The solution to tampering is to attach an integrity check that only key holders can create. For years, developers did this by hand: encrypt with one key, then compute a MAC (Chapter 6) over the ciphertext with another key. The order matters. **Encrypt-then-MAC** is safe: the receiver checks the MAC first and rejects any altered ciphertext before decrypting anything. The other orderings, used by older TLS and SSH versions, led to attacks.

Hand-assembled constructions proved fragile, so cryptographers created **authenticated encryption with associated data (AEAD)**: single algorithms that encrypt and authenticate together, with a simple interface:

```
ciphertext, tag = AEAD_Encrypt(key, nonce, plaintext, associated_data)
plaintext       = AEAD_Decrypt(key, nonce, ciphertext, tag, associated_data)
                  # fails completely if anything was altered
```

**Associated data (AD)** is information that must be protected against tampering but does not need to be secret, such as a packet header, a database record ID, or a version number. It is authenticated but not encrypted. Binding context this way prevents an attacker from moving a valid ciphertext into a different context, for example swapping the encrypted salary fields of two employees' records.

The decryption rule is strict: if the tag does not verify, the function returns an error and **no plaintext at all**. Never use or display partially decrypted data from a failed check.

## 5.5 AES-GCM

**Galois/Counter Mode (GCM)** combines CTR-mode encryption with a fast authenticator called GHASH, computed with multiplication in the finite field GF(2^128). It is the most widely used AEAD in the world: the default for TLS 1.3, IPsec, and most cloud storage encryption.

Its properties:

- Fast, especially with hardware support for AES and carry-less multiplication.
- A 96-bit nonce, which must be unique per key.
- A 128-bit tag.

GCM's weakness is how badly it fails when a nonce repeats. Reusing a nonce not only exposes the XOR of the two plaintexts, as with CTR. It also leaks enough about the internal authentication key that an attacker can forge valid tags for any message from then on. One nonce repeat turns GCM into unauthenticated encryption under attacker control.

### Managing GCM nonces

You have two safe options:

1. **Counters.** Use a message counter as the nonce, with one counter per key, stored reliably. Ideal when one process owns the key.
2. **Random nonces.** Generate 96 random bits per message. Because of the birthday bound (Chapter 3), NIST limits random-nonce GCM to 2^32 messages per key, which keeps the collision chance below about one in four billion.

If many machines encrypt with the same key, counters are hard to coordinate and random nonces hit the limit faster. The usual fix is to give each machine or each data object its own key, derived from a master key (Chapter 6), so no single key is ever used too much.

> **Watch out.** Nonce reuse is not a theoretical concern. It happens when systems restore a counter from an old backup, when virtual machines are cloned with the same state, and when developers hard-code a nonce "for testing" and forget it. A 2016 internet-wide study found 184 HTTPS servers repeating GCM nonces, exposing them to forgery.

## 5.6 ChaCha20-Poly1305

**ChaCha20-Poly1305** pairs the ChaCha20 stream cipher with the Poly1305 authenticator. It is standardised in RFC 8439, mandatory to support in TLS 1.3, and used by WireGuard, SSH and many messaging apps.

| Property | AES-256-GCM | ChaCha20-Poly1305 |
| --- | --- | --- |
| Speed with AES hardware | Fastest | Fast |
| Speed without AES hardware | Slow, and hard to make constant-time | Fast and naturally constant-time |
| Nonce | 96 bits | 96 bits (XChaCha20 variant: 192 bits) |
| Nonce reuse consequence | Catastrophic | Catastrophic |
| Standards and compliance | FIPS-approved | Not FIPS-approved |

Choose AES-GCM where FIPS validation is required or AES hardware is available. Choose ChaCha20-Poly1305 for software implementations on varied hardware. The extended-nonce variant **XChaCha20-Poly1305** uses a 192-bit nonce, large enough that random nonces never realistically collide, which makes it a forgiving choice for applications.

## 5.7 Misuse-resistant encryption

Because nonce reuse is so damaging, cryptographers designed **nonce-misuse-resistant** AEADs. The best known is **AES-GCM-SIV** (RFC 8452). It computes the authentication tag first and uses it as the effective IV. If a nonce is accidentally repeated, the only thing leaked is whether two messages were identical, which is a dramatic improvement over GCM's total failure. The cost is that encryption must make two passes over the data.

**AES Key Wrap** (RFC 3394 and the padded variant RFC 5649) and **AES-SIV** (RFC 5297) are related deterministic constructions used to encrypt keys with other keys, where there is no natural nonce. You will see Key Wrap constantly in key management systems and HSMs (Part VI).

## 5.8 Disk encryption is a special case

Encrypting a disk sector has an unusual constraint: the ciphertext must be exactly the same size as the plaintext, so there is no room for a nonce or a tag. Disk encryption therefore uses **XTS mode**, which ties each block's encryption to its sector number. XTS hides content but does not detect tampering, which is acceptable for protecting a stolen laptop, the threat disk encryption is designed for, but not for data sent over a network.

## 5.9 Choosing a mode: the decision table

| Situation | Use | Avoid |
| --- | --- | --- |
| General data encryption in an application | AES-256-GCM, or XChaCha20-Poly1305 via a high-level library | Hand-built CBC plus HMAC |
| Very high message volume per key, or risk of nonce reuse | AES-GCM-SIV, or derive per-message keys | Random-nonce GCM beyond 2^32 messages |
| Encrypting keys with other keys | AES Key Wrap or AES-SIV | GCM with fixed nonces |
| Full-disk or volume encryption | AES-XTS | GCM, CBC |
| Legacy interoperability | CBC with Encrypt-then-MAC, only if forced | ECB, CBC without a MAC |

## Lab: break CTR mode with a reused nonce

This Python lab uses the widely available `cryptography` package (`pip install cryptography`).

```python
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
import os
key, nonce = os.urandom(32), os.urandom(16)
def ctr(msg):
    e = Cipher(algorithms.AES(key), modes.CTR(nonce)).encryptor()
    return e.update(msg) + e.finalize()
p1 = b"Transfer 100 USD to account 1234"
p2 = b"Meeting moved to Thursday at 3pm"
c1, c2 = ctr(p1), ctr(p2)            # same key, same nonce: the mistake
x = bytes(a ^ b for a, b in zip(c1, c2))
print(bytes(a ^ b for a, b in zip(x, p1)))   # recovers p2 from p1 alone
```

The attacker never touched the key. Knowing (or guessing) one plaintext reveals the other.

**Now tamper with an unauthenticated message:**

```python
c = bytearray(ctr(p1))
c[9] ^= ord("1") ^ ord("9")          # flip the bits that turn "1" into "9"
d = Cipher(algorithms.AES(key), modes.CTR(nonce)).decryptor()
print(d.update(bytes(c)))             # "Transfer 900 USD ..."
```

**Finally, see AEAD refuse the same trick:**

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
g, n = AESGCM(key), os.urandom(12)
c = bytearray(g.encrypt(n, p1, b"record-42"))
c[9] ^= ord("1") ^ ord("9")
g.decrypt(n, bytes(c), b"record-42")  # raises InvalidTag: tampering detected
```

## Failure story: Zerologon and the all-zero IV

In August 2020, Microsoft patched a vulnerability in the Netlogon protocol that Windows domain controllers use to authenticate machines. Researchers named it **Zerologon**, and it allowed an attacker on the internal network to take over a domain controller, and so the entire Windows domain, in seconds.

The root cause was a mode of operation. Netlogon computed a login credential using AES in a mode called CFB8 with a **fixed IV of all zeros**. With an all-zero IV, there is a 1-in-256 chance, for any key, that encrypting an all-zero input produces an all-zero output. An attacker could simply send an all-zero credential repeatedly; on average, after 256 attempts, it would be accepted as valid. From there, the attacker could reset the domain controller's own machine password.

AES was never weakened. The designers broke the one rule of the mode: the IV must be unpredictable. The flaw went unnoticed for years in one of the most widely deployed authentication systems in the world. It was rated at the maximum severity score and actively exploited by ransomware groups after disclosure.

## Chapter summary

- Modes turn a block cipher into practical encryption by mixing in changing values. IVs and nonces carry most of the risk.
- CBC needs unpredictable IVs and padding; CTR needs unique nonces. Neither provides integrity.
- Unauthenticated encryption leaks through tampering and through how systems react, as padding oracle attacks show.
- AEAD algorithms combine encryption and integrity. AES-GCM and ChaCha20-Poly1305 are the standard choices; associated data binds ciphertext to its context.
- GCM fails catastrophically on nonce reuse. Manage nonces deliberately, cap messages per key, or use misuse-resistant modes such as AES-GCM-SIV.
