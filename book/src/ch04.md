## 4.1 What a block cipher does

A **block cipher** takes a fixed-size block of data and a key, and produces a scrambled block of the same size. With the same key, the scrambling can be reversed. AES uses 128-bit blocks, so it turns 16 bytes of plaintext into 16 bytes of ciphertext.

```
ciphertext_block = AES_encrypt(key, plaintext_block)
plaintext_block  = AES_decrypt(key, ciphertext_block)
```

Think of a block cipher as a giant codebook. For every possible key, there is a different codebook that maps each of the 2^128 possible input blocks to a unique output block. Nobody could ever write such a codebook down, but the cipher computes any entry on demand.

A good block cipher should be indistinguishable from a **random permutation**: a random shuffling of all possible blocks. An attacker who does not know the key, and who can ask for the encryption of any blocks they like, should not be able to tell whether they are talking to AES or to a truly random shuffle. Cryptographers call this being a **pseudo-random permutation (PRP)**, and it is the formal security goal for block ciphers.

### A block cipher alone is not encryption

This is the first important lesson of the chapter. A block cipher only handles one 16-byte block. Real messages are longer, and encrypting each block independently with the same key leaks patterns: identical plaintext blocks produce identical ciphertext blocks. To encrypt real data, you combine the block cipher with a **mode of operation** (Chapter 5). The cipher is an engine; the mode is the vehicle built around it.

## 4.2 A short history: from DES to AES

The **Data Encryption Standard (DES)** was published in 1977 and protected banking and government data for two decades. It used a 56-bit key, which was small even then. By 1998, a purpose-built machine costing about 250,000 US dollars found a DES key in days. A stop-gap called **Triple DES (3DES)** applied DES three times, but it was slow and still had a 64-bit block, which became a problem of its own.

The 64-bit block matters because of the birthday bound from Chapter 3. After about 2^32 blocks, which is only 32 gigabytes, repeats become likely and leak information. In 2016, the **Sweet32** attack recovered secret cookies from long-lived HTTPS connections using 3DES this way. NIST has since disallowed 3DES for encryption after 2023.

In 1997, NIST launched an open, international competition for a replacement. Fifteen designs were submitted and attacked publicly for three years. In 2000, NIST selected **Rijndael**, designed by two Belgian cryptographers, Joan Daemen and Vincent Rijmen. It was published in 2001 as the **Advanced Encryption Standard (AES)**, FIPS 197. The open competition model worked so well that NIST used it again for SHA-3 and for post-quantum cryptography.

## 4.3 Inside AES

You will never implement AES yourself, but knowing its structure helps you understand its strength, its key sizes and its attacks.

AES treats a 16-byte block as a 4 by 4 grid of bytes, called the **state**. It transforms the state through a series of **rounds**: 10 rounds for a 128-bit key, 12 for 192-bit, and 14 for 256-bit. Each round applies four steps:

| Step | What it does | Why it is there |
| --- | --- | --- |
| **SubBytes** | Replaces each byte with another using a fixed lookup table (the S-box) | Adds non-linearity, so the cipher cannot be described by simple equations |
| **ShiftRows** | Shifts each row of the grid left by 0, 1, 2 or 3 positions | Spreads bytes across columns |
| **MixColumns** | Mixes the four bytes of each column together using arithmetic in GF(2^8) | Spreads each byte's influence across the whole column |
| **AddRoundKey** | XORs the state with a round key derived from the main key | Brings in the secret; without it, anyone could reverse the steps |

After two rounds, every output bit depends on every input bit. This property is called **diffusion**, and the non-linear S-box gives **confusion**, a term introduced by Claude Shannon in 1949 to describe hiding the relationship between key and ciphertext. Ten or more rounds give a large safety margin: the best known attacks on full AES are barely better than trying every key.

The **key schedule** expands the main key into one round key per round. It is the part of AES most often criticised by researchers, because related-key attacks exploit it for AES-256 in artificial settings where an attacker can get data encrypted under several keys with a known relationship. Real systems never create related keys if they use proper key derivation (Chapter 6), so these attacks have no practical impact.

## 4.4 AES-128 or AES-256?

AES comes in three key sizes. Only two are common in practice.

| Variant | Rounds | Classical security | Security against quantum search | Typical use |
| --- | --- | --- | --- | --- |
| AES-128 | 10 | 128 bits | About 64 bits in theory, much more in practice | General-purpose encryption, TLS |
| AES-192 | 12 | 192 bits | About 96 bits | Rarely used |
| AES-256 | 14 | 256 bits | About 128 bits | Long-lived data, government profiles, key wrapping |

Grover's algorithm (Chapter 25) lets a quantum computer search keys in roughly the square root of the usual time, which halves the effective key length on paper. In practice, Grover's algorithm parallelises badly and needs extraordinarily long, error-free quantum computations, so AES-128 is not considered at real risk. Still, the guidance has settled on a simple rule:

- Use **AES-256** for data that must stay confidential for decades, for keys that protect other keys, and wherever a regulation asks for it. The US NSA's CNSA 2.0 suite, for example, requires AES-256.
- **AES-128** remains perfectly sound for short-lived data such as most TLS sessions, and it is about 40 percent faster.

When in doubt, choose AES-256. The performance difference rarely matters on modern hardware.

## 4.5 Implementing AES safely: side channels

The mathematics of AES has held up for 25 years. Implementations have not always been so lucky. A **side-channel attack** learns secrets not from the inputs and outputs, but from how the computation behaves: how long it takes, how much power it draws, what it leaves in the processor's cache, or the electromagnetic signals it emits.

The classic AES side channel is the **cache-timing attack**. Fast software AES uses lookup tables. The table entry read depends on the data and the key, and whether that entry happens to be in the processor's cache changes the timing by a few nanoseconds. In 2005, researchers recovered full AES keys from a server over the network by measuring these timing differences across many requests.

There are two defences:

1. **Hardware AES instructions.** Almost every modern processor includes dedicated AES instructions (AES-NI on x86, the cryptography extensions on ARM). They run AES in constant time with no tables, and they are many times faster than software. Mature libraries use them automatically.
2. **Bit-sliced, constant-time software** for processors without hardware support.

Physical side channels, such as power analysis on smart cards and hardware security modules, need hardware countermeasures as well. This is one of the things certification schemes like FIPS 140-3 test for (Chapter 23).

> **In practice.** You will almost never choose an AES implementation directly. You choose a library. Check that it is current, widely used, and built with hardware acceleration enabled. On most servers, `openssl speed -evp aes-256-gcm` reports several gigabytes per second, which tells you the hardware path is active.

## 4.6 Other block and stream ciphers you will meet

AES dominates, but you will see others:

| Cipher | Type | Status | Where you see it |
| --- | --- | --- | --- |
| ChaCha20 | Stream cipher | Recommended | TLS 1.3, WireGuard, SSH, mobile devices without AES hardware (Chapter 5) |
| 3DES | Block cipher (64-bit block) | Disallowed for new encryption | Legacy payment systems |
| Blowfish | Block cipher (64-bit block) | Legacy | Old software, the bcrypt password hash |
| Camellia, ARIA, SM4 | Block ciphers | National standards (Japan, Korea, China) | Regional compliance requirements |
| RC4 | Stream cipher | Broken, prohibited in TLS | Very old systems only |

A **stream cipher** produces a long stream of pseudo-random bits from a key and a nonce, and encrypts by XOR-ing that stream with the data. ChaCha20 is the modern standard, designed by Daniel Bernstein, and it is fast and constant-time even in plain software, which is why phones without AES hardware historically preferred it.

## Lab: AES at the command line

You need OpenSSL 3, which is installed on most Linux and macOS systems.

**1. See the speed of hardware AES.**

```bash
openssl speed -evp aes-128-gcm aes-256-gcm chacha20-poly1305
```

Compare the throughput columns. On most modern laptops, both AES variants run at multiple gigabytes per second.

**2. See why a raw block cipher leaks patterns.** Create a file with repeated 16-byte blocks and encrypt it block by block (ECB mode, which you should never use for real data):

```bash
python3 -c "print('YELLOW SUBMARINE'*8, end='')" > blocks.txt
openssl enc -aes-128-ecb -K 000102030405060708090a0b0c0d0e0f -in blocks.txt | xxd
```

Every 16-byte line of output is identical, revealing that the input repeats. That is exactly the leak modes of operation exist to prevent.

**3. Now use a proper mode.** Encrypt the same file with CTR mode and a random IV:

```bash
openssl enc -aes-128-ctr -K 000102030405060708090a0b0c0d0e0f \
  -iv $(openssl rand -hex 16) -in blocks.txt | xxd
```

The output no longer repeats. Chapter 5 explains why, and why even this is not enough without integrity protection.

## Failure story: the encrypted penguin

The most famous image in cryptography education is a bitmap of the Linux mascot, Tux the penguin, encrypted with AES in ECB mode. The encrypted file is meaningless noise at the byte level, yet when displayed as an image, the penguin's outline is clearly visible, because every identical block of background colour encrypts to the same ciphertext block.

The penguin is a classroom example, but the same mistake has appeared in real products. In 2013, a breach at a large software company exposed about 150 million user records in which passwords had been encrypted with 3DES in ECB mode instead of being hashed. Because identical passwords produced identical ciphertext, and users' password hints were stored in plain text next to them, attackers could group users who shared a password and guess it from the combined hints, without ever recovering the key.

Two lessons follow. A strong block cipher used in the wrong mode leaks patterns. And passwords should never be encrypted at all: they should be hashed with a dedicated password hashing function (Chapter 6).

## Chapter summary

- A block cipher transforms fixed-size blocks under a key and should behave like a random permutation. On its own, it is not a complete encryption scheme.
- DES fell to brute force and 3DES to the birthday bound on its small block. AES was chosen through an open competition and has resisted attack for 25 years.
- AES rounds combine substitution, shifting, mixing and key addition to achieve confusion and diffusion.
- Prefer AES-256 for long-lived data and key protection; AES-128 remains sound for short-lived data.
- Side channels, not mathematics, are AES's practical weakness. Hardware AES instructions remove the classic timing attacks.
