## 1.1 What cryptography is for

Every system that handles information has to answer a few basic questions. Who can read this? Has anyone changed it? Who sent it? Can the sender later deny sending it? Cryptography gives mathematical answers to these questions, so that the answers hold even when the information travels over networks you do not control and sits on disks you cannot watch.

The answers are grouped into four **security goals**. Learn these four words now, because every tool in this book serves one or more of them.

| Goal | The question it answers | Everyday example | Main tools |
| --- | --- | --- | --- |
| **Confidentiality** | Can only the intended people read it? | Nobody on the café Wi-Fi can read your banking session | Encryption (AES, ChaCha20) |
| **Integrity** | Has it been changed, accidentally or on purpose? | A downloaded file is exactly what the publisher released | Hash functions, MACs |
| **Authentication** | Is it really from who it claims to be from? | Your browser knows it is talking to your bank, not an impostor | MACs, digital signatures, certificates |
| **Non-repudiation** | Can the sender later deny it? | A signed contract or a signed software release | Digital signatures |

Two points about this table trip people up.

First, **confidentiality does not give you integrity.** Encryption hides content, but on its own it does not stop an attacker from changing the encrypted bytes. With some older encryption methods, an attacker who flips a bit in the encrypted data flips the same bit in the decrypted result, without ever knowing the key. Modern designs combine encryption with integrity protection for exactly this reason (Chapter 5).

Second, **authentication is about the origin of data, not about people logging in.** When cryptographers say "authenticated", they mean "we can prove this came from the holder of a particular key". Whether that key belongs to the right person is a separate problem, solved by certificates and identity systems (Parts IV and V).

## 1.2 Keys are the whole game

Almost every cryptographic tool works the same way: a public, well-known **algorithm** plus a secret **key**. The algorithm is like the design of a lock, which anyone can study. The key is like the physical key, which only the owner holds.

This leads to the single most important principle in the field, stated by the Dutch cryptographer Auguste Kerckhoffs in 1883:

> **Kerckhoffs's principle.** A system should remain secure even if everything about it, except the key, is public knowledge.

The principle sounds obvious, yet people break it constantly. They invent a private encryption scheme and assume it is safe because nobody knows how it works. History shows that secret designs get reverse-engineered, leaked or guessed, and then every copy of the system is broken at once, with no way to fix it except replacing the design everywhere. A public algorithm that has survived years of attack by the world's experts is far safer, and if a key leaks, you replace one key instead of a whole design.

The consequence for your work is simple and permanent: **protecting keys is the job.** The mathematics of a well-chosen algorithm is rarely what fails. Keys are generated badly, stored carelessly, copied too widely, never rotated, or stolen. Most of this book after Part III is about keys: how to create them, where to keep them, who may use them, how to replace them, and how to prove all of that to an auditor.

## 1.3 Symmetric and asymmetric: two families

Cryptographic tools come in two families, and you need to know which family a tool belongs to.

**Symmetric cryptography** uses one shared secret key. The same key encrypts and decrypts, or creates and checks an integrity tag. It is fast, which makes it the workhorse for encrypting data in bulk: every web page, every file on an encrypted disk, every database backup. Its weakness is distribution: both sides need the same secret, and getting it to them safely is a problem.

**Asymmetric cryptography**, also called **public-key cryptography**, uses a pair of linked keys. The **public key** can be shared with anyone. The **private key** is kept secret by one owner. What one key does, only the other can undo or check. It solves the distribution problem: you can publish your public key on a website, and anyone can use it to send you something only you can read, or to check something only you could have signed. Its weakness is speed: it is hundreds to thousands of times slower than symmetric cryptography.

Real systems use both, each for what it is good at. This pattern, called **hybrid encryption**, appears everywhere:

1. Use asymmetric cryptography to agree on, or deliver, a fresh symmetric key.
2. Use that symmetric key to protect the actual data.

A TLS connection to a website does exactly this. A few milliseconds of public-key work at the start produce a shared session key, and everything after that is fast symmetric encryption.

## 1.4 Threat models: secure against whom?

"Is this secure?" has no answer on its own. The useful question is "secure against whom, doing what, for how long?" Writing that down is called a **threat model**. A short threat model has four parts:

1. **Assets.** What are you protecting? Customer records, a signing key, a payment flow.
2. **Adversaries.** Who might attack it, and what can they do? A curious employee, a criminal group, a nation-state with a large budget.
3. **Capabilities.** What can the attacker see or touch? Network traffic only? A stolen laptop? A copy of your backups? Physical access to a server?
4. **Time.** How long must the protection last? A one-time login code needs seconds. Medical records need decades.

The last point matters more every year. An attacker can record encrypted traffic today and keep it until a future technology, such as a large quantum computer, can break the encryption. This is called **harvest now, decrypt later**. For data that must stay secret for 10 or more years, the threat model already includes quantum attackers (Part VII).

Cryptographers also describe attackers by what they can do to the cryptography itself. You will meet these terms in later chapters:

| Attack model | What the attacker can do | Why it matters |
| --- | --- | --- |
| Ciphertext-only | Sees encrypted messages | The weakest attacker; any modern cipher must resist far more |
| Known-plaintext | Sees some messages and their encryptions | Common in reality: file headers and protocol messages are predictable |
| Chosen-plaintext | Can get messages of their choice encrypted | Realistic on the web, where attackers can trigger requests |
| Chosen-ciphertext | Can submit altered ciphertexts and learn something from the reaction | Behind many real breaks, such as padding oracle attacks (Chapter 5) |

Modern algorithms are designed to resist the strongest of these attackers. When a real system is broken, it is usually because the surrounding software leaks extra information, turning a strong algorithm into a weak system.

## 1.5 How strong is strong enough? Security levels

Cryptographic strength is measured in **bits of security**. An algorithm with 128-bit security needs roughly 2^128 operations to break by the best known attack. That number is so large that if every computer on Earth worked on it until the Sun burned out, it would still not be finished.

Different algorithms reach the same security level with very different key sizes, which confuses many newcomers:

| Security level | Symmetric key | Hash output | RSA key | Elliptic curve key |
| --- | --- | --- | --- | --- |
| 112 bits (minimum today) | 112 | 224 | 2048 | 224 |
| 128 bits (standard) | 128 | 256 | 3072 | 256 |
| 192 bits | 192 | 384 | 7680 | 384 |
| 256 bits | 256 | 512 | 15360 | 512 |

The values follow NIST guidance (SP 800-57). The practical lesson is that a 256-bit elliptic curve key is about as strong as a 3072-bit RSA key, and a 128-bit AES key is stronger than a 2048-bit RSA key. Comparing raw key lengths across algorithm families is meaningless.

> **Current development.** NIST's draft transition plan (IR 8547, published for comment in November 2024) proposes deprecating RSA and elliptic-curve algorithms at the 112-bit level after 2030 and disallowing them entirely after 2035, because quantum computers would break them regardless of key size. Symmetric algorithms survive with larger keys. Part VII explains why.

## 1.6 What cryptography cannot do

Cryptography is powerful but narrow. Knowing its limits will save you from expensive mistakes.

- **It cannot protect data while it is being used.** Data must be decrypted to be processed. If an attacker controls the server that decrypts it, encryption does not help. (Confidential computing, Chapter 23, narrows this gap.)
- **It cannot fix bad key handling.** A key stored next to the data it protects, or printed in a log file, gives no protection.
- **It cannot tell you who someone really is.** It proves that a message came from a key holder. Linking that key to a real person or server is the job of certificates and identity processes.
- **It cannot stop authorised people from misusing access.** An administrator who can decrypt a database can copy it.
- **It cannot survive broken randomness.** Keys made from predictable random numbers are guessable, however strong the algorithm (Chapter 3).

A useful habit: when someone says "it's encrypted, so it's safe", ask three questions. Encrypted with what? Where is the key? Who can use the key?

## 1.7 The golden rules of applied cryptography

Experienced practitioners follow a short list of rules. You will see each one justified in later chapters.

1. **Do not invent your own algorithms or protocols.** Use well-studied standards.
2. **Do not implement primitives yourself in production.** Use mature libraries such as OpenSSL, BoringSSL, libsodium, or your platform's built-in cryptography. Tiny implementation details, such as how long a comparison takes, can leak keys.
3. **Prefer high-level, hard-to-misuse interfaces.** A function called `encrypt(key, message)` that handles nonces and integrity for you is safer than assembling AES, a mode and a MAC by hand.
4. **Always authenticate what you encrypt.** Use authenticated encryption (Chapter 5).
5. **Treat keys as the most valuable asset.** Generate them with good randomness, store them in protected places, give them owners and lifetimes, and plan their replacement from day one.
6. **Design for change.** Algorithms age. Build systems that can switch algorithms and keys without a rewrite. This property, **crypto agility**, is now a regulatory expectation because of the post-quantum transition.

> **In practice**
>
> - When you review a design, write its threat model in five lines before discussing algorithms.
> - Ask where every key lives, who can use it, and how it would be replaced.
> - Be suspicious of anything described as "proprietary encryption" or "military-grade" without naming a standard.

## Failure story: the debugging change that broke a million keys

In 2006, a maintainer of the Debian Linux distribution removed two lines from OpenSSL's random number generator. A code analysis tool had warned that the lines used uninitialised memory, and removing them made the warning go away. Unfortunately, those lines were how the generator collected most of its unpredictability. After the change, the only varying input was the process ID, a number usually below 32,768.

For almost two years, every SSH key, TLS key and other key generated on Debian and Ubuntu systems came from a pool of only about 32,000 possibilities per key type and size. An attacker could simply generate all of them and try each one. When the flaw was found in May 2008, administrators worldwide had to replace keys, revoke certificates and re-issue credentials.

The algorithms were never weak. RSA and DSA were fine. The failure was in the surrounding engineering: a well-meant change to code the maintainer did not fully understand, in the most sensitive part of the system, without review by someone who did. Three of this chapter's rules apply directly: do not modify cryptographic code casually, randomness is a single point of failure, and plan for the day every key must be replaced.

## Chapter summary

- Cryptography provides four goals: confidentiality, integrity, authentication and non-repudiation. Encryption alone provides only the first.
- Security rests on keys, not secret designs (Kerckhoffs's principle). Protecting and managing keys is the real work.
- Symmetric cryptography is fast but needs a shared secret; asymmetric cryptography solves distribution but is slow. Hybrid designs use both.
- A threat model names assets, adversaries, capabilities and time. Long-lived secrets must already consider quantum attackers.
- Strength is measured in bits of security, and key sizes are not comparable across algorithm families.
- Cryptography cannot fix bad key handling, bad randomness or compromised endpoints.
