## 7.1 Why these tools matter

Most cryptographic operations in a large organisation do not encrypt anything. They check. A build server checks that a package is unaltered, an API gateway that a request came from a partner, a payment switch that nobody changed the amount, and a directory that your password matches, without storing that password.

All of these checks rest on three related tools:

- **Hash functions** produce a short fingerprint of any data, with no key.
- **Message authentication codes (MACs)** produce a fingerprint that only holders of a shared secret key can create or check.
- **Key derivation functions (KDFs)** turn one secret into one or more keys, either quickly (for strong secrets) or deliberately slowly (for passwords).

These tools fail quietly. A weak hash, a naive request-signing scheme or a fast password hash produces no error message; it works perfectly until an attacker arrives.

## 7.2 What a hash function is

A **cryptographic hash function** takes input of any length and produces a fixed-length output, called a **digest** or **hash**. SHA-256, for example, always produces 256 bits (32 bytes), whether you hash one letter or a 10-gigabyte backup image.

```text
SHA-256("hello")  = 2cf24dba5fb0a30e26e83b2ac5b9e29e
                    1b161e5c1fa7425e73043362938b9824
SHA-256("hello.") = 1589999b0ca6ef8814283026a9f166d5
                    1c70a910671c3d44049755f07f2eb910
```

A one-character change to the input changes about half of the output bits, unpredictably. This is called the **avalanche effect**. There is no key: anyone can compute a hash. Hashes detect change but cannot prove who created the data: an attacker who can replace a file can replace its published hash too, unless the hash is signed (Chapter 10).

## 7.3 The three security properties

A cryptographic hash must resist three kinds of attack. Learn them in order of difficulty for the attacker:

| Property | The attacker's task | Generic cost for an n-bit hash | Why it matters |
| --- | --- | --- | --- |
| **Preimage resistance** | Given a hash, find any input that produces it | 2^n | Hashes of secrets must not reveal the secret |
| **Second-preimage resistance** | Given an input, find a different input with the same hash | 2^n | Nobody can swap a signed file for a malicious one with the same hash |
| **Collision resistance** | Find any two inputs with the same hash | 2^(n/2), by the birthday bound | Signatures and certificates sign hashes; a collision lets one signature cover two documents |

The **birthday bound** explains the last column. In a room of 23 people there is a better than even chance that two share a birthday, because you are comparing every pair, not looking for one specific date. In the same way, an attacker who generates about 2^128 random inputs to SHA-256 expects to find two with the same 256-bit output. So SHA-256 gives 128 bits of collision security, not 256.

Collision resistance is the hardest property to keep, because the attacker chooses both inputs. It is also the first property to fall when a hash function weakens.

## 7.4 The fall of MD5 and SHA-1

**MD5** (1992) and **SHA-1** (1995) were the standard hashes for two decades. Their histories show how cryptographic deprecation really works.

- **2004:** researchers found practical MD5 collisions.
- **2008:** a team used MD5 collisions to create a rogue certificate authority certificate that browsers trusted (section 7.11).
- **2012:** the Flame malware used an MD5 collision to forge a Microsoft code-signing certificate and spread through Windows Update.
- **2017:** Google and CWI Amsterdam announced **SHAttered**, the first real SHA-1 collision: two different PDF files with the same SHA-1 hash, computed with about 2^63 operations.
- **2020:** the **Shambles** attack made chosen-prefix SHA-1 collisions cost about 45,000 US dollars of cloud computing, and demonstrated an impersonation attack on PGP keys.

Systems had over a decade of warning, and many still did not migrate in time. Today, MD5 and SHA-1 must not be used for signatures, certificates, or any purpose that needs collision resistance. NIST plans to withdraw SHA-1 entirely by 2030.

> **In practice.** You will still find MD5 and SHA-1 as non-security checksums, for example to detect accidental corruption in a file transfer, and in Git's original object IDs. Accidental corruption cannot exploit collisions, so those uses are tolerable, although Git is moving to SHA-256. Any use where an attacker could choose the input is not tolerable. HMAC-SHA1 (section 7.6) does not depend on collision resistance and is not broken, but new designs should use HMAC-SHA256.

In an enterprise, SHA-1 lingers in places nobody looks: old internal CA hierarchies, signed firmware on network appliances, SAML assertions from legacy identity providers, Java keystores and mainframe integrations. Finding it is an inventory problem (Chapter 43), not a mathematics problem.

## 7.5 How hash functions are built

### Merkle-Damgård: SHA-2

**SHA-2** (SHA-224, SHA-256, SHA-384, SHA-512) uses the **Merkle-Damgård** construction. The message is padded and split into blocks. A compression function absorbs one block at a time into an internal state, and the final state is the hash.

This design has one surprising flaw: the **length extension attack**. Because the hash output *is* the final internal state, anyone who knows `SHA-256(secret || message)` and the length of the secret can compute `SHA-256(secret || message || padding || extra)` without knowing the secret. They simply resume hashing from the published state.

This breaks naive authentication schemes such as `tag = SHA-256(key || message)`, which some web APIs used in the 2000s. An attacker could append a parameter like `&admin=true` to a signed request and compute a valid tag. The fix is HMAC (section 7.6), or a hash immune to extension: SHA-512/256 (a truncated SHA-512) or SHA-3.

### Sponges: SHA-3

**SHA-3** was chosen through a NIST public competition and standardised in 2015 (FIPS 202). It uses a different design called a **sponge**: data is absorbed into a large internal state, which is then squeezed to produce output. Only part of the state is ever output, so length extension is impossible.

SHA-3 also provides **SHAKE128** and **SHAKE256**, called **extendable-output functions (XOFs)**, which produce output of any requested length. The post-quantum standards ML-KEM and ML-DSA use SHAKE heavily (Chapter 45).

| Hash | Output | Collision security | Length extension | Notes |
| --- | --- | --- | --- | --- |
| SHA-256 | 256 bits | 128 bits | Vulnerable | The default for most uses |
| SHA-384 | 384 bits | 192 bits | Resistant (truncated) | Required by high-assurance profiles such as CNSA 2.0 |
| SHA-512 | 512 bits | 256 bits | Vulnerable | Faster than SHA-256 on many 64-bit CPUs |
| SHA3-256 | 256 bits | 128 bits | Resistant | Different design; a hedge if SHA-2 ever weakens |
| BLAKE2 / BLAKE3 | Variable | 128 bits or more | Resistant | Very fast; common in software, not FIPS-approved |

## 7.6 Message authentication codes

A **message authentication code (MAC)** is like a hash that requires a key. Only key holders can create or check a valid tag, so MACs give integrity and authentication between parties who share a secret. They do not give non-repudiation: either side could have produced the tag. Proof that one specific party acted needs a digital signature (Chapter 10).

```text
tag    = MAC(key, message)
verify = MAC(key, received_message) == received_tag
```

### HMAC

**HMAC** (RFC 2104, FIPS 198-1) builds a MAC from any hash function by hashing twice, with the key mixed in differently each time:

```text
HMAC(K, m) = H( (K XOR opad) || H( (K XOR ipad) || m ) )
```

Here `ipad` and `opad` are fixed constants. The outer hash hides the inner hash's final state, so length extension fails, and HMAC remains secure even with hash functions whose collision resistance has weakened. HMAC-SHA256 is probably the most widely deployed MAC in the world: it signs API requests, protects session cookies and JSON Web Tokens (Chapter 16), and forms the core of the TLS 1.3 key schedule (Chapter 20).

Other MACs you will meet: **CMAC** (NIST SP 800-38B), built from AES and common in payments and smart cards; **GMAC**, inside AES-GCM (Chapter 6); **Poly1305**, paired with ChaCha20; and **KMAC**, the SHA-3 family's native MAC.

### Compare tags in constant time

Never verify a tag with ordinary string comparison. It stops at the first mismatched byte, so its timing reveals how many leading bytes were correct, and an attacker can discover a valid tag byte by byte. Every mainstream language offers a **constant-time comparison**: `hmac.compare_digest` in Python, `MessageDigest.isEqual` in Java, `crypto.timingSafeEqual` in Node.js, `subtle.ConstantTimeCompare` in Go and `CryptographicOperations.FixedTimeEquals` in .NET.

## 7.7 HMAC in APIs and payments

### Signing API requests

Bearer tokens prove that a caller holds a token. They do not prove that the request body or URL arrived unaltered, and anyone who captures the token can reuse it. **Request signing** closes that gap: the caller computes an HMAC over the important parts of each request with a secret key, and the server recomputes it.

Many public APIs use this pattern, each with its own details, as of 2026:

- **AWS Signature Version 4** signs a canonical form of the method, path, query, selected headers and body hash. It derives a **signing key** from the secret through a chain of HMACs over the date, region and service, so a leaked derived key is useful for only one service, region and day.
- **Azure Storage Shared Key** computes HMAC-SHA256 over a defined string built from the request.
- **Webhook providers** such as Stripe and GitHub sign each callback body with HMAC-SHA256 and a per-endpoint secret. Stripe also signs a timestamp, so receivers can reject old messages.

These designs share five elements, and your own APIs need all of them:

1. **Canonicalisation.** Both sides must build exactly the same bytes. Proxies that reorder parameters or re-encode JSON break signatures, so sign the raw body's hash.
2. **Coverage.** Sign the method, path, body and any header that changes meaning. Anything unsigned can be altered.
3. **Freshness.** Sign a timestamp and reject requests older than a few minutes; add a nonce where replays matter, as for payment instructions.
4. **Key identification.** Send a key ID, so secrets can be rotated with an overlap instead of a flag day.
5. **Constant-time verification**, as in section 7.6.

> **Watch out.** An HMAC secret is a symmetric key, so the server holds a copy of every client's secret, and one leak exposes every partner. Keep these secrets in a secrets manager (Chapter 35), never in code or configuration files, and prefer asymmetric signing or mutual TLS (Chapter 21) when many independent partners connect, as open banking profiles such as FAPI do (Chapter 39).

### MACs in payments

Payment systems used MACs long before the web. Messages between terminals, acquirers, switches and card networks carry a MAC under a shared **MAC key**, so a changed amount or account number is detected. Common algorithms include:

- the **retail MAC** (ISO/IEC 9797-1 MAC algorithm 3, also known from ANSI X9.19), built on Triple DES and still common in older interfaces;
- **AES-CMAC**, the modern replacement, also used to protect the integrity of TR-31 key blocks (Chapter 37);
- **HMAC-SHA256** in newer API-based payment schemes.

These MAC keys live inside **payment HSMs** and cloud payment cryptography services, which generate and verify MACs without ever releasing the key, under a key hierarchy that lets keys be exchanged and rotated without anyone seeing them in clear (Chapter 38).

HMAC also solves a different payments problem: finding a card number without storing it. PCI DSS allows a stored primary account number (PAN) to be replaced by a hash, but a plain hash of a 16-digit PAN is easy to reverse, because the issuer prefix and check digit leave only around a billion candidates for a given card range. PCI DSS v4.0 therefore requires that hashes used to render PAN unreadable be keyed cryptographic hashes of the entire PAN, with key management around them. In practice that means HMAC-SHA256 with a key held in an HSM or KMS.

> **At Meridian.** Meridian Pay verifies AES-CMAC from newer terminals and the retail MAC from older ones inside its payment HSM cluster, owned by Payments Security. The open banking gateway, owned by Platform Engineering, verifies HMAC-signed partner webhooks, with each partner's secret in the enterprise vault under a key ID and a 90-day rotation. The fraud data lake joins transactions by an HMAC-SHA256 token of the PAN, keyed in the cloud KMS. The PKI and Cryptography Services team sets the approved algorithms for all three, and GRC maps them to PCI DSS.

## 7.8 Key derivation functions

A **key derivation function (KDF)** turns some input secret into one or more cryptographic keys. There are two very different kinds, and confusing them is a common mistake.

### KDFs for high-entropy secrets: HKDF

When the input is already a strong secret, such as the shared value from a Diffie-Hellman exchange or a master key, you use a fast KDF. The most common is **HKDF** (RFC 5869), built from HMAC in two steps:

1. **Extract:** condense the input, which may have uneven randomness, into a uniform pseudo-random key.
2. **Expand:** produce as many keys as needed, each bound to a distinct **context label**.

```text
prk     = HKDF-Extract(salt, shared_secret)
enc_key = HKDF-Expand(prk, "app v1 encryption key", 32)
mac_key = HKDF-Expand(prk, "app v1 MAC key", 32)
```

The labels guarantee that keys for different purposes are independent: knowing one reveals nothing about the others. This **key separation** principle is central to key management (Chapter 32). TLS 1.3 derives all of its traffic keys with HKDF and labels such as "c hs traffic" and "s ap traffic". NIST describes equivalent constructions in SP 800-108 (KDFs from a key) and SP 800-56C (KDFs after key agreement), which matters when you must use FIPS-validated modules.

Enterprises use the same idea to avoid storing millions of keys: one master key per customer, with a per-object key derived using the object ID as the label. Payment terminals do something similar with DUKPT (Chapter 37).

### KDFs for passwords: deliberately slow

Passwords are the opposite of high-entropy secrets. Humans choose them, and attackers can test billions of guesses per second against a fast hash using graphics cards. If you store `SHA-256(password)`, an attacker who steals the database can test every common password against every account almost instantly.

**Password hashing functions** defend against this in three ways:

1. A unique random **salt** per password, so identical passwords produce different hashes and precomputed tables are useless.
2. A tunable **work factor**, so each guess costs real time.
3. **Memory hardness**, so each guess also needs a lot of memory, which blunts the advantage of graphics cards and custom chips.

| Function | Memory-hard | Status | Guidance |
| --- | --- | --- | --- |
| **Argon2id** | Yes | Winner of the 2015 Password Hashing Competition; RFC 9106 | First choice for new systems |
| **scrypt** | Yes | Widely available | Good choice |
| **bcrypt** | Partly | Mature and common | Acceptable; ignores password bytes beyond 72 |
| **PBKDF2-HMAC-SHA256** | No | FIPS-approved (SP 800-132) | Use when FIPS is required, with a high iteration count (OWASP suggests 600,000) |
| Plain or salted SHA-256 | No | Unsuitable | Never use for passwords |

## 7.9 Password storage in the enterprise

Choosing Argon2id for a new application is the easy part. An enterprise stores passwords in dozens of places it did not design: directories, cloud identity providers, databases, network devices, the mainframe and vendor applications. The architect's job is to know how each stores them and to limit the damage if one is stolen.

### Where passwords live

- **Active Directory** stores each account's **NT hash**: an MD4 hash of the password with no salt and no work factor. It is directly usable as a credential in **pass-the-hash** attacks, so a stolen copy of the directory database (`ntds.dit`) is equivalent to every password. Protecting domain controllers and retiring NTLM (Chapter 16) matter more here than any hash setting.
- **Cloud identity providers** keep their own hashes. With Microsoft Entra ID password hash synchronisation, the sync agent salts the NT hash and runs it through PBKDF2 with HMAC-SHA256 for 1,000 iterations before uploading it, as of 2026. Ask other providers, such as Okta and Ping Identity, for their storage design during due diligence.
- **Self-hosted identity servers and frameworks** let you choose: Keycloak sets the algorithm and iterations in each realm's password policy, and Spring Security and ASP.NET Core Identity ship configurable hashers.
- **Operating systems and databases** have their own formats. Several Linux distributions default to yescrypt, and PostgreSQL's SCRAM-SHA-256 stores a salted, iterated verifier.

### Design rules

1. **Use a memory-hard function with tuned parameters.** OWASP's current minimums for Argon2id are 19 MiB of memory, two iterations and one degree of parallelism. Tune upwards until a login costs a few tens of milliseconds on your hardware.
2. **Add a pepper for high-value stores.** A **pepper** is a secret key, applied with HMAC and held outside the database, ideally in an HSM or KMS. An attacker who steals only the database cannot test guesses. NIST SP 800-63B describes this as an additional keyed hashing step.
3. **Store the algorithm and parameters with each hash.** Formats such as `$argon2id$v=19$m=19456,t=2,p=1$salt$hash` make upgrades possible.
4. **Upgrade legacy hashes without waiting for logins.** Wrap each old hash in the new function (`Argon2id(old_sha1_hash)`) immediately, then replace it with a direct hash of the password when the user next signs in.
5. **Reduce the number of password stores.** Every application that federates to the central identity provider (Chapter 16) is one fewer password database to protect, and passkeys remove the stored secret entirely.

> **Watch out.** In 2012, about 6.5 million LinkedIn password hashes were posted online. They were unsalted SHA-1, and most were cracked within days. In 2016, a much larger set from the same breach, over 100 million accounts, appeared for sale. Password reuse carried the damage far beyond LinkedIn, into corporate accounts.

> **Compliance hook.** PCI DSS v4.0.1 requirement 8.3.2 requires strong cryptography to render authentication factors unreadable in transmission and storage, and requirement 3.5.1.1 requires keyed hashes for PAN. NIST SP 800-63B sets salted, costly password hashing for verifiers. ISO/IEC 27001:2022 controls A.5.17 (authentication information) and A.8.24 (use of cryptography) expect a documented standard such as the rules above.

## 7.10 Lab: hashes, MACs and passwords

You need OpenSSL 3 and Python 3.

1. **See the avalanche effect.**

    ```bash
    echo -n "hello"  | openssl dgst -sha256
    echo -n "hello." | openssl dgst -sha256
    ```

2. **Demonstrate length extension safely.** The open-source tool `hash_extender` takes `SHA-256(secret || "user=alice")` and the secret's length, and produces a valid hash for `"user=alice" + padding + "&admin=true"`. Then confirm that HMAC gives the attacker nothing to extend:

    ```python
    import hmac, hashlib
    key = b"server-secret"
    tag = hmac.new(key, b"user=alice", hashlib.sha256).hexdigest()
    print(tag)
    ```

3. **Sign and verify a request like an API gateway.**

    ```python
    import hmac, hashlib, time
    key = b"partner-42-secret"
    body = b'{"amount": 100, "to": "GB00TEST"}'
    ts = str(int(time.time()))
    base = "\n".join(["POST", "/v1/payments", ts,
                      hashlib.sha256(body).hexdigest()])
    tag = hmac.new(key, base.encode(), hashlib.sha256).hexdigest()
    # Server side: rebuild base, recompute, compare in constant time
    good = hmac.new(key, base.encode(), hashlib.sha256).hexdigest()
    print(hmac.compare_digest(tag, good))
    ```

    Change the amount to 900 in the body, rebuild `base` on the server side only, and confirm the comparison fails.

4. **Derive two keys with HKDF.**

    ```bash
    openssl kdf -keylen 32 -kdfopt digest:SHA256 \
      -kdfopt hexkey:000102030405060708090a0b0c0d0e0f \
      -kdfopt salt:lab -kdfopt info:"app v1 encryption key" HKDF
    openssl kdf -keylen 32 -kdfopt digest:SHA256 \
      -kdfopt hexkey:000102030405060708090a0b0c0d0e0f \
      -kdfopt salt:lab -kdfopt info:"app v1 MAC key" HKDF
    ```

    The two outputs are unrelated, although they come from the same secret.

5. **Feel the cost of password hashing.**

    ```python
    import hashlib, time, os
    pw, salt = b"Summer2026!", os.urandom(16)
    t = time.time(); hashlib.sha256(pw).digest()
    print("sha256", time.time() - t)
    t = time.time()
    hashlib.scrypt(pw, salt=salt, n=2**15, r=8, p=1,
                   maxmem=64 * 1024 * 1024)
    print("scrypt", time.time() - t)
    ```

    SHA-256 finishes in microseconds; scrypt takes tens of milliseconds and uses 32 MB of memory. A user signing in will not notice the difference. An attacker trying a billion guesses certainly will.

**Optional cloud extension.** AWS KMS and Google Cloud KMS both offer HMAC keys whose material never leaves the service, as of 2026; check Azure Key Vault's current key types if you use Azure. Create one, compute an HMAC of a test PAN through the API, and confirm that the same input always gives the same token. Cost warning: keys carry a monthly charge and operations are billed, so schedule the key for deletion when you finish.

## 7.11 Failure story: the hash that forged a CA

In December 2008, at the Chaos Communication Congress, a team of researchers revealed that they had created a certificate authority certificate trusted by every major browser, without the CA's permission.

They exploited three weaknesses at once. A commercial CA still signed certificates using MD5. Its certificates had predictable serial numbers and validity dates. And MD5 was vulnerable to chosen-prefix collisions. The team prepared two certificates with the same MD5 hash: an ordinary website certificate, and a CA certificate with the power to sign any website. They bought the ordinary certificate. The CA's signature on it was equally valid for the colliding CA certificate. Computing the collision took a cluster of about 200 PlayStation 3 consoles a few days.

The researchers deliberately set their rogue certificate to expire in the past so it could not be abused, and worked with browser makers before disclosure. Within weeks, CAs stopped issuing MD5-signed certificates and began using random serial numbers, a defence that the CA/Browser Forum later made mandatory. Every public certificate you see today contains at least 64 bits of randomness in its serial number because of this attack (Chapter 12).

The lesson is about timing. MD5 collisions had been public for four years, and the CA had not acted because nothing had visibly broken. Deprecate weak algorithms on the schedule research sets, not the one an incident sets.

## 7.12 Chapter summary

- Hash functions produce fixed-size fingerprints and must resist preimages, second preimages and collisions. Collision security is only half the output size.
- MD5 and SHA-1 are broken for collision resistance and still hide in old hierarchies, firmware and integrations. Use SHA-256, SHA-384 or SHA-3.
- SHA-2 is vulnerable to length extension; never use `hash(key || message)` as a MAC. Use HMAC.
- Signed API requests need canonicalisation, full coverage, freshness, key IDs and secrets kept in a vault.
- Payments use CMAC, the retail MAC and HMAC inside payment HSMs, and PCI DSS requires keyed hashes for PAN.
- Use HKDF or NIST KDFs with distinct labels for strong secrets, and Argon2id, scrypt or bcrypt for passwords.
- Enterprise password risk lives in directories and vendor products as much as in your own code; know how each store hashes, add peppers to high-value stores and reduce the number of stores.
