## 14.1 From certificate to trust decision

When a client receives a certificate chain, it must answer one question: should I trust that this public key belongs to this name, for this purpose, right now? Answering takes two steps:

1. **Path building:** find a chain of certificates from the server's **leaf certificate** (the end-entity certificate) up to a **trust anchor**, a root certificate in the client's trust store.
2. **Path validation:** check every certificate in that chain against a long list of rules.

These steps run in every TLS handshake, every VPN connection, every signed software update and every smart card logon. Most of the time nobody notices them. When they fail, they fail loudly: a payment API rejects a partner, a fleet of laptops cannot reach Wi-Fi, or a mobile app stops talking to its backend. Understanding exactly what the client checks is the fastest way to diagnose those failures, and the only way to design certificates that will not cause them.

## 14.2 Path building

Servers are supposed to send the leaf plus its intermediates, in order. In reality, chains arrive incomplete, out of order, with extra certificates, or with expired cross-signs. Because several valid paths can exist (cross-signing, Chapter 12), clients must search:

- Match each certificate's **Issuer** name and **Authority Key Identifier** against candidate issuers' Subject names and Subject Key Identifiers.
- Look for candidates in the certificates the server sent, in a local cache, in the trust store and, in some clients, by downloading from the **Authority Information Access (AIA)** URL in the certificate. Downloading missing intermediates this way is called **AIA chasing**.
- If a path fails (for example, it ends at an expired root), backtrack and try another.

Good path builders, as in modern browsers and current versions of major platform libraries, search all possibilities. Simpler ones take the first path and fail if it is bad, which caused the 2020 and 2021 root expiry outages described in Chapter 12. This is why the same server can work in a browser and fail in a mobile app or a Java service.

### Why clients disagree

Every major platform has its own verifier, its own trust store and its own habits:

| Verifier | Trust store | Notable behaviour |
| --- | --- | --- |
| Windows CryptoAPI (used by .NET, IIS, Edge for some purposes) | Windows certificate store, updated by Microsoft's root program and Group Policy | Performs AIA chasing; logs detailed failures in the CAPI2 event log |
| Apple Security framework (macOS, iOS) | Apple's root store plus configuration profiles | Enforces Apple's CT and lifetime policies for public certificates |
| Chrome Certificate Verifier | The Chrome Root Store, plus enterprise roots from the operating system | Same behaviour across platforms; enforces CT for public certificates |
| OpenSSL, BoringSSL, Go, Rust libraries | Usually a CA bundle file or the operating system store | No AIA chasing; the server must send the full chain |
| Java PKIX | A `cacerts` keystore shipped with each Java runtime | Separate trust store per runtime; often years out of date in long-lived applications |

The practical lesson is that "it works in my browser" proves very little. A browser may have fetched a missing intermediate from AIA or remembered one from an earlier visit. A Go microservice, a Java batch job or an appliance will not. The rule for servers is simple: **always send the complete chain**, leaf first, up to but not including the root.

> **At Meridian.** Meridian runs every one of the verifiers in the table above: Windows laptops, iOS and Android mobile apps, Java services on the mainframe's distributed tier, Go services on Kubernetes, and appliances with their own embedded stores. The PKI and Cryptography Services team publishes a **trust store standard** that names which roots each platform type must trust, and Platform Engineering bakes those roots into container base images and Java runtimes. When a private root is added or retired, the change ticket lists every trust store type, because a root missing from one Java `cacerts` file is enough to stop a payment flow.

## 14.3 Path validation

Once a candidate path exists, the client checks it using the algorithm in RFC 5280, section 6. For each certificate, from the trust anchor down to the leaf:

| Check | What fails it |
| --- | --- |
| Signature verifies with the issuer's public key | A forged or corrupted certificate |
| Current time is within Not Before and Not After | An expired or not-yet-valid certificate, or a wrong system clock |
| Issuer is allowed to be a CA (Basic Constraints CA:TRUE) | A leaf certificate pretending to be a CA |
| Path length constraints are respected | Too many CAs below a constrained intermediate |
| Name constraints are respected | An internal CA issuing for a domain outside its permitted space |
| Key usage permits certificate signing for CAs | Misused keys |
| Not revoked | A compromised or withdrawn certificate (sections 14.4 to 14.7) |
| Policy constraints are met | Rare outside government and high-assurance PKIs |

Then, for the leaf only:

- The **hostname** must match a Subject Alternative Name (SAN) entry. The Common Name is ignored by modern clients.
- The **Extended Key Usage (EKU)** must allow the purpose, such as serverAuth for a TLS server or clientAuth for a client certificate.
- For public TLS, browsers also check **Certificate Transparency** proofs (Chapter 13).

Two of these checks deserve attention because enterprises can use them as security controls. **Name constraints** let you limit a private issuing CA to your own domains, so that even a stolen issuing CA key cannot create trusted certificates for a bank's competitors or for a public site. **EKU constraints** on intermediates stop a device-identity CA from issuing code signing certificates. Both are checked by the client, so they work even if the CA itself is compromised, provided the client implements them (most modern libraries do; some older appliances do not, which is worth testing).

> **Watch out.** Writing your own certificate validation is one of the most reliably dangerous things a developer can do. A 2012 study titled "The Most Dangerous Code in the World" found that many non-browser applications, including payment SDKs and cloud clients, disabled or broke validation, often through a single misused library option (section 14.10). Use your platform's validation, and never ship code that turns verification off "temporarily".

## 14.4 Revocation: the hard part

Sometimes a certificate must stop being trusted before it expires, usually because its private key was exposed, it was issued wrongly, or the device or person it identifies has left. **Revocation** is how the CA announces this. There are three classic mechanisms, and all of them have serious problems.

### Certificate Revocation Lists (CRLs)

A **CRL** is a signed list of the serial numbers of revoked, unexpired certificates, published by the CA at the URL in the certificate's **CRL Distribution Points (CDP)** extension. Each CRL carries a **This Update** time and a **Next Update** time; a client treats the list as current until Next Update.

- **Strengths:** simple, cacheable, and private: downloading the whole list does not reveal which site you are visiting.
- **Weaknesses:** lists can grow to megabytes for a busy CA, so downloading them on every connection is impractical; and a newly revoked certificate stays trusted until clients fetch the next list.

Large CAs manage size by **partitioning** CRLs (each certificate points to one of many smaller CRLs) and, in some products such as Microsoft AD CS, by publishing **delta CRLs** that list only changes since the last full CRL.

### OCSP

The **Online Certificate Status Protocol** (RFC 6960) lets a client ask the CA's responder about one certificate and receive a signed "good", "revoked" or "unknown" answer.

- **Strengths:** small, current answers.
- **Weaknesses:** an extra network request on every new connection, slowing page loads; a **privacy leak**, because the CA learns which sites each user visits; and a single point of failure, because if the responder is down, clients must decide what to do.

### OCSP stapling

With **OCSP stapling**, the server fetches its own OCSP response periodically and attaches ("staples") it to the TLS handshake. The client gets fresh, signed status without contacting the CA. It fixes the speed and privacy problems, but only if every server enables it, and an attacker with a stolen key can simply not staple. The **Must-Staple** certificate extension was designed to require stapling, but it saw little adoption.

## 14.5 Soft-fail: why revocation rarely protects anyone

What should a browser do if it cannot reach the OCSP responder? If it refuses the connection (**hard-fail**), every responder outage breaks large parts of the web. So browsers **soft-fail**: if the check fails, they proceed as if the certificate were good.

Now consider the attacker. Someone able to intercept your connection with a stolen certificate is, by definition, in a position to block your OCSP request too. Soft-fail therefore protects you only from attackers who are not able to carry out the attack. Security researcher Adam Langley summarised it in 2014: soft-fail revocation checking is like a seat belt that snaps when you crash.

This is why Chrome stopped doing online OCSP checks for most certificates years ago.

## 14.6 What browsers do instead

Browsers moved revocation from the network moment to a push model:

- **CRLSets (Chrome)** and **disallowed lists (other platforms)** are curated lists of high-priority revocations, such as compromised intermediates and major incidents, pushed to browsers through their update mechanism.
- **CRLite (Firefox)** compresses the revocation status of all publicly trusted certificates, gathered from CRLs and CT logs, into a compact data structure, and pushes updates to browsers several times a day. Firefox can then check revocation locally, privately and with hard-fail semantics. Mozilla enabled it for all desktop users in 2025.
- **Short-lived certificates** make revocation less necessary: if a certificate lives a few days, a leaked key is useful only briefly.

> **Current development.** The industry is retiring OCSP for the public web. In 2023 the CA/Browser Forum made OCSP optional for public CAs and required CRLs instead (Ballot SC-063). Let's Encrypt, the largest CA, ended its OCSP service in August 2025 and now publishes revocation only through CRLs. Combined with lifetimes falling to 47 days (Chapter 13), public revocation is becoming a matter of CRLs aggregated by browsers, plus short validity, rather than live per-connection checks.

The change has a knock-on effect inside enterprises. Firewalls, proxies and appliances that were configured to hard-fail on OCSP for public certificates, often by a well-meaning hardening guide, start failing when the CA's responder disappears. Check for such settings before your public CA turns OCSP off, not after.

## 14.7 Revocation inside organisations

Inside private PKIs (Chapter 15), the picture is different and often better:

- You control both the CA and the clients, so you can configure **hard-fail** checks where they matter, such as for VPN, Wi-Fi (802.1X) or mTLS clients.
- CRLs for a private CA are usually small and can be cached and refreshed predictably.
- You can run your own OCSP responders close to the clients, for example Microsoft's Online Responder role for AD CS, the validation authority component in EJBCA, or the OCSP responders offered by cloud private CAs such as AWS Private CA.
- You can use very short lifetimes (hours or days) for workloads and devices, which is the most robust approach of all.

### Choosing soft-fail or hard-fail

The choice is a trade-off between availability and security, and it should be made per use case, not once for the whole organisation:

| Use case | Typical choice | Reason |
| --- | --- | --- |
| Remote access VPN and 802.1X network access | Hard-fail on CRL | Revoking a lost laptop's certificate must lock it out; the CRL is cached, so a brief CDP outage is survivable |
| Smart card and certificate logon to Windows | Hard-fail | Domain controllers check revocation of user certificates; a leaver's card must stop working |
| Service mesh workload certificates | No revocation check; lifetimes of hours | Rotation is faster than any revocation mechanism |
| Internal web applications | Soft-fail or none | Users would be blocked by every CDP outage for little gain |

### Operating revocation infrastructure

Whatever the mechanism, operations matter:

- **Publish before Next Update.** CRLs must be re-signed and published before their Next Update time, even if nothing changed. An offline root's CRL is a classic trap: it may have a validity of six or twelve months, so someone must bring the root out of the safe on schedule to sign a new one.
- **Make distribution points highly available.** CDP and OCSP URLs are usually plain HTTP (the data is signed, so TLS is not needed, and TLS would create a circular dependency). Host them on more than one server or behind a CDN, reachable from every network segment whose clients check.
- **Monitor freshness, not just availability.** Alert when a CRL is within days of its Next Update without a newer one published.

An expired CRL is one of the most damaging failures in a private PKI: hard-failing clients reject every certificate the CA ever issued, at once.

> **Compliance hook.** NIST SP 800-53 control SC-17 (Public Key Infrastructure Certificates) expects certificates to be issued under an approved policy, and IA-5(2) covers validating certificates, including revocation status, for PKI-based authentication. PCI DSS v4.0.1 requirement 4.2.1 requires that certificates protecting cardholder data in transit are confirmed valid and not expired or revoked. Auditors will ask how revocation status is checked on those paths and how CRL publication is monitored.

## 14.8 The right order for revocation

Revoking a certificate that is still installed takes the service down for every client that checks. The safe order is always:

1. **Replace** the certificate on every installation, with a new key.
2. **Verify** each installation now serves the replacement.
3. **Revoke** the old certificate, with the correct reason code (key compromise, superseded, cessation of operation, affiliation changed).

With a key compromise, follow the same order, only faster. With a public CA there may be no choice: the Baseline Requirements oblige CAs to revoke within 24 hours or five days for certain problems, including mis-issuance found by the CA itself. In July 2024, DigiCert found that some of its DNS-based domain validations had omitted a required underscore prefix, and announced that it would revoke the affected certificates, tens of thousands of them, within 24 hours, which left many customers replacing certificates at very short notice. This is one of many reasons an accurate inventory of where every certificate is installed (Chapter 17) is essential, and why ARI's ability to signal early renewal matters.

> **At Meridian.** Meridian's mass-revocation runbook, owned by the PKI team and rehearsed twice a year with the SOC, starts from the CLM inventory: list every installation of the affected certificates, push replacements through the automation, verify each endpoint, then revoke. The runbook also names the people who can approve an emergency standard change at 2 a.m., because the slowest step in past rehearsals was finding someone with authority.

## 14.9 Lab: validate chains and check revocation

These steps need OpenSSL and curl. Use any public HTTPS site.

1. **Capture a chain.** Save the server's certificates into separate files:

    ```bash
    echo | openssl s_client -connect www.example.com:443 \
      -servername www.example.com -showcerts 2>/dev/null \
      | awk '/BEGIN CERT/{n++} {print > ("cert" n ".pem")}'
    mv cert1.pem leaf.pem; mv cert2.pem intermediate.pem
    ```

    Remove any non-certificate text lines from the files if your awk version keeps them.

2. **Validate the chain manually.**

    ```bash
    openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt \
      -untrusted intermediate.pem leaf.pem
    ```

    Remove `-untrusted intermediate.pem` and observe the failure: this is what a Go or OpenSSL client sees from a server with an incomplete chain.

3. **Fetch and read a CRL.**

    ```bash
    openssl x509 -in leaf.pem -noout -ext crlDistributionPoints
    curl -s -o ca.crl <URL-from-the-output>
    openssl crl -in ca.crl -inform DER -noout -text | head -30
    ```

    Note the **This Update** and **Next Update** times and count the revoked entries.

4. **Query OCSP, where still offered.**

    ```bash
    openssl x509 -in leaf.pem -noout -ocsp_uri
    openssl ocsp -issuer intermediate.pem -cert leaf.pem \
      -url <OCSP-URI> -resp_text | head -20
    ```

    If the certificate has no OCSP URI, its CA has already moved to CRL-only revocation.

5. **Test hostname and time failures.** Use `openssl verify` with `-verify_hostname wrong.example` and with `-attime` set to a date after expiry, and read the errors. These are the two most common real-world validation failures.

6. **Build a private CRL and watch it expire.** With the two-tier lab CA from Chapter 15 (or any OpenSSL CA), generate a CRL with `openssl ca -gencrl -crldays 1`, revoke a test certificate, and verify it with `openssl verify -crl_check -CRLfile`. Then use `-attime` two days ahead and observe the "CRL has expired" failure that hard-failing clients would see.

**Optional cloud extension.** Create a short-lived-mode CA in a cloud private CA service, enable its CRL publication to object storage, and inspect the published CRL. Cost warning: cloud private CAs are billed monthly per CA, often hundreds of US dollars for a general-purpose CA, so delete the CA (and confirm its deletion) the same day.

## 14.10 Failure story: the most dangerous code in the world

In 2012, researchers from Stanford and the University of Texas published "The Most Dangerous Code in the World: Validating SSL Certificates in Non-Browser Software". They tested widely used software that made TLS connections outside browsers: payment gateway libraries from major merchants, cloud storage clients, popular HTTP libraries and mobile app frameworks.

They found that certificate validation was broken in a striking number of them. Some libraries checked the chain but not the hostname, so any valid certificate for any site was accepted. Others had confusing APIs where a parameter that looked like "verify hostname = true" actually meant something else. Many applications had simply disabled validation, often with a code comment about getting tests to pass. In every case, an attacker on the network could intercept supposedly secure connections, including payment traffic, with a self-made certificate.

The cryptography was sound; the checks around it were missing. The paper drove fixes across many libraries and remains a useful checklist for any enterprise code review: verify the chain, verify the hostname, never disable verification, and test that your code rejects bad certificates, not only that it accepts good ones. Add negative tests (expired, wrong host, untrusted root) to the CI pipeline of every service that makes outbound TLS calls.

## 14.11 Chapter summary

- Trust decisions require path building, which may need backtracking, and path validation against RFC 5280 rules, plus hostname and purpose checks.
- Platforms differ in trust stores, AIA chasing and path building; servers must always send the full chain.
- Name and EKU constraints on intermediates are enforced by clients and limit the damage of a compromised private CA.
- CRLs are private but slow to update; OCSP is current but slow, leaky and fragile; stapling helps but is optional.
- Browsers soft-fail on online revocation, which protects little, so they moved to pushed lists (CRLSets, CRLite) and short lifetimes.
- OCSP is being retired from the public web; CRLs plus short-lived certificates are the future, and appliances that hard-fail on OCSP must be found.
- Private PKIs should choose hard-fail per use case, keep CRLs fresh and highly available, and monitor their Next Update times.
- Always replace before revoking, and keep an inventory that makes mass replacement possible.
