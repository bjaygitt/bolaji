## 32.1 Why key management is the real work

Kerckhoffs's principle (Chapter 1) says a system should stay secure even if everything about it except the key is public. The other side of that principle is less comfortable: **every weakness in how keys are handled becomes a weakness in the system.** Real breaches rarely break AES. They find keys:

- in source code repositories and container images
- in configuration files, environment variables and logs
- in memory and crash dumps
- in backups stored next to the data they protect
- with administrators and services that never needed them
- long after they should have been rotated or destroyed

None of these failures is mathematical. Each is a failure of process. **Key management** is the set of decisions and controls that say, for every key an organisation holds, where it lives, who may use it, how long it exists and how it is replaced.

This chapter is the foundation for the rest of Part VIII: HSMs (Chapter 33), enterprise key managers (Chapter 34) and secrets (Chapter 35). Cloud KMS services (Chapter 28) and payment key hierarchies (Chapter 37) apply the same principles.

## 32.2 NIST SP 800-57 and the vocabulary of keys

The most widely used reference for the discipline is NIST's **SP 800-57**, the *Recommendation for Key Management*. It comes in three parts:

**Part 1** (Revision 5, 2020) defines key types, key states, cryptoperiods and security strengths; **Part 2** covers policies, roles and planning for organisations; **Part 3** gives guidance for specific protocols such as TLS, IPsec and PKI. Auditors and vendors borrow its terms, so use them precisely. NIST also publishes **SP 800-130**, a framework for designing a **cryptographic key management system (CKMS)**, the technical system that carries out these practices. Chapter 34 uses that framework for enterprise key managers.

### Classifying keys by purpose

Keys are classified by algorithm family and, more importantly, by purpose. **Each key should have exactly one purpose.**

| Key type | Purpose | Example |
| --- | --- | --- |
| **Data encryption key (DEK)** | Encrypts application data | A per-file AES-256 key |
| **Key encryption key (KEK)** | Encrypts (wraps) other keys | A master key in a key management service |
| **Signing key** | Creates digital signatures | Code signing, token signing, CA keys |
| **Verification key** | Checks signatures | Public keys in trust stores and JWKS documents |
| **Key agreement key** | Establishes shared secrets | Static or ephemeral ECDH keys; ML-KEM keys |
| **MAC key** | Creates and checks message authentication codes | HMAC keys for API request signing |
| **Key derivation key** | Derives other keys | An HKDF master secret |

SP 800-57 goes further and distinguishes **symmetric** keys (one secret shared by both parties) from **private** and **public** keys, and **static** keys (used for a long period) from **ephemeral** keys (used once, as in TLS 1.3 key exchange). A static CA signing key needs hardware and a ceremony; an ephemeral ECDH key lives for milliseconds in memory and needs neither.

### Why one purpose per key

Using one key for two purposes, for example signing and decryption, or the same RSA key in two protocols, lets an attacker turn one use against the other. The DROWN attack (Chapter 11) worked because servers shared an RSA key between modern TLS and the broken SSLv2 protocol, so weaknesses in the old protocol exposed traffic protected by the new one. This **key separation** principle (Chapter 7) costs almost nothing to follow at design time. Untangling shared keys after an incident costs a great deal.

### Security strength

SP 800-57 expresses every algorithm and key size as a **security strength**, the approximate bits of work needed to break it: 128 for AES-128 and P-256, about 112 for RSA-2048. A hierarchy is only as strong as its weakest link, so wrapping an AES-256 key under RSA-2048 gives you 112 bits, not 256.

- **Pre-activation:** the key exists but may not yet be used, such as a successor generated ahead of a rollover.
- **Active:** the key may protect new data and process existing data.
- **Suspended:** use is paused, perhaps during an investigation.
- **Deactivated:** the key may no longer protect new data but may still decrypt or verify old data.
- **Compromised:** the key is known or suspected to be in unauthorised hands, and may only be used under strict control while its data moves to a new key.
- **Destroyed:** every copy of the key has been removed.

The states matter only if the key system enforces them. A key marked "deactivated" in a spreadsheet but still usable by the application is, in practice, active.

### What each stage needs

| Stage | What happens | Controls that matter |
| --- | --- | --- |
| **Generation** | The key is created | Approved algorithm and size; a strong random source (Chapter 4); generated inside the system that will protect it |
| **Registration and distribution** | The key is recorded, given metadata, and delivered to its users | Inventory entry with owner, purpose and expiry; keys delivered wrapped, never in plain text |
| **Storage** | The key rests | Hardware protection for high-value keys (Chapter 33); wrapped by a KEK otherwise; never stored with the data it protects |
| **Use** | The key performs its purpose | Access control per operation; logging; usage limits such as AES-GCM message counts |
| **Rotation** | A new key replaces it for new data | Scheduled cryptoperiods and event-driven rotation |
| **Backup and archival** | Copies kept for recovery | Encrypted, split or HSM-protected backups in a separate location; tested restores |
| **Deactivation** | The key stops protecting new data | Enforced by the key system, not by convention |
| **Destruction** | All copies are removed | Including backups and caches; destruction recorded and witnessed for high-value keys |

Destruction has a powerful side effect. Once every copy of a key is gone, everything encrypted under it is permanently unreadable. **Crypto-shredding** uses this deliberately: give each customer or dataset its own key, and destroy the key when the data must be deleted, even from backups that cannot be edited. Chapter 29 covers crypto-shredding and how to prove that deletion happened.

> **Watch out.** Backup and destruction pull in opposite directions. Every backup copy you make for resilience is another copy you must find and destroy at the end of the key's life. Record where every backup of a key lives, or crypto-shredding becomes a claim you cannot prove.

## 32.4 Key hierarchies and envelope encryption

Encrypting large amounts of data directly with a master key held in a hardware security module (HSM) would be slow, and it would expose that master key to heavy use. Instead, almost every modern system uses a **key hierarchy**, in which keys at each level protect the keys below them, and **envelope encryption** to connect the hierarchy to data:

1. Generate a fresh **data encryption key (DEK)** for each object: a file, a database record, a disk or a backup.
2. Encrypt the data locally with the DEK, using authenticated encryption (Chapter 6).
3. Send the DEK to the key management system to be **wrapped** (encrypted) under a **key encryption key (KEK)** that never leaves the key system.
4. Store the wrapped DEK next to the encrypted data, and erase the plain DEK from memory.

To decrypt, the application sends the wrapped DEK to the key management system, receives the plain DEK if it is authorised, and decrypts locally.

The benefits explain why every cloud KMS, key manager and storage system works this way:

- **Performance:** bulk encryption happens locally; the key system handles only small wrap and unwrap operations.
- **Containment:** each object has its own DEK, so one leaked DEK exposes one object.
- **Cheap rotation:** rotating a KEK means re-wrapping DEKs, not re-encrypting the data.
- **Access control and audit:** every unwrap is an authorised, logged call, so you can see who decrypted what and revoke access centrally.
- **Separation of duties:** storage administrators hold encrypted data, key administrators hold keys, and neither alone can read the data.

The higher a key sits in the hierarchy, the fewer systems touch it, the less often it changes and the more ceremony surrounds it. A root key may change once a decade under a witnessed ceremony; a DEK may be used thousands of times a second and discarded with its object.

### Derived keys

An alternative to storing wrapped DEKs is to **derive** them with HKDF from a master key and a context label such as a tenant or object ID (Chapter 7). Derivation removes the need to store wrapped keys but makes rotating the master key harder, because every derived key changes with it. Many systems combine the two: a wrapped key per tenant, from which per-object keys are derived. DUKPT (Chapter 37) derives a unique key for every card transaction this way.

> **At Meridian.** The PKI and Cryptography Services team publishes a three-level hierarchy as a standard. Root keys live in HSM clusters in DC-East and DC-West or in a cloud HSM-backed key service, and are owned by that team. KEKs exist per application and per environment, owned by the application team but created through the team's self-service portal, so each one lands in the inventory automatically. DEKs belong to the applications and never appear in the inventory individually; the inventory records the KEK that wraps them and the data classification they protect. Payments Security runs its own hierarchy for card keys under payment rules (Chapter 38), and GRC reviews both hierarchies once a year.

## 32.5 Cryptoperiods and rotation

A **cryptoperiod** is the time span during which a key is authorised for use. Limiting it limits three things: how much data any one key protects, how long a stolen key stays useful, and how much material an attacker can gather against one key.

SP 800-57 splits the cryptoperiod of a symmetric key into two parts. The **originator-usage period** is how long the key may protect new data. The **recipient-usage period** is how long it may still decrypt or verify that data, and it can run years longer. A data encryption key might protect new data for up to two years, then remain available for decryption for several more, until the data it protects is re-encrypted or deleted. This is exactly the difference between the active and deactivated states.

Typical practice, informed by SP 800-57's suggested ranges:

| Key | Typical cryptoperiod |
| --- | --- |
| Symmetric data encryption key | Up to 2 years for protecting; may decrypt for longer |
| Key encryption key | 1 to 2 years |
| TLS server key | Lifetime of its certificate; a new key at every renewal (Chapter 19) |
| Code signing key | 1 to 3 years, with timestamps extending signature validity (Chapter 36) |
| CA keys | Root 10 to 20 years; issuing CA 2 to 5 years (Chapter 15) |
| API secrets and tokens | Days to months; better replaced with short-lived credentials (Chapter 35) |

SP 800-57 lists the factors that shorten or lengthen a cryptoperiod, including algorithm strength, data volume, the operating environment (an HSM in a locked data centre versus a mobile app), the cost of rotation and the impact of a leak. A cryptoperiod is a risk decision, and your policy should record its reasons.

### Two kinds of rotation

- **Scheduled rotation** at the end of each cryptoperiod should be fully automated. Cloud KMS services and key managers use **key versions** behind a stable key name: new data uses the new version, and old versions remain for decryption.
- **Event-driven rotation** follows a suspected compromise, a departure or a vulnerability. It tests whether your systems can rotate at all, and if it has never been practised it will fail when you need it.

> **Watch out.** Rotating a KEK protects new data immediately but does nothing for data already wrapped under the old version. If an old KEK is believed compromised, you must re-wrap (or re-encrypt) everything it protected, and only then destroy it. Ask any vendor whose product offers "automatic rotation" which of the two it does.

## 32.6 Inventory, ownership and policy

### The key inventory

You cannot manage keys you do not know about. A **key inventory** records, for every key or key family:

- an identifier and version
- algorithm, size and purpose
- where it lives (which HSM, key manager, cloud KMS, application or file) and whether it can be exported
- the owning team and the systems that use it
- creation date, cryptoperiod and next rotation date
- what it protects (data classification and regulatory scope)
- its current lifecycle state

An inventory built by hand is out of date within weeks. Build it from the key systems' own APIs and logs, and use discovery tools to find keys that escaped them. The inventory is also the starting point for the post-quantum migration. A **cryptographic bill of materials (CBOM)** extends the idea to every use of cryptography in an application, including algorithms inside libraries and protocols, not only managed keys (Chapter 46).

### Policy and roles

A short written **key management policy**, approved by security leadership, should state at least:

- approved algorithms and minimum sizes
- where each class of key must be stored (for example, "CA and root keys in HSMs validated to FIPS 140-3 Level 3")
- cryptoperiods, with their reasons
- who may create, use, export, rotate and destroy each class of key
- logging, monitoring and review
- backup and recovery, including tested restores
- how a suspected compromise is reported and handled

Separate the roles. The people who administer the key system should not be the people who own the data, and high-risk actions should need more than one person. **Dual control** means an action requires two or more people acting together, such as two administrators each presenting a smart card to restore an HSM backup. **Split knowledge** means no single person ever knows a whole key; each holds a **key component**, and the components are combined only inside secure hardware. Payment standards require both for the most sensitive keys, and Chapter 38 shows how key ceremonies put them into practice.

> **Compliance hook.** PCI DSS v4.0.1 Requirements 3.6 and 3.7 require documented key management procedures across the lifecycle, including cryptoperiods, replacement of compromised keys, and split knowledge and dual control for manual clear-text key operations. ISO/IEC 27001:2022 Annex A control 8.24 and NIST SP 800-53 control SC-12 expect the same lifecycle discipline. A current inventory, a written policy and logs of rotation and destruction are the evidence all of them ask for.

## 32.7 Lab: envelope encryption in practice

This Python lab simulates a key management service with a local KEK, so you can see envelope encryption, rotation and crypto-shredding work end to end. It needs Python 3 and the `cryptography` package (`pip install cryptography`).

1. Save the following as `envelope.py`:

```python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.keywrap import (
    aes_key_wrap, aes_key_unwrap)

# In real life the KEK lives inside a KMS or HSM.
KEKS = {1: AESGCM.generate_key(bit_length=256)}
CURRENT = 1

def kms_wrap(dek):
    return CURRENT, aes_key_wrap(KEKS[CURRENT], dek)

def kms_unwrap(version, wdek):
    return aes_key_unwrap(KEKS[version], wdek)

def encrypt_object(data, object_id):
    dek = AESGCM.generate_key(bit_length=256)
    nonce = os.urandom(12)
    ct = AESGCM(dek).encrypt(nonce, data, object_id)
    ver, wdek = kms_wrap(dek)
    return {"ver": ver, "wdek": wdek, "nonce": nonce,
            "ct": ct, "id": object_id}

def decrypt_object(blob):
    dek = kms_unwrap(blob["ver"], blob["wdek"])
    return AESGCM(dek).decrypt(blob["nonce"], blob["ct"], blob["id"])

store = {i: encrypt_object(f"customer record {i}".encode(),
                           f"rec-{i}".encode()) for i in range(3)}
print(decrypt_object(store[1]))
```

2. Run `python3 envelope.py` and confirm the record decrypts. The object ID is passed as associated data.

3. **Rotate the KEK.** Add a version 2 KEK, set `CURRENT = 2`, then loop over `store`: unwrap each DEK with its recorded version, re-wrap it with version 2 and update `ver` and `wdek`. Confirm every record still decrypts, and that the `ct` values never changed.

4. **Deactivate and destroy.** Delete `KEKS[1]` and show that decryption still works, because nothing depends on version 1 any more. Then try the same deletion before re-wrapping and observe the failure: this is why you re-wrap before you destroy.

5. **Crypto-shred.** Delete one object's `wdek` and show its data is unrecoverable, while the other records are untouched.

6. **Context binding.** Try decrypting `rec-1`'s ciphertext with the ID `rec-2` and observe the `InvalidTag` error: associated data stops an attacker swapping records.

**Optional cloud extension.** Replace `kms_wrap` and `kms_unwrap` with calls to a cloud KMS (for example its encrypt and decrypt operations, or a generate-data-key call that returns both plain and wrapped DEKs), and enable automatic rotation on the key. Look at the audit log to see each unwrap recorded. Cloud KMS keys and API calls are billed; delete or schedule deletion of the key when you finish, remembering that most services enforce a waiting period of several days before deletion.

## 32.8 Failure story: the keys in the CI platform

In January 2023, CircleCI, a widely used continuous integration service, disclosed that an attacker had stolen customer secrets: environment variables, tokens and keys that customers had stored for their build pipelines. The intrusion began with malware on one engineer's laptop that stole a single sign-on session cookie, which let the attacker impersonate the engineer and reach production systems. The company reported that, although the customer data was encrypted at rest, the attacker extracted encryption keys from a running process, so the encryption gave no protection. CircleCI told every customer to rotate every secret it had ever stored on the platform.

Encryption at rest helped little, because the attacker reached a place where keys and data were both accessible. And many customers found they could not rotate quickly: secrets had been copied into many places, had no recorded owner, or were long-lived cloud credentials used by systems nobody remembered. Organisations with an inventory, short-lived credentials and practised rotation recovered far faster than those without.

The lessons map onto this chapter. Keep KEKs in a separate, access-controlled key system so that compromising the application tier does not hand over the root of the hierarchy. Replace stored secrets with short-lived credentials (Chapter 35). Keep a live inventory with owners, so that "rotate everything" is a list, not a hunt.

## 32.9 Chapter summary

- Breaches find keys far more often than they break algorithms; key management is where applied cryptography succeeds or fails.
- NIST SP 800-57 supplies the shared vocabulary: key types, key states, cryptoperiods and security strengths.
- Give every key exactly one purpose; key separation prevents one use being turned against another.
- Every key moves through pre-activation, active, suspended, deactivated, compromised and destroyed states, and the key system must enforce them.
- Envelope encryption with a key hierarchy gives speed, containment, cheap rotation, central access control and audit.
- Cryptoperiods are risk decisions with recorded reasons; SP 800-57 separates the period for protecting data from the period for processing it.
- Automate scheduled rotation, practise event-driven rotation, and remember that rotating a KEK does not re-protect data wrapped under the old one.
- A live, system-generated key inventory with owners, plus a written policy with dual control and split knowledge, is the evidence auditors and regulators ask for.
