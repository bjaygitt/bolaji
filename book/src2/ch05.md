## 5.1 What a block cipher does

When a Meridian customer opens the mobile app, a laptop wakes from sleep or a backup tape is ejected, data is encrypted with the same algorithm: AES.

A **block cipher** takes a fixed-size block of data and a key, and produces a scrambled block of the same size. With the same key, the scrambling can be reversed. AES uses 128-bit blocks, so it turns 16 bytes of plaintext into 16 bytes of ciphertext.

```text
ciphertext_block = AES_encrypt(key, plaintext_block)
plaintext_block  = AES_decrypt(key, ciphertext_block)
```

Think of a block cipher as a giant codebook. For every possible key there is a different codebook that maps each of the 2^128 possible input blocks to a unique output block.

A good block cipher should be indistinguishable from a **random permutation**: a random shuffling of all possible blocks. An attacker who does not know the key, and who can ask for the encryption of any blocks they like, should not be able to tell whether they are talking to AES or to a truly random shuffle. Cryptographers call this being a **pseudo-random permutation (PRP)**, and it is the formal security goal for block ciphers (Chapter 11 returns to definitions like this).

### A block cipher alone is not encryption

A block cipher handles exactly one 16-byte block. Real messages are longer, and encrypting each block independently with the same key leaks patterns: identical plaintext blocks produce identical ciphertext blocks. To encrypt real data, you combine the block cipher with a **mode of operation** (Chapter 6). The cipher is an engine; the mode is the vehicle built around it. When a data sheet says "AES-256 encryption", your next question should be "in which mode, with which key management?"

## 5.2 A short history: from DES to AES

The **Data Encryption Standard (DES)** was published in 1977 and protected banking and government data for two decades. Its 56-bit key was small even then. By 1998, a purpose-built machine costing about 250,000 US dollars found a DES key in days. A stop-gap called **Triple DES (3DES or TDEA)** applied DES three times. It was slow, and it kept DES's 64-bit block, which became a problem of its own.

The 64-bit block matters because of the birthday bound from Chapter 4. After about 2^32 blocks, only 32 gigabytes, repeated ciphertext blocks become likely and leak information. In 2016, the **Sweet32** attack recovered secret cookies from long-lived HTTPS connections using 3DES this way. NIST has since disallowed 3DES for encryption after 2023. You will still meet 3DES in payment systems, where older key hierarchies were built on it and are being migrated to AES (Chapters 37 and 38).

In 1997, NIST launched an open, international competition for a replacement. Fifteen designs were attacked publicly for three years. In 2000, NIST selected **Rijndael**, designed by the Belgian cryptographers Joan Daemen and Vincent Rijmen. It was published in 2001 as the **Advanced Encryption Standard (AES)**, FIPS 197.

## 5.3 Inside AES

AES treats a 16-byte block as a 4 by 4 grid of bytes, called the **state**. It transforms the state through a series of **rounds**: 10 for a 128-bit key, 12 for 192-bit, and 14 for 256-bit. Each round applies four steps:

| Step | What it does | Why it is there |
| --- | --- | --- |
| **SubBytes** | Replaces each byte using a fixed lookup table (the S-box) | Adds non-linearity, so the cipher cannot be described by simple equations |
| **ShiftRows** | Shifts each row of the grid left by 0, 1, 2 or 3 positions | Spreads bytes across columns |
| **MixColumns** | Mixes the four bytes of each column using arithmetic in GF(2^8) | Spreads each byte's influence across the column |
| **AddRoundKey** | XORs the state with a round key derived from the main key | Brings in the secret |

After two rounds, every output bit depends on every input bit. This property is called **diffusion**. The non-linear S-box provides **confusion**, a term introduced by Claude Shannon in 1949 to describe hiding the relationship between key and ciphertext. The best known attacks on full AES are barely better than trying every key.

The **key schedule** expands the main key into one round key per round. Researchers have found related-key attacks that exploit it for AES-256, in artificial settings where an attacker gets data encrypted under several keys with a known mathematical relationship. Systems that derive keys properly (Chapter 7) never create related keys, so these attacks have no practical impact.

## 5.4 AES-128 or AES-256?

| Variant | Rounds | Classical security | Against quantum search | Typical use |
| --- | --- | --- | --- | --- |
| AES-128 | 10 | 128 bits | About 64 bits on paper, far more in practice | General-purpose encryption, TLS |
| AES-192 | 12 | 192 bits | About 96 bits | Rarely used |
| AES-256 | 14 | 256 bits | About 128 bits | Long-lived data, key wrapping |

Grover's algorithm (Chapter 44) lets a quantum computer search keys in roughly the square root of the usual time, which halves the effective key length on paper. In practice it parallelises badly and needs extraordinarily long, error-free computations, so AES-128 is not considered at real risk. The guidance has settled on a simple rule:

- Use **AES-256** for data that must stay confidential for decades, for keys that protect other keys, and wherever a regulation asks for it. The US NSA's CNSA 2.0 suite, for example, requires AES-256.
- **AES-128** remains sound for short-lived data such as most TLS sessions, and it is roughly 40 percent faster (10 rounds instead of 14).

When in doubt, choose AES-256. A single enterprise default is easier to defend to auditors than a matrix of exceptions.

## 5.5 Implementing AES safely: side channels

The mathematics of AES has held up for 25 years. Implementations have not always been so lucky. A **side-channel attack** learns secrets from how a computation behaves: how long it takes, how much power it draws, or what it leaves in the processor's cache.

The classic AES side channel is the **cache-timing attack**. Fast software AES uses lookup tables. Which entry is read depends on the data and the key, and whether that entry is in the cache changes the timing by a few nanoseconds. In 2005, researchers recovered full AES keys from a server over the network by measuring these differences across many requests.

There are two defences:

1. **Hardware AES instructions.** Almost every modern server and laptop processor runs each AES round as a single instruction, in constant time and with no tables. Mature libraries use them automatically.
2. **Bit-sliced, constant-time software** for processors without hardware support.

Physical side channels, such as power analysis and fault injection against smart cards and HSMs, need hardware countermeasures as well. Testing for these is part of what FIPS 140-3 and Common Criteria do (Chapter 40).

## 5.6 Where AES runs in the enterprise

AES is not one thing an organisation "has". It is implemented many times over, in components owned by different teams, each with its own keys and certification status.

### In the processor

Intel added **AES-NI** instructions to its processors from 2010, with a carry-less multiplication instruction (PCLMULQDQ) that accelerates the GCM mode described in Chapter 6. AMD followed, and 64-bit Arm processors, including the Arm-based server chips offered by all three hyperscalers, provide equivalent cryptography extensions. A single core can now encrypt several gigabytes per second, which is what made encrypting everything affordable.

Hardware acceleration can be lost silently. Old hypervisor CPU compatibility modes and some nested or emulated environments hide the AES flag from the guest, and throughput drops by an order of magnitude with no error. The lab in section 5.9 shows how to check.

### In hardware security modules

A **hardware security module (HSM)** is a tamper-resistant device that stores keys and performs cryptography inside a protected boundary (Chapter 33). General-purpose HSMs such as Thales Luna, Entrust nShield and Utimaco, and cloud services such as AWS CloudHSM, Azure Managed HSM and Google Cloud HSM, all implement AES. They rarely encrypt bulk data. Their AES work is mostly **key wrapping**, encrypting one key under another (Chapter 6), so that data keys can leave the HSM while the keys above them never do. Payment HSMs such as Thales payShield, Futurex and Utimaco Atalla use AES, and still 3DES, for PIN blocks and key blocks.

### In storage controllers, drives and tape

Most storage encryption happens below the operating system:

- **Self-encrypting drives (SEDs)** following the TCG Opal or Enterprise specifications encrypt every sector with an AES key generated inside the drive controller.
- **Enterprise arrays** from vendors such as NetApp, Dell and Pure Storage encrypt data at rest with AES-256, in the controllers or by managing SEDs, and can fetch key-encrypting keys from an external key manager over KMIP (Chapter 34). Architectures differ by product line; check each vendor's public documentation (as of 2026).
- **LTO tape drives**, from LTO-4 onwards, encrypt in the drive with AES-256-GCM, with keys supplied by backup software or a key manager.

### In the network

Switches implement **MACsec** (IEEE 802.1AE) with AES-GCM in port hardware, so data-centre links can be encrypted at line rate (Chapter 22). Load balancers, CDNs and service-mesh proxies rely on the processor instructions above.

> **At Meridian.** The PKI and Cryptography Services team keeps an "AES map" in the cryptographic inventory: every place AES is implemented, its owner and where its keys come from. Entries include the general-purpose HSM clusters in DC-East and DC-West (the team itself), the payment HSMs (Payments Security), the SAN arrays and tape library (Platform Engineering, keys from the enterprise key manager over KMIP), laptop disk encryption (the endpoint team), MACsec on the inter-DC dark fibre (Network Engineering) and managed encryption in the three clouds (Platform Engineering, keys in each cloud KMS). When GRC asks whether customer data is encrypted at rest, the map turns a vague yes into evidence.

## 5.7 Design decisions and compliance

Most AES decisions are made by choosing components rather than writing code. Ask of any product that claims AES:

- **Which mode?** GCM or XTS are normal; ECB is a red flag (Chapter 6).
- **Is the implementation validated?** A module with a FIPS 140-3 certificate has had its AES tested by NIST's Cryptographic Algorithm Validation Program and its boundary reviewed (Chapter 40). "Uses an approved algorithm" is a much weaker claim.
- **Where is the key generated and stored,** and can you rotate or destroy it?
- **Is hardware acceleration active** on every platform the software runs on?

> **Compliance hook.** AES with keys of 128 bits or more counts as strong cryptography for PCI DSS v4.0.1 (for example, Requirement 3.5.1 on rendering stored account data unreadable) and NIST SP 800-131A. ISO/IEC 27001:2022 control A.8.24 asks for a defined policy on algorithms and key lengths, which is where your AES-256 default belongs. Auditors usually ask for the algorithm and key length, the module's validation status and the key management procedures.

## 5.8 Other ciphers you will meet

| Cipher | Type | Status | Where you see it |
| --- | --- | --- | --- |
| ChaCha20 | Stream cipher | Recommended | TLS 1.3, WireGuard, SSH, devices without AES hardware |
| 3DES (TDEA) | 64-bit block cipher | Disallowed for new encryption | Legacy payment systems |
| Blowfish | 64-bit block cipher | Legacy | The bcrypt password hash |
| Camellia, ARIA, SM4 | Block ciphers | National standards | Regional compliance requirements |
| RC4 | Stream cipher | Broken | Very old systems only |

A **stream cipher** XORs the data with a pseudo-random stream generated from a key and a nonce. ChaCha20 is not FIPS-approved, which matters in regulated environments.

## 5.9 Lab: AES at the command line

You need OpenSSL 3 and Python 3 on an x86 Linux machine (on Apple silicon, skip step 2).

**1. Check that your processor advertises AES instructions.**

```bash
grep -o -m1 -w aes /proc/cpuinfo      # prints "aes" if present
```

**2. Measure hardware AES, then switch it off.** OpenSSL can mask CPU features on x86. This mask hides AES-NI and carry-less multiplication.

```bash
openssl speed -seconds 2 -bytes 16384 -evp aes-128-gcm
OPENSSL_ia32cap="~0x200000200000000" \
  openssl speed -seconds 2 -bytes 16384 -evp aes-128-gcm
```

On a typical modern machine the hardware path is well over ten times faster. That is what a guest loses when a hypervisor hides the AES flag.

**3. See why a raw block cipher leaks patterns.** Encrypt repeated 16-byte blocks in ECB mode:

```bash
python3 -c "print('YELLOW SUBMARINE'*8, end='')" > blocks.txt
openssl enc -aes-128-ecb -K 000102030405060708090a0b0c0d0e0f \
  -in blocks.txt | xxd
```

Every 16-byte line of output is identical, revealing that the input repeats.

**4. Now use a proper mode.** Encrypt the same file with CTR mode and a random IV:

```bash
openssl enc -aes-128-ctr -K 000102030405060708090a0b0c0d0e0f \
  -iv $(openssl rand -hex 16) -in blocks.txt | xxd
```

The output no longer repeats. Chapter 6 explains why, and why even this is not enough without integrity protection.

**Optional cloud extension.** Run step 2 on the smallest x86 and Arm instances your cloud provider offers and compare throughput. Small instances cost cents per hour, but terminate them afterwards to avoid charges.

## 5.10 Failure story: the encrypted penguin and the password database

The most famous image in cryptography teaching is a bitmap of Tux, the Linux penguin, encrypted with AES in ECB mode. Displayed as an image, the outline is clearly visible, because identical blocks of background colour encrypt identically.

The same mistake has appeared in real products. In 2013, a breach at a large software company exposed about 150 million user records in which passwords had been encrypted with 3DES in ECB mode instead of being hashed. Identical passwords produced identical ciphertext, and users' password hints were stored in plain text alongside. Attackers could group users who shared a password and guess it from the combined hints, without ever recovering the key.

The lessons: a strong cipher in the wrong mode leaks patterns; a 64-bit legacy cipher stayed in service long after better options existed, which is why inventory matters; and passwords should never be encrypted at all, but hashed with a dedicated password hashing function (Chapter 7).

## 5.11 Chapter summary

- A block cipher transforms fixed-size blocks under a key and should behave like a random permutation. On its own, it is not a complete encryption scheme.
- DES fell to brute force and 3DES to the birthday bound on its 64-bit block. AES was chosen through an open competition and has resisted attack for 25 years.
- AES rounds combine substitution, shifting, mixing and key addition to achieve confusion and diffusion.
- Prefer AES-256 for long-lived data and key protection; AES-128 remains sound for short-lived data.
- Side channels, not mathematics, are AES's practical weakness. Hardware instructions remove classic timing attacks and make bulk encryption cheap.
- In an enterprise, AES runs in processors, HSMs, drives, arrays, tape drives and switches, each owned by a different team.
- "Uses AES" says little. Ask about the mode, the key management and module validation.
