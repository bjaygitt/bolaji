## 35.1 What counts as a secret, and why secrets sprawl

A **secret** is any value that grants access or capability to whoever knows it:

- passwords for databases, service accounts and administrators
- API keys and access tokens for internal and third-party services
- cloud access keys
- private keys for TLS, SSH, signing and encryption
- webhook signing secrets, HMAC keys and session encryption keys
- connection strings that embed any of the above

Keys managed in a KMS or HSM (Chapters 28 and 33) are a special case: they never leave their protected boundary, and applications ask the KMS to use them. Most other secrets must be handed to the software that uses them, and that hand-off is where trouble starts.

Secrets spread because copying them is easy and every copy feels harmless. They end up hard-coded in source "temporarily", committed in configuration and `.env` files, baked into container images and VM templates, pasted into chat and tickets, stored as long-lived CI/CD variables, and printed in logs. This is **secret sprawl**.

Once in a Git repository, a secret is effectively permanent: deleting the file does not remove it from history, forks or clones. Attackers scan public repositories continuously, and leaked cloud keys are often abused within minutes of being pushed. Industry studies by secret-scanning vendors have counted tens of millions of secrets leaked to public repositories in a single year, with a large share still valid long after.

> **In practice.** Treat any secret that has appeared in a repository, image, ticket or log as compromised. Revoke and replace it first; clean up history second.

## 35.2 What a secrets manager does

A **secrets manager** is a hardened service that stores secrets encrypted, controls access to them by identity and policy, records every read, and supports rotation. Think of it as the counterpart of the key manager in Chapter 34: a key manager mostly protects keys that encrypt data, while a secrets manager protects credentials that grant access.

| Feature | Why it matters |
| --- | --- |
| Encryption at rest under a KMS or HSM key | Storage compromise does not reveal secrets |
| Identity-based access policies | Each workload reads only its own secrets |
| Audit log of every read and change | You can answer "who accessed this, and when?" |
| Versioning | Roll a secret forward or back without breaking consumers |
| Rotation support | Change secrets on a schedule or on demand |
| Leases and expiry | Secrets that expire on their own |
| Dynamic secrets | Credentials created on demand, per consumer (section 35.7) |
| High availability and replication | It becomes a dependency of every service |

Encryption at rest is almost always **envelope encryption** (Chapter 6): each secret, or the store as a whole, is encrypted with a data key, and the data key is wrapped by a master key in a KMS or HSM. Compromise of the database alone yields ciphertext.

## 35.3 The products side by side

As of 2026, five families cover most enterprise deployments. They overlap but were born for different jobs.

### HashiCorp Vault and OpenBao

**HashiCorp Vault** is a general secrets platform, self-managed or offered as a managed service, and since early 2025 part of IBM. Its building blocks are:

- **Secrets engines**, plug-ins that store or generate secrets: key-value (KV), database, cloud credentials, PKI (Chapter 15), SSH, transit (encryption as a service) and, in the Enterprise edition, KMIP.
- **Auth methods**, which verify a client's identity and map it to policies: Kubernetes service accounts, JWT and OIDC, cloud instance identity, TLS certificates, AppRole and human logins.
- **Leases**: every dynamic secret has a time to live and can be renewed or revoked.
- **Seal and unseal**: Vault's storage is encrypted under a root key that is itself protected either by Shamir key shares held by custodians or by **auto-unseal** through a cloud KMS or HSM.

In 2023 HashiCorp moved Vault to a source-available licence, and the community created **OpenBao**, an open-source fork hosted by the Linux Foundation. OpenBao keeps the same core model and API, so most of this chapter applies to both.

### CyberArk Conjur and Secrets Hub

CyberArk, a privileged access management (PAM) vendor that became part of Palo Alto Networks in February 2026, offers two secrets products alongside its vault for human privileged accounts.

- **Conjur** is a secrets manager for applications and machines, available as open source, self-hosted enterprise and SaaS editions. Access is defined in declarative policy files, and workloads authenticate through **authenticators** for Kubernetes, JWT (for CI systems), and the AWS, Azure and Google identity services.
- **Secrets Hub** takes a different approach. Instead of asking developers to call another API, it synchronises secrets from the CyberArk PAM vault into the cloud-native stores (AWS Secrets Manager, Azure Key Vault and Google Secret Manager), where developers already read them. The PAM vault stays the source of truth and handles rotation, while applications use native cloud SDKs.

### The cloud secret stores

| Capability | AWS Secrets Manager | Azure Key Vault | Google Secret Manager |
| --- | --- | --- | --- |
| Encryption | AWS KMS key, AWS-managed or customer-managed | Service-managed HSM-backed keys; secrets, keys and certificates in one vault | Google-managed or customer-managed (Cloud KMS) keys |
| Access control | IAM policies plus resource policies on each secret | Azure RBAC (recommended) or legacy access policies | IAM on each secret |
| Rotation | Built in: Lambda rotation functions, and managed rotation for some AWS services | Event Grid events on near-expiry; you build rotation with a function | Rotation schedules publish Pub/Sub notifications; you build the rotation |
| Replication | Cross-region replicas | Paired region and backup | Automatic or user-managed replication; regional secrets |
| Protection | Recovery window before deletion | Soft delete (mandatory) and purge protection | Version disable and destroy |
| Workload auth | IAM roles for compute | Managed identities | Service accounts |

AWS also offers **Parameter Store** within Systems Manager, a cheaper store for configuration that supports encrypted SecureString parameters but has fewer rotation features.

### Others

**Akeyless** offers SaaS secrets management with a distributed key design, **Doppler** and **Infisical** target developer workflows, and **1Password** and **Bitwarden** offer secrets products that extend from their password managers. Kubernetes-native options are covered in section 35.4.

### Choosing

- If your workloads live in one cloud, its native store is usually the simplest and best-integrated option.
- If you span clouds and data centres, a platform such as Vault, OpenBao or Conjur gives you one policy model and dynamic secrets everywhere, at the cost of running a critical service.
- If your PAM vault already rotates privileged credentials, a sync model such as Secrets Hub avoids a second source of truth.

> **At Meridian.** Meridian runs a self-managed secrets platform cluster across DC-East and DC-West for on-premises workloads and the on-premises Kubernetes platform, auto-unsealed by the general-purpose HSMs. Cloud workloads use each cloud's native secret store. Privileged credentials for databases, the mainframe and network devices stay in the PAM vault, which synchronises a short list of them into the cloud stores. The PKI and Cryptography Services team owns the secrets platform; IAM owns PAM; Platform Engineering owns the Kubernetes integrations.

## 35.4 Getting secrets to applications

Storing secrets centrally solves half the problem. Delivery is the other half.

- **API or SDK at start-up**, keeping the secret only in memory. Preferred: nothing on disk, and the application can refresh when the secret rotates.
- **Agent or sidecar** that authenticates, fetches secrets and writes them to a memory-backed file, refreshing on rotation. Examples are Vault Agent, the AWS Secrets Manager Agent and Conjur's sidecar injectors. Useful for applications you cannot change.
- **Environment variables.** Common but weaker: they leak into crash reports, child processes and debugging tools, and they never refresh without a restart.

### Kubernetes

A **Kubernetes Secret** is an API object whose values are only base64-encoded, which is encoding, not encryption. By default it is stored in etcd as-is. Three steps make it acceptable:

1. Enable **encryption at rest** for etcd with a KMS provider, so Secrets are envelope-encrypted under a key in your KMS or HSM. The KMS v2 provider is stable since Kubernetes 1.29.
2. Restrict RBAC so that only the workload's service account can read its Secrets. Anyone who can create a pod in a namespace can usually mount any Secret in it.
3. Keep the source of truth outside the cluster.

For step 3, two open-source tools dominate:

- **External Secrets Operator (ESO)** defines `SecretStore` and `ExternalSecret` resources. It authenticates to an external manager (Vault, OpenBao, Conjur, the three cloud stores and many more), fetches the values, and writes ordinary Kubernetes Secrets, refreshing them on a schedule. Applications need no change.
- The **Secrets Store CSI Driver** mounts secrets from an external store directly into a pod as files, with providers for Vault, AWS, Azure and Google. It can avoid creating a Kubernetes Secret at all.

Vault also offers its own agent injector and a Vault Secrets Operator. Chapter 24 covers the platform side of Kubernetes encryption.

### GitOps

When configuration lives in Git, tools such as **SOPS** (which encrypts values in YAML or JSON with a KMS, age or PGP key) and **Sealed Secrets** (which encrypts with a key held by a controller in the cluster) let the encrypted file live in the repository. Only authorised deployment systems can decrypt. ESO is the alternative: Git holds only a reference, never the secret.

## 35.5 Secrets management and PAM

**Privileged access management (PAM)** grew up protecting human administrators: it vaults the passwords of domain administrators, root accounts and database administrators, checks them out to approved people, records sessions, and rotates the password after use. Products include CyberArk, Delinea, BeyondTrust and One Identity.

Secrets management grew up protecting machines: CI pipelines, microservices and scripts that need credentials thousands of times a day without a human in the loop.

The two meet in the middle, and the boundary needs a deliberate decision.

| Question | PAM | Secrets manager |
| --- | --- | --- |
| Who uses the credential? | People, through check-out | Software, through APIs |
| Typical frequency | A few times a day | Thousands of times a second |
| Key controls | Approval, session recording, check-in rotation | Workload authentication, short leases, audit |
| Typical secrets | Domain admin, root, DBA, network device credentials | Application database users, API keys, cloud credentials |

Two patterns cause trouble. The first is applications reading human-style privileged accounts from the PAM vault at high volume, which PAM products were not designed for and which concentrates enormous privilege in one application credential. The second is engineers storing human administrator passwords in a developer secrets manager with no session controls or approval. Decide which system owns which class of credential, and where both must hold the same credential, use a synchronisation pattern with one source of truth.

> **Watch out.** The PAM vault and the secrets manager are the most valuable targets in your environment. The credential that authenticates to them, and the people who administer them, deserve the strongest protection you have: phishing-resistant MFA (Chapter 16), quorum for policy changes, and no stored copies in scripts. Section 35.11 shows what happens otherwise.

## 35.6 Rotation

Every static secret should have an owner, a rotation schedule and a tested rotation procedure. Rotation without downtime usually follows a three-step pattern:

1. Create the new secret and make it valid **alongside** the old one, for example a database user with two valid passwords, or two active API keys.
2. Update every consumer to use the new secret, and verify.
3. Revoke the old secret.

AWS Secrets Manager's rotation functions follow this pattern explicitly, and its "alternating users" strategy keeps two database users so one is always valid. Systems that allow only one valid credential at a time force a risky cut-over, and are a common reason rotation is postponed forever. Prefer systems that support overlapping credentials, and record the ones that do not as exceptions with an owner.

## 35.7 Dynamic secrets and short-lived credentials

The strongest way to reduce secret risk is to stop having long-lived secrets at all.

**Dynamic secrets** are created on demand for one consumer and expire automatically. When an application starts, it asks the secrets manager for database credentials; the secrets manager creates a new database user with exactly the needed permissions and a lease of, say, one hour, renews it while the application runs, and deletes the user when the lease ends. The benefits:

- Every credential is unique, so the audit trail shows exactly which instance did what.
- A leaked credential expires on its own, usually before anyone could use it.
- There is nothing to rotate, because nothing lives long enough.

Vault and OpenBao offer dynamic secrets for databases, cloud providers, message brokers and more; Conjur and the cloud stores lean more on rotation of static secrets plus native workload identity.

The same principle appears throughout this book: SSH certificates valid for hours (Chapter 25), TLS certificates valid for days (Chapter 18), OAuth access tokens valid for minutes (Chapter 16). Short lifetimes are the most reliable revocation mechanism there is.

## 35.8 Workload identity: replacing secrets with identity

### The secret zero problem

To read secrets, an application must authenticate to the secrets manager, which seems to need a secret of its own. This is **secret zero**. If you solve it by giving the application a static token, you have moved the problem rather than solved it.

The answer is **workload identity**: authenticate with something the platform already proves about the workload. A cloud VM has an instance identity signed by the provider. A Kubernetes pod has a service account token signed by the cluster. A CI job has a token signed by the CI platform. These identities are issued, scoped and rotated by the platform, so no human ever handles them.

### Cloud workload identity and OIDC federation

Each cloud gives its own compute an identity and issues short-lived credentials for it automatically: IAM roles in AWS, managed identities in Azure, service accounts in Google Cloud. Kubernetes services in each cloud extend this to pods (for example EKS Pod Identity and IAM roles for service accounts, AKS Workload Identity, and GKE Workload Identity Federation).

Across platforms, **workload identity federation** connects them using OpenID Connect (Chapter 16). The flow:

1. The workload's platform (a CI system, a Kubernetes cluster, another cloud) issues a signed OIDC token describing the workload: issuer, audience, and subject claims such as repository, branch and environment.
2. The workload presents that token to the target cloud's security token service.
3. The cloud fetches the issuer's public keys from its OIDC discovery document, validates the signature, and checks the token against a **trust policy**.
4. If it matches, the cloud returns credentials valid for an hour or less.

AWS calls the call `AssumeRoleWithWebIdentity`, Azure uses federated identity credentials on an app registration or managed identity, and Google uses workload identity pools and providers. For on-premises servers without an OIDC issuer, AWS IAM Roles Anywhere accepts X.509 certificates from your own CA instead.

Federation has removed long-lived cloud keys from many CI/CD pipelines, but the trust policy is now the security boundary. It must check the issuer, the audience and the specific subject. A trust policy for a GitHub Actions deployment to AWS looks like this:

```json
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub":
        "repo:meridian-example/payments-api:environment:prod"
    }
  }
}
```

> **Watch out.** A trust policy that checks only the issuer and audience lets every workflow in every repository on the same CI platform assume the role. Wildcards in the subject (`repo:*`) have the same effect. Review every federated trust policy, and alert on any new one.

### SPIFFE and SPIRE

**SPIFFE** (Secure Production Identity Framework for Everyone), a graduated Cloud Native Computing Foundation project, standardises workload identity across platforms:

- Every workload gets a **SPIFFE ID**, a URI such as `spiffe://meridian.example/payments/api`.
- The identity is delivered as an **SVID** (SPIFFE Verifiable Identity Document): a short-lived X.509 certificate for mTLS, or a JWT.
- **SPIRE**, the reference implementation, **attests** each workload before issuing an SVID, checking evidence about the node it runs on (for example its cloud instance identity or TPM) and the workload itself (for example its Kubernetes namespace and service account), and rotates SVIDs automatically, typically every hour or less.

SPIRE can publish an OIDC discovery document for its JWT-SVIDs, so the same federation pattern lets a SPIFFE-identified workload on premises obtain cloud credentials, or authenticate to Vault or Conjur, without any stored secret. Chapter 24 covers SPIFFE's role in service meshes and service-to-service mTLS.

> **At Meridian.** Meridian's CI platform deploys to all three clouds through OIDC federation, with trust policies pinned to repository and protected environment, and no cloud access keys exist in CI. On-premises Kubernetes workloads authenticate to the secrets platform with their service account tokens. The payments platform uses SPIRE-issued SVIDs for mTLS between services, and Payments Security reviews every new SPIFFE ID registration in its namespace.

## 35.9 Detecting and responding to leaks

Even with good practices, secrets leak. Layer detection:

- **Pre-commit and CI scanning** for secret patterns before code is pushed (gitleaks, TruffleHog, detect-secrets).
- **Repository and image scanning** across history and registries.
- **Platform push protection**: major code-hosting platforms block pushes containing recognised secrets and notify issuers, many of whom revoke leaked keys automatically.
- **Honeytokens**: fake credentials placed where attackers look, which alert when used.
- **Anomaly detection** on secrets manager and cloud audit logs: unusual readers, unusual volumes, reads from new networks.

Prepare the response before you need it: for each class of secret, a runbook that says how to revoke, replace and verify, who owns it, and how to find every place it was used. Chapter 43 places these runbooks in the wider incident playbook set.

> **Compliance hook.** Central secrets management with audit supports PCI DSS v4.0.1 Requirement 8.6 (management of system and application accounts, including protecting their passwords against misuse and changing them periodically), Requirement 8.3 (strong authentication), and Requirement 10 (logging access). It also maps to ISO/IEC 27001 Annex A controls 5.17 (authentication information) and 8.24 (use of cryptography), NIST SP 800-53 IA-5 (authenticator management), and SOX access control testing for financially significant systems.

## 35.10 Lab: from static secret to dynamic credentials to Kubernetes

You need Docker, the `vault` CLI (or `bao` from OpenBao, with identical commands), `kind`, `kubectl`, `helm` and `gitleaks`.

1. **Start Vault in dev mode**, listening on all interfaces so the kind cluster can reach it. Dev mode is in memory and insecure; never use it for real secrets.

```bash
vault server -dev -dev-root-token-id=root \
  -dev-listen-address=0.0.0.0:8200 &
export VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=root
vault kv put secret/payments/db password='Static-Pa55'
vault kv get secret/payments/db
```

2. **Dynamic database credentials.** Start PostgreSQL and configure the database secrets engine with a read-only role and a one-hour lease.

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=adminpw \
  -p 5432:5432 postgres:16
vault secrets enable database
vault write database/config/pg \
  plugin_name=postgresql-database-plugin allowed_roles=readonly \
  connection_url="postgresql://{{username}}:{{password}}@127.0.0.1:5432/postgres?sslmode=disable" \
  username=postgres password=adminpw
vault write database/roles/readonly db_name=pg \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN \
PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; \
GRANT pg_read_all_data TO \"{{name}}\";" \
  default_ttl=1h max_ttl=24h
vault read database/creds/readonly
vault read database/creds/readonly
```

3. Note the two different usernames. Connect with one using `psql`, then revoke all leases and confirm the users are gone.

```bash
vault lease revoke -prefix database/creds/readonly
docker exec pg psql -U postgres -c '\du'
```

4. **Sync into Kubernetes with External Secrets Operator.** Create a kind cluster, install ESO, and store the Vault token in a Kubernetes Secret (acceptable in a lab; in production use the Kubernetes auth method instead).

```bash
kind create cluster --name secrets-lab
helm repo add external-secrets https://charts.external-secrets.io
helm install external-secrets external-secrets/external-secrets \
  -n external-secrets --create-namespace --wait
kubectl create secret generic vault-token --from-literal=token=root
docker network inspect kind -f '{{(index .IPAM.Config 0).Gateway}}'
```

5. Apply a `SecretStore` and an `ExternalSecret`, replacing `172.18.0.1` with the gateway address printed above. Older ESO releases use `apiVersion: external-secrets.io/v1beta1`.

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: vault
spec:
  provider:
    vault:
      server: "http://172.18.0.1:8200"
      path: "secret"
      version: "v2"
      auth:
        tokenSecretRef:
          name: vault-token
          key: token
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: payments-db
spec:
  refreshInterval: 1m
  secretStoreRef:
    name: vault
    kind: SecretStore
  target:
    name: payments-db
  data:
    - secretKey: password
      remoteRef:
        key: payments/db
        property: password
```

6. Read the synced Secret, then change the value in Vault and watch it update within a minute.

```bash
kubectl get secret payments-db -o jsonpath='{.data.password}' \
  | base64 -d
vault kv put secret/payments/db password='Rotated-Pa55'
```

7. **Scan for leaks.** Create a test repository, commit a fake AWS-style key in a file, delete the file in a second commit, and run `gitleaks detect` against the repository. Note that the scanner still finds it in history.

**Optional cloud extension.** Configure GitHub Actions OIDC federation to an AWS role with a trust policy like the one in section 35.8, run a workflow that calls `aws sts get-caller-identity`, then change the branch in the subject condition and watch the next run fail. Cost warning: IAM and STS are free, but anything the role is allowed to create is billed; scope it to read-only actions and delete the role and OIDC provider when done.

## 35.11 Failure story: the script with keys to the vault

In September 2022, a ride-sharing company disclosed a breach that began with social engineering. According to the company's own update, an attacker obtained a contractor's password, probably bought from a criminal marketplace after malware on the contractor's personal device, and then sent repeated multi-factor approval requests until the contractor accepted one. From there the attacker reached several employee accounts and elevated permissions to tools including the company's collaboration suite and messaging platform.

Screenshots the attacker shared, widely reported at the time, showed how the access spread: on an internal network share the attacker found PowerShell scripts, one of which contained hard-coded administrator credentials for the company's privileged access management system, the very system meant to protect secrets. With those, the attacker claimed access to cloud consoles, internal tools and security systems.

The pattern is common: a single long-lived secret, stored where many people could read it, unlocks the vault that holds every other secret. The defences are the ones in this chapter:

- no secrets in scripts or shares, and scanning to find the ones that slip through
- the strongest authentication for the PAM and secrets platforms themselves, with no stored administrator credentials
- phishing-resistant authentication for people (Chapter 16), which defeats push-fatigue attacks
- workload identity and short-lived credentials, so the most powerful access is never a static string someone can copy

## 35.12 Chapter summary

- Secrets sprawl into code, images, CI systems, logs and chat; leaked secrets are exploited within minutes and must be treated as compromised.
- A secrets manager stores secrets under envelope encryption, enforces identity-based access, audits every read and supports rotation, leases and replication.
- Vault and OpenBao, CyberArk Conjur and Secrets Hub, and the AWS, Azure and Google secret stores differ in scope, rotation features and operating model; choose by footprint and existing PAM investment.
- Deliver secrets in memory through APIs or agents; in Kubernetes, encrypt etcd with a KMS provider, restrict RBAC and keep the source of truth outside the cluster with ESO or the CSI driver.
- PAM protects human privileged access; secrets management protects machine access. Decide which owns each credential class, and protect both as tier-zero systems.
- Rotate with overlapping credentials; dynamic secrets and short lifetimes remove rotation and limit leak damage.
- Workload identity and OIDC federation solve secret zero, but the trust policy becomes the boundary and must check issuer, audience and subject.
- SPIFFE and SPIRE give attested, short-lived identities across platforms and can federate to clouds and secrets managers.
