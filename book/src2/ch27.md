## 27.1 Why encrypt above the storage layer

Chapter 26 showed that storage encryption protects data from people who obtain the media without the running system. Inside a database server, that leaves a large group of people and programs who see plaintext:

- **Database administrators**, who can query any table.
- **Anyone holding a privileged database account**, including an attacker who has stolen one.
- **The application's own database account**, which a SQL injection flaw hands to the attacker.
- **Backup and replication processes**, which write copies of the data elsewhere.
- **Support staff and tools** with access to data files, logs and memory dumps.

Database and application-layer encryption narrow that group. The design question at each step up is the same: **who holds the key, and where does decryption happen?** If the database decrypts, everyone the database trusts can read the data. If only the application decrypts, the database and its administrators hold ciphertext. If only the end user's client decrypts, even the application servers do not see plaintext.

Each step up costs something: lost query capability, more complex key management, and changes to application code. The art is to apply the higher layers to the small set of fields that justify them, such as card numbers, national identifiers, health data and authentication secrets, and leave the rest to storage and database encryption.

## 27.2 Transparent data encryption

**Transparent data encryption (TDE)** is encryption performed by the database engine as it writes pages to disk and reverses as it reads them into memory. It is "transparent" because applications and queries are unchanged: a `SELECT` returns plaintext to any authorised session.

All TDE implementations share a two-tier key hierarchy:

1. **Data encryption keys** (per database, tablespace or table) encrypt the pages. They are stored, wrapped, inside the database files or headers.
2. A **master key** (also called the TDE master encryption key or protector) wraps the data keys. It is held outside the data files: in a local keystore, an HSM, an enterprise key manager or a cloud KMS.

Rotating the master key re-wraps the small data keys and is quick; rotating the data keys means re-encrypting the data. TDE protects data files, transaction logs, temporary files and (usually) backups taken by the database's own tools. It does not protect anything returned by a query.

### Oracle

**Oracle TDE** encrypts either whole tablespaces or individual columns. Tablespace encryption is the recommended default because indexes and range scans work normally. The master key lives in a **keystore**: a software wallet file, an HSM through PKCS#11, **Oracle Key Vault** (Oracle's own key manager, which also speaks KMIP), or OCI Vault for databases in Oracle's cloud. In multitenant databases, each pluggable database can have its own keystore in **isolated mode**, which matters when tenants require separate keys.

### Microsoft SQL Server

**SQL Server TDE** encrypts a whole database with a **database encryption key (DEK)** stored in the database boot record. The DEK is protected by a certificate in the `master` database (which is itself protected by the service master key) or by an asymmetric key held in an **Extensible Key Management (EKM)** provider, such as the connector for Azure Key Vault or an HSM vendor's EKM module. Enabling TDE on any database also encrypts `tempdb`. In Azure SQL Database and Azure SQL Managed Instance, TDE is on by default for new databases, with either a service-managed key or a customer-managed key in Key Vault or Managed HSM.

The classic SQL Server failure is operational: a database restored on another server is unreadable because nobody backed up the TDE certificate and its private key.

### PostgreSQL

Community PostgreSQL, as of 2026, has no built-in TDE. Options are:

- **Percona's pg_tde**, an open-source extension that reached general availability in 2025 for Percona's distribution, encrypting tables, indexes and the write-ahead log, with keys from Vault, OpenBao or KMIP key managers.
- **Commercial distributions** such as EDB Postgres Advanced Server and others that add TDE.
- **Managed services** (Amazon RDS and Aurora, Azure Database for PostgreSQL, Google Cloud SQL and AlloyDB), which encrypt the underlying storage with the cloud KMS. This is storage-layer encryption with a customer-managed key option, not TDE inside the engine, but it addresses the same threat.
- **Volume encryption** with LUKS under a self-managed server.

### MySQL and MariaDB

**MySQL InnoDB data-at-rest encryption** encrypts tablespaces, redo and undo logs and binary logs. Each tablespace key is wrapped by a master key supplied by a **keyring component**. The community edition includes a file-based keyring; MySQL Enterprise Edition adds keyrings for KMIP servers, Oracle Key Vault, AWS KMS and HashiCorp Vault. MariaDB has its own encryption with key management plugins, including file, AWS KMS and Vault options.

| Database (as of 2026) | Native TDE scope | Master key options |
| --- | --- | --- |
| **Oracle** | Tablespace or column | Wallet, HSM (PKCS#11), Oracle Key Vault, OCI Vault |
| **SQL Server** | Whole database, plus `tempdb` | Certificate in `master`, EKM provider (HSM, Azure Key Vault) |
| **PostgreSQL** | None in community; extensions and distributions add it | Depends on extension: Vault, OpenBao, KMIP |
| **MySQL** | Tablespaces, redo, undo, binary logs | Keyring components: file (community); KMIP, Oracle Key Vault, AWS KMS, Vault (Enterprise) |

> **Watch out.** TDE is the most over-credited control in database security. Auditors see "TDE enabled" and tick encryption at rest; attackers run queries through the application account and receive plaintext. TDE addresses stolen files and backups. It is worth having everywhere, but it does nothing against SQL injection, stolen credentials or a rogue DBA.

## 27.3 Column- and field-level encryption

**Column-level encryption** encrypts selected columns rather than whole files. It comes in two very different forms, and confusing them is a common design error.

**Server-side column encryption** uses database functions or features: Oracle TDE column encryption, SQL Server cell-level encryption with `ENCRYPTBYKEY`, PostgreSQL's `pgcrypto` extension, MySQL's `AES_ENCRYPT`. The database holds or receives the key, so a DBA or anyone who can run queries with the right privileges can still decrypt. It also tends to leak keys: with `pgcrypto`, the key is often passed as a literal in the SQL statement, where it lands in query logs and monitoring tools.

**Client-side field-level encryption** encrypts in the application or the database driver before data is sent. The database stores ciphertext and never sees the key. This is the form that defeats DBAs, SQL injection through other accounts, and database backups taken by anyone. Its price is that the database cannot compute on the ciphertext: no sorting, no range queries, no `LIKE`, and equality only if you deliberately allow it.

The rest of this chapter is about the second form, because it is the one that changes who can read the data.

## 27.4 SQL Server Always Encrypted

**Always Encrypted** is Microsoft's client-side encryption for SQL Server and Azure SQL. It uses two keys:

- A **column encryption key (CEK)** encrypts data in one or more columns. The database stores it only in wrapped form.
- A **column master key (CMK)** wraps the CEKs. It lives outside the database: in the Windows certificate store, Azure Key Vault or Managed HSM, or an HSM through CNG or a custom provider. The database stores only metadata saying where the CMK is.

The client driver (ADO.NET, JDBC, ODBC and others) does the work. When the application sends a parameterised query, the driver asks the server which parameters target encrypted columns, fetches and unwraps the CEK using the CMK, encrypts the parameters, and decrypts results. Applications change little beyond a connection-string setting and the use of parameters.

Each column chooses one of two encryption types:

- **Deterministic:** the same plaintext always yields the same ciphertext, so the server can do equality lookups, joins and grouping. The cost is leakage: anyone who can see the column learns which rows share a value, and low-cardinality columns (gender, country, status) can often be decoded by frequency.
- **Randomised:** every encryption is different, which leaks nothing about equality but supports no server-side operations.

**Always Encrypted with secure enclaves**, introduced in SQL Server 2019 and available in Azure SQL, adds a protected region of memory in the database server, using virtualisation-based security on Windows or Intel SGX in some Azure configurations. After the client verifies the enclave through attestation, it lets the enclave use the CEK, and the enclave can then evaluate range comparisons, pattern matching and sorting on randomised columns, and encrypt existing columns in place without moving the data out. The trust model shifts: you now trust the enclave and its attestation service (Chapter 30) instead of only the client.

> **In practice.** Always Encrypted protects against DBAs only if DBAs cannot reach the CMK. Put the CMK in a key vault or HSM whose access is granted to application identities, not to database administrators, and separate the people who provision keys from the people who run the database. Microsoft's guidance makes this role separation explicit.

## 27.5 MongoDB Queryable Encryption

MongoDB offers two client-side schemes. **Client-Side Field Level Encryption (CSFLE)** encrypts chosen fields in the driver, deterministically (for equality queries) or randomly. **Queryable Encryption**, generally available since MongoDB 7.0, goes further: it encrypts fields randomly yet still supports **equality queries**, and since 8.0 **range queries**, by having the client generate encrypted search tokens and the server maintain encrypted metadata collections that it can match without decrypting. MongoDB 8.2 added prefix, suffix and substring queries as a public preview, with a warning that the preview format will not be compatible with the eventual release.

Queryable Encryption rests on research in **structured encryption** and was designed to leak less than deterministic encryption: the server does not see which stored values are equal until queries reveal it. It still leaks something, such as the pattern of which documents match each query and, over time, information about the distribution of queried values. It also costs storage for the metadata collections and needs a field-by-field encryption schema decided in advance, since each field supports one query type.

Keys follow the usual envelope pattern. Each field has a **data encryption key** stored in a key vault collection, wrapped by a **customer master key** in AWS KMS, Azure Key Vault, Google Cloud KMS, or any KMIP-compliant key manager.

Comparable features exist elsewhere: cloud data warehouses offer client-side or column-level encryption with KMS keys, and products such as CipherStash and various database proxies provide searchable encryption for PostgreSQL. Evaluate each against the leakage questions in section 27.8.

## 27.6 Client-side and envelope encryption done right

Many teams build field encryption in their own code. Done well, it is the strongest layer in this chapter. Done badly, it gives the appearance of protection with none of the substance. The following rules come from repeated failures.

1. **Use a maintained library, not raw primitives.** The AWS Encryption SDK, Google's **Tink**, the Azure SDK's client-side encryption and libsodium handle nonces, key wrapping and message formats for you. Hand-rolled code is where nonce reuse and unauthenticated modes appear.
2. **Use authenticated encryption.** AES-GCM or ChaCha20-Poly1305 (Chapter 6). An unauthenticated mode lets an attacker who can write to the database alter ciphertext undetected.
3. **Bind ciphertext to its context with associated data.** Include the table, column and record identifier as **additional authenticated data (AAD)**. Otherwise an attacker with write access can copy an encrypted salary or card number from one row to another, and it will decrypt happily. Cloud KMS **encryption context** applies the same idea to wrapped keys.
4. **Use envelope encryption.** Generate data keys locally or from the KMS, encrypt data with them, and store each data key wrapped by a KMS key next to the ciphertext. Cache data keys briefly to control KMS cost and latency, but bound the cache by time and message count.
5. **Store a key identifier and format version with every ciphertext.** Rotation, migration to new algorithms (including post-quantum key wrapping, Chapter 46) and incident response all depend on knowing which key and which format produced each value.
6. **Keep keys out of the database and out of logs.** Application identities reach the KMS; DBAs do not.
7. **Plan rotation and re-encryption from the start.** Rotating the KMS key re-wraps data keys cheaply; rotating data keys requires a background re-encryption job that reads, decrypts and rewrites rows.

A minimal sketch in Python shows rules 2 and 3. The record ID is bound as AAD, so moving the ciphertext to another row fails.

```python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

dek = AESGCM.generate_key(bit_length=256)  # wrap with KMS in practice
aead = AESGCM(dek)

def enc(value: str, table: str, row_id: str) -> bytes:
    nonce = os.urandom(12)
    aad = f"{table}:{row_id}".encode()
    return nonce + aead.encrypt(nonce, value.encode(), aad)

def dec(blob: bytes, table: str, row_id: str) -> str:
    aad = f"{table}:{row_id}".encode()
    return aead.decrypt(blob[:12], blob[12:], aad).decode()

c = enc("4111111111111111", "cards", "row-42")
print(dec(c, "cards", "row-42"))  # works
dec(c, "cards", "row-43")         # raises InvalidTag
```

To find records by an encrypted field (for example, a customer by national ID), store a **blind index**: an HMAC of the normalised value under a separate key. The database can match the HMAC for equality without learning the value, with the same frequency leakage as deterministic encryption.

> **At Meridian.** Meridian's application teams do not write cryptographic code directly. The PKI and Cryptography Services team publishes an internal "field encryption" library, a thin wrapper over a well-known open-source library, that enforces AES-256-GCM, record-ID binding as AAD, a versioned ciphertext header with key ID, and data keys wrapped by each cloud's KMS or, on-premises, by the enterprise key manager. Its use is mandatory for fields classified as "restricted", and a static analysis rule flags direct imports of low-level cipher APIs in application repositories.

## 27.7 Tokenisation versus format-preserving encryption

Some systems cannot store ciphertext. A 16-digit card number field, a mainframe record layout or a partner's file format may reject a 60-byte base64 string. Two techniques produce substitute values that fit.

**Tokenisation** replaces a sensitive value with a random **token** of the same format and stores the mapping in a secure **token vault**. The token has no mathematical relationship to the original: without the vault, it reveals nothing. **Vaultless tokenisation** products instead derive tokens with keyed functions or precomputed random tables, avoiding a central database at the cost of being, in effect, a form of encryption.

**Format-preserving encryption (FPE)** encrypts a value into another value of the same format, so a 16-digit number encrypts to a 16-digit number. NIST SP 800-38G specifies the **FF1** mode (and FF3-1); FF3 was weakened by published attacks and revised to FF3-1, which later research has also weakened, so FF1 is the safer choice. FPE needs no vault, only a key, and decryption is a computation rather than a lookup.

| Question | Tokenisation (vaulted) | Format-preserving encryption |
| --- | --- | --- |
| What does a stolen token or ciphertext reveal? | Nothing without the vault | Nothing without the key, assuming a sound mode |
| What must be protected? | The vault database and its access | The key, usually in an HSM or KMS |
| Scale and latency | Vault lookups; vault grows with distinct values | Pure computation; scales horizontally |
| Reversibility across organisations | Only via the vault owner | Anyone given the key |
| Compliance scope (PCI DSS) | Systems holding only tokens can often be removed from scope | Systems holding ciphertext may stay in scope if they can reach the key |
| Small domains | Fine | Weak for very short values; FF1 requires a minimum domain size |

Products in this space include the tokenisation services of payment processors and card networks (network tokens, Chapter 39), data security platforms such as Thales CipherTrust, Protegrity, Voltage (OpenText) and Fortanix, and cloud services such as Google's Sensitive Data Protection, which offers FPE and deterministic tokenisation.

The decision usually turns on who needs to reverse the value. If almost nobody does (analytics, testing, most downstream systems), tokenisation removes those systems from risk and from audit scope. If many distributed systems must reverse values at high volume, FPE with a well-guarded key avoids a vault bottleneck.

## 27.8 Searchable encryption trade-offs

Every scheme that lets a server query encrypted data without the key leaks something. The question is how much, and whether the attacker you care about can exploit it.

| Technique | Queries supported | What the server learns |
| --- | --- | --- |
| **Randomised encryption** | None | Only sizes and access patterns |
| **Deterministic encryption, blind indexes** | Equality | Which records share a value; frequencies |
| **Order-preserving or order-revealing encryption** | Range, sorting | Order of all values; often approximate values |
| **Structured encryption (for example, Queryable Encryption)** | Equality, range, some text | Query results and access patterns over time |
| **Trusted execution (enclaves)** | Most SQL | Nothing beyond the enclave, if the enclave is sound |
| **Fully homomorphic encryption** | Arbitrary, slowly | Nothing (Chapter 31) |

The research record is sobering. In 2015, Naveed, Kamara and Wright showed that frequency analysis and sorting attacks recovered large fractions of deterministically encrypted and order-preserving encrypted fields in realistic medical databases, using only public auxiliary data. Later work extended such **leakage-abuse attacks** to range queries and access patterns.

Practical guidance follows:

- Use deterministic encryption or blind indexes only on high-cardinality fields with roughly uniform values (account numbers, national identifiers), never on low-cardinality ones.
- Avoid order-preserving encryption for anything sensitive.
- Consider the attacker: leakage matters against a persistent attacker who watches queries over time, much less against one who steals a single backup.
- Where rich queries on sensitive data are essential, enclaves or a separate, tightly controlled analytics environment are often more honest than a leaky scheme.

## 27.9 What each layer protects against

The table below is the one to show auditors and executives. It answers "we encrypt that data, so are we protected?" for the common threats.

| Threat | Storage or FDE | TDE | Server-side column | Client-side field, Always Encrypted, QE | Tokenisation |
| --- | --- | --- | --- | --- | --- |
| Stolen disk or decommissioned drive | Yes | Yes | Yes | Yes | Yes |
| Stolen data file or database backup | Partly (if copied as files, no) | Yes | Yes | Yes | Yes |
| Compromised OS or storage administrator | No | Partly (keys may be reachable) | Partly | Yes | Yes |
| Rogue or compromised DBA | No | No | No | Yes, if DBAs cannot reach the CMK | Yes, if DBAs cannot reach the vault |
| SQL injection through the application | No | No | Usually no | Partly: the attacker gets ciphertext, unless the application decrypts for them | Yes for token-only systems |
| Compromised application server | No | No | No | No: the application holds the keys | No, if it can detokenise |
| Cloud provider insider | With customer-managed or external keys, partly | Same | Same | Yes | Yes |

Two patterns stand out. First, **nothing below the application protects against a compromised application**: once the code that legitimately decrypts is controlled by the attacker, they read what it reads. Rate limits, anomaly detection on decryption volumes and narrow per-service keys are the remaining defences. Second, **the higher layers are only as strong as the separation of key access**: client-side encryption with the CMK readable by DBAs gives the same protection as TDE at much higher cost.

> **Compliance hook.** PCI DSS v4.0.1 Requirement 3.5.1 requires PAN to be unreadable wherever stored, by one-way hashes, truncation, index tokens or strong cryptography with associated key management, and Requirement 3.5.1.2 limits disk-level encryption alone. Requirements 3.6 and 3.7 cover key management for the keys involved. HIPAA's security rule treats encryption as an addressable safeguard, GDPR Article 32 names encryption and pseudonymisation, and ISO/IEC 27001:2022 control A.8.24 covers the use of cryptography. Field-level encryption and tokenisation are the controls that most reduce PCI DSS scope.

## 27.10 Lab: TDE versus field encryption in PostgreSQL

This lab uses Docker, the PostgreSQL image and Python with the `cryptography` package. It shows what a DBA sees under storage-style encryption compared with client-side field encryption.

1. Start PostgreSQL and open a shell:

    ```bash
    docker run -d --name pg -e POSTGRES_PASSWORD=lab \
      -p 5432:5432 postgres:16
    pip install cryptography psycopg2-binary
    ```

2. Create a table and insert a plaintext card number as the "application":

    ```bash
    docker exec -i pg psql -U postgres -c \
      "CREATE TABLE cards(id text primary key, pan text, pan_enc bytea);"
    docker exec -i pg psql -U postgres -c \
      "INSERT INTO cards(id, pan) VALUES ('row-42','4111111111111111');"
    ```

3. As the "DBA", query the table. Note that even if this database's volume were encrypted with LUKS or the cloud KMS, the DBA would see the PAN.

4. Write a short Python script, using the `enc` and `dec` functions from section 27.6, that reads the PAN, stores its encryption in `pan_enc` with AAD `cards:row-42`, and sets `pan` to NULL. Keep the DEK in a local file to represent a KMS.

5. As the DBA, query again. Only ciphertext is visible.

6. Simulate a tampering attack: as the DBA, insert a second row `row-43` and copy `row-42`'s `pan_enc` into it. Have the script decrypt `row-43` and observe the authentication failure.

7. Optional: try `pgcrypto` with `pgp_sym_encrypt(pan, 'secret-key')`, then enable `log_statement = 'all'` and look in the server log for the key. This is why server-side column encryption with literal keys is weak.

**Optional cloud extension.** Replace the local DEK file with a data key from a cloud KMS (`GenerateDataKey` in AWS KMS, or the equivalent in Azure Key Vault or Google Cloud KMS), passing the record ID as encryption context, and confirm the KMS audit log records each unwrap. *Cost warning:* KMS keys and requests are billed; schedule deletion of the key when finished.

## 27.11 Failure story: encrypted at rest, stolen in plaintext

*A composite scenario, based on common patterns:*

A retailer's compliance programme required encryption at rest for all customer data. The database team enabled TDE on every production database, with master keys in an HSM, and the cloud team enabled customer-managed key encryption on every volume and backup. Quarterly reports showed 100 percent compliance.

An attacker found a SQL injection flaw in a little-used order-lookup page. The page connected to the database with an account that could read the whole customer schema. Over several weeks, the attacker extracted millions of customer records, including dates of birth and partial payment details, in small batches that did not trigger volume alerts. Every row arrived in plaintext, because TDE had decrypted each page for an authorised session exactly as designed.

The post-incident review found three gaps. The encryption controls answered the threat of stolen disks and backups, which had never been the main risk. The most sensitive fields had no field-level encryption or tokenisation, so the application account could read them all. And the application used one database account with broad read rights for every page.

The lessons: **match encryption layers to the threat model, not to the control wording**; encrypt or tokenise the small set of high-value fields above the database; give each application function the narrowest database and key permissions it needs; and monitor decryption and query volumes, not only whether encryption is switched on.

## 27.12 Chapter summary

- TDE encrypts database files, logs and backups with a two-tier key hierarchy; it protects against stolen files and media, not against queries.
- Oracle, SQL Server and MySQL have native TDE with external master key options; community PostgreSQL relies on extensions, distributions, managed services or volume encryption.
- Server-side column encryption still lets the database, and often its logs, see keys; client-side field encryption keeps keys away from the database.
- Always Encrypted uses CMK and CEK keys and a client driver; deterministic encryption allows equality but leaks frequencies, and secure enclaves add richer queries at the cost of trusting the enclave.
- MongoDB Queryable Encryption supports equality and range queries on randomly encrypted fields with less leakage than deterministic encryption, but not none.
- Client-side encryption done right uses a maintained library, AEAD, record-bound associated data, envelope encryption, key IDs in every ciphertext and a rotation plan.
- Tokenisation removes systems from risk and scope; FPE (prefer FF1) avoids a vault but spreads key dependence.
- Searchable encryption always leaks; match the scheme to the field's cardinality and to the attacker you face.
