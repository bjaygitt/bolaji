## 36.1 Why devices are a cryptographic problem

Earlier chapters put keys in HSMs, cloud key management services and secrets managers. Most keys, though, live somewhere far less controlled: on laptops, phones, branch routers, badge readers and ATMs, all running software someone else compiled and shipped.

That raises two questions:

- **Can I trust this device?** Is it the device it claims to be, are its keys protected, and is it running the software it should be running?
- **Can I trust this software?** Did it come from who it says it came from, and has it changed since?

The first rests on a **hardware root of trust**: a small, tamper-resistant component that holds keys software cannot extract and records what has run. The second rests on **code signing**: a digital signature over software, checked before it runs or installs. The two meet at boot.

## 36.2 The TPM 2.0

### What it is

A **Trusted Platform Module (TPM)** is a secure cryptoprocessor defined by the Trusted Computing Group and published as ISO/IEC 11889. Version 2.0 replaced the SHA-1-bound version 1.2 and supports algorithm agility (RSA, elliptic curves, SHA-256 and others). It comes in three forms:

- a **discrete TPM**, a separate chip on the motherboard
- a **firmware TPM (fTPM)**, running in a protected area of the main processor, such as Intel PTT or AMD's fTPM
- a TPM integrated into a security processor on the CPU die, such as Microsoft **Pluton**

Windows 11 requires TPM 2.0, and cloud virtual machines offer **virtual TPMs (vTPMs)** backed by the hypervisor.

### Keys that never leave

A TPM organises keys into **hierarchies**, each rooted in a secret seed burned into the chip. Two keys matter most:

- The **endorsement key (EK)** is unique to each TPM and usually comes with an **EK certificate** from the manufacturer. It proves "this is a genuine TPM from vendor X". Because it identifies one chip permanently, it is used sparingly, for privacy reasons.
- The **storage root key (SRK)** wraps other keys. When an application asks the TPM for a key, the TPM generates it, encrypts the private part under the SRK and hands the encrypted blob back. The blob is useless on any other TPM.

From these, you create the keys you actually use: an **attestation key (AK)** for signing statements about the platform, and ordinary signing or decryption keys for VPN, Wi-Fi or certificate authentication. Windows exposes TPM keys through the **Microsoft Platform Crypto Provider**, so a certificate enrolled with that provider has a non-exportable private key bound to that laptop. Linux uses the `tpm2-tss` stack and a PKCS#11 or OpenSSL provider.

### PCRs and sealing

A TPM has a bank of **platform configuration registers (PCRs)**, typically 24 per hash algorithm. A PCR cannot be written directly, only **extended**:

```text
PCR_new = SHA-256( PCR_old || SHA-256(measurement) )
```

Each boot stage hashes the next before running it and extends a PCR with the result. Because extension is one-way and order-dependent, the final value fingerprints the exact sequence of code that ran, and only a reboot resets it.

**Sealing** binds a secret to PCR values: the TPM will release it only if the PCRs match a stated policy. BitLocker uses this to release the volume key only when the boot chain is unchanged (Chapter 26), and Linux can do the same with `systemd-cryptenroll`.

## 36.3 Secure boot and measured boot

**Secure boot** enforces. In **UEFI Secure Boot**, firmware holds a small set of keys and databases:

- the **platform key (PK)**, owned by the device manufacturer, which controls updates to the KEK
- the **key exchange keys (KEK)**, which authorise updates to the two databases below
- **db**, the allow list of certificates and hashes that may boot
- **dbx**, the deny list of revoked signatures and hashes

Before running a bootloader, firmware checks its Authenticode signature against db and dbx. If it fails, the device does not boot it. Most PCs trust Microsoft's certificates in db: one for Windows Boot Manager and one, the third-party UEFI CA, which signs Linux **shim** loaders and option ROMs. Shim then checks the distribution's own signing key.

**Measured boot** records. Each stage measures the next into PCRs and appends an entry to the **TCG event log**. Nothing is blocked, but a verifier can later replay the log, check it reproduces the PCR values, and decide whether the device is acceptable. Secure boot stops known-bad code from running; measured boot lets someone else find out what actually ran, including unexpected but validly signed code.

> **Current development.** The Microsoft certificates that anchor Secure Boot on most PCs were issued in 2011 and expire in 2026: the Microsoft Corporation KEK CA 2011 and the Microsoft UEFI CA 2011 in June 2026, and the Windows Production PCA 2011 in October 2026. Microsoft has been distributing 2023 replacements through Windows Update and firmware updates. Devices that never receive the new certificates keep booting, but cannot receive new boot manager or dbx updates. Treat this as a fleet certificate rotation, tracked in your inventory like any other (as of October 2026).

> **Watch out.** Revocation is the weak point of secure boot. The **dbx** has limited space in firmware, so vendors cannot revoke every vulnerable bootloader by hash. The BlackLotus bootkit, analysed publicly by ESET in 2023, abused an old, validly signed but vulnerable Windows boot manager to bypass Secure Boot on fully patched systems, and Microsoft's mitigation needed a staged rollout over many months. A signed binary stays trusted until it is explicitly distrusted.

## 36.4 Device attestation

**Attestation** is a device proving its state to a remote party. With a TPM, it works like this:

1. The verifier sends a fresh random **nonce**.
2. The device asks its TPM for a **quote**: a structure containing selected PCR values and the nonce, signed by the attestation key.
3. The device sends the quote, the event log and the AK certificate (or proof that the AK lives in the same TPM as a known EK).
4. The verifier checks the signature and the nonce, replays the event log against the PCRs and compares the result with a policy: Secure Boot on, expected bootloader, no debug mode.

The nonce prevents replay of an old, healthy quote. The same pattern appears across platforms:

| Platform | Mechanism (as of 2026) | Typical consumer |
| --- | --- | --- |
| Windows | TPM quotes and the measured boot log, evaluated by Microsoft's attestation services | Intune compliance and Conditional Access |
| Linux servers | TPM quotes evaluated by **Keylime**, an open-source CNCF project, or by vendor tools | Server integrity monitoring |
| Cloud VMs | vTPM-backed boot integrity (Google Shielded VM, Azure Trusted Launch, AWS NitroTPM) | Cloud security posture |
| Android | **Key Attestation**: a certificate chain proving a key lives in the TEE or StrongBox, plus Play Integrity verdicts | Banking apps, MDM |
| Apple | **App Attest** for apps, and **Managed Device Attestation** for MDM | Banking apps, MDM certificate issuance |

Apple's Managed Device Attestation (iOS 16 and later) lets the Secure Enclave prove device properties such as serial number to an ACME server before a certificate is issued, using the IETF draft `device-attest-01` challenge. That closes a long-standing gap: the CA learns that the key is hardware-bound to a genuine, managed device, not just that someone knew an enrolment password.

## 36.5 Mobile secure elements

- **Apple Secure Enclave.** A separate subsystem inside Apple's systems on chip, with its own processor, boot ROM and memory encryption. Keys created with the Secure Enclave flag (P-256 only) never leave it; the app gets a handle and can ask for signatures, optionally gated by Face ID or Touch ID. Apple Pay credentials live in a separate **embedded secure element**, a certified smart-card chip.
- **Android Keystore.** By default, keys live in a **trusted execution environment (TEE)**, an isolated mode of the main processor. Since Android 9, devices may also offer **StrongBox**, a Keystore backed by a discrete secure element with its own CPU, storage and true random number generator, such as Google's Titan M2 in Pixel phones or Samsung Knox Vault. An app requests StrongBox explicitly with `setIsStrongBoxBacked(true)` and must handle devices that lack it.

A TEE resists malware on the phone; a discrete secure element also resists physical attacks such as fault injection. Requiring StrongBox excludes many cheaper Android devices, so most banks require hardware-backed keys (TEE or better), verify that with key attestation, and prefer StrongBox where available.

> **At Meridian.** Meridian's mobile banking app generates a P-256 device-binding key in the Secure Enclave or Android Keystore at registration. The app sends the public key and, on Android, its key attestation chain; the backend checks the chain against Google's attestation roots and records whether the key is TEE or StrongBox backed. Payment approvals over a set amount must be signed with that key after a biometric check. The **PKI and Cryptography Services** team owns the attestation-verification library and its trust anchors; the mobile team owns the app; the fraud team consumes the "hardware-backed" signal as a risk input.

## 36.6 Code and firmware signing

### Why sign code

A code signature answers two questions for the device about to run something: who published it, and has it changed since signing. The publisher hashes the software, signs the hash with a private key and attaches a certificate chaining to a root the platform trusts. The verifier recomputes the hash and checks the signature and chain.

Code signing has one property that TLS does not: **signatures must outlive certificates**. The solution is a **timestamp**: at signing, the signer sends the hash to a **time-stamping authority (TSA)** using RFC 3161, which returns a signed statement that the signature existed at that time. A verifier then accepts the signature if the certificate was valid when the timestamp was made, even after it has expired. Without a timestamp, signed software stops verifying the day the certificate expires.

### The main ecosystems

**Microsoft Authenticode** embeds a PKCS#7 (CMS) signature in Windows executables, drivers, installers and PowerShell scripts, using a certificate from a publicly trusted code signing CA. Windows SmartScreen also builds **reputation** for each publisher and file, so a new certificate may trigger warnings until reputation accrues. Kernel drivers must additionally be signed through Microsoft's own hardware developer portal.

**Apple** requires a **Developer ID** certificate, issued by Apple itself, for software distributed outside the App Store. Since macOS Catalina, such software must also be **notarised**: the developer uploads it to Apple's notary service (with `notarytool`), which scans it for malware and returns a ticket that can be **stapled** to the app so Gatekeeper can verify it offline.

**Sigstore** is an open-source project of the OpenSSF that takes a different route, aimed at open-source packages and containers. Its `cosign` tool supports **keyless signing**:

- The signer authenticates with an OpenID Connect identity, such as a GitHub Actions workflow or a corporate identity provider.
- **Fulcio**, Sigstore's CA, issues a certificate valid for about ten minutes, binding an ephemeral key to that identity.
- The signature and certificate are recorded in **Rekor**, a public append-only transparency log, which proves the signature was made while the certificate was valid.

There is no long-lived key to steal, and verification checks identity ("signed by this workflow in this repository"). npm, PyPI and Kubernetes publish Sigstore-backed signatures or provenance, and cosign also works with ordinary keys held in a cloud KMS or HSM for private use.

**Firmware** (UEFI capsules, BMC images, network and payment terminal software) follows the same pattern, with the public key or its hash in the device's boot ROM. Such keys often cannot be rotated in the field, so their protection matters even more.

### The CA/B Forum hardware key rule

For years, many publishers kept code signing keys as PFX files on build servers, and stolen keys regularly turned up signing malware. The CA/Browser Forum's Code Signing Baseline Requirements changed this. From **1 June 2023**, private keys for all publicly trusted code signing certificates, not only EV ones, must be generated and stored in hardware certified to at least **FIPS 140-2 Level 2 or Common Criteria EAL 4+**: a USB token, an on-premises HSM, a cloud HSM or a signing service. The CA must verify how the key was generated. A further ballot cut maximum code signing certificate validity from 39 months to **460 days** for certificates issued from 1 March 2026.

> **Compliance hook.** Hardware-held signing keys and controlled release support NIST SP 800-53 SI-7 (software, firmware and information integrity) and CM-14 (signed components), NIST SP 800-218 (Secure Software Development Framework) practices on protecting the integrity of releases, and ISO/IEC 27001 Annex A 8.24 (use of cryptography). For DORA and NIS2, signing evidence feeds the ICT supply chain controls.

| Sigstore keyless with a private or public Fulcio and Rekor | Identity-based, ephemeral keys | Strong for containers and internal artefacts; Windows and macOS still need their own ecosystems |

### Design decisions

- **Hash, not file.** The client computes the digest locally and sends only the hash. Large artefacts never cross the network, and the service never sees source code.
- **Separate build and sign.** The build system can request a signature but cannot use the key directly. Release signing requires a passing pipeline, a tagged commit and, for production keys, a human approval.
- **Separate keys by purpose.** Test signing keys, which should not chain to a public root, sign every build; release keys sign only releases. Driver, firmware and container keys are separate again.
- **Timestamp everything**, from at least two TSAs for resilience.
- **Record provenance.** Frameworks such as **SLSA** (Supply-chain Levels for Software Artifacts) attach a signed statement of how, where and from what source an artefact was built.

> **At Meridian.** Meridian signs Windows tools for branches, the macOS and mobile builds of its apps, internal PowerShell, container images and firmware for its fleet of branch devices. Code signing keys sit in a dedicated partition of the general-purpose HSM cluster, fronted by Meridian's signing platform. Platform Engineering owns the CI integration; the **PKI and Cryptography Services** team owns keys, certificates and policy; release managers approve production signing requests. Container images are signed with cosign against a KMS-held key, and the Kubernetes admission controller refuses unsigned images in production.

## 36.8 IoT and OT device identity

ATMs, building controllers, cameras and PLCs need identity too. They live for 10 to 20 years, often have no user interface or reliable clock, and are installed by contractors.

### IEEE 802.1AR

**IEEE 802.1AR** (Secure Device Identity, current edition 2018) defines a standard way for a device to carry a cryptographic identity:

- An **IDevID** (initial device identifier) is a key pair and X.509 certificate installed by the manufacturer at the factory, ideally in a TPM or secure element. It typically contains the serial number and model, signed by the manufacturer's CA. It is meant to last the device's life and is never deleted.
- An **LDevID** (locally significant device identifier) is issued by the owner's own CA after the device is deployed. It carries the owner's naming and policy, and can be rotated or revoked by the owner.

The IDevID proves "this is genuine model X, serial 12345, made by vendor Y". The LDevID proves "this is Meridian's device, approved for this network". You use the first to obtain the second, then use the second for day-to-day authentication, such as 802.1X.

### Onboarding

Turning an IDevID into an LDevID needs an enrolment protocol. **EST** (RFC 7030) is the modern choice and runs over TLS, so the device can authenticate with its IDevID. **BRSKI** (RFC 8995) adds zero-touch bootstrapping: the device presents its IDevID to the owner's registrar, the manufacturer issues a signed **voucher** confirming the ownership, and the device then enrols over EST without anyone typing a password. Consumer IoT has its own variants: the **Matter** smart-home standard gives each device a device attestation certificate chaining to a product and vendor hierarchy. In OT, IEC 62443-4-2 lists device authentication and key protection among the component requirements vendors are assessed against.

> **Watch out.** An IDevID proves the manufacturer made the device, not that you own it. A network that admits anything with a valid vendor certificate admits every unit that vendor ever sold, including ones bought on the second-hand market. Always map the IDevID to your own asset inventory before issuing an LDevID.

## 36.9 MDM and SCEP

### Fleet certificates

Laptops and phones need certificates for Wi-Fi (802.1X EAP-TLS), VPN, and device-based Conditional Access. A **mobile device management (MDM)** platform such as Microsoft Intune, Jamf Pro or Omnissa Workspace ONE (formerly VMware) pushes a configuration profile that tells the device how to get one. Chapter 18 covers the connector set-up; this section explains the protocol choice.

### SCEP

The **Simple Certificate Enrollment Protocol (SCEP)**, published as RFC 8894 in 2020 after two decades as a draft, is the protocol nearly every operating system supports natively. The device generates a key pair, wraps a certificate request in a PKCS#7 envelope encrypted to the CA or a **registration authority (RA)**, and authenticates with a **challenge password**.

SCEP's weakness is that password: in its basic form, a shared secret that lets anyone holding it obtain a certificate with any subject. Modern MDMs fix this with a dynamic, single-use challenge: the MDM generates a challenge tied to one device and one requested subject, and the RA asks the MDM to validate the request before forwarding it to the CA. Intune's certificate connector and Jamf's SCEP proxy work this way, as do cloud CA services with built-in SCEP endpoints, such as Microsoft Cloud PKI for Intune.

The alternatives:

- **PKCS delivery**: the CA or connector generates the key centrally and pushes a PFX to the device. Simpler, but the private key existed outside the device; acceptable for S/MIME decryption keys that need escrow, not for authentication keys.
- **ACME with device attestation**: on Apple platforms, the profile can use ACME with Managed Device Attestation (section 36.4), so the key is generated in the Secure Enclave and the CA receives proof of it. This is where fleet enrolment is heading.

> **In practice.** Ask for the private key to be generated in hardware (TPM on Windows, Secure Enclave on Apple, Keystore on Android) in every SCEP profile. The Intune and Jamf profiles have settings for this, and it means a stolen backup or copied profile cannot carry the device certificate to another machine.

## 36.10 Lab: TPM PCRs, quotes and attestation with a software TPM

This lab uses **swtpm**, a software TPM emulator, and **tpm2-tools**. It runs on any Linux machine or VM without touching a real TPM.

1. Install the tools (Debian or Ubuntu):

```bash
sudo apt install -y swtpm swtpm-tools tpm2-tools
mkdir -p ~/tpmlab/state && cd ~/tpmlab
```

2. Start the emulator in one terminal:

```bash
swtpm socket --tpm2 --tpmstate dir=$HOME/tpmlab/state \
  --server type=tcp,port=2321 --ctrl type=tcp,port=2322 \
  --flags not-need-init,startup-clear
```

3. In a second terminal, point the tools at it and read PCRs 0, 7 and 16:

```bash
export TPM2TOOLS_TCTI="swtpm:host=localhost,port=2321"
cd ~/tpmlab
tpm2_getrandom --hex 16
tpm2_pcrread sha256:0,7,16
```

4. Simulate a boot stage by measuring a file into PCR 16 (the resettable debug PCR), then extend it a second time and watch the value change:

```bash
echo "bootloader v1" > stage.bin
H=$(sha256sum stage.bin | cut -d' ' -f1)
tpm2_pcrextend 16:sha256=$H
tpm2_pcrread sha256:16
tpm2_pcrextend 16:sha256=$H
tpm2_pcrread sha256:16
```

5. Create an endorsement key and an attestation key under it:

```bash
tpm2_createek -c ek.ctx -G rsa -u ek.pub
tpm2_createak -C ek.ctx -c ak.ctx -G rsa -g sha256 -s rsassa \
  -u ak.pub -f pem -n ak.name
```

6. Act as the verifier: choose a nonce, ask for a quote over PCRs 0, 7 and 16, and verify it:

```bash
NONCE=$(openssl rand -hex 16)
tpm2_quote -c ak.ctx -l sha256:0,7,16 -q $NONCE -g sha256 \
  -m quote.msg -s quote.sig -o quote.pcrs
tpm2_checkquote -u ak.pub -m quote.msg -s quote.sig \
  -f quote.pcrs -g sha256 -q $NONCE
```

7. Run `tpm2_checkquote` again with a different nonce and confirm it fails. Then run `tpm2_pcrreset 16`, extend with a different file, take a new quote and compare the PCR 16 value: a verifier holding the expected value would reject this "boot".

**Cloud extension (optional).** Create a small Google Shielded VM or Azure Trusted Launch VM, enable integrity monitoring, and read the boot integrity measurements in the console. Change a boot setting and watch the measurement change. **Cost warning:** VMs are billed while running; delete them when finished.

## 36.11 Failure story: SolarWinds and the signed backdoor

In December 2020, FireEye disclosed that it had been breached and that the attackers had entered through a trojanised update to **SolarWinds Orion**, a network monitoring platform used by thousands of organisations. SolarWinds told the US Securities and Exchange Commission that fewer than 18,000 customers had installed affected versions, released between March and June 2020. CISA issued an emergency directive ordering US federal agencies to disconnect Orion immediately.

The malicious component, named **SUNBURST**, was a modified Orion DLL. It was **digitally signed with SolarWinds' legitimate code signing certificate**, so every check a customer could make passed. The attackers had not stolen the signing key. CrowdStrike's analysis of SolarWinds' build server found an implant, **SUNSPOT**, that watched for Orion builds, swapped one source file for a backdoored version during compilation, then put the original back. The build system compiled the attackers' code and the signing step signed it, exactly as designed.

The lessons for an architect:

- **A signature proves origin, not intent.** It shows the code passed through the publisher's pipeline. If the pipeline is compromised, the signature makes the malware more trusted, not less.
- **Protect the build, not only the key.** Hardware-held keys stop key theft; they do nothing against a poisoned build. Isolated, ephemeral build workers, reproducible builds that an independent system can rebuild and compare, and signed provenance (SLSA) address this.
- **Signing should be a decision.** A signing service that signs whatever the build hands it is a rubber stamp. Tie release signing to source review, provenance checks and approvals.

## 36.12 Chapter summary

- A hardware root of trust holds keys software cannot extract and records what has run; the TPM 2.0 is the standard one for PCs and servers, with EK, SRK and attestation keys.
- PCRs can only be extended, so their values fingerprint the boot sequence; sealing releases secrets only when PCRs match.
- Secure boot enforces signature checks against db and dbx; measured boot records what ran so a verifier can judge it. The 2011 Microsoft Secure Boot certificates expire during 2026.
- Attestation is a signed quote over PCRs and a fresh nonce; Android key attestation and Apple's App Attest and Managed Device Attestation play the same role on phones.
- Mobile apps should require hardware-backed keys (Secure Enclave, TEE or StrongBox) and verify that claim with attestation.
- Code signatures need timestamps to outlive certificates. Authenticode, Apple notarisation and Sigstore keyless signing solve the same problem for different ecosystems.
- Since 1 June 2023, publicly trusted code signing keys must live in certified hardware, and certificates issued from 1 March 2026 last at most 460 days; a central HSM-backed signing service with policy and approvals is the usual answer.
- IEEE 802.1AR gives devices a factory IDevID and an owner-issued LDevID, linked by EST or BRSKI onboarding.
- MDM platforms issue fleet certificates through SCEP with dynamic challenges, PKCS delivery, or ACME with device attestation.
- SolarWinds showed that a correctly signed update can be malicious: protect the build pipeline and provenance as carefully as the key.
