## 22.1 Why private networks need encryption

The old enterprise network was a castle: strong walls at the internet edge and trusted traffic inside. That model broke for three reasons.

- **The inside stopped being a building.** A bank like Meridian connects hundreds of branches over broadband and 4G, links two data centres over fibre that runs through public ducts, and reaches three clouds over leased circuits. Each path passes through someone else's equipment, where a technician, a compromised router or a fibre tap can read traffic that never "left" the private network.
- **Attackers inside became normal.** Ransomware operators spend days moving laterally after the first foothold, harvesting clear-text LDAP binds, database logins and replication streams.
- **Auditors stopped accepting "it is internal".** NIST's zero trust architecture states that network location alone grants no trust.

The answer is a set of protocols at different layers:

| Layer | Protocol | Typical use | Who authenticates |
| --- | --- | --- | --- |
| Link (layer 2) | MACsec | Switch-to-switch, data-centre and cloud interconnects | The two link endpoints |
| Network (layer 3) | IPsec with IKEv2 | Site-to-site VPN, SD-WAN, remote access | Gateways, or gateway and client |
| Network (layer 3) | WireGuard | Modern remote access and mesh overlays | Peers identified by public keys |
| Transport | TLS, DTLS | VPN clients, ZTNA, applications (Chapter 21) | Server, optionally client |
| Access | 802.1X with EAP-TLS | Wi-Fi and wired port admission | Device or user to a RADIUS server |

Lower layers protect everything above them without application changes but authenticate boxes, not people or services. A sound design uses both: link or network encryption for the path, and TLS with strong identity so that nobody relies on the path alone.

## 22.2 IPsec from first principles

**IPsec** is a suite of protocols that protects IP packets inside the operating system or network device, so any traffic routed through it is protected without the application knowing.

### Security associations

The central idea is the **security association (SA)**: a one-way agreement between two peers about which algorithms and keys protect a flow of packets. A conversation needs a pair. The receiver identifies each SA by a 32-bit **Security Parameter Index (SPI)** carried in every packet.

Each implementation keeps two databases:

- The **Security Policy Database (SPD)** says whether each kind of traffic is protected, bypassed or discarded, using **traffic selectors** (ranges of addresses, protocols and ports).
- The **Security Association Database (SAD)** holds the live SAs: SPIs, keys, counters and lifetimes.

Outbound, the SPD decides whether a packet needs protection and the SAD supplies the SA. Inbound, the SPI selects the SA, and after decryption the SPD is checked again to confirm the packet matches the agreed selectors. That second check stops a peer smuggling traffic for networks it was never authorised to reach.

### ESP

**Encapsulating Security Payload (ESP)** carries the protected data: the SPI, a sequence number, the encrypted payload and an integrity check. Today the cipher is almost always **AES-GCM** (Chapter 6), which gives confidentiality and integrity in one pass. The older Authentication Header (AH) gives integrity only, breaks through NAT and is rarely used.

ESP runs in **tunnel mode**, which encrypts the whole original packet and wraps it in a new header between two gateways (the normal site-to-site case), or **transport mode**, which protects only the payload between two hosts.

The **sequence number** provides replay protection: the receiver drops repeats and packets that fall too far behind a sliding window. On fast links a 32-bit counter runs out quickly, so implementations use 64-bit **extended sequence numbers**, and every SA must be replaced before its counter wraps, because nonce reuse under AES-GCM destroys both confidentiality and integrity.

ESP is IP protocol 50 and has no ports, so NAT devices cannot track it. **NAT traversal** detects a NAT during key exchange and wraps ESP in UDP port 4500. A firewall that allows UDP 500 but not 4500 produces tunnels that negotiate and then carry nothing, a classic support call.

## 22.3 IKEv2: agreeing keys and proving identity

The **Internet Key Exchange version 2 (IKEv2)** protocol authenticates the peers, runs a Diffie-Hellman exchange (Chapter 9) and creates the SAs. It replaced IKEv1, whose multiple modes and weak pre-shared key handling made it fragile. New designs should use IKEv2 only.

### The exchanges

IKEv2 first builds its own protected channel, the **IKE SA**, then uses it to create the ESP SAs, which it calls **Child SAs**:

1. **IKE_SA_INIT** (in the clear). The initiator proposes algorithms and sends a Diffie-Hellman public value and a nonce. The responder chooses a proposal and replies in kind. Both now share keys for the IKE SA, but neither knows who the other is.
2. **IKE_AUTH** (encrypted). Each side sends its identity, usually a certificate, and an **AUTH** payload proving it holds the credential. AUTH covers the first exchange, so a man in the middle who altered the proposals or public values is detected here. This exchange also creates the first Child SA with its traffic selectors.

Later, **CREATE_CHILD_SA** adds or rekeys Child SAs, and **INFORMATIONAL** exchanges carry deletes, errors and liveness checks.

### Perfect forward secrecy

**Perfect forward secrecy (PFS)** means that stealing a long-term key tomorrow does not decrypt traffic recorded today. In IKEv2 the certificates or pre-shared keys only authenticate the handshake; session keys come from the ephemeral Diffie-Hellman exchange, so the IKE SA always has forward secrecy.

The subtlety is in the Child SAs. The first Child SA's keys are derived from the IKE SA's key material. A later rekey may or may not include a fresh key exchange. Without one, every Child SA ever derived from that IKE SA falls with its single secret. With one, each rekey is independent. Vendors call this the "PFS group" on the Child SA. Turn it on and make sure both peers agree: a mismatch usually lets the tunnel come up and then fail at the first rekey, an hour or eight hours later.

### Algorithms and lifetimes

IKEv2 negotiates an encryption algorithm, a pseudorandom function (PRF) for key derivation, an integrity algorithm (unneeded with AEAD) and a key exchange group. The IETF publishes and updates implementation requirements for these. A defensible baseline in 2026:

| Transform | Recommended | Avoid |
| --- | --- | --- |
| Encryption (IKE and ESP) | AES-256-GCM (AES-128-GCM acceptable) | DES, 3DES, AES-CBC with SHA-1 |
| PRF | HMAC-SHA-256 or SHA-384 | HMAC-MD5, HMAC-SHA-1 |
| Key exchange | ECP-256, ECP-384, Curve25519, MODP 3072 or larger; plus ML-KEM where supported | DH groups 1, 2 and 5 |
| Authentication | ECDSA or RSA certificates | Short or shared pre-shared keys |
| Lifetimes | IKE SA 8 to 24 hours; Child SA 1 to 8 hours | Days, or no rekey |

> **Current development.** RFC 9370 defines how IKEv2 adds post-quantum KEMs alongside the classic exchange, using up to seven additional key exchanges after IKE_SA_INIT, and further IETF work defines how ML-KEM (Chapter 45) plugs into that framework. strongSwan 6.0, released in December 2024, added ML-KEM, and firewall vendors have been shipping hybrid options since. Site-to-site tunnels carry long-lived confidential data, so they are a priority for harvest-now-decrypt-later protection (Chapter 46).

### Certificates versus pre-shared keys

With a **pre-shared key (PSK)**, both peers hold the same secret and AUTH is a MAC keyed with it. It is quick to set up, and its weaknesses are structural:

- **Offline guessing.** An attacker who captures or provokes an authentication can test candidate keys offline. The IKEv2 specification warns that a PSK needs the entropy of a real key; passphrases do not have it.
- **Sharing.** One PSK is often reused across many tunnels or given to every remote client, so whoever learns it can impersonate any peer.
- **Rotation and revocation.** Changing a PSK needs coordinated change on both ends, often at two companies, so PSKs live for years in tickets and spreadsheets. A stolen branch router cannot be revoked; its key must be changed everywhere.

With **certificate authentication**, each peer has its own private key and a certificate from a CA the other trusts, and AUTH is a digital signature (Chapter 10). Keys are unique, stolen devices can be revoked, and renewal is one side's job. The price is a PKI: an issuing CA (Chapter 15) and enrolment for every gateway, often by SCEP or EST (Chapter 17). Three details cause most certificate outages:

- **Identity matching.** The IKE identity (an FQDN, IP address or distinguished name) must match what the peer expects and appear in the certificate, usually as a SAN. Renewing with a different subject format breaks tunnels.
- **Key usage.** Some implementations require particular extended key usage values; the IETF's PKI profile for IKE describes them. Check before standardising a template.
- **Revocation reachability.** A gateway that must fetch a CRL through the tunnel that is down cannot come up. Publish CRLs where gateways can reach them directly, and document fail-open or fail-closed behaviour.

Remote access often uses **EAP inside IKEv2**: the user authenticates with credentials and MFA through RADIUS, while the gateway still proves itself with a certificate.

> **In practice.** Treat PSKs as an approved exception. Where a partner insists, generate at least 32 random bytes, make the key unique to the tunnel, store it in the secrets manager (Chapter 35) and set a rotation date. Some cloud VPN gateways (AWS Site-to-Site VPN, for example) accept certificate authentication, so ask before defaulting to a PSK.

## 22.4 Site-to-site designs: MPLS, SD-WAN and cloud

### MPLS is separation, not encryption

An **MPLS** layer 3 VPN keeps each customer's routes in a separate table inside the carrier network. That gives separation and quality of service but no confidentiality: packets cross the carrier core in the clear, and a misconfigured route target can leak routes between customers.

Point-to-point IPsec over MPLS turns a branch mesh into hundreds of tunnels. **Group encryption** avoids that: a key server distributes one group key to every member router with the **Group Domain of Interpretation (GDOI)** protocol, and routers encrypt while keeping the original IP header so carrier routing still works. Cisco GETVPN and Juniper Group VPN are the best-known examples. The trade-off is that every member holds the same traffic key, so one compromised router exposes the group until the key server rekeys without it.

### SD-WAN

**SD-WAN** builds encrypted overlays over ordinary internet links, with a central controller choosing paths per application. Underneath, the data plane is almost always IPsec ESP with AES-GCM. What differs is how keys and device identities are managed:

| Product (as of 2026) | Control plane | Data plane keys |
| --- | --- | --- |
| Cisco Catalyst SD-WAN (formerly Viptela) | Devices authenticate to controllers over DTLS or TLS with device certificates | Controllers distribute data-plane keys, so edges build IPsec tunnels without per-pair IKE |
| Fortinet Secure SD-WAN | FortiManager-managed FortiGate IPsec configuration | Standard IKE between hubs and spokes, with ADVPN for on-demand spoke-to-spoke tunnels |
| Palo Alto Networks Prisma SD-WAN | Devices claim to a cloud controller with device certificates | IPsec between devices, keys managed by the controller |
| HPE Aruba Networking EdgeConnect, Versa, VeloCloud | Certificates or tokens to an orchestrator | IPsec overlays with orchestrator-driven keys |

Two consequences follow. First, the controller is now a key-management system: ask where its CA lives, whether you can substitute your own, and how a stolen branch device is revoked. Second, the overlay ends at the branch box, so it does not replace TLS for applications. Many deployments also send branch internet traffic to a cloud security service (the **SASE**, secure access service edge, model), which then sees decrypted traffic, a custody question like the CDN keys in Chapter 23.

### Cloud connectivity

Each hyperscaler offers managed IPsec gateways (AWS Site-to-Site VPN, Azure VPN Gateway, Google Cloud HA VPN) and private circuits (AWS Direct Connect, Azure ExpressRoute, Google Cloud Interconnect). Like MPLS, private circuits are not encrypted by default, so run IPsec over them or use MACsec on dedicated high-speed ports, which all three providers document.

> **At Meridian.** Network Engineering runs the SD-WAN across about 240 branches and offices. Each branch device enrols for a certificate from an issuing CA under Meridian's private root rather than the vendor's built-in CA, so the PKI and Cryptography Services team can revoke a stolen device in one step. PSKs are allowed only for third parties that cannot use certificates, each recorded in the secrets platform with an owner and rotation date. Circuits to the three clouds carry IPsec, and GRC maps them to the DORA register of ICT third-party services.

## 22.5 MACsec on data-centre and inter-DC links

**MACsec** (IEEE 802.1AE) protects Ethernet frames on one link: between two directly connected ports, or across a carrier service that behaves like a wire. It runs in port hardware, so it encrypts at line rate (10 to 400 Gbit/s) with little latency. That makes it the natural choice for switch-to-switch links and dark fibre between data centres, where IPsec would be too slow or costly.

Each frame carries a **SecTAG** after the MAC addresses, then the encrypted payload and an integrity check. Cipher suites are AES-GCM with 128-bit or 256-bit keys, and the **extended packet numbering (XPN)** variants use 64-bit packet numbers so that fast links do not exhaust them in minutes. MACsec is hop by hop: each switch decrypts, forwards and re-encrypts, so traffic is clear inside each device.

### Keys: MKA and the CAK

Keys are managed by the **MACsec Key Agreement (MKA)** protocol, defined in IEEE 802.1X:

- The **connectivity association key (CAK)**, named by a **CKN**, is the long-term secret for the link. It is either a static pre-shared key or derived from an EAP-TLS authentication to a RADIUS server.
- An elected **key server** generates the **secure association key (SAK)**, which actually encrypts frames, distributes it wrapped under a key derived from the CAK, and replaces it regularly.

Data-centre and inter-DC links nearly always use static CAKs, because fixed infrastructure must come up without a RADIUS server. A static CAK has the weaknesses of an IPsec PSK, so generate it randomly, use one per link, store it in a key or secrets manager, and use vendor "key chain" features to roll in a new CAK with overlapping validity so the change is hitless.

### Carrier and optical links

On **dark fibre**, MACsec runs between your own switches and the carrier sees only ciphertext. On **carrier Ethernet services** the provider may need VLAN tags, so vendors can send the 802.1Q tag in the clear ahead of the SecTAG; test the exact service first. Optical equipment (Ciena, Nokia, Cisco and others) can instead encrypt the wavelength at layer 1, but then the keys sit with whoever runs the optical gear, which may be the carrier.

> **At Meridian.** DC-East and DC-West are joined by two diverse dark-fibre paths running MACsec with GCM-AES-XPN-256 on every interconnect port. CAKs are unique per link, generated by the PKI and Cryptography Services team's key manager, pushed by the network automation pipeline so that no engineer sees one, and rolled every six months through overlapping key chains. Inside each data centre, MACsec covers spine-to-border and border-to-firewall links, while application traffic relies on TLS and mesh mTLS (Chapter 24).

## 22.6 Remote access: VPNs and zero trust network access

### The remote access VPN

A **remote access VPN** connects a laptop to the corporate network as if it were in the office. Two protocol families dominate: **IKEv2/IPsec**, built into Windows, macOS, iOS and Android; and **TLS and DTLS-based VPNs** on port 443, such as Cisco Secure Client (formerly AnyConnect), Palo Alto Networks GlobalProtect, Fortinet FortiClient and Ivanti Connect Secure, which pass through hotel firewalls that block IPsec. The certificates involved are the concentrator's server certificate, optional device certificates from the enterprise CA, and the SAML or RADIUS integration for user login.

The weakness is architectural: a full tunnel puts the laptop where it can reach far more than the user needs, and the concentrator is an internet-facing appliance that attackers target relentlessly (Section 22.11).

### Zero trust network access

**Zero trust network access (ZTNA)** connects a verified user on a verified device to one application, and re-evaluates every session. Google's BeyondCorp papers described the approach from 2014, and NIST formalised zero trust architecture in 2020. The building blocks are:

- a **client agent** that proves device identity (ideally with a hardware-bound key) and reports posture;
- an **identity provider** for the user (Chapter 16);
- a cloud **policy decision point**;
- an **app connector** beside the application that makes only **outbound** connections, so the application has no inbound port on the internet.

The provider terminates and stitches the agent's and connector's tunnels, so it is a trusted intermediary. Keep application TLS inside the tunnels where the provider should not see content.

| Service (as of 2026) | Client and tunnel | Connector side |
| --- | --- | --- |
| Zscaler Private Access | Zscaler Client Connector, TLS-based tunnels | App Connectors enrol with a provisioning key and connect outbound |
| Palo Alto Networks Prisma Access | GlobalProtect (IPsec or TLS) or agentless browser access | ZTNA Connector, or IPsec from data centres |
| Cloudflare One | WARP client using WireGuard or MASQUE (HTTP/3-based) tunnels | `cloudflared` makes outbound tunnels; Access can issue a signed JWT the origin verifies |
| Netskope Private Access, Microsoft Entra Private Access, Cisco Secure Access | Vendor agents | Outbound publishers or connectors |

Compare them on four cryptographic questions: where TLS is terminated and by whom; whether device identity is bound to a TPM or secure enclave; whether you can use your own CA for device certificates; and how connector credentials are enrolled, rotated and revoked.

> **Watch out.** ZTNA makes a cloud provider a party that can see and steer internal application traffic. Under DORA and similar regimes that is a third-party risk decision, not only a network change. Keep a documented break-glass path for when the provider is down.

> **At Meridian.** Meridian is moving staff from legacy VPN concentrators to a ZTNA service. Laptops carry a TPM-bound device certificate issued through the MDM from Meridian's private CA, which policy requires alongside an identity provider login with phishing-resistant MFA. App connectors in each data centre and cloud connect outbound only. A small VPN remains for Network Engineering's break-glass access. IAM owns the access policy; the PKI team owns the device certificate profile.

## 22.7 WireGuard

**WireGuard**, created by Jason Donenfeld and merged into the Linux kernel in 2020, takes the opposite approach to IPsec. It has about 4,000 lines of kernel code and **no algorithm negotiation at all**:

| Purpose | WireGuard uses |
| --- | --- |
| Key exchange | X25519 |
| Encryption | ChaCha20-Poly1305 |
| Hashing | BLAKE2s |
| Handshake framework | The Noise protocol framework (Noise_IK) |

Peers are identified only by public keys configured in advance, much like SSH `authorized_keys`. Each peer entry lists the addresses allowed from that key, a rule called **cryptokey routing**. Session keys are replaced every two minutes, giving forward secrecy, and a cookie mechanism protects busy responders from floods.

Nothing can be downgraded, and the small code base has been formally analysed, but a broken primitive would need a new protocol version: a deliberate rejection of algorithm agility (Chapter 42). An optional pre-shared key mixed into the handshake gives interim quantum resistance, and projects such as Rosenpass generate it with a post-quantum exchange.

For the enterprise, two gaps matter. WireGuard has no users, certificates, revocation or MFA, so products built on it (Tailscale, NetBird, Cloudflare WARP and others) add a coordination service that authenticates users and distributes and withdraws keys; that service is the real trust anchor. And its algorithms are not available in FIPS 140-3 validated modes, so where validation is mandatory, IPsec or TLS VPNs with validated modules remain the choice (Chapter 40).

## 22.8 Enterprise Wi-Fi and network access control

### 802.1X and EAP

Wi-Fi is the most exposed private network: its signal leaves the building. Enterprise Wi-Fi and wired port security rest on **IEEE 802.1X**, with three roles: the **supplicant** on the device, the **authenticator** (access point or switch port), which blocks traffic until authentication succeeds, and the **authentication server**, a **RADIUS** server that decides and returns keying material and policy such as a VLAN. The conversation uses the **Extensible Authentication Protocol (EAP)**, and the method inside EAP decides the security.

**EAP-TLS** runs a full TLS handshake: the RADIUS server and the device each present a certificate. There is no password to phish or crack, and the device key can live in a TPM or secure enclave. TLS 1.3 is now specified for EAP-TLS. The cost is device enrolment, normally by MDM through SCEP or a PKCS connector (Chapters 18 and 36).

**PEAP with MSCHAPv2** builds a tunnel using only the server certificate, then runs a password challenge whose captured exchange can be cracked. It is safe only if every client strictly validates the server certificate. A client that does not will complete the tunnel to an attacker's "evil twin" access point and hand over the challenge.

### RADIUS server certificates

A supplicant has no URL to compare against, so it validates the RADIUS server differently from a browser. The device profile, pushed by MDM or Group Policy, names the **trusted CA** and the **expected server name**. This is why a **private CA** is usually right: if supplicants trust a public CA, anyone who obtains a matching certificate from it could impersonate the network. Public certificates are also moving to 47-day validity (Chapter 13), and many supplicants prompt or fail when the server certificate changes. Renewing under the same CA and name is invisible to managed clients; changing the CA requires updating every device profile first.

> **Watch out.** RADIUS protects its responses with an MD5-based construction. In July 2024 researchers published **Blast-RADIUS**, which uses an MD5 chosen-prefix collision to let a man in the middle between RADIUS client and server turn a reject into an accept. Require the Message-Authenticator attribute on all packets, apply vendor updates, and carry RADIUS between sites over TLS (**RadSec**) or IPsec, never plain UDP across untrusted networks.

### WPA3-Enterprise

After 802.1X succeeds, the Wi-Fi **four-way handshake** derives session keys from the shared master key. **WPA3**, introduced by the Wi-Fi Alliance in 2018, makes **Protected Management Frames** mandatory, stopping forged disconnects, and adds a **192-bit mode** for high-security networks: GCMP-256, HMAC-SHA-384 and EAP-TLS with P-384 or RSA 3072-bit keys. The defensible corporate design in 2026 is WPA3-Enterprise (with transition mode only where old devices force it), EAP-TLS only, a private CA for both device and RADIUS certificates, and supplicant profiles that pin the CA and server name.

### Network access control

**Network access control (NAC)** products are the RADIUS policy engines: they assign VLANs or roles, check posture, and admit devices without supplicants (printers, cameras, building systems) by **MAC authentication bypass**, which trusts a hardware address that is easily spoofed. Examples include Cisco Identity Services Engine, HPE Aruba Networking ClearPass, Fortinet FortiNAC and Forescout, with cloud RADIUS services such as Portnox and Juniper Mist Access Assurance. Whatever the product, the duties are the same: protect the RADIUS server key, trust only the right issuing CAs, check device certificate revocation and protect RADIUS transport. Switches can also add MACsec on access ports, keyed from the EAP-TLS session.

> **At Meridian.** The corporate SSID uses WPA3-Enterprise with EAP-TLS. Laptops and phones receive TPM- or enclave-bound device certificates through the MDM. The NAC cluster in each data centre holds a RADIUS server certificate from a dedicated private issuing CA, and supplicant profiles pin that CA and the name `radius.corp.meridian.example`. Branch RADIUS traffic travels inside the SD-WAN overlay. Payment terminals in Meridian Pay offices use MAC authentication bypass on a tightly restricted VLAN, an exception Payments Security reviews every year.

## 22.9 Design decisions, operations and compliance

The design rules from this chapter:

- **Encrypt every link you do not physically control**: MACsec on fibre and interconnects, IPsec or SD-WAN on carrier and internet links, and application TLS regardless.
- **Prefer certificates to shared keys** for IKEv2, SD-WAN devices and Wi-Fi. Where PSKs or CAKs remain, make them random, unique, stored and rotated.
- **Use IKEv2 with AES-GCM, strong groups and PFS on rekey**, and plan hybrid post-quantum exchange for long-lived tunnels.
- **Move remote access toward ZTNA** with hardware-bound device certificates, keeping a small, well-patched break-glass path.

Operationally, put gateway, SD-WAN, RADIUS and device certificates, plus every static PSK and CAK, in the certificate and key inventory with owners (Chapters 17 to 19). Monitor rekey failures, proposal mismatches, gateway CRL fetch failures and RADIUS failure rates, which spike when a server certificate or CA changes. Send IKE and RADIUS logs to the SOC: bursts of IKE_AUTH failures often mean password spraying.

> **Compliance hook.** PCI DSS v4.0.1 requirement 4.2.1 requires strong cryptography for cardholder data over open, public networks; requirement 4.2.1.2 covers wireless networks that transmit cardholder data or connect to the cardholder data environment; requirement 8.4.3 requires MFA for remote network access from outside the entity's network. NIST SP 800-77 Rev. 1 is the guide to IPsec VPNs and NIST SP 800-207 describes zero trust architecture. NIST SP 800-53 controls SC-8, AC-17, AC-18 and IA-3 map to transmission protection, remote access, wireless and device authentication. ISO/IEC 27001:2022 Annex A controls 8.20, 8.21 and 8.24 apply, and under DORA, SD-WAN, ZTNA and carrier providers supporting critical functions belong in the ICT third-party register.

## 22.10 Lab: IKEv2 site-to-site with strongSwan in Docker

In this lab you build a certificate-authenticated IKEv2 tunnel between two containers, watch the SAs and ESP packets, test PFS on rekey and compare a PSK. You need Docker on Linux (or Docker Desktop, which runs a Linux VM). The containers need the `NET_ADMIN` capability to install IPsec policies in the kernel.

**1. Create a network and a working directory.**

```bash
mkdir -p ~/lab22 && cd ~/lab22
docker network create --subnet 172.30.0.0/24 ipsec-lab
```

**2. Start two gateways, `moon` and `sun`, with strongSwan installed.**

```bash
for h in moon sun; do
  ip=172.30.0.10; [ "$h" = sun ] && ip=172.30.0.20
  docker run -d --name "$h" --hostname "$h" \
    --network ipsec-lab --ip "$ip" \
    --cap-add NET_ADMIN -v "$PWD":/lab \
    alpine:3.20 sleep infinity
  docker exec "$h" apk add --no-cache strongswan tcpdump
done
docker exec moon swanctl --version
```

**3. Create a small CA and one certificate per gateway** with strongSwan's `pki` tool. Each certificate carries the gateway's name as a SAN, which becomes its IKE identity.

```bash
docker exec -w /lab moon sh -c '
pki --gen --type ecdsa --size 384 --outform pem > ca.key
pki --self --ca --lifetime 3650 --in ca.key --type ecdsa \
  --dn "CN=Lab IPsec CA" --outform pem > ca.crt
for h in moon sun; do
  pki --gen --type ecdsa --size 384 --outform pem > $h.key
  pki --pub --in $h.key --type ecdsa | pki --issue \
    --cacert ca.crt --cakey ca.key --lifetime 90 \
    --dn "CN=$h.lab" --san "$h.lab" \
    --flag serverAuth --flag ikeIntermediate \
    --outform pem > $h.crt
done
pki --print --in moon.crt'
```

**4. Install the keys and write the configuration.** Run this for each gateway, swapping names and addresses for `sun`.

```bash
docker exec moon sh -c '
cp /lab/ca.crt /etc/swanctl/x509ca/
cp /lab/moon.crt /etc/swanctl/x509/
cp /lab/moon.key /etc/swanctl/private/
cat > /etc/swanctl/conf.d/lab.conf <<EOF
connections {
  lab {
    version = 2
    local_addrs = 172.30.0.10
    remote_addrs = 172.30.0.20
    proposals = aes256gcm16-prfsha384-ecp384
    local {
      auth = pubkey
      certs = moon.crt
      id = moon.lab
    }
    remote {
      auth = pubkey
      id = sun.lab
    }
    children {
      net {
        esp_proposals = aes256gcm16-ecp384
        rekey_time = 1h
        start_action = trap
      }
    }
  }
}
EOF'
```

Note that `esp_proposals` includes `ecp384`: that is the PFS group used when the Child SA is rekeyed.

**5. Start the daemons and load the configuration** on both gateways.

```bash
for h in moon sun; do
  # run the IKE daemon (charon) in the background
  docker exec -d "$h" sh -c \
    '$(find /usr/lib* -name charon -type f | head -n 1)'
  sleep 2
  docker exec "$h" swanctl --load-all
done
```

The `find` is there because distributions install `charon` in different library directories.

**6. Bring the tunnel up and inspect it.**

```bash
docker exec moon swanctl --initiate --child net
docker exec moon swanctl --list-sas
docker exec moon ip xfrm state
docker exec moon ip xfrm policy
```

`--list-sas` shows the IKE SA (with the negotiated algorithms and both identities) and the Child SA with its two SPIs, one per direction. `ip xfrm state` shows the same SAs as the Linux kernel holds them, including the keys, which is a reminder of why gateway memory must be protected.

**7. Watch ESP on the wire.** In one terminal capture, in another send traffic.

```bash
docker exec sun tcpdump -ni eth0 esp or udp port 500
docker exec moon ping -c 3 172.30.0.20
```

You see ESP packets with the SPI and an incrementing sequence number, and no visible ICMP. Earlier you would have seen the IKE_SA_INIT and IKE_AUTH packets on UDP 500.

**8. Rekey and confirm PFS.** Force a rekey of the Child SA and list the SAs again.

```bash
docker exec moon swanctl --rekey --child net
docker exec moon swanctl --list-sas
```

The SPIs change, and the Child SA line shows the ECP_384 group, meaning a fresh Diffie-Hellman exchange was done. Remove `-ecp384` from `esp_proposals` on one side only, reload with `swanctl --load-all`, and rekey again: depending on which side initiates, the rekey fails with a proposal mismatch while the established SA keeps running, exactly the silent time bomb described in Section 22.3.

**9. Compare a pre-shared key.** Replace `auth = pubkey` with `auth = psk` on both sides, add a secret, and reload.

```text
secrets {
  ike-lab {
    id-1 = moon.lab
    id-2 = sun.lab
    secret = 0sY2hhbmdlLW1lLXRvLXJhbmRvbS0zMi1ieXRlcw==
  }
}
```

Append that block to each `lab.conf`, then terminate and re-initiate the tunnel. It works just as well, which is the problem: nothing in the protocol tells you the secret is weak, shared or old. Generate a real one with `openssl rand -base64 32` and note how you would have to deliver it to the other side.

**10. Optional: hybrid post-quantum key exchange.** If `swanctl --version` reports strongSwan 6.0 or later, change the IKE proposal to `aes256gcm16-prfsha384-ecp384-ke1_mlkem768`, reload both sides and re-initiate. `--list-sas` now lists an additional key exchange. Clean up with `docker rm -f moon sun` and `docker network rm ipsec-lab`.

**Optional cloud extension.** Create a site-to-site VPN in a cloud provider (for example AWS Site-to-Site VPN with certificate authentication from AWS Private CA, or the equivalent service in another cloud) and terminate it on a strongSwan virtual machine. VPN gateways, private CAs and virtual machines are billed by the hour or month, and a private CA can cost hundreds of dollars a month; delete everything when you finish.

## 22.11 Failure story: the Ivanti Connect Secure compromises

In January 2024 the security firm Volexity reported that attackers were exploiting two unknown vulnerabilities in Ivanti Connect Secure, a widely used TLS-based remote access VPN appliance: an authentication bypass (CVE-2023-46805) and a command injection flaw (CVE-2024-21887). Chained, they let an unauthenticated attacker run commands on the appliance as root. Mass exploitation followed within days.

The US Cybersecurity and Infrastructure Security Agency (CISA) issued Emergency Directive 24-01 requiring federal agencies to apply mitigations, then supplemental direction that went much further: disconnect affected appliances, rebuild them from clean images, and assume that anything the appliance held was compromised. Agencies were told to revoke and reissue the certificates, keys and passwords stored on or exposed to the appliance, and to reset credentials for accounts that had passed through it. CISA later warned that Ivanti's own integrity checking tool could fail to detect compromise.

The cryptography was not broken. The failure was that one internet-facing box concentrated everything a remote access design gathers: the server key users trust, authentication flows, cached credentials and a network position inside the perimeter. Once it was owned, all of them were.

The lessons:

- **Know every key and certificate on each edge appliance**, so "revoke and reissue everything it held" is a list, not an investigation.
- **Keep edge keys in hardware where the platform allows**, so an attacker can use a key while controlling the box but cannot copy it.
- **Shrink what the appliance can reach.** Outbound-only ZTNA connectors and per-application access limit the blast radius.
- **Rehearse rebuilding an edge device**, including certificate reissue and client trust updates, before an emergency forces it.

## 22.12 Chapter summary

- Private paths cross carrier, cloud and wireless infrastructure the enterprise does not control, so they need encryption at several layers, with application TLS on top.
- IPsec protects packets with ESP, usually AES-GCM in tunnel mode, using one-way SAs selected by SPI and checked against policy selectors.
- IKEv2 builds the IKE SA with ephemeral Diffie-Hellman and authenticates peers in IKE_AUTH; Child SA rekeys need a fresh key exchange for full PFS, and hybrid ML-KEM exchanges are now available.
- Certificates beat pre-shared keys because each key is unique, revocable and rotated by one party; unavoidable PSKs must be random, unique, stored and rotated.
- MPLS gives separation, not confidentiality; SD-WAN overlays use IPsec with controller-managed keys, which makes the controller a key-management system.
- MACsec encrypts Ethernet at line rate, keyed by MKA from a CAK, and suits data-centre links, dark fibre and cloud interconnects.
- ZTNA replaces network-level access with per-application, identity- and device-based access through outbound connectors, at the price of a trusted provider in the path.
- WireGuard is simple and fixed-algorithm, relies on a coordination service for enterprise identity, and does not fit where FIPS validation is mandatory.
- Enterprise Wi-Fi should use WPA3-Enterprise with EAP-TLS, device certificates and supplicant profiles pinned to a private CA and RADIUS server name, with RADIUS hardened against Blast-RADIUS.
