## 20.1 What a secure channel must provide

Part V of this book is about **data in transit**: data moving between two systems over a network that neither of them controls. The network might be the public internet, a branch office's broadband line, a cloud provider's backbone or a data-centre switch. In every case you should assume that someone else can read, record, change or replay the packets.

A **secure channel** is a connection that gives two parties, usually a client and a server, three guarantees over such a network:

1. **Confidentiality:** nobody else can read the data.
2. **Integrity:** nobody can change, reorder, drop or replay records without detection.
3. **Authentication:** at least the server, and optionally the client, proves its identity.

**Transport Layer Security (TLS)** provides all three by combining the tools from Parts II and III: ephemeral (EC)DH key agreement (Chapter 9), signatures and certificates for authentication (Chapters 10 and 12), HKDF for key derivation (Chapter 7) and authenticated encryption (Chapter 6).

TLS has two layers:

- The **handshake protocol** negotiates parameters, authenticates the server (and optionally the client), and establishes shared keys.
- The **record protocol** splits application data into records and protects each one with an AEAD cipher, using a sequence number as part of the nonce so that records cannot be reordered or replayed.

TLS matters to an enterprise architect because it is everywhere. A single customer request may pass through four or five separate TLS connections before it reaches a database, and each one has its own certificate, configuration and owner. Chapter 21 deals with that deployment reality. This chapter makes sure you understand the protocol itself well enough to reason about every one of those hops.

## 20.2 A short history of TLS

| Version | Year | Status |
| --- | --- | --- |
| SSL 2.0 and 3.0 | 1995 to 1996 | Broken (POODLE, DROWN); prohibited |
| TLS 1.0 and 1.1 | 1999, 2006 | Deprecated by RFC 8996 in 2021; removed from browsers in 2020 |
| TLS 1.2 | 2008 | Still widely supported; secure only with modern settings |
| TLS 1.3 | 2018 (RFC 8446) | The current standard; used by the large majority of web traffic |

TLS 1.3 was designed after two decades of attacks on earlier versions (Chapter 11 tells several of those stories). Its designers removed everything that had caused trouble:

- RSA key transport, which gave no forward secrecy and invited Bleichenbacher attacks (Chapter 8).
- CBC mode and MAC-then-encrypt, which led to padding oracles and Lucky Thirteen.
- Static Diffie-Hellman, compression (the cause of CRIME), renegotiation, weak hashes, and custom DH groups (Logjam).

What remains is small enough to analyse formally, and TLS 1.3 was the first major protocol to be designed alongside machine-checked security proofs. The result is a protocol with far fewer settings to get wrong, which is exactly what you want when thousands of teams configure it.

**ClientHello.** The client sends a random value, the TLS versions and cipher suites it supports, and one or more **key shares**: ephemeral public keys for the key exchange groups it guesses the server will accept. It also sends extensions, including **Server Name Indication (SNI)**, which names the website it wants, and **Application-Layer Protocol Negotiation (ALPN)**, which names the application protocol (such as HTTP/2).

**ServerHello.** The server picks a cipher suite and one of the client's key shares, and replies with its own ephemeral key share. At this moment both sides can compute the shared secret, and everything that follows is encrypted.

**EncryptedExtensions, Certificate, CertificateVerify.** The server sends its certificate chain, then a **CertificateVerify** message: a signature, made with its certificate's private key, over a hash of every handshake message so far. This proves that the server holds the private key and binds its identity to this exact key exchange, which defeats man-in-the-middle attacks.

**Finished.** Each side sends a MAC over the whole transcript, using a key derived from the handshake secret. This confirms that both sides saw identical messages, so an attacker cannot have silently removed or altered anything, such as stripping the strongest algorithms from the client's offer.

If the server does not support any of the groups the client guessed, it sends a **HelloRetryRequest** naming a group it does support, and the client tries again. That costs an extra round trip, which is why the order and choice of key shares a client sends has a measurable effect on latency.

### Disguising itself for old middleboxes

During its design, TLS 1.3 broke on real networks because firewalls and proxies that parsed TLS rejected anything unfamiliar. The fix was **middlebox compatibility mode**: a TLS 1.3 ClientHello pretends to be a TLS 1.2 resumption, the real version is carried in a `supported_versions` extension, and the handshake includes dummy messages that old devices expect. The lesson for an enterprise is that the devices you put in the path, from inspection firewalls to load balancers, shape which protocols can be deployed. Every new protocol feature since, from ECH to post-quantum key shares, has met the same problem, known as **protocol ossification**.

### Cipher suites in TLS 1.3

TLS 1.3 cipher suites name only the AEAD and the hash; key exchange and signatures are negotiated separately. There are five, and three are used in practice:

| Cipher suite | Use |
| --- | --- |
| TLS_AES_128_GCM_SHA256 | Mandatory to implement; the most common |
| TLS_AES_256_GCM_SHA384 | Where policy requires AES-256 |
| TLS_CHACHA20_POLY1305_SHA256 | Devices without AES hardware |

The other two use AES-CCM and are mostly found in constrained IoT devices.

## 20.4 What changed from TLS 1.2, and why it matters

Most enterprises run TLS 1.2 and 1.3 side by side for years, so you need to know what differs:

| Aspect | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| Round trips for a full handshake | Two | One |
| Key exchange | RSA key transport, static or ephemeral (EC)DH | Ephemeral (EC)DH or hybrid KEM only |
| Forward secrecy | Optional | Always (except for PSK-only resumption) |
| Server certificate on the wire | In clear text | Encrypted |
| Record protection | CBC, RC4 or AEAD | AEAD only |
| Signature covers | The key exchange parameters | The whole transcript |

**Forward secrecy** means that recorded traffic stays safe even if the server's long-term private key is stolen later, because each session's keys came from ephemeral key pairs that were thrown away. In TLS 1.2 with RSA key transport, the client encrypted the session secret to the server's certificate key. Anyone holding that key, including the server's owner, could decrypt any recorded session, years later.

That property was used deliberately inside enterprises. Network monitoring tools, intrusion detection systems and application performance tools were loaded with copies of server private keys and decrypted traffic **passively** from a network tap. TLS 1.3 ended that technique. Every session now uses fresh ephemeral keys, so a copy of the certificate key decrypts nothing.

Some organisations, especially in finance, argued that this broke compliance monitoring and troubleshooting. The ETSI standards body published a variant, TS 103 523-3, that uses a static Diffie-Hellman key on the server so that a holder of that key can decrypt traffic. It deliberately removes forward secrecy, and browser makers and most security practitioners reject it. The mainstream answer is to decrypt **actively** at a proxy or load balancer that terminates TLS, or to export keys from endpoints, which Chapter 21 covers.

> **At Meridian.** Meridian's Network Engineering team once relied on passive decryption appliances on the DC-East core to troubleshoot payment API latency. When the public load balancers moved to TLS 1.3, those appliances went blind. The PKI and Cryptography Services team refused a request to re-enable RSA key transport. Instead, Meridian now terminates TLS on its load balancers, which log timing and request metadata, and sends a mirror of decrypted traffic to approved tools inside the same PCI DSS segment. The decision is recorded in the cryptographic standard (Chapter 42) as a named exception path rather than a weakening of the protocol.

## 20.5 The key schedule

TLS 1.3 derives every key from the shared secret through a **key schedule** built entirely on HKDF (Chapter 7). It runs in three stages, each mixing in more secret material and the transcript hash so far:

1. **Early secret.** Derived from a pre-shared key when resuming a session, otherwise from zeros.
2. **Handshake secret.** Mixes in the (EC)DH or KEM shared secret. Produces the keys that encrypt the rest of the handshake.
3. **Master secret.** Produces the **application traffic keys**, separate for each direction.

Each key is derived with a distinct label ("c hs traffic", "s ap traffic", "exp master" and so on) and the transcript hash, so keys for different purposes and different connections are independent. Compromising the key for one direction or one stage tells an attacker nothing about another.

Two further outputs matter in enterprise systems:

- **KeyUpdate.** Either side can send a KeyUpdate message on a long-lived connection to move to a fresh traffic key derived from the current one. This limits how much data any one key protects, which matters for connections that stay open for days, such as database pools or message brokers.
- **Exporters.** An application can ask TLS for an **exported key** bound to this connection. Protocols use this to tie their own authentication to a specific TLS session. Token binding schemes and some open banking profiles (Chapter 39) rely on the same idea of binding a credential to the channel.

> **In practice.** For debugging, most TLS libraries can write the derived secrets to a **key log file** (the `SSLKEYLOGFILE` environment variable in browsers, curl and many language runtimes). Wireshark uses it to decrypt captured traffic. Never enable this on production systems: anyone with the file can read the traffic. Treat a key log found on a server as a security incident.

## 20.6 Resumption and 0-RTT

Full handshakes cost public-key operations and a round trip. TLS 1.3 lets clients **resume** a previous session:

- After a handshake, the server sends one or more **session tickets** that let the client derive a pre-shared key (PSK) for future connections.
- On reconnection, the client presents the ticket. The server can skip certificate verification, and the handshake can still include a fresh (EC)DH exchange to preserve forward secrecy (the recommended `psk_dhe_ke` mode).

Session tickets are usually encrypted with a **ticket key** held by the server. In a fleet of load balancers, that key is shared across every node so that any node can resume any session. A long-lived, shared ticket key is a quiet weak point: whoever steals it can decrypt resumed sessions that used PSK-only mode. Rotate ticket keys often, and keep them in memory only.

### 0-RTT early data and replay

TLS 1.3 also lets a resuming client send application data in its very first message, before the handshake completes. This **0-RTT** (zero round trip) data makes repeat visits faster, but it has a serious weakness: **it can be replayed.** An attacker who captures the client's first flight can send it to the server again, and the server may process the request twice. 0-RTT data also lacks forward secrecy with respect to the ticket key.

The rule is simple: **only allow 0-RTT for requests that are safe to repeat**, such as fetching a public page. Never accept it for payments, state changes or anything non-idempotent. CDNs that support 0-RTT typically pass a header such as `Early-Data: 1` to the origin so the application can refuse a risky request. Many servers disable 0-RTT entirely, and that is a sensible default for a bank.

## 20.7 Client authentication

By default only the server authenticates. The server can also send a **CertificateRequest**, and the client then returns its own Certificate and CertificateVerify. This is **mutual TLS (mTLS)**. It is widely used between services, in service meshes (Chapter 24), for device authentication and for high-security partner APIs. It needs a way to issue and rotate client certificates at scale, usually from a private CA (Chapter 15).

In TLS 1.3 the client certificate is encrypted, so a passive observer can no longer see which user or device connected. That is good for privacy, but it means firewalls that used to read the client certificate from the wire must now terminate TLS to make decisions on it.

> **Watch out.** Public certificate authorities have removed the client authentication purpose from public TLS certificates. Chrome's root program requires dedicated server-only hierarchies, with new public TLS issuance moving to server-only certificates during 2026. Any system that used a public TLS certificate as a client certificate, a common shortcut for partner integrations, must move to a private PKI. Check your CA's current timeline and inventory those uses now.

Chapter 21 covers how to deploy mTLS in practice.

## 20.8 Hiding the server name: Encrypted Client Hello

Even with TLS 1.3, one important piece of information remains visible: the **SNI** in the ClientHello, which names the site the user is visiting. Network operators, censors and attackers can all read it, and so can enterprise web filters.

**Encrypted Client Hello (ECH)** fixes this. The server publishes an ECH public key in DNS, in an HTTPS resource record. The client encrypts its real ClientHello, including the SNI, using HPKE (Chapter 9), and wraps it inside an outer ClientHello that names only a shared front end, such as a CDN. Observers see that you connected to the CDN, not which of its thousands of sites you visited.

> **Current development.** ECH was published as RFC 9849 in March 2026, after years of drafts. Major browsers shipped support in 2023 and 2024, and large CDNs enable it for hosted sites. It depends on encrypted DNS: if DNS lookups are visible, the site name leaks there instead.

ECH matters to enterprises in two directions. On the outbound side, a secure web gateway that classified traffic by SNI loses that signal, which is one reason managed browsers in many enterprises disable ECH by policy and why inspection designs are moving to full proxying (Chapter 21). On the inbound side, Meridian's customer website gains privacy for its customers if its CDN enables ECH. Chapter 23 covers ECH at the edge.

## 20.9 Post-quantum key exchange in TLS

The ephemeral ECDH exchange in TLS is vulnerable to **harvest now, decrypt later**: an attacker who records traffic today could decrypt it once a large quantum computer exists (Chapter 44). TLS 1.3's design makes the fix straightforward, because the key exchange is just a named group carried in the key share.

The new group **X25519MLKEM768** combines classical X25519 with the post-quantum KEM ML-KEM-768 (Chapter 45). Both shared secrets are concatenated and fed into the key schedule, so the connection is secure as long as **either** algorithm holds. This **hybrid** design protects against quantum attackers while hedging against an undiscovered weakness in the newer algorithm.

> **Current development.** X25519MLKEM768 has been the default key exchange in Chrome and Edge since version 131 and in Firefox since version 132 (late 2024). Apple added it across iOS 26 and macOS in 2025. Cloudflare reported that by late 2025 roughly half of the human-initiated traffic reaching its network used hybrid post-quantum key exchange. Server-side and internal adoption lag far behind, which is the migration challenge Chapter 46 addresses.

The hybrid key share is larger: about 1,216 bytes from the client instead of 32. This occasionally breaks old middleboxes that cannot handle a ClientHello spanning more than one network packet, another case of ossification. Enterprises meet this first on outbound inspection proxies and on old load balancers, where an upgrade, not a protocol change, is the fix.

Note what the hybrid group does **not** do. It protects confidentiality against future decryption. Authentication still uses classical signatures in certificates, which only need to resist an attacker at the moment of the handshake. Post-quantum certificates are a separate and later migration.

## 20.10 Where TLS 1.3 lives in the enterprise

Rolling out TLS 1.3 is rarely a protocol problem. It is an inventory problem, because the protocol has to be enabled on every terminating device and library, each owned by a different team:

- **Edge and load balancers:** CDNs and cloud load balancers enable TLS 1.3 by policy setting; on-premises ADCs need a profile change and sometimes a firmware upgrade.
- **Runtimes and libraries:** OpenSSL 1.1.1 and later, Java 11 and later, .NET on current Windows versions, and Go all support TLS 1.3. Older Java 8 builds, embedded devices and some mainframe stacks lag.
- **Inspection devices:** must support TLS 1.3 on both sides of the proxy, or they silently downgrade every connection to TLS 1.2.

> **At Meridian.** The PKI and Cryptography Services team owns Meridian's TLS standard, but Network Engineering owns the CDN, WAF and load balancers, Platform Engineering owns the Kubernetes ingress and mesh, and application teams own their own runtimes. The standard says "TLS 1.3 preferred, TLS 1.2 permitted with forward-secret AEAD suites, nothing older". Compliance is measured by the scanning described in Chapter 21, not by asking teams.

> **Compliance hook.** PCI DSS v4.0.1 requirement 4.2.1 requires strong cryptography to protect cardholder data during transmission over open, public networks, and requirement 4.2.1.1 requires an inventory of the trusted keys and certificates used for it. NIST SP 800-52 Rev. 2 sets TLS rules for US federal systems and requires support for TLS 1.3. ISO/IEC 27001:2022 control A.8.24 (use of cryptography) and DORA's ICT risk requirements expect a documented policy for protocols in transit. A TLS 1.3 first configuration with a measured inventory satisfies the spirit of all of them.

## 20.11 Lab: watch a TLS 1.3 handshake

You need OpenSSL (3.5 or later for step 2), curl and Wireshark.

**1. Inspect a live handshake.**

```bash
openssl s_client -connect example.com:443 \
  -servername example.com -tls1_3 < /dev/null 2>/dev/null \
  | grep -E "Protocol|Cipher|Temp Key|Peer signature|Verif"
```

You will see the protocol version, the AEAD cipher suite, the key exchange group and the signature algorithm.

**2. Request post-quantum key exchange.** OpenSSL 3.5 and later support ML-KEM:

```bash
openssl s_client -connect cloudflare.com:443 \
  -groups X25519MLKEM768 < /dev/null 2>/dev/null \
  | grep -iE "temp key|group"
```

Repeat with `-groups X25519` and compare the size of the ClientHello in a packet capture.

**3. Decrypt your own traffic.** Set a key log file, make a request, and open the capture in Wireshark:

```bash
export SSLKEYLOGFILE=$HOME/tlskeys.log
curl -s https://example.com > /dev/null
```

In Wireshark, set Preferences, Protocols, TLS, "(Pre)-Master-Secret log filename" to that file while capturing. The encrypted records become readable, and you can match every message in Figure 20.1. Delete the key log afterwards.

**4. Prove that a stolen certificate key no longer helps.** Run a local server with `openssl s_server -www -cert cert.pem -key key.pem -accept 8443`, capture a TLS 1.3 session, and try to decrypt it in Wireshark using only the RSA private key (Preferences, Protocols, TLS, RSA keys list). Nothing decrypts. Force TLS 1.2 with the RSA key exchange cipher `AES128-GCM-SHA256` and try again: this time the key decrypts the session. This is the forward secrecy difference from section 20.4.

**Optional cloud extension.** Create a cloud load balancer with a TLS 1.3 only policy in front of a small instance and repeat step 1. Delete it afterwards: load balancers bill by the hour even when idle.

## 20.12 Failure story: the downgrade that TLS 1.3 was built to stop

In 2016, researchers published **DROWN**. Many servers that supported only modern TLS for their websites still had **SSLv2**, a protocol from 1995, enabled on another service that shared the same RSA key, such as an old mail server configuration. SSLv2's weaknesses let an attacker use that server as a Bleichenbacher oracle (Chapter 8) to decrypt recorded *modern TLS* connections that used RSA key exchange with the same key. At disclosure, about a third of HTTPS servers were vulnerable, including many large sites.

DROWN combined three things TLS 1.3 removed by design: RSA key transport (no forward secrecy, and an oracle target), the reuse of one key across protocols, and support for ancient protocol versions. TLS 1.3 also signs the full transcript and puts special values in the server random that let clients detect downgrade attempts.

Its lesson for enterprise operators remains: a key is only as safe as the weakest service that uses it. Disable old protocols everywhere a key is used, not only on the main website, never share keys across services, and keep the certificate inventory (Chapter 17) detailed enough to tell you where each key lives.

## 20.13 Chapter summary

- TLS provides confidentiality, integrity and authentication through a handshake protocol and an AEAD record protocol.
- TLS 1.3 completes a full handshake in one round trip, encrypts everything after the ServerHello, signs the whole transcript, and removes the legacy features behind two decades of attacks.
- Forward secrecy is mandatory, which ended passive decryption with copied server keys; enterprises now decrypt actively at a terminating proxy or load balancer.
- An HKDF key schedule derives independent, labelled keys at each stage, with KeyUpdate for long connections and exporters for channel binding.
- Session resumption speeds reconnection; ticket keys must be rotated, and 0-RTT data can be replayed and must be limited to safe requests.
- Client certificates are encrypted in TLS 1.3, and public TLS certificates no longer serve as client certificates.
- ECH hides the destination site and weakens SNI-based filtering.
- Hybrid X25519MLKEM768 key exchange protects against harvest now, decrypt later and is already the browser default; servers and internal systems are the lagging half.
