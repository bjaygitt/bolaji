## 16.1 Identity is a key-management problem

Three words are often mixed up:

- **Authentication** answers "who are you?" (logging in).
- **Authorisation** answers "what may you do?" (permissions).
- **Federation** lets one system trust another system's answer, so a user who logged in once can use many services. This is **single sign-on (SSO)**.

Identity protocols carry these answers between systems as **tokens** or **tickets**: small data structures that say "this user authenticated, at this time, for this service", protected by a signature or a MAC. The protection is what lets a service trust a token without calling back to the issuer every time. It also means the issuer's key is one of the most powerful keys in any organisation. Anyone who holds it can mint any identity, including an administrator's, and the forged tokens look exactly like real ones.

An enterprise typically runs at least three generations of identity protocol side by side:

| Generation | Protocol | Typical use | Protected by |
| --- | --- | --- | --- |
| On-premises | Kerberos (Active Directory) | Windows logon, file shares, intranet apps | Symmetric keys derived from passwords and service secrets |
| Web SSO | SAML 2.0 | Enterprise SaaS sign-in | XML signatures with an RSA key and certificate |
| Modern web and API | OAuth 2.0, OpenID Connect, JWT | Mobile apps, APIs, cloud consoles, workload identity | JSON signatures with keys published as a JWKS |
| Authenticators | FIDO2 passkeys, PIV smart cards, client certificates | Proving the user is present | Private keys in secure hardware |

The first three rows carry an identity claim between systems; the last row is how the user proves who they are in the first place.

## 16.2 Kerberos and Active Directory

**Kerberos**, designed at MIT in the 1980s and specified today in RFC 4120, is the authentication protocol at the heart of Microsoft **Active Directory (AD)**. It lets users and services prove their identities over an untrusted network using only symmetric cryptography, without ever sending passwords.

The answer is a trusted third party, the **Key Distribution Centre (KDC)**, which in AD runs on every domain controller. The KDC shares a long-term secret key with every **principal** (user, computer or service). For a user, that key is derived from their password. For a service, it is derived from the service account's password or a random machine secret.

A logon works in three exchanges:

1. **Authentication service exchange.** The user's machine proves knowledge of the user's key by encrypting a timestamp with it (this is **pre-authentication**). The KDC replies with a **ticket-granting ticket (TGT)**, encrypted with the key of a special account called **krbtgt**, and a session key the user can read.
2. **Ticket-granting exchange.** When the user wants a service, such as a file server, the machine presents the TGT and asks for a **service ticket**. The KDC issues one, encrypted with the service account's key.
3. **Application exchange.** The machine presents the service ticket to the file server, which decrypts it with its own key and learns who the user is. The user's password never crossed the network.

The **encryption type** decides how strong all of this is. Modern AD uses AES-256 and AES-128 with HMAC-SHA1. Older domains still allow **RC4-HMAC**, whose key is simply the unsalted NT hash of the password. During 2026 Microsoft moved domain controllers to AES-only defaults, so RC4 now works only where an administrator explicitly enables it.

### The keys that matter, and how they are attacked

Two attacks show why Kerberos is a key-management problem:

- **Golden Ticket.** The krbtgt key encrypts every TGT in the domain. An attacker who steals it (usually by dumping it from a compromised domain controller) can forge a TGT for any user, with any group memberships and any lifetime. The fix after compromise is to reset the krbtgt password **twice**, because AD keeps the previous key valid so that tickets in flight still work.
- **Kerberoasting.** Any authenticated user can request a service ticket for any service account. The ticket is encrypted with that account's password-derived key, so the attacker takes it offline and guesses passwords until one decrypts it. Weak service-account passwords and RC4 make this fast. The defence is **group managed service accounts (gMSA)**, whose passwords are long, random and rotated automatically, plus AES-only encryption.

**PKINIT** (RFC 4556) replaces the password-derived key in the first exchange with a certificate and private key, usually on a smart card. This is how Windows smart card logon works, and it connects Kerberos to the enterprise PKI of Chapter 15 (see section 16.8).

> **At Meridian.** The IAM team owns Active Directory, but the krbtgt key is on the PKI and Cryptography Services team's register of critical keys alongside the root CAs. It is rotated twice a year by a scripted, staggered procedure, and immediately after any suspected domain controller compromise. The SOC alerts on TGTs with lifetimes longer than the domain policy allows, which is the most common sign of a forged ticket.

## 16.3 SAML 2.0

**SAML 2.0**, standardised by OASIS in 2005, is the XML-based federation standard that still carries most enterprise SSO into SaaS applications. The two parties are the **identity provider (IdP)**, which authenticates the user, and the **service provider (SP)**, the application.

In the common SP-initiated flow, the user visits the application, is redirected to the IdP, logs in, and is sent back with a **SAML response** containing an **assertion**: an XML document stating the user's identity, attributes such as email and group memberships, the intended audience, and a validity window. The IdP signs the assertion (or the whole response) with **XML Digital Signature**, using an RSA key whose certificate the SP was given in advance in the IdP's **metadata** file. The SP verifies the signature with that certificate and trusts the contents.

Two points make SAML different from what Chapter 12 taught about certificates:

- The signing certificate is usually **self-signed** and long-lived. Nobody validates its chain. Trust comes from the fact that the SP administrator pasted it into the configuration.
- When the IdP rotates its key, every SP must be given the new certificate. An enterprise with 300 SAML applications has 300 places to update, which is why SAML certificate expiry is a classic cause of SSO outages.

XML signatures are notoriously difficult to verify correctly. In a **signature wrapping attack**, the attacker moves the signed element elsewhere in the document and inserts an unsigned, forged one where the application looks for it. The signature still verifies, but the application reads the forgery. If you must accept SAML, use a mature, maintained library, require signed assertions, check audience, recipient and validity times, and keep the library patched.

## 16.4 OAuth 2.0 and OpenID Connect

**OAuth 2.0** (RFC 6749) lets a user grant an application limited access to their resources without giving it their password. It has four roles:

| Role | Example |
| --- | --- |
| **Resource owner** | The user |
| **Client** | The application that wants access |
| **Authorisation server** | The system that authenticates the user and issues tokens |
| **Resource server** | The API holding the data |

The recommended flow for most applications is the **authorisation code flow with PKCE**:

1. The client sends the user to the authorisation server with a **code challenge**, the hash of a random secret called the **code verifier**.
2. The user logs in and approves access.
3. The authorisation server redirects back with a short-lived **authorisation code**.
4. The client exchanges the code, plus the original code verifier, for an **access token** and often a **refresh token**.

**PKCE** (Proof Key for Code Exchange, RFC 7636) makes a stolen authorisation code useless without the verifier, which never left the client. The OAuth 2.1 consolidation of best practices requires it for all clients. Machine-to-machine calls use the **client credentials** flow instead, where the client authenticates with a secret or, better, a signed JWT or client certificate.

Access tokens are usually **bearer tokens**: whoever presents one gets access, like cash. Defences are short lifetimes (minutes), narrow **scopes**, and **sender-constrained tokens** bound to a key the client holds. With mutual TLS (RFC 8705) the token is bound to the client's certificate. With **DPoP** (RFC 9449) the client signs each request with a private key, so a stolen token alone is not enough.

OAuth on its own is about access, not identity. **OpenID Connect (OIDC)** adds an **ID token**: a signed statement from the identity provider that a user authenticated, when, how, and for which client. Modern enterprise SSO and cloud workload identity federation (a CI pipeline proving its identity to a cloud provider without a stored secret) both use OIDC.

An OIDC provider publishes a **discovery document** at `/.well-known/openid-configuration`, which names its issuer, endpoints and **jwks_uri**. That URL serves a **JSON Web Key Set (JWKS)**: the provider's current signing public keys, each with a **key ID (kid)**. Relying services fetch the JWKS over TLS, cache it, and verify token signatures locally. Section 16.6 explains how this design makes key rotation almost painless compared with SAML.

## 16.5 JSON Web Tokens

Both OIDC ID tokens and many access tokens are **JSON Web Tokens (JWT)**, RFC 7519, signed using the JSON Web Signature format. A JWT has three base64url-encoded parts separated by dots:

```text
header.payload.signature
{"alg":"ES256","kid":"2026-09"}
{"iss":"https://id.example","sub":"u123","aud":"api","exp":1791500000}
<signature over header and payload>
```

The **header** names the signing algorithm and key. The **payload** holds **claims**: issuer (`iss`), subject (`sub`), audience (`aud`), expiry (`exp`) and others. A JWT is signed, not encrypted: anyone who holds it can read the payload, so never put secrets in it. (Encrypted JWTs, called JWE, exist but are less common.)

### How to validate a JWT

Each of these checks has a real breach behind it:

1. **Fix the algorithm on your side.** Accept only the algorithm you expect for this issuer, such as ES256 or RS256. Never let the token's header choose.
2. **Verify the signature** with the issuer's key, selected by `kid` from a JWKS you fetched over TLS from a configured URL.
3. **Check the issuer** (`iss`) is the one you trust. In multi-tenant IdPs, check the tenant too.
4. **Check the audience** (`aud`) is your service. Otherwise a token issued for another service can be replayed against yours.
5. **Check time claims** (`exp`, `nbf`, `iat`) with a small allowance for clock skew.
6. **Check token type and purpose**, so an ID token is not accepted as an access token.

### Classic JWT attacks

| Attack | How it works | Prevention |
| --- | --- | --- |
| `alg: none` | Attacker sets the algorithm to "none" and removes the signature; naive libraries accept it | Reject "none"; fix the algorithm (check 1) |
| Algorithm confusion | Attacker changes RS256 to HS256 and signs with the server's public key as an HMAC secret | Bind each key to one algorithm |
| `kid` or `jku` injection | Attacker points the header at a key they control, or injects paths into `kid` | Only use keys from configured JWKS URLs |
| Missing audience check | Token for service A accepted by service B | Always check `aud` |
| Weak HMAC secret | Short shared secrets for HS256 guessed offline | Use asymmetric signatures, or 256-bit random secrets |

> **In practice.** Prefer asymmetric signing (ES256, RS256 or EdDSA) for tokens consumed by more than one service. With HMAC (HS256), every service that verifies tokens holds the secret and can therefore also mint them. Give application teams one approved library or gateway that performs every check above: most token breaches come from teams writing their own validation.

## 16.6 How identity providers manage their signing keys

The **identity provider (IdP)** authenticates users and signs the tokens. Most enterprises use Microsoft Entra ID, Okta and Ping Identity, sometimes alongside on-premises Active Directory Federation Services (AD FS). Each must rotate its signing keys while thousands of relying applications keep working.

### Rotation by publication: the JWKS pattern

OIDC solves rotation with three steps:

1. **Pre-publish.** The IdP generates a new key pair and adds the public key to the JWKS while still signing with the old key. Relying services that refresh their cache now know both keys.
2. **Switch.** The IdP starts signing with the new key. Each token's `kid` tells verifiers which key to use, so old and new tokens both verify.
3. **Retire.** Once every token signed with the old key has expired, the IdP removes the old public key.

This only works if relying services fetch keys dynamically; an application that hard-codes the public key breaks on rotation day.

### How the major providers do it

The table summarises public documentation as of 2026; check current documentation before you design around it.

| Provider | OIDC and OAuth signing keys | SAML signing keys | Customer control |
| --- | --- | --- | --- |
| Microsoft Entra ID | Tenant-wide keys published in the JWKS; rolled periodically and immediately in an emergency, with no fixed published schedule | A signing certificate per enterprise application, valid for three years by default; admins add a new one and activate it before expiry | Relying applications must handle rollover automatically |
| Okta | Keys per authorisation server; rotated automatically about four times a year, with new keys published weeks ahead | Per-application signing certificates that admins generate and roll over | Automatic or manual rotation per authorisation server |
| Ping Identity (PingFederate, PingOne) | PingFederate can rotate OAuth and OIDC signing keys automatically or use static keys you manage | Signing certificates managed in the certificate store, optionally in an HSM | Self-managed PingFederate can keep keys in a customer HSM |
| AD FS | Token-signing certificates with optional automatic rollover | Same token-signing certificate | Fully customer-managed, which is both the strength and the risk |

Three differences matter to an architect:

- **Who holds the private key.** With cloud IdPs such as Entra ID and Okta, the provider generates and protects the signing keys inside its own infrastructure, and you cannot export them. With self-hosted products such as PingFederate or AD FS, you hold them, so their protection (HSM or not) is your responsibility.
- **Shared versus per-application keys.** A tenant-wide OIDC key is simple to rotate but means one key signs tokens for every application. Per-application SAML certificates limit blast radius but multiply the rotation work.
- **Notification.** Some providers warn before rotation and some do not. Okta's documentation, for example, says there is no built-in event before a rotation, and recommends watching the JWKS endpoint.

### Why these keys deserve root-CA protection

Two incidents show what happens when identity signing keys escape:

- In the **2020 software supply-chain intrusion** that affected many US agencies and companies, attackers who reached on-premises AD FS servers stole token-signing certificates and forged SAML assertions, a technique researchers named **Golden SAML**. Forged tokens gave access to cloud email and documents and bypassed multi-factor authentication, because the attacker never logged in at all.
- In the **2023 Storm-0558** incident (Chapter 10), an acquired Microsoft consumer signing key, combined with a validation flaw that let enterprise systems accept consumer-signed tokens, allowed attackers to forge tokens for enterprise mailboxes. The key had been created in 2016, and the government review board criticised the absence of automated rotation that would have retired it years earlier.

Keep self-managed signing keys in HSMs, rotate them on a schedule, scope keys by tenant and purpose, validate issuer and tenant on every token, and monitor for tokens that do not match normal issuance (a valid signature with no matching sign-in log is the signature of Golden SAML).

> **At Meridian.** Meridian runs a cloud IdP for workforce SSO and a separate customer identity platform for the mobile app and website, with on-premises AD for Windows. The IAM team owns all three. The PKI and Cryptography Services team owns the rotation calendar for every self-managed signing key, keeps the customer platform's keys in its general-purpose HSM cluster, and runs a JWKS watcher that posts to the owning teams' channels whenever a new `kid` appears at any of the IdPs. SAML signing certificates are tracked in the same certificate inventory as TLS certificates (Chapter 17), so they appear in the 60-day expiry report.

## 16.7 FIDO2 and passkeys

Passwords are phishable, and so are one-time codes, which a fake login page can relay in real time. **FIDO2**, made up of the W3C **WebAuthn** browser API and the FIDO Alliance's **CTAP** protocol for external authenticators, replaces shared secrets with public-key cryptography. **Passkeys** are the user-friendly name for FIDO2 credentials.

How it works:

1. **Registration.** The **authenticator** (a phone, a laptop's secure hardware, or a USB or NFC security key) creates a new key pair for this specific website, called the **relying party**. The public key goes to the website. The private key stays in the authenticator, unlocked by a fingerprint, face or PIN that never leaves the device.
2. **Login.** The website sends a random challenge. The authenticator signs it together with the website's origin (its exact domain), and the site verifies the signature with the stored public key.

Two properties make FIDO2 **phishing-resistant**:

- The signature covers the origin. A key created for `bank.example` will never sign for `bank-example.login.site`. The browser enforces this, not the user.
- There is no shared secret on the server. A breached website loses only public keys.

### Synced and device-bound passkeys

Passkeys come in two forms, and the difference matters to an enterprise:

- **Synced passkeys** are backed up and synchronised across a user's devices by a platform or password manager (Apple, Google, Microsoft and third-party managers). They recover easily when a phone is lost, which suits customers, but the private key exists on several devices and in the sync provider's end-to-end encrypted store.
- **Device-bound passkeys** never leave one piece of hardware, such as a FIDO2 security key from Yubico, Feitian or Google, or a passkey held in Microsoft Authenticator. They give the strongest assurance and suit administrators and high-risk staff.

During registration an authenticator can provide **attestation**: a statement, signed by a key the manufacturer installed, proving the make and model. Enterprises use attestation, checked against the FIDO Alliance Metadata Service, to allow only approved hardware for privileged accounts. All three major IdPs support FIDO2 for workforce sign-in and can restrict which authenticator models are accepted.

> **Current development.** US federal guidance has required phishing-resistant multi-factor authentication for agency staff since 2022. NIST's digital identity guidelines classify device-bound hardware authenticators at the highest assurance level (AAL3), and a 2024 supplement recognised synced passkeys as meeting AAL2. As of 2026, many regulated organisations require FIDO2 or smart cards for all administrators and are extending them to all staff.

## 16.8 Smart cards, PIV and certificate-based authentication

Before passkeys, the strongest workforce authenticator was the **smart card**: a chip card holding a private key that cannot be extracted, unlocked with a PIN. The model is the US government's **Personal Identity Verification (PIV)** card, defined in FIPS 201-3, and its Department of Defense counterpart, the **Common Access Card (CAC)**. Many regulated firms use PIV-compatible cards or USB tokens.

A PIV card holds several key pairs in standard slots, each with its own X.509 certificate issued by the organisation's PKI:

| Slot | Purpose | Typical use |
| --- | --- | --- |
| 9A | PIV Authentication | Windows logon, VPN, web sign-in |
| 9C | Digital Signature | Signing email and documents |
| 9D | Key Management | Decrypting S/MIME email (key often escrowed) |
| 9E | Card Authentication | Physical door access, no PIN |

**Certificate-based authentication (CBA)** is the general pattern: the user proves possession of a private key, and the server validates the matching certificate's chain, validity and revocation status (Chapter 14), then maps the certificate to a user account. The mapping step is where most of the risk lives.

### Mapping certificates to accounts

In Active Directory, smart card logon uses PKINIT. The domain controller validates the certificate, then maps it to an account, traditionally by the user principal name in the certificate's SAN. In 2022 researchers showed that weak mappings let an attacker who could obtain a certificate with a crafted name authenticate as someone else, including a domain controller. Microsoft's response, KB5014754, introduced **strong certificate mapping**: certificates carry a security identifier (SID) extension, or are explicitly mapped by issuer and serial number. Domain controllers moved to full enforcement during 2025, and certificates without a strong mapping are now refused. Any enterprise PKI template used for logon (Chapter 15) must include the SID extension.

Cloud IdPs support the same pattern:

- **Microsoft Entra ID** offers native certificate-based authentication: you upload your issuing CA certificates, configure revocation checking, and choose which certificate field binds to which user attribute.
- **Okta** supports PIV and smart card sign-in through a smart card identity provider configuration, validating against the CA chain you supply.
- **Ping Identity** supports X.509 certificate authentication through a PingFederate adapter and in PingOne.

**Derived PIV credentials** (NIST SP 800-157) put an equivalent certificate and key into a phone's secure hardware, so staff without card readers keep the same assurance.

> **Compliance hook.** PCI DSS v4.0.1 requirement 8.4.2 requires multi-factor authentication for all access into the cardholder data environment, and 8.5.1 requires that MFA systems resist replay. NIST SP 800-63B defines assurance levels and requires phishing resistance at AAL3. ISO/IEC 27001:2022 controls A.5.17 (authentication information) and A.8.5 (secure authentication) expect a documented authentication standard. DORA and NIS2 both call for strong authentication. FIDO2 or PIV for administrators, with IdP signing keys in HSMs and a rotation record, gives auditors clean evidence.

## 16.9 Lab: build and break a JWT, then watch a JWKS

You need Python 3 with `pip install pyjwt cryptography`, plus curl and jq.

**1. Create and verify a signed JWT.**

```python
import jwt, time
from cryptography.hazmat.primitives.asymmetric import ec
key = ec.generate_private_key(ec.SECP256R1())
tok = jwt.encode({"iss": "https://id.lab", "aud": "api", "sub": "u1",
                  "exp": int(time.time()) + 300}, key, algorithm="ES256",
                 headers={"kid": "lab-1"})
print(jwt.decode(tok, key.public_key(), algorithms=["ES256"],
                 audience="api", issuer="https://id.lab"))
```

**2. Try the "none" attack.** Change the header to `{"alg":"none"}`, change `sub` to `admin`, and drop the signature (keep the trailing dot). Pass it to `jwt.decode` with `algorithms=["ES256"]`. It is rejected, because the verifier fixes the algorithm.

**3. Try the audience attack.** Encode a token with `aud: "other-service"` and decode with `audience="api"`. It is rejected. Remove the `audience` argument and note that the library refuses to skip the check silently.

**4. Simulate a key rotation.** Generate a second key, sign a new token with `kid: "lab-2"`, and write a verifier that holds a dictionary of keys by `kid`. Verify old and new tokens, then delete `lab-1` and confirm that only the new token verifies. This is the pattern of section 16.6.

**5. Inspect a real IdP.** Fetch a public discovery document and its JWKS:

```bash
curl -s https://login.microsoftonline.com/common/v2.0/\
.well-known/openid-configuration | jq -r .jwks_uri
curl -s https://www.googleapis.com/oauth2/v3/certs \
  | jq '.keys[] | {kid, alg, kty}'
```

Record the `kid` values and fetch them again in a few weeks to observe rotation.

**Optional cloud extension.** Create a free developer tenant with any of the IdPs in section 16.6, register an OIDC application, and decode the ID token it returns. Developer tiers are usually free, but paid features can start billing; delete the tenant afterwards.

## 16.10 Failure story: the token that trusted its own header

In 2015, security researcher Tim McLean reviewed popular JWT libraries across several languages and found two critical flaws in many of them. Some libraries accepted tokens with `"alg": "none"` as valid, even when the application expected signed tokens, so anyone could forge any identity by deleting the signature. Others allowed **algorithm confusion**: when a server expected RSA signatures, an attacker could change the header to HS256 and compute an HMAC using the server's public RSA key, which the library then used as the HMAC secret and accepted.

The mistake was the same in both cases: the library let attacker-controlled data, the token header, decide how the token would be verified. Libraries were patched to require callers to name allowed algorithms, and the JWT best-practice RFC 8725 was published in 2020 to codify the lessons. Variants still appear in custom code, which is why "fix the algorithm on your side" is the first rule of token validation, and why an enterprise should centralise validation rather than trust each team to rediscover it.

## 16.11 Chapter summary

- Identity protocols carry authentication as signed or encrypted tokens, so the issuer's key can mint any identity and deserves root-CA-level protection.
- Kerberos uses symmetric keys held by the KDC; the krbtgt key and service-account keys are prime targets, and RC4 is being retired in favour of AES.
- SAML signs XML assertions with keys whose certificates are distributed in metadata; rotation requires updating every service provider, and signature wrapping attacks demand mature libraries.
- OAuth 2.0 delegates access with the code flow and PKCE; OIDC adds signed ID tokens and publishes keys as a JWKS, which makes rotation a matter of pre-publishing new keys.
- Entra ID, Okta and Ping differ in who holds the signing keys, how often they rotate and whether they warn you; relying applications must fetch keys dynamically.
- FIDO2 passkeys bind signatures to the website's origin and resist phishing; device-bound passkeys and attestation suit privileged users.
- PIV smart cards and certificate-based authentication depend on strong certificate-to-account mapping, now enforced in Active Directory.
