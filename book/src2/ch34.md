## 34.1 Why centralised key managers exist

Almost every product in a data centre can encrypt. A storage array encrypts its drives. A tape library encrypts cartridges. A hypervisor encrypts virtual machines. A database encrypts its files with transparent data encryption (Chapter 27). Each product ships with a way to hold its own keys, usually a local keystore protected by a password or a file on disk.

That works for one system. At scale it creates four problems.

- **Separation.** If the array holds the key that encrypts its own drives, an attacker who steals the whole array (or a backup of its configuration) gets the key with it. Encryption at rest is only meaningful when the key lives somewhere other than the data.
- **Visibility.** Auditors ask "where are all your keys, who can use them, and when were they last rotated?" With fifty local keystores, nobody can answer.
- **Recovery.** Every local keystore needs its own backup and its own recovery procedure. Lose one array's key backup and the data on that array is gone.
- **Policy.** Key lengths, rotation periods, who may destroy a key: each product enforces these differently, if at all.

An **enterprise key manager** (EKM, also called a centralised key management system) is a hardened service that creates, stores, distributes, rotates and destroys keys for many different consumers, under one policy, with one audit log, usually anchored in a hardware security module (Chapter 33). NIST describes the design requirements for such systems in **SP 800-130**, its framework for cryptographic key management systems, which builds on the lifecycle concepts of SP 800-57 covered in Chapter 32.

A useful analogy is a bank's safe-deposit vault. Each branch could keep valuables in its own cupboard, but a central vault gives you one set of thick walls, one guard rota, one visitor log and one insurance policy. The key manager is that vault for keys, and the HSM is the steel door inside it.

> **At Meridian.** The PKI and Cryptography Services team runs Meridian's enterprise key manager as a shared service. Its clients include the SAN and NAS arrays in DC-East and DC-West, the tape library, the vSphere clusters, the database estate's TDE master keys, and the key broker that feeds the three cloud KMS services. Platform Engineering owns the consuming systems; the PKI team owns the keys, the policy and the recovery runbooks.

## 34.2 What a key manager does

Under the marketing, every enterprise key manager has the same anatomy.

- **A root of trust.** A master key that protects every other key in the system's database. In a strong design this lives in an HSM, either embedded in a physical appliance or external (a network HSM or a cloud HSM). Some products also offer a software root for lower assurance deployments.
- **A key database.** Every managed key is stored wrapped (encrypted) under the root. The database holds the key's metadata too: owner, algorithm, state, dates and links to related objects.
- **Client interfaces.** KMIP for storage and infrastructure (section 34.3), PKCS#11 and JCE for applications, REST APIs for automation, and often agents or connectors for specific products.
- **Policy and access control.** Which client may create, read, use or destroy which keys, and which administrator may change that.
- **Audit.** A tamper-evident record of every key operation, exported to the security information and event management (SIEM) platform.
- **Clustering.** Several nodes replicating keys and configuration so the service survives failure (section 34.9).

Two design distinctions matter when you compare products.

The first is **key serving versus key use**. Most data-centre integrations are key serving: the array asks for its key, the key manager sends the key over a mutually authenticated TLS channel, and the array holds it in memory to do the encryption. The key leaves the key manager. Other integrations are key use: the client sends data and the key manager encrypts or decrypts it, so the key never leaves. Key serving is fast and suits devices that encrypt at line rate. Key use gives stronger custody but adds latency and load to every operation.

The second is **separation of duties**. A good key manager lets you split the security officer (who manages keys and policy) from the system administrator (who patches nodes and manages networking), and requires a quorum of several people for dangerous actions such as destroying keys or restoring a backup. Chapter 32 explains why these controls matter.

## 34.3 KMIP in depth

Before standardisation, each storage vendor spoke its own key management protocol, so an organisation with three storage vendors needed three key managers. The **Key Management Interoperability Protocol (KMIP)**, an OASIS standard first approved in 2010, fixed that by defining one protocol that any client can use to talk to any server.

### The message format

KMIP messages are encoded in **TTLV** (Tag, Type, Length, Value). Every field is a tag identifying what it is (for example, Cryptographic Algorithm), a type (integer, enumeration, text string, byte string, structure and so on), a length, and the value. Structures nest, so a request is a tree of TTLV items. TTLV is compact and easy for firmware to parse, which matters for devices such as tape drives and disk controllers. Later versions also define XML and JSON encodings, mostly used for testing and web-style clients.

Messages travel over TLS, normally on TCP port **5696**. A request message has a header (protocol version, authentication, batch count) and one or more batch items, each naming an operation and its payload. The server returns a response with a result status for each batch item.

### Managed objects

KMIP manages more than symmetric keys. Its **managed objects** include:

| Object | Typical use |
| --- | --- |
| Symmetric Key | Drive, tape, VM and TDE encryption keys |
| Public Key and Private Key | Asymmetric pairs, often linked to each other |
| Certificate | X.509 certificates related to key pairs |
| Secret Data | Passwords and other opaque secrets |
| Opaque Object | Anything the server should store but not interpret |
| Split Key | One share of a key split among custodians |

Each object carries **attributes**: a Unique Identifier assigned by the server, a Name, Cryptographic Algorithm and Length, a Cryptographic Usage Mask (encrypt, decrypt, wrap and so on), Object Group, Links to related objects, and a set of dates. Attributes are how clients find keys later.

### Operations and the key lifecycle

The core **operations** map directly onto the key lifecycle:

- **Create** and **Create Key Pair** generate keys on the server. **Register** stores a key the client generated.
- **Locate** finds objects by attributes, such as "the active key named array-07-kek".
- **Get** returns the key material, usually wrapped or over the TLS session.
- **Activate**, **Revoke** and **Destroy** move the object through its states.
- **Re-key** creates a replacement key linked to the old one.
- **Get Attributes**, **Add Attribute** and **Modify Attribute** manage metadata.
- **Encrypt**, **Decrypt**, **Sign** and **MAC**, added in later versions, let the server use the key without releasing it.
- **Query** and **Discover Versions** let a client learn what the server supports.

KMIP's object states follow NIST's lifecycle model: **Pre-Active**, **Active**, **Deactivated**, **Compromised**, **Destroyed** and **Destroyed Compromised**. A key in the Deactivated state can still decrypt old data but should not encrypt new data, which is exactly the behaviour you want during rotation.

### Versions and profiles

KMIP has evolved through versions 1.0 to 1.4, then a cleaned-up 2.0 and 2.1, the latter approved as an OASIS Standard in 2020. As of 2026, version 3.0 exists as committee drafts that add, among other things, post-quantum algorithm identifiers, but production deployments still target 2.1 or earlier. Clients and servers negotiate the version with Discover Versions, so a server must support every version its oldest client speaks.

The specification is large, so OASIS also publishes **profiles**: defined subsets that a client or server claims to implement, such as a baseline server, a storage array with self-encrypting drives, a tape library client, or symmetric key lifecycle management. When a vendor says "KMIP compliant", ask which version and which profiles, and whether the combination of their client with your server has been tested. Vendors demonstrate interoperability at OASIS interop events and publish compatibility matrices; check both.

### Authentication and ownership

KMIP has a credential field in the request header, but nearly every real deployment authenticates the client with its **TLS client certificate**. The key manager maps the certificate's subject to a client identity, and that identity owns the keys it creates. This has consequences:

- The client certificate is effectively the password to every key that client owns. Protect its private key, monitor its expiry, and plan its renewal like any other critical certificate (Chapter 17).
- If ten arrays share one certificate, they share one identity, so any of them can read the others' keys. Issue one certificate per device, or at least per cluster.
- When a client certificate expires, the client cannot fetch keys. That is fine while keys are cached in memory and disastrous at the next reboot (see the failure story in section 34.11).

> **Watch out.** Some products default to accepting any client certificate signed by the configured CA. If that CA also issues certificates for thousands of other devices, every one of them can talk to your key manager. Use a dedicated issuing CA for KMIP clients, or pin client identities explicitly.

## 34.4 KMIP in the data centre: storage, tape and databases

### Storage arrays and self-encrypting drives

Enterprise arrays (NetApp ONTAP, Dell PowerMax and PowerStore, Pure Storage FlashArray, HPE and IBM arrays, among others) encrypt data either in the controller or with **self-encrypting drives** (SEDs) that hold the encryption inside each drive (Chapter 26). In both cases the drive or controller has a data encryption key that never leaves it, protected by an **authentication key** or key encryption key that the array fetches from the key manager.

The typical flow at boot:

1. The array controller establishes a TLS session to the key manager with its client certificate.
2. It sends Locate and Get for its authentication keys.
3. It uses those keys to unlock the drives, then holds them in memory.
4. If the key manager is unreachable, the drives stay locked and the array does not serve data.

That last step is the whole point of external key management (a stolen array cannot unlock itself) and also its biggest operational risk.

### Tape libraries

Tape encryption is built into LTO drives from LTO-4 onwards: the drive encrypts with AES-256-GCM as it writes. The question is who supplies the key. In **application-managed** encryption the backup software provides it. In **library-managed** encryption the library fetches keys from a key manager, through KMIP or a vendor protocol such as IBM's IPP. Because tapes are kept for years and leave the building, tape keys need long retention in the key manager, and crypto-shredding a set of tapes (Chapter 29) becomes a matter of destroying their keys.

### Databases

Oracle, SQL Server, MySQL and others can store their TDE master keys in an external key manager, through KMIP, PKCS#11 or a vendor connector (Chapter 27 covers the database side). Here the key manager often performs key use rather than key serving: it unwraps the database's internal keys on request.

## 34.5 VMware vSphere key providers

vSphere is the most common KMIP client in many data centres, and its design shows the trade-offs clearly. As of vSphere 8, there are three kinds of **key provider**.

| Key provider | Where keys come from | Notes |
| --- | --- | --- |
| **Standard Key Provider** | An external KMIP key manager, brokered by vCenter | The original model from vSphere 6.5. vCenter fetches keys and pushes them to hosts |
| **Native Key Provider** | vCenter itself, no external key manager | Added in vSphere 7.0 Update 2. Easy to deploy; back it up or lose access to encrypted VMs |
| **Trusted Key Provider** | An external key manager reached by attested Trust Authority hosts | Part of vSphere Trust Authority. Hosts get keys only after attesting their boot state |

The encryption model is the same in all three: a **key encryption key** (KEK) from the provider wraps a **data encryption key** (DEK) that ESXi generates for each encrypted VM or vSAN datastore. The wrapped DEK is stored with the VM. When a host needs to power on an encrypted VM, it obtains the KEK and unwraps the DEK. VM encryption, encrypted vMotion, virtual TPMs and vSAN data-at-rest encryption all rest on this.

From vSphere 7.0 Update 2, hosts with a TPM can use **key persistence**, caching keys so that encrypted VMs can start even when the key server is briefly unavailable. That improves availability but weakens the "stolen host cannot unlock itself" property, so decide deliberately.

> **In practice.** The Native Key Provider is attractive because it needs no external system, but it moves key custody into vCenter, alongside the infrastructure it protects. It suits branch clusters and labs. For regulated workloads, the Standard Key Provider pointed at a clustered, HSM-backed key manager gives separation of duties and a single audit trail. Whichever you choose, export and safely store the Native Key Provider backup the moment you create it.

> **At Meridian.** The vSphere clusters in DC-East and DC-West use a Standard Key Provider configured with all four key manager nodes, two per data centre. The branch hyperconverged clusters use the Native Key Provider, with the backup file escrowed in the key manager itself as Secret Data and protected by quorum.

How to choose among them:

- **Start from the client list.** A key manager is only as useful as its tested integrations. Get the compatibility matrix for your exact arrays, tape libraries, hypervisor and database versions.
- **Decide on the root of trust.** If you already run HSMs (Chapter 33), prefer a key manager that can use them. If you need FIPS 140-3 Level 3 assurance for the root, check the validation certificate, not the datasheet.
- **Look at the cloud story.** Do you need BYOK key brokering, external key stores, or both (sections 34.7 and 34.8)?
- **Count operational cost.** Appliances need firmware management and hardware refresh. SaaS removes that but places your root of trust with a vendor, which may conflict with the sovereignty goals that led you to an external key manager in the first place.

### AWS KMS External Key Store (XKS)

AWS launched the **External Key Store** in late 2022. A KMS key in an external key store has no key material inside AWS KMS. Instead, KMS calls an **XKS proxy** that the customer runs or buys, using a published proxy API specification. The proxy translates KMS requests into operations on the customer's key manager or HSM.

Key points from the AWS documentation:

- The proxy API is a small REST interface (encrypt, decrypt, key metadata and health status). KMS signs requests to the proxy with AWS Signature Version 4 using a proxy authentication credential.
- Connectivity can be over a public endpoint or through an Amazon VPC endpoint service, so traffic can stay on private links.
- Data is **double encrypted**: KMS first encrypts with key material held in its own HSMs, then the external key encrypts the result. Neither party alone can decrypt.
- AWS published an open-source reference proxy for PKCS#11 HSMs, and several key manager vendors (including Thales, Fortanix and Entrust, among others named at launch) offer proxies built into their products.

### Google Cloud External Key Manager (Cloud EKM)

Google's **Cloud EKM** lets a Cloud KMS key refer to a key held by a supported partner, reached over the internet or over a VPC network. Google lists its partners in its documentation; as of 2026 they include Fortanix, Futurex and Thales. Keys reached over VPC can be **coordinated external keys**, where Cloud KMS drives key creation and rotation in the partner system through an API, rather than an administrator configuring both sides by hand.

Cloud EKM pairs with **Key Access Justifications** (KAJ): each request to the external key manager carries a reason code, such as customer-initiated access or a Google-initiated system operation, and the partner can allow or deny on that basis. That is a genuine policy lever, but Google warns that denying the routine reason codes makes your own service unavailable.

### Microsoft Azure options

Azure has historically offered strong custody options inside its boundary: Key Vault Premium and **Managed HSM**, a single-tenant FIPS 140-3 Level 3 HSM service (Chapter 28). For Microsoft 365 content, **Double Key Encryption** keeps a second key on customer infrastructure for a small set of highly sensitive labelled documents (Chapter 29).

> **Current development.** As of 2026, Azure Key Vault Managed HSM offers **external key management** in public preview: the key encryption key sits in a customer-operated HSM outside Azure, and Managed HSM delegates wrap and unwrap operations to it through a customer-run EKM proxy, over mutual TLS. Thales and Entrust have announced support. Check preview terms and service coverage before you plan production workloads on it.

### What external key management really buys you

External key stores give you a kill switch: cut off the proxy and the cloud can no longer decrypt. They also give you an independent log of every use of the key. They do not stop the cloud from seeing plaintext while it processes data it has already decrypted, and they make your key manager a hard dependency of the cloud service. AWS's own guidance is explicit that XKS is for customers with a regulatory or contractual need, not a default. Reserve it for a small, clearly justified set of data.

## 34.8 Key brokering and multi-cloud key orchestration

Most organisations need something less extreme than HYOK. They want keys generated on their own HSMs, imported into cloud KMS (**bring your own key**, BYOK), rotated on a schedule, and visible in one inventory. Doing that by hand across three clouds and dozens of accounts does not scale. A **key broker**, or cloud key orchestration tool, automates it.

A key broker typically:

- Connects to each cloud's KMS with credentials scoped to key administration.
- Generates key material in the customer's HSM or key manager and imports it using each cloud's wrapping protocol.
- Schedules rotation, re-imports, disablement and deletion.
- Pulls back an inventory of native cloud keys (including ones created without the broker) and their usage logs.
- Offers a single view of key state for auditors.

Examples include Thales CipherTrust Cloud Key Manager, Fortanix DSM's cloud data control features, and Entrust's cloud key management capabilities; cloud-native alternatives exist within each provider's own tooling.

The broker becomes a very powerful system: it holds credentials able to disable every customer-managed key in every cloud account. Treat it like a tier-zero identity system, with quorum approval for destructive actions, network isolation and its own break-glass plan.

> **At Meridian.** Meridian uses BYOK through its key broker for most cloud workloads, giving it HSM-generated keys, one inventory and documented rotation. Only one EU dataset, required by a sovereignty commitment to a regulator, uses an external key store, and GRC signed off on the availability risk explicitly. The SOC receives alerts from the broker whenever a cloud key is disabled or scheduled for deletion.

## 34.9 High availability and disaster recovery

A key manager is a dependency of everything it serves. If it is down when an array reboots, a VM powers on or a database restarts, that system stays dark. Design for availability first.

### Clustering

Most products cluster several nodes that replicate keys and configuration, either active-active (any node serves requests) or with one writer and several readers. Place nodes in both data centres, and in the cloud if cloud services depend on them. Configure every client with the full list of nodes; KMIP clients, vCenter and most arrays accept several servers and fail over in order.

### Caching and its trade-off

Clients cache keys in memory, so a running array survives a key manager outage. The risk is concentrated at restart: a power event across a data centre is exactly when every client asks for keys at once, and exactly when the key manager is most likely to be unavailable. Test a cold start of the whole site.

### Dependency loops

> **Watch out.** Never run the only key manager nodes on storage or virtual machines that need that key manager to start. A virtual key manager on an encrypted datastore whose key it serves will not come back after a full power loss. Keep at least one node on independent hardware, with its own unencrypted boot path or a separate key source, and document the cold-start order.

### Backup and recovery

Clustering protects against node failure, not against corruption, ransomware or an administrator destroying keys. You also need:

- **Encrypted backups** of the key database, protected by a backup key that is itself split among custodians (M of N) or held in an offline HSM.
- **Root of trust recovery.** If the root is in an HSM, the HSM's own backup or cloning procedure (Chapter 33) is part of the key manager's DR plan.
- **Restore tests** at least yearly, into an isolated environment, proving that a backup really decrypts and that the restored node serves a real client.
- **Retention aligned with data.** A tape written today may need its key in ten years. Keys for archived data cannot be deleted just because the active system no longer uses them.

DORA in the EU and similar operational resilience rules expect you to test recovery of critical ICT services, and a key manager that underpins core banking storage is clearly one of them.

> **Compliance hook.** A centralised key manager is direct evidence for PCI DSS Requirements 3.6 and 3.7 (key management procedures, dual control and split knowledge), ISO/IEC 27001 Annex A control 8.24 (use of cryptography), NIST SP 800-53 SC-12 (cryptographic key establishment and management), and the key management practices of NIST SP 800-57 and SP 800-130. Its audit log, key inventory and restore test records are the artefacts auditors ask for.

## 34.10 Lab: run a KMIP server and client

This lab uses **PyKMIP**, an open-source Python KMIP implementation whose server is meant for testing, not production. PyKMIP depends on Python features removed in 3.12, so run it in a Python 3.11 container.

1. Start a container and install PyKMIP and OpenSSL.

```bash
docker run -it --name kmip -p 5696:5696 python:3.11 bash
pip install pykmip
mkdir -p /lab/policies && cd /lab
```

2. Create a small CA, a server certificate and a client certificate. The client certificate's common name becomes the KMIP client identity.

```bash
openssl req -x509 -newkey rsa:3072 -nodes -days 30 \
  -keyout ca.key -out ca.crt -subj "/CN=Lab KMIP CA"
printf "subjectAltName=DNS:localhost\nextendedKeyUsage=serverAuth\n" \
  > server.ext
printf "extendedKeyUsage=clientAuth\n" > client.ext
openssl req -newkey rsa:3072 -nodes -keyout server.key \
  -out server.csr -subj "/CN=localhost"
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -days 30 -out server.crt -extfile server.ext
openssl req -newkey rsa:3072 -nodes -keyout client.key \
  -out client.csr -subj "/CN=array-07"
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -days 30 -out client.crt -extfile client.ext
```

3. Write the server configuration and start the server in the background.

```bash
cat > server.conf <<'EOF'
[server]
hostname=0.0.0.0
port=5696
certificate_path=/lab/server.crt
key_path=/lab/server.key
ca_path=/lab/ca.crt
auth_suite=TLS1.2
policy_path=/lab/policies
enable_tls_client_auth=True
database_path=/lab/pykmip.db
logging_level=INFO
EOF
pykmip-server -f server.conf &
```

4. Create, locate, get and destroy a key from a client script, and watch the server log each operation.

```python
from kmip.pie.client import ProxyKmipClient
from kmip.core import enums

c = ProxyKmipClient(hostname="localhost", port=5696,
                    cert="/lab/client.crt", key="/lab/client.key",
                    ca="/lab/ca.crt")
with c:
    uid = c.create(enums.CryptographicAlgorithm.AES, 256,
                   name="array-07-kek")
    print("created", uid)
    print("located", c.locate())
    key = c.get(uid)
    print("length", len(key.value) * 8)
    c.activate(uid)
    c.revoke(enums.RevocationReasonCode.CESSATION_OF_OPERATION,
             uid)
    c.destroy(uid)
```

5. Issue a second client certificate with a different common name and try to Get the first client's key. Observe that ownership follows the certificate identity.
6. Let a client certificate expire (issue one with `-days 1` and change the container clock, or simply delete `client.crt`) and observe the failure mode a storage array would see at reboot.

**Optional cloud extension.** Deploy the AWS open-source XKS reference proxy backed by SoftHSM on a small virtual machine, create an external key store in AWS KMS, and encrypt an object with it. Then stop the proxy and watch decrypt calls fail. Cost warning: external key store keys, the KMS requests, the virtual machine and any VPC endpoint service all incur charges; delete the key store, schedule key deletion and terminate the instance when you finish.

## 34.11 Failure story: the key manager that could not start

A composite scenario, based on common patterns:

A mid-sized organisation consolidated its key management onto a two-node virtual key manager cluster, both nodes running on the same vSphere cluster. To satisfy an audit finding, the virtualisation team then enabled VM encryption on that cluster, using the same key manager as its Standard Key Provider, and the key manager VMs were encrypted along with everything else. Separately, the KMIP client certificates on the storage arrays had been issued with a one-year lifetime by a CA whose renewal was manual, and nobody owned the renewal.

Months later a scheduled power maintenance in the primary data centre went wrong and the whole site lost power. On restart, the arrays tried to fetch their authentication keys. The key manager nodes were VMs whose own keys came from the key manager, so they could not start. When engineers broke the loop by restoring a key manager node from backup onto an unencrypted standalone host, a second problem appeared: two arrays' client certificates had expired three weeks earlier. The arrays had run happily on cached keys, but now the TLS handshake failed and the drives stayed locked. Recovery took most of a day, involving an emergency certificate issuance and vendor support to re-establish trust.

The lessons:

- Keep key manager nodes off the storage and hypervisors that depend on them, and test a cold start of the whole site.
- Treat KMIP client certificates as critical certificates in your CLM inventory, with automated renewal and expiry alerting.
- Cached keys hide failures. A system that has not restarted in a year has not proved it can.
- Write the cold-start order down before you need it.

## 34.12 Chapter summary

- Enterprise key managers centralise key creation, storage, distribution, rotation and destruction for many consumers, separating keys from the data they protect and giving one policy, inventory and audit trail.
- They are built from a root of trust (ideally an HSM), a wrapped key database, client interfaces, policy, audit and clustering.
- KMIP, an OASIS standard, uses TTLV messages over mutually authenticated TLS on port 5696; its managed objects, attributes, operations and states map onto the NIST key lifecycle, and profiles define tested subsets.
- KMIP client identity is usually the TLS client certificate, so those certificates need per-device issuance, inventory and automated renewal.
- Storage arrays, tape libraries, databases and vSphere (Standard, Native and Trusted Key Providers) are the main KMIP consumers, mostly using key serving with in-memory caching.
- Thales CipherTrust Manager, Fortanix DSM, Entrust KeyControl, IBM GKLM and others differ in form factor, root of trust, integrations and cloud features; choose from your client compatibility list.
- AWS XKS, Google Cloud EKM and Azure Managed HSM external key management keep key material outside the cloud at a real availability cost; key brokering with BYOK suits most workloads.
- Design for availability: multi-site clusters, client failover lists, no dependency loops, encrypted backups with split custody, and tested cold starts and restores.
