## 30.1 The data-in-use gap

Part VI showed how to encrypt data at rest, and Part V how to encrypt it in transit. Both stop at the same place. A fraud model cannot score a transaction it cannot read, and a database cannot sort a column of ciphertext. Somewhere, the data must be decrypted into memory, and once it is there it is visible to anything with enough privilege on the machine: the operating system kernel, the hypervisor, a cloud provider's host software, a backup agent taking a memory snapshot, or an administrator with a debugger.

For most of computing history the answer was simply "trust the platform". You trusted your own data centre staff, and when you moved to the cloud you trusted the provider's staff and software, backed by contracts and audits. That answer is weakest exactly where the stakes are highest: when data is regulated, when two organisations want to combine data neither will hand to the other, or when the key that decrypts everything has to sit in a server's memory to be useful.

**Confidential computing** is the protection of data in use by performing computation in a hardware-based, attested **trusted execution environment (TEE)**. That definition, from the industry's Confidential Computing Consortium, has two halves, and both matter:

- **Isolation.** The processor encrypts the TEE's memory with keys that never leave the chip, and refuses access from software outside the TEE, including more privileged software such as the hypervisor.
- **Attestation.** The processor can produce a signed statement, rooted in a key the chip vendor certified, describing what is running inside the TEE. A remote party can check that statement before trusting the workload with data or keys.

Isolation without attestation is a locked room nobody can inspect. Attestation is what turns the hardware feature into something a security architect can build policy on.

### What changes in the threat model

It helps to be precise about whom you stop trusting. In a conventional cloud virtual machine, the **trusted computing base (TCB)**, meaning every component whose failure could break your security, includes the processor, the firmware, the hypervisor, the host operating system, the provider's management stack and the people who operate it. In a confidential VM, the hypervisor and host are moved outside the TCB: they still schedule your VM and move its pages around, but they see only ciphertext and cannot silently change your memory. The TCB shrinks to the processor, its security firmware, and your own guest software.

You never remove trust entirely. You move it from a large, changeable software stack run by someone else to a smaller set of hardware and firmware components whose behaviour can be measured and attested. Section 30.7 returns to what that remaining trust costs.

## 30.2 How TEEs work

All the current designs share four mechanisms, even though the details differ.

**Memory encryption.** A hardware engine in the memory controller encrypts every cache line on its way to DRAM and decrypts it on the way back. Each TEE gets its own key, generated inside the processor and never exposed to software. A physical attacker who freezes and reads DRAM, or a hypervisor that maps the TEE's pages into its own address space, sees only ciphertext.

**Access control and integrity.** Encryption alone is not enough. A malicious hypervisor could replay old ciphertext into a page, remap two pages onto one, or swap pages between processes. Modern designs keep a hardware-enforced table of which physical page belongs to which TEE and refuse writes from anyone else. AMD calls this the reverse map table; Intel TDX uses a combination of ownership tracking and integrity checks. This is the part the first generation of AMD's technology lacked, and it is why "SEV-SNP" (Secure Nested Paging) rather than plain "SEV" is the version to require.

**Measurement.** As the TEE is built, the processor or its security firmware hashes the initial code and data loaded into it. That **measurement** is a fingerprint of exactly what started. Change one byte of the initial image and the measurement changes. Later components, such as the guest kernel and applications, can extend further measurement registers in the same way a TPM's PCRs work (Chapter 36).

**Attestation reports.** On request, the hardware produces an **attestation report** (Intel calls it a quote, AMD a report, AWS an attestation document) containing the measurement, security-relevant configuration such as whether debugging is enabled, the firmware and microcode versions (the **TCB version**), and a small field of caller-chosen data. The report is signed with a key derived inside the processor and certified by the vendor's PKI. The caller-chosen field is how you bind the report to something useful: typically the hash of a public key the workload just generated, plus a fresh nonce from the party who will check the report.

## 30.3 The hardware technologies

Four families matter in enterprise and cloud deployments in 2026.

| Technology | Unit of isolation | What sits inside the TCB | Typical use |
| --- | --- | --- | --- |
| Intel SGX | An enclave: part of one process | Processor plus the enclave code only | Small, hardened services such as key handling, wallets, private contact discovery |
| Intel TDX | A whole VM (trust domain) | Processor, TDX module firmware, the guest OS | Lift-and-shift confidential VMs |
| AMD SEV-SNP | A whole VM | Processor, AMD Secure Processor firmware, the guest OS | Confidential VMs on all three major clouds |
| Arm CCA | A realm: a VM-like environment | Processor, realm management monitor, the guest | Arm servers, emerging in 2026 |
| AWS Nitro Enclaves | A stripped-down VM carved from a parent instance | Nitro hypervisor and cards, the enclave image | Isolated key handling next to an EC2 workload |

### Intel SGX

**Intel Software Guard Extensions (SGX)**, introduced in 2015, isolates an **enclave**: a protected region of a single process's address space. The operating system can schedule the process but cannot read the enclave's memory. The attraction is a tiny TCB, because only the enclave's own code is trusted. The cost is that applications must be split into trusted and untrusted halves and rewritten against an SDK or a library OS (such as Gramine or Occlum), and every call across the boundary is expensive.

SGX also became the most attacked TEE in history, for reasons section 30.7 explains. Intel has since removed it from its recent client processors and positions it for Xeon servers, where it remains useful for small, well-understood services. Some key management products use SGX to protect a software-defined HSM, an approach you will meet in Chapter 34.

### Intel TDX

**Intel Trust Domain Extensions (TDX)**, available on 4th-generation Xeon Scalable processors and later, takes the opposite approach: it isolates a whole virtual machine, called a **trust domain**, from the hypervisor. A small Intel-signed firmware component, the TDX module, runs in a special processor mode and mediates between the hypervisor and trust domains. Because the unit is a VM, ordinary applications run unchanged. The trade-off is that the guest operating system is now inside your TCB, so its hardening is your responsibility.

### AMD SEV-SNP

AMD's **Secure Encrypted Virtualization (SEV)** encrypts VM memory with per-VM keys managed by the AMD Secure Processor, a separate security core on the chip. The original SEV (2017) and SEV-ES (which added encryption of register state) did not stop a hypervisor from tampering with memory. **SEV-SNP**, on 3rd-generation EPYC processors and later, adds integrity protection through the reverse map table and a richer attestation report signed by a chip-unique key (the VCEK) certified through AMD's key distribution service. SEV-SNP is the most widely deployed confidential VM technology across the major clouds.

### Arm CCA

The **Arm Confidential Compute Architecture (CCA)**, part of Armv9-A, introduces **realms**: a new world alongside the normal and secure worlds, managed by a small realm management monitor that the hypervisor cannot bypass. The design resembles TDX and SEV-SNP in spirit. As of 2026 the software stack (realm support in Linux and KVM, attestation formats) is maturing and CCA-capable server hardware and cloud offerings are only beginning to appear, so treat it as something to track rather than to deploy at scale.

### AWS Nitro Enclaves

**AWS Nitro Enclaves** are not a processor feature at all. AWS's Nitro system offloads virtualisation to dedicated cards and a minimal hypervisor, and a Nitro Enclave is an isolated VM carved out of a parent EC2 instance's CPU and memory. It has no persistent storage, no network interface, and no interactive access; it talks to its parent only over a local socket (vsock). Its attestation document is signed by the Nitro hypervisor through an AWS-operated PKI and contains **platform configuration register (PCR)** values: PCR0 is a hash of the enclave image file, and others cover the kernel, the application, the parent instance's IAM role and the certificate used to sign the image.

The trust model differs from the processor-based TEEs. You are trusting AWS's Nitro hardware and hypervisor rather than Intel or AMD silicon, and you are protected from the parent instance's administrators and software, not from AWS. For many enterprise use cases, such as keeping a decryption key away from the application team's own root users, that is exactly the right boundary.

### Confidential GPUs

AI workloads pushed the idea onto accelerators. Recent data-centre GPUs can run in a confidential mode where the GPU's memory is protected and the transfer path to a confidential VM is encrypted, with the GPU producing its own attestation that the VM verifies. The GPU's trust is anchored in the confidential VM, so the VM's attestation still matters most.

## 30.4 Confidential computing in the three major clouds

All three hyperscalers offer confidential VMs, and each pairs them with a different attestation and key release service. The table summarises the public documentation as of 2026; machine series and regions change often.

| | AWS | Microsoft Azure | Google Cloud |
| --- | --- | --- | --- |
| Confidential VMs | AMD SEV-SNP on selected EC2 instance families | AMD SEV-SNP (DCasv5/ECasv5 and later series) and Intel TDX (DCesv5/ECesv5 and later) | AMD SEV and SEV-SNP (N2D and later), Intel TDX (C3) |
| Enclave-style option | Nitro Enclaves | SGX-based DCsv3 series; confidential containers | Confidential Space (a hardened confidential VM image for containers) |
| Attestation service | Nitro attestation documents; SEV-SNP reports verified by the customer | Microsoft Azure Attestation (MAA) issues signed JWTs | Google Cloud Attestation issues OIDC tokens |
| Key release | AWS KMS key policy conditions on enclave PCRs | Secure Key Release from Key Vault Premium or Managed HSM | Workload Identity Federation conditions on attestation claims |

Three design points are worth drawing out.

First, **confidential VMs need a full measured boot chain** to be meaningful. A VM whose initial firmware is measured but which then boots an unmeasured kernel from an unencrypted disk proves little. The cloud offerings add a virtual TPM inside the confidential VM, measured boot through it, and full-disk encryption whose key is released only after attestation.

Second, **who verifies the evidence** shapes the trust model. If the cloud provider's own attestation service checks the hardware report and issues a token, you are trusting that service. Azure and Google both let you verify the raw hardware evidence yourself or use independent verifiers (such as Intel's Trust Authority) if you want the provider out of the loop.

Third, **key release is policy**, and policy is where mistakes happen. That is the subject of the next section.

> **In practice.** A confidential VM changes nothing about application security. SQL injection, a stolen API token or a vulnerable library inside the VM still exposes the data, because the attacker is now inside the TEE with the data. Confidential computing removes the infrastructure operator from your threat model; it does not remove the need for everything else in this book.

## 30.5 Attestation flows and attestation-gated key release

The most valuable enterprise pattern is simple to state: **the key that decrypts sensitive data is released only to a workload that proves it is the approved code running in a genuine TEE.** Everything else, including the cloud operator, your own platform administrators and a copy of the same workload running outside a TEE, gets nothing.

The IETF's Remote Attestation Procedures (RATS) architecture gives the parts precise names, which most vendor documentation now follows:

- The **attester** is the workload and its hardware, which produce **evidence** (the signed report).
- The **verifier** checks the evidence against **endorsements** (the chip vendor's certificates and known-good TCB versions) and **reference values** (the measurements you approved), and issues an **attestation result**, usually a signed token.
- The **relying party** (here, a key broker or KMS) consumes the result and decides whether to release a key.

### The flow step by step

1. **Boot and measure.** The TEE starts; the hardware records the measurement of what loaded.
2. **Generate an ephemeral key pair inside the TEE.** Its private half never leaves the TEE's encrypted memory.
3. **Request evidence.** The workload asks the hardware for a report whose user-data field contains the hash of the new public key and a nonce supplied by the verifier or relying party, which proves freshness.
4. **Verify.** The verifier checks the signature chain up to the chip vendor's root, checks that the TCB version is not below the minimum (so a machine with unpatched firmware is refused), checks that debug mode is off, and compares the measurements to the approved reference values.
5. **Decide.** The relying party compares the attestation result to its **release policy**: which measurements, which signer of the image, which cloud project or account, which minimum security version.
6. **Release, wrapped.** The data key is encrypted to the TEE's public key and returned. Even if the response is intercepted, or logged by a proxy, only the attested TEE can unwrap it.

The binding in step 3 is the heart of the design. Without it, an attacker could obtain a genuine report from a genuine TEE and then present someone else's public key alongside it.

### How the clouds implement it

**AWS KMS and Nitro Enclaves.** The enclave calls KMS (through its parent's vsock proxy) with a `Recipient` parameter carrying its attestation document. KMS validates the document, and the key policy can require specific values with condition keys such as `kms:RecipientAttestation:ImageSha384` (matching PCR0) or `kms:RecipientAttestation:PCR` followed by the register number. KMS then returns the plaintext encrypted to the enclave's public key from the attestation document, rather than in the clear, so the parent instance relays a blob it cannot read.

**Azure Secure Key Release.** A key in Key Vault Premium or Managed HSM is created as exportable with an attached release policy: a JSON document listing the attestation authority (a Microsoft Azure Attestation endpoint) and the claims that must be present, for example that the VM is an Azure-compliant SEV-SNP confidential VM. The workload obtains an MAA token, presents it, and Key Vault releases the key wrapped to a key bound into the token.

**Google Confidential Space.** The workload runs in a hardened container launcher on a confidential VM. Google Cloud Attestation verifies the hardware evidence and issues an OIDC token with claims such as the container image digest and whether the image runs in a production (non-debug) mode. A Workload Identity Federation pool trusts that issuer and maps its claims to an identity; IAM conditions then decide which Cloud KMS keys or storage buckets that identity can use. External relying parties can request tokens with their own audience and nonce.

> **At Meridian.** Meridian Pay's fraud-scoring service runs on confidential VMs in one of Meridian's three clouds. The model weights and the card-data tokenisation key are encrypted under a key in the cloud KMS whose release policy requires a SEV-SNP confidential VM, debug disabled, a minimum TCB version, and an image digest signed by Meridian's release pipeline. Platform Engineering owns the VM images; the PKI and Cryptography Services team owns the release policies and the signing key for images, which lives in an HSM (Chapter 33); Payments Security approves any change to the reference measurements. A new model version therefore means a new image digest, a reviewed policy change, and a logged release, which is exactly the evidence the PCI assessor asks for.

## 30.6 Where it lives in the enterprise

Confidential computing earns its cost in a handful of patterns.

- **Protecting keys in use.** A TLS terminator, token signer or tokenisation service that must hold a key in memory can run inside a TEE so that host compromise does not expose the key. This sits between a plain software key and a full HSM in assurance, and costs far less latency than a network HSM call.
- **Regulated workloads in public cloud.** Some regulators and customers ask what stops the cloud provider seeing the data. A confidential VM plus customer-controlled key release is a technical answer, which complements contractual ones and the external key manager patterns in Chapter 28.
- **Multi-party analytics.** Two banks that want to find shared mule accounts, or an insurer and a hospital network matching claims, can each verify that a jointly agreed program runs in a TEE and release their data keys only to it. Chapter 31 compares this hardware approach with purely cryptographic alternatives.
- **Protecting AI models and prompts.** Model owners use TEEs to deploy proprietary weights onto infrastructure they do not control, and users of hosted models use them to keep prompts away from the operator.
- **Digital asset custody and signing.** Custody platforms combine TEEs, HSMs and threshold signing (Chapter 31) to protect signing keys.

The teams involved cross the usual boundaries. Platform Engineering builds and patches the images. The cryptography team owns attestation policy and keys. Application teams must design for no interactive access, because a production confidential workload that allows SSH has a shell inside the TCB. The SOC needs the attestation and key release logs, because a burst of refused releases is either a broken deployment or someone probing.

## 30.7 What it does not protect

Confidential computing is a strong control with a long list of honest caveats. An architect should be able to state them before a vendor does.

### Side channels

A TEE shares the processor's caches, branch predictors, execution ports and power delivery with untrusted code. Microarchitectural side-channel attacks measure that sharing to infer secrets. SGX bore the brunt because its threat model explicitly included a malicious operating system, which can single-step an enclave and observe every page fault. **Foreshadow** (2018) used speculative execution to read enclave memory and extract SGX attestation keys; later attacks (Plundervolt using undervolting, ÆPIC Leak using an architectural bug) followed. Intel's response, repeatedly, was microcode and a **TCB recovery**: a new TCB version, with attestation verifiers expected to reject machines below it.

VM-based TEEs have a smaller attack surface for some of these attacks but their own history. Researchers have shown hypervisors abusing interrupt injection and cache behaviour against SEV-SNP guests, and **BadRAM** (2024) showed that a cheaply modified memory module could lie about its size, create aliased addresses and defeat SEV-SNP's integrity protection, enough to forge attestation; AMD issued firmware mitigations.

### Physical attacks

Memory encryption in current TEEs uses a deterministic, tweakable mode (AES-XTS style) without full integrity or freshness for every cache line, because those would cost too much bandwidth. In 2025 several research groups showed what that means against an attacker with physical access to a server. **Battering RAM** and **WireTap** used inexpensive interposers on DDR4 memory buses to break SGX and SEV-SNP guarantees, and **TEE.fail** extended interposer attacks to DDR5 systems running Intel TDX and AMD SEV-SNP, recovering keys and forging attestation. Intel and AMD responded that physical attacks of this kind are outside their stated threat models.

That answer is accurate and important. **Current TEEs mainly defend against privileged software, not against a determined attacker with the server on a bench.** For a cloud tenant, the physical attacker is the provider's insider or a compromised supply chain, which is exactly the threat some buyers hoped confidential computing removed.

### The trusted computing base you still have

- **The chip vendor.** The root of attestation is the vendor's PKI and its firmware. A vendor signing key compromise, or a firmware bug, affects every customer.
- **The guest software.** In a confidential VM, your kernel, libraries and application are inside the TCB. A vulnerable guest is a vulnerable TEE.
- **The interface with the host.** The host still controls I/O, interrupts and the timing of everything. Guest kernels have had to be hardened against malicious virtual devices, and several research papers have shown how a hostile hypervisor can attack an unhardened guest through these paths.
- **The verifier and policy.** A release policy that accepts any measurement, or that never raises the minimum TCB version, turns attestation into theatre.
- **Availability.** The host can always stop, pause or starve your TEE. Confidential computing offers confidentiality and integrity, never availability.

> **Watch out.** "Runs in a TEE" is not an assurance claim on its own. Ask which technology, which TCB version is enforced, who verifies evidence, what the release policy checks, whether debug is disabled in production, and what happens when the vendor announces a TCB recovery. If the answer to the last question is "nothing", the next published side channel will apply to you indefinitely.

## 30.8 Design decisions and operations

### Choosing a model

| Question | Leans towards |
| --- | --- |
| Must existing applications run unchanged? | Confidential VMs (SEV-SNP or TDX) |
| Is the sensitive part small and stable, such as a signing or decryption service? | Enclaves (SGX) or Nitro Enclaves |
| Is the main adversary your own administrators rather than the cloud provider? | Nitro Enclaves or confidential VMs with customer-held key release |
| Do you need assurance against physical attack? | An HSM (Chapter 33), not a TEE |
| Do several organisations need to trust the same code? | Attested containers (Confidential Space style) with reproducible builds |

### Operating it

- **Reproducible builds and signed images.** A measurement is only useful if you can explain where it came from. Build images reproducibly, sign them, and store the expected measurements with the release record.
- **Policy as code.** Keep release policies in version control with review, in the same way as cipher policy (Chapter 21).
- **TCB currency.** Subscribe to Intel, AMD and cloud security advisories; when a TCB recovery is published, raise the minimum accepted TCB version on a schedule, and expect some workloads to fail attestation until hosts are patched.
- **Logging.** Record every attestation result and key release, including refusals, with the measurement and TCB version, and forward them to the SOC.
- **Performance testing.** Memory encryption and the extra cost of I/O through shared buffers typically add modest overhead to compute-bound work and more to I/O-heavy work. Measure your own workload.

> **Compliance hook.** Confidential computing helps evidence controls on protecting data in use and on separating provider and customer duties: ISO/IEC 27001:2022 Annex A 8.24 (use of cryptography) and the cloud provider responsibility controls in CSA CCM, PCI DSS v4.0.1 Requirement 3 (protecting stored account data and its keys, where a TEE protects keys in use), and the GDPR Article 32 "state of the art" test for technical measures. DORA's ICT third-party risk requirements make a documented answer to "what can the provider see?" more valuable. No framework yet mandates confidential computing; treat it as a compensating or strengthening control and record its assumptions in the risk register.

## 30.9 Lab: attestation-gated key release in miniature

Cloud confidential VMs cost money, but the logic of attestation and key release can be practised locally. This lab builds a toy attester, verifier and key broker in Python so that you can see every check and break each one. It provides no real hardware protection.

1. Install the Python cryptography library and create a working folder.

```bash
python3 -m pip install cryptography
mkdir -p ~/cc-lab && cd ~/cc-lab
echo "payments scoring model v7" > approved.bin
cp approved.bin image.bin
echo "v7 with a debug shell" > patched.bin
```

2. Save the following as `attest_lab.py`. The "vendor" key stands in for the chip vendor's attestation root; the report stands in for a hardware-signed SEV-SNP report or Nitro attestation document.

```python
# attest_lab.py: a toy model of attestation-gated key release.
import hashlib, json, os, sys
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import ec, rsa, padding

OAEP = padding.OAEP(mgf=padding.MGF1(hashes.SHA256()),
                    algorithm=hashes.SHA256(), label=None)

# 1. The "chip vendor" root key. Real roots live in the vendor's PKI.
vendor = ec.generate_private_key(ec.SECP384R1())

# 2. The verifier's policy: the measurement of the approved image.
approved = open("approved.bin", "rb").read()
policy = {"measurement": hashlib.sha384(approved).hexdigest()}

# 3. Inside the TEE: measure the loaded image, make a key pair, and
#    obtain a signed report binding the public key and nonce to it.
image = open(sys.argv[1], "rb").read()
debug = len(sys.argv) > 2 and sys.argv[2] == "debug"
wl_key = rsa.generate_private_key(public_exponent=65537, key_size=3072)
wl_pub = wl_key.public_key().public_bytes(
    serialization.Encoding.PEM,
    serialization.PublicFormat.SubjectPublicKeyInfo)
nonce = os.urandom(16).hex()            # issued by the verifier
report = {"measurement": hashlib.sha384(image).hexdigest(),
          "debug": debug, "nonce": nonce,
          "report_data": hashlib.sha256(wl_pub).hexdigest()}
body = json.dumps(report, sort_keys=True).encode()
sig = vendor.sign(body, ec.ECDSA(hashes.SHA384()))


# 4. The key broker: check signature, freshness, policy, key binding.
def release_key(body, sig, wl_pub, expected_nonce):
    vendor.public_key().verify(sig, body, ec.ECDSA(hashes.SHA384()))
    r = json.loads(body)
    if r["nonce"] != expected_nonce:
        raise PermissionError("stale or replayed report")
    if r["debug"]:
        raise PermissionError("debug-mode TEE")
    if r["measurement"] != policy["measurement"]:
        raise PermissionError("unknown code measurement")
    if r["report_data"] != hashlib.sha256(wl_pub).hexdigest():
        raise PermissionError("key not bound to report")
    dek = os.urandom(32)
    pub = serialization.load_pem_public_key(wl_pub)
    return dek, pub.encrypt(dek, OAEP)


try:
    dek, wrapped = release_key(body, sig, wl_pub, nonce)
    assert wl_key.decrypt(wrapped, OAEP) == dek
    print("released: DEK unwrapped inside the TEE")
except PermissionError as e:
    print("refused:", e)
```

3. Run the three cases and compare the results.

```bash
python3 attest_lab.py image.bin          # released
python3 attest_lab.py image.bin debug    # refused: debug-mode TEE
python3 attest_lab.py patched.bin        # refused: unknown measurement
```

## 30.10 Failure story: the consensus seed that left the enclave

Secret Network is a public blockchain that offers private smart contracts. Its design relied on Intel SGX: every validator node ran an enclave, and all enclaves shared a 32-byte **consensus seed** from which the keys that encrypt contract state and transactions were derived. Only genuine, attested SGX enclaves were supposed to be able to register and receive it.

In 2022 a team of academic researchers studying SGX's real-world security, published as "SGX.Fail", showed what happens when the hardware's guarantees lapse faster than the ecosystem can respond. Two SGX vulnerabilities, ÆPIC Leak and the MMIO stale data issues, had been disclosed in August 2022, and Intel's TCB recovery, which would let verifiers reject unpatched machines, had not yet arrived. The researchers registered a vulnerable machine as a validator node, which the network's attestation accepted, and extracted the consensus seed. Because the seed was a master secret for the whole network, its exposure would allow retrospective decryption of private transactions since the chain began. The team disclosed responsibly and helped the network deploy mitigations, including freezing new node registration in October 2022. The project's developers disputed the practical impact, and there is no public evidence that an attacker exploited it.

The lessons apply directly to enterprise designs:

- **One shared secret across every TEE is a single point of failure.** One vulnerable enclave anywhere exposed everything. Per-workload keys, released per session by attestation, contain the damage.
- **Attestation policy must track TCB recovery.** Accepting any genuine SGX report, regardless of TCB version, meant the network trusted machines with known, published flaws.
- **The vendor's timeline becomes your timeline.** Between disclosure and TCB recovery there is a window in which attestation cannot distinguish patched from unpatched machines. Plan compensating controls for it.
- **Past ciphertext is at risk.** A key that protects historical data and leaks from a TEE leaks the history too. Rotation and forward secrecy matter inside TEEs as much as outside.

## 30.11 Chapter summary

- Confidential computing protects data in use by running workloads in hardware-isolated TEEs whose memory is encrypted with keys held by the processor, and by proving what runs inside through remote attestation.
- SGX isolates enclaves inside a process with a small TCB but heavy porting and a long side-channel history; TDX, SEV-SNP and Arm CCA isolate whole VMs, so applications run unchanged but the guest OS joins the TCB.
- AWS Nitro Enclaves use AWS's Nitro hypervisor rather than processor features, and protect a workload from its parent instance's administrators rather than from AWS.
- All three major clouds offer confidential VMs with their own attestation services: Nitro attestation with KMS conditions, Microsoft Azure Attestation with Secure Key Release, and Google Cloud Attestation with Workload Identity Federation.
- Attestation-gated key release wraps keys to a public key bound into a fresh, signed report, so only the attested TEE can use them; the release policy is where most of the security lives.
- TEEs mainly defend against privileged software. Side channels, firmware bugs, and 2024 to 2025 memory-bus attacks such as BadRAM, Battering RAM, WireTap and TEE.fail show their limits against physical attackers.
- You still trust the chip vendor, your guest software, the verifier and your own policies, and you never get availability guarantees.
- Operate TEEs with reproducible signed images, policy as code, enforced minimum TCB versions and logged releases.
