## 8.1 The idea

In 1977, Ron Rivest, Adi Shamir and Leonard Adleman published a system in which anyone could encrypt a message using a public key, but only the holder of the matching private key could decrypt it. The same system, run in reverse, gave the world its first practical **digital signature**: only the private key holder could produce a value that anyone with the public key could check. The security rests on the **factoring problem** from Chapter 3: multiplying two large primes is easy, but recovering them from their product is not.

RSA works with ordinary modular exponentiation. A message, represented as a number m smaller than the modulus n, is encrypted by raising it to a public power and decrypted by raising the result to a private power:

```text
encrypt:  c = m^e mod n
decrypt:  m = c^d mod n
```

The exponents e and d are chosen so that the two powers cancel each other out mod n, and computing d from e requires knowing the factors of n. Think of it as a padlock that anyone can snap shut (e) but only one key opens (d), where making the key requires a secret recipe (the factors) that the padlock maker throws away after use.

## 8.2 Generating a key pair

1. Choose two large random primes, p and q, each half the desired key size. For a 3072-bit key, each is 1536 bits.
2. Compute the **modulus** `n = p × q`. This is public.
3. Compute `φ(n) = (p − 1)(q − 1)`. This must stay secret, because it reveals the factors.
4. Choose the **public exponent** e. Almost everyone uses `e = 65537`, which makes encryption and signature verification fast.
5. Compute the **private exponent** `d = e^(−1) mod φ(n)`, using the extended Euclidean algorithm.

The **public key** is (n, e). The **private key** is d, usually stored with p, q and a few precomputed values that let decryption use the **Chinese Remainder Theorem (CRT)**, which makes it roughly four times faster.

Anyone who factors n can repeat step 5 and obtain d. That is why key size, and the quality of the random primes, is everything.

A small worked example makes the steps concrete. With p = 61 and q = 53, n = 3233 and φ(n) = 3120. Choose e = 17; then d = 2753, because 17 × 2753 = 46,801, which is 1 more than 15 × 3120. Encrypting m = 65 gives c = 65^17 mod 3233 = 2790, and 2790^2753 mod 3233 returns 65. Real keys follow exactly these steps with numbers hundreds of digits long.

## 8.3 Textbook RSA is broken

The formulas above, used directly, are called **textbook RSA**, and they are insecure in several ways:

- **Deterministic.** Encrypting the same message twice gives the same ciphertext. An attacker can guess likely messages ("yes", "no", "approve") and check each guess by encrypting it with the public key.
- **Malleable.** Multiplying a ciphertext by `2^e mod n` produces a valid encryption of `2m`. An attacker can transform encrypted values without decrypting them.
- **Small messages leak.** If m is small and e is small, `m^e` may be smaller than n, so no modular wrap-around happens and the attacker simply takes an ordinary e-th root.
- **Signatures can be forged.** With textbook signatures (`s = m^d mod n`), multiplying two valid signatures gives a valid signature on the product of their messages.

The solution to all of these is **padding**: a structured, randomised encoding applied to the message before exponentiation. Padding is not optional decoration. It is half of the security of RSA, and nearly every famous RSA break has been a padding break.

## 8.4 Padding for encryption: PKCS#1 v1.5 and OAEP

**PKCS#1 v1.5 encryption padding** (1993) wraps the message as `00 02 [random non-zero bytes] 00 [message]`. It adds randomness but has a fatal flaw, discovered by Daniel Bleichenbacher in 1998. If a server reveals, by error message or timing, whether a decrypted ciphertext had valid padding, it becomes a **padding oracle**: an attacker can decrypt any ciphertext by sending many carefully chosen variations and watching which ones the server accepts. This is the same pattern as the CBC padding oracle in Chapter 6, with a different mathematical engine.

The attack has returned again and again: in 2012 against hardware tokens and smart cards, in 2017 as **ROBOT** (Return Of Bleichenbacher's Oracle Threat), which affected TLS implementations from major vendors and some of the largest websites in the world, and in 2023 as the **Marvin** attack, which found timing variants in many libraries.

**OAEP** (Optimal Asymmetric Encryption Padding), standardised in PKCS#1 v2, mixes the message with randomness using hash-based masks in a way that comes with a security proof. Use **RSA-OAEP with SHA-256** whenever RSA encryption is unavoidable.

> **In practice.** Modern protocols have largely stopped using RSA for encryption at all. TLS 1.3 removed RSA key transport entirely; RSA now appears in TLS only to sign the handshake. RSA encryption survives mainly for **key wrapping**: encrypting a symmetric key to a public key, as when you import key material into a cloud KMS or load keys into payment devices. If a design proposes RSA encryption for new data, ask why it is not using ECDH or ML-KEM with symmetric encryption (Chapters 9 and 45).

## 8.5 Padding for signatures: PKCS#1 v1.5 and PSS

An RSA signature is created by hashing the message, padding the hash, and raising it to the private exponent:

```text
sign:    s = pad(hash(m))^d mod n
verify:  s^e mod n == pad(hash(m))
```

- **PKCS#1 v1.5 signature padding** is deterministic and, unlike its encryption counterpart, has no practical attack when verified strictly. It remains the most common RSA signature format in certificates, JSON Web Tokens (where it is called RS256) and SAML. Loose verification has caused forgeries: in 2006, Bleichenbacher showed that verifiers which did not check the padding fully could be fooled with forged signatures when `e = 3`.
- **RSA-PSS** (Probabilistic Signature Scheme) adds randomness and has a strong security proof. It is required in TLS 1.3 for RSA handshake signatures, appears in JWTs as PS256, and is the better choice for new designs where every verifier supports it.

The catch is compatibility. Some older clients, appliances and mainframe stacks cannot verify PSS-signed certificates, so most CAs still sign with PKCS#1 v1.5 while TLS libraries use PSS for the handshake. Both can be safe; the choice depends on who must verify.

## 8.6 Where RSA lives in the enterprise

RSA arrived first, so it sits in the oldest and most deeply embedded parts of an estate. Each use has its own owner and its own constraints on replacement.

| Where | What RSA does | Typical size and padding | Usual owner |
| --- | --- | --- | --- |
| Root and issuing CAs | Signs certificates and CRLs | RSA 4096 roots, 3072 or 2048 issuing CAs; PKCS#1 v1.5 | PKI team |
| TLS server certificates | Signs the handshake | RSA 2048 or 3072; PSS in TLS 1.3 | Network and Platform Engineering |
| Smart cards and Windows logon | User authentication, Kerberos PKINIT | RSA 2048 on most cards | IAM |
| Code signing | Signs software and firmware releases | RSA 3072 or larger, keys in hardware | Release engineering, PKI team |
| SAML and OIDC identity providers | Signs assertions and tokens | RS256, increasingly PS256 or ECDSA | IAM |
| SSH | Host and user keys | RSA 3072 with SHA-2 signatures, often being replaced by Ed25519 | Platform Engineering |
| Cloud KMS and HSM key import | Wraps symmetric keys for transport | RSA-OAEP with SHA-256 | Cryptography Services |
| Payment terminals | Remote key loading under ANSI TR-34 | RSA 2048 and larger | Payments Security |

### How products expose RSA

Products present the same primitive with different names and options, as of 2026:

- **Cloud KMS.** AWS KMS offers RSA key specs of 2048, 3072 and 4096 bits, with OAEP for encryption and both PSS and PKCS#1 v1.5 for signing. Azure Key Vault offers software and HSM-protected RSA keys of the same sizes, with algorithms named in the JSON Web Algorithms style (RSA-OAEP-256, PS256, RS256). Google Cloud KMS fixes the size, padding and hash into each key's algorithm, such as an RSA 3072 PSS signing key, so a key cannot be misused with a different padding.
- **HSMs.** General-purpose HSMs from Thales, Entrust, Utimaco and others expose RSA through PKCS#11 mechanisms (`CKM_RSA_PKCS_OAEP`, `CKM_RSA_PKCS_PSS`), Java JCE providers and Microsoft CNG (Chapter 33). An HSM policy can disable the raw RSA mechanism (`CKM_RSA_X_509`) and PKCS#1 v1.5 decryption, which closes the textbook and Bleichenbacher routes at the source.
- **Libraries.** OpenSSL, Java and .NET still let a developer choose PKCS#1 v1.5 encryption or even no padding, so code review should look for those choices.

> **At Meridian.** Meridian's offline root CA uses RSA 4096 in a general-purpose HSM, and its issuing CAs use RSA 3072 alongside a newer ECDSA P-384 hierarchy. IAM still issues RSA 2048 smart cards to administrators, because the card stock supports nothing larger. The cloud team imports customer-managed key material into all three clouds' KMS services by wrapping it with RSA-OAEP. Payments Security loads keys into terminals with TR-34, which depends on RSA. The PKI and Cryptography Services team tracks every one of these in its cryptographic inventory, because RSA's retirement date (section 8.7) applies to all of them at once.

## 8.7 Key sizes and lifetime

| RSA modulus | Security level | Status |
| --- | --- | --- |
| 1024 bits | About 80 bits | Broken in practice for well-funded attackers; disallowed |
| 2048 bits | 112 bits | Today's minimum; the floor for public TLS certificates |
| 3072 bits | 128 bits | Recommended for new keys with long lifetimes; the minimum for public code signing |
| 4096 bits | About 140 bits | Common for root CAs; markedly slower to sign |

The largest RSA number publicly factored by classical computers is 829 bits (RSA-250, in 2020), which took about 2,700 core-years of computation. 2048-bit RSA is far beyond classical reach. It is not, however, beyond the reach of a large, error-corrected quantum computer running Shor's algorithm (Chapter 44). Estimates of the quantum resources needed keep falling: a 2025 analysis by Google researchers estimated that 2048-bit RSA could be factored in under a week with fewer than one million noisy qubits, a twentyfold reduction from their 2019 estimate. No such machine exists, but the trend is why governments now set retirement dates for RSA.

> **Current development.** NIST's draft transition plan proposes that 2048-bit RSA be deprecated after 2030 and all RSA be disallowed after 2035 for federal use. Larger RSA keys do not help against quantum attackers: a 4096-bit key buys almost nothing against Shor's algorithm. The replacements are ML-DSA for signatures and ML-KEM for key establishment (Chapter 45).

Size also costs performance. RSA verification is fast because e is small, but signing and decryption grow roughly with the cube of the key size, so moving from 2048 to 4096 bits makes each signature several times slower. On a busy load balancer, that shows up in CPU budgets. ECDSA P-256 signs far faster at a higher security level, which is one reason many sites now serve ECDSA certificates first (Chapter 10).

## 8.8 Implementation pitfalls

Correct mathematics is not enough. RSA implementations have failed in these ways:

- **Weak prime generation.** In 2012, two research teams scanned the internet's public keys and found that tens of thousands of devices, mostly routers and firewalls generating keys at first boot with poor randomness, shared a prime factor with another device. A simple greatest common divisor (gcd) computation between pairs of keys factored them instantly.
- **Structured primes.** The **ROCA** vulnerability (2017) found that a widely used security chip generated primes with a special structure that made factoring feasible (section 8.11).
- **Fault attacks.** A single computing error during CRT decryption or signing can reveal a prime factor from one faulty output, a result first shown in 1997. Libraries and HSMs now verify each signature before releasing it.
- **Timing attacks.** Decryption time can leak bits of d. Implementations use **blinding**, multiplying the input by a random value before exponentiation and removing it afterwards, so timing no longer correlates with the secret.
- **Small or shared exponents.** Never use a small private exponent d, and never share a modulus n between users or devices.

The rules for you are short: generate RSA keys only with mature libraries or certified hardware, use OAEP for encryption and PSS (or strictly verified PKCS#1 v1.5) for signatures, use at least 3072 bits for anything long-lived, and plan RSA's replacement.

## 8.9 Design decisions

An architect makes four RSA decisions, and each needs a defensible reason.

1. **RSA or elliptic curves?** Choose RSA where verifiers are old or fixed: smart card stock, mainframe partners, appliances that verify only RSA chains, and payment devices that require TR-34. Choose ECDSA or Ed25519 everywhere you control both ends, for speed and smaller keys. Many organisations run both, for example by serving dual RSA and ECDSA certificates on the same TLS endpoint.
2. **Which size?** 3072 bits for new long-lived keys such as CAs and code signing; 2048 bits only where a device cannot do more and the key will be retired before 2030; 4096 bits for roots if your HSM and clients cope with the cost.
3. **Which padding?** OAEP with SHA-256 for any encryption or key wrapping; PSS for new signature formats; PKCS#1 v1.5 signatures only for compatibility, with strict verification. Disable PKCS#1 v1.5 decryption wherever the product allows it.
4. **Where is the key generated and kept?** CA, code signing and key-wrapping keys belong in an HSM or cloud KMS with non-exportable keys. Record which hardware generated each key, so that a flaw like ROCA can be scoped in hours rather than weeks.

> **Compliance hook.** NIST SP 800-131A sets the transitions for RSA key sizes and padding schemes, and SP 800-56B covers RSA key establishment. The CA/Browser Forum Baseline Requirements set the RSA minimum for public certificates. PCI DSS v4.0.1 requires strong cryptography and documented key management for keys that protect cardholder data (requirements 3.6 and 3.7), and PCI PIN security rules govern RSA use in remote key loading. ISO/IEC 27001:2022 control A.8.24 expects all of this in a written cryptographic standard.

## 8.10 Lab: RSA by hand, then RSA done right

You need Python 3 and OpenSSL 3.

1. **Toy RSA and its weaknesses.**

```python
p, q, e = 1009, 1013, 65537
n, phi = p * q, (p - 1) * (q - 1)
d = pow(e, -1, phi)
m = 42
c = pow(m, e, n); print(pow(c, d, n))       # 42
# Malleability: double the plaintext without the key
c2 = (c * pow(2, e, n)) % n
print(pow(c2, d, n))                          # 84
# Determinism: the same vote always encrypts the same way
print(pow(1, e, n) == pow(1, e, n))           # True
```

2. **Generate and inspect a real key.**

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 \
  -out rsa.key
openssl pkey -in rsa.key -text -noout | head -20
openssl pkey -in rsa.key -pubout -out rsa.pub
```

Find the modulus, the public exponent 65537, and the two primes.

3. **Sign with PSS and verify.**

```bash
echo "release v2.4.1" > release.txt
openssl dgst -sha256 -sigopt rsa_padding_mode:pss \
  -sign rsa.key -out release.sig release.txt
openssl dgst -sha256 -sigopt rsa_padding_mode:pss \
  -verify rsa.pub -signature release.sig release.txt
```

Change one character in `release.txt` and verify again. Verification fails.

4. **Wrap a key with OAEP, as a KMS import does.**

```bash
openssl rand -out aes.key 32
openssl pkeyutl -encrypt -pubin -inkey rsa.pub \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 \
  -in aes.key -out aes.wrapped
ls -l aes.key aes.wrapped
```

The 32-byte key becomes 384 bytes, the size of the modulus.

5. **Measure the cost of key size.**

```bash
openssl speed rsa2048 rsa3072 rsa4096 ecdsap256
```

Compare signs per second with verifies per second, and RSA with ECDSA.

6. **The shared-prime attack in miniature.**

```python
from math import gcd
n1, n2 = 1009 * 1013, 1009 * 1019  # two devices shared a prime
print(gcd(n1, n2))                  # 1009: both keys factored
```

**Optional cloud extension.** Create an asymmetric RSA 3072 key in AWS KMS, Azure Key Vault or Google Cloud KMS, download its public key, verify a signature made by the service with OpenSSL, and note which padding modes the service lets you choose. Cost warning: asymmetric keys carry a monthly charge and each operation is billed, so schedule the key for deletion afterwards.

## 8.11 Failure story: ROCA and the national ID cards

In October 2017, researchers from Masaryk University in the Czech Republic published **ROCA**. A cryptographic library built into Infineon security chips generated RSA primes using a shortcut that made them faster to find. The shortcut left a hidden structure: every key generated by the chip could be recognised by a quick test on the public key alone, and its modulus factored using a specialised method. The researchers estimated that a 2048-bit key could be factored for tens of thousands of US dollars of cloud computing, and a 1024-bit key for far less.

The chip was certified to high security standards and used in national identity cards, trusted platform modules in business laptops, hardware security keys and smart cards. The library's design had never been published, so nobody outside the manufacturer could review it. Kerckhoffs's principle from Chapter 1 is not only about algorithms: secret implementation shortcuts can be just as dangerous as secret algorithms.

Recovery was expensive. Estonia suspended the certificates of 760,000 ID cards and asked citizens to update their keys. Laptop makers shipped firmware updates, and every key generated by an affected chip had to be replaced. Enterprises with TPM-generated device keys had to find them first. Because ROCA keys were recognisable from the public key, a scan of every certificate in a CA database could identify them quickly, but only for organisations that had such a database. The episode is a strong argument for crypto agility and for recording key provenance.

## 8.12 Chapter summary

- RSA security rests on factoring. Anyone who knows the factors of n can compute the private exponent d.
- Textbook RSA is deterministic and malleable. Padding is mandatory: OAEP for encryption, PSS or strictly verified PKCS#1 v1.5 for signatures.
- Bleichenbacher-style padding oracles have recurred for 25 years. Modern protocols avoid RSA encryption, which now survives mainly for key wrapping.
- RSA is embedded in CAs, smart cards, code signing, identity tokens, KMS key import and payment key loading, each with a different owner.
- Cloud KMS and HSMs expose RSA with different options; disable PKCS#1 v1.5 decryption where you can.
- Use 3072-bit keys for long-lived uses; 2048-bit is the minimum and is scheduled for deprecation after 2030, with all RSA disallowed after 2035 under NIST's draft plan.
- Bad randomness, faults and secret implementation shortcuts (shared primes, ROCA) have broken millions of RSA keys. Record where every key was generated.
