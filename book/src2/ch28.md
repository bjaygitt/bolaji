## 28.1 Why cloud key management matters

When data moves to a cloud, the organisation hands over its disks, its networks and the people who operate them. Encryption at rest is switched on by default in every major cloud, so the question an auditor or regulator asks is no longer "is it encrypted?" but **"who can decrypt it?"** The honest answer depends entirely on where the keys live and who controls their use.

Three kinds of party might decrypt cloud data: your own staff and workloads, the provider's staff and systems, and governments that can compel the provider. A cloud **key management service (KMS)** controls the first precisely and the other two to varying degrees. Chapter 32 covers key management fundamentals and Chapter 34 the on-premises key managers that feed the cloud.

## 28.2 How a cloud KMS works

A cloud KMS stores keys inside hardware security modules, performs operations with them on request through an API authenticated by the cloud's identity system, and logs every request. The defining property is that **master keys are non-exportable**: you can ask the KMS to use a key, but never to hand it over.

Cloud services use the KMS through **envelope encryption** (Chapter 27):

1. You create a **customer-managed key** in a region and grant a service, such as object storage or a managed database, permission to use it.
2. When the service writes data, it generates a random **data encryption key (DEK)**, encrypts the data with it, and asks the KMS to wrap the DEK under your key (the **key encryption key**, KEK). It stores the wrapped DEK beside the data.
3. When the service reads data, it sends the wrapped DEK to the KMS. The KMS checks your policy, unwraps it, and returns the DEK, which the service uses in memory.
4. Every wrap and unwrap appears in your audit log.

The KMS never sees your data. Its key is a control point: disable it and dependent services can no longer unwrap DEKs, so the data becomes unreadable once cached DEKs expire.

Clouds distinguish **provider-managed keys**, which encrypt by default but give you no control or visibility, from **customer-managed keys (CMKs)**, which live in your account under your policy. Provider-managed keys answer the threat of a stolen disk. Customer-managed keys let you decide who may decrypt, see every use, and make data unreadable by disabling or destroying the key.

| **HYOK / external key management** | The provider cannot decrypt without a live call to your key manager; an instant kill switch | Simplicity and availability: your key manager is in the path of every access |

### How BYOK import works

BYOK uses a standard wrapping pattern that AWS, Azure, Google Cloud, Oracle and HashiCorp Vault all share in some form:

1. The KMS generates an RSA **wrapping key pair** inside its HSM and gives you the public key, often with an expiry.
2. In your own HSM, you generate the target key (for example AES-256) and a one-time ephemeral AES key.
3. You wrap the target key with the ephemeral key using **AES Key Wrap with Padding** (RFC 5649), and wrap the ephemeral key with the RSA public key using RSA-OAEP with SHA-256. HSMs offer this as a single mechanism, `CKM_RSA_AES_KEY_WRAP` in PKCS#11.
4. You upload the two wrapped blobs. The KMS unwraps them inside its HSM, so the key is never exposed in plaintext outside an HSM.

Two points are widely misunderstood. **BYOK is about origin and escrow, not control**: once imported, the provider uses your key like any other, so BYOK alone does not stop the provider decrypting. And **escrow copies cut both ways**: data you "crypto-shredded" in the cloud remains recoverable from your HSM backup, which matters for deletion evidence (Chapter 29).

## 28.4 AWS Key Management Service

**AWS KMS** is a regional, multi-tenant service whose keys live in HSMs that AWS validates under FIPS 140 at Security Level 3. As of 2026 it supports symmetric AES-256-GCM keys, HMAC keys, and asymmetric RSA, elliptic curve and ML-DSA keys for signing.

Access control combines three mechanisms:

- A **key policy** attached to each key, which is the primary authority. Without a statement granting the account access, even the account's administrators cannot use the key.
- **IAM policies**, which apply only where the key policy delegates to IAM.
- **Grants**, temporary and narrowly scoped permissions that AWS services create programmatically, for example when an EBS volume is attached to an instance.

**Encryption context**, key-value pairs bound to each ciphertext as authenticated data and logged in CloudTrail, can be used in policy conditions, so a DEK wrapped for tenant A cannot be unwrapped in a request for tenant B. **Multi-Region keys** share key material across Regions, which helps disaster recovery but weakens regional isolation. Automatic rotation adds new key material on a configurable period, and deletion requires a 7 to 30 day wait.

AWS KMS offers two **custom key stores**:

- An **AWS CloudHSM key store** places key material in a single-tenant CloudHSM cluster you own, while services still use the normal KMS API.
- An **external key store (XKS)**, launched in 2022, keeps the key material in your own HSM or key manager outside AWS. KMS calls an XKS proxy for every operation and double-encrypts: it encrypts first with material in its own HSMs, then with your external key. Chapter 34 describes the proxy and its vendors.

> **Current development.** The AWS European Sovereign Cloud opened its first Region, in Brandenburg, Germany, in January 2026. It is operated separately from other AWS Regions, by EU-resident staff, with its own KMS. Treat keys there as independent of your keys elsewhere, and check which KMS features, such as multi-Region keys, cross that boundary.

## 28.5 Azure Key Vault and Managed HSM

Microsoft offers several tiers, as of 2026:

| Offering | Tenancy | Typical use |
| --- | --- | --- |
| Key Vault Standard | Multi-tenant, software-protected keys | Secrets, certificates, low-sensitivity keys |
| Key Vault Premium | Multi-tenant, HSM-protected keys | Customer-managed keys for most Azure services |
| **Managed HSM** | Single-tenant HSM pool, FIPS 140-3 Level 3 | High-assurance CMKs, BYOK, regulated workloads |
| Azure Cloud HSM | Single-tenant HSM cluster you administer | Lift-and-shift HSM applications using PKCS#11, JCE or CNG |
| Azure Payment HSM | Dedicated payment HSMs | Payment processing (Chapter 38) |

Azure Cloud HSM is generally available and is the successor to Azure Dedicated HSM, which accepts no new customers and is supported until July 2028.

Access uses **Azure RBAC**, with roles such as Key Vault Crypto User and Key Vault Crypto Officer separating use from administration. **Soft delete** keeps deleted keys recoverable for 7 to 90 days, and **purge protection** stops anyone, administrators included, from permanently deleting a key before then; customer-managed key features in Azure services require it.

Managed HSM's trust model rests on its **security domain**. At activation you supply at least three RSA public keys, and the HSM exports the encrypted material needed to recover its keys, protected by a quorum of those keys that you choose. Only the quorum holders can restore the HSM, not Microsoft. Treat these keys like HSM ceremony smart cards (Chapter 33): offline, split between custodians, and tested.

Azure BYOK follows section 28.3's pattern: you create a **key exchange key** (an RSA-HSM key) in Key Vault, wrap your key to it with your HSM vendor's tool, and upload a `.byok` file. External key management for Managed HSM, in which the KEK stays in a customer HSM reached through a proxy, was in public preview as of 2026 (Chapter 34).

## 28.6 Google Cloud KMS and Cloud EKM

**Google Cloud KMS** organises keys into **key rings** in a location, each key having **versions**, and each key a **protection level**:

- `SOFTWARE`: keys protected by Google's software KMS
- `HSM`: keys in Google's **Cloud HSM**, FIPS 140 Level 3 validated hardware, used through the same API
- `EXTERNAL` and `EXTERNAL_VPC`: keys held in a partner key manager reached through **Cloud External Key Manager (Cloud EKM)**, over the internet or a VPC network

Permissions use IAM roles on the key ring or key, such as `cloudkms.cryptoKeyEncrypterDecrypter` for use and `cloudkms.admin` for management, with the useful property that the admin role cannot encrypt or decrypt. Key versions scheduled for destruction wait for a configurable period (30 days by default) before material is destroyed. Import uses **import jobs** with methods such as RSA-OAEP-3072 with SHA-256 and AES key wrap.

Two features matter at enterprise scale. **CMEK organisation policies** (`constraints/gcp.restrictNonCmekServices` and `constraints/gcp.restrictCmekCryptoKeyProjects`) let a central team require customer-managed keys and limit which projects may host them. **Cloud KMS Autokey**, introduced in 2024, creates a key per resource automatically in a designated key project when developers create storage or databases, which removes the main reason teams skip CMEK.

Cloud EKM pairs with **Key Access Justifications**: every request to the external key carries a reason code, and the partner key manager can refuse requests by reason. Google lists its EKM partners in its documentation; as of 2026 they include Fortanix, Futurex and Thales. For regulated and public-sector customers, **Assured Workloads** constrains data location and personnel access, and Google offers sovereign cloud services in some EU countries through local partners, such as S3NS with Thales in France.

## 28.7 Oracle and IBM

**Oracle Cloud Infrastructure (OCI) Vault** offers keys in a shared, multi-tenant HSM-backed vault or in a **virtual private vault**, an isolated partition with its own throughput. **OCI Dedicated KMS** provides a single-tenant HSM partition the customer manages, and the **External Key Management Service** lets an OCI vault hold only references to keys kept in a third-party key manager outside Oracle, which Oracle explicitly describes as hold-your-own-key. Thales announced support across OCI regions, including the Oracle EU Sovereign Cloud, in 2023. For Oracle databases on-premises and in hybrid estates, **Oracle Key Vault** centralises TDE master keys (Chapter 27).

**IBM Cloud** offers **Key Protect**, a multi-tenant KMS backed by FIPS 140-2 Level 3 HSMs, and **Hyper Protect Crypto Services (HPCS)**, a dedicated HSM domain on hardware certified to FIPS 140-2 **Level 4**. IBM markets HPCS as **keep your own key (KYOK)**: the customer loads the master key in a smart-card ceremony, so IBM operators cannot access it. Its **Unified Key Orchestrator** manages keys across IBM Cloud and the hyperscalers, like the key brokers in Chapter 34.

## 28.8 Designing key policies

A KMS is only as strong as its policy. The rules carry across every provider:

- **Separate administration from use.** Key administrators create, rotate, disable and schedule deletion; they cannot decrypt. Applications use keys; they cannot change policy. No human routinely holds both.
- **Least privilege by operation.** A service that only writes needs encrypt or generate-data-key, not decrypt. A verifier needs only the public key.
- **Scope keys narrowly.** One key per application, environment and data class, not one company-wide key, so a misconfiguration has a small blast radius and destroying one key shreds one dataset.
- **Use conditions and context.** Restrict use by calling service, network or account, and bind encryption context so a wrapped key cannot be used for another tenant.
- **Protect deletion.** Use waiting periods, purge protection, alerts and separate approval, because deleting a key destroys every byte under it.
- **Watch the logs.** Alert on policy changes, disables, scheduled deletions, decrypts from unusual identities and volume spikes.

> **Watch out.** The commonest cloud key failure is a policy that grants decrypt to every role in the account "to make things work". Dashboards then show "encrypted at rest: 100 percent" while any compromised workload can decrypt everything. Encryption only stops attackers who are *not* authorised to use the key.

## 28.9 Multi-cloud key strategy

An enterprise using several clouds has to decide how much of its key management to unify. Three patterns are common:

- **Native per cloud, governed centrally.** Each cloud's KMS is used natively, but one team sets common standards (naming, tagging, rotation, policy templates) enforced by policy as code, and pulls inventory and logs into one place. This is the simplest and keeps each cloud's failure domain separate.
- **BYOK through a key broker.** Key material is generated in the organisation's HSMs and imported into each cloud by a key broker or orchestration tool (Chapter 34), giving one inventory and escrow. Cloud services still depend only on their own KMS at run time.
- **Central external key manager.** A single HYOK key manager serves several clouds. This gives the strongest independence but makes one system a dependency of every cloud workload at once, so it is usually reserved for a few datasets.

Whatever the pattern, never make a workload in one cloud depend on a KMS in another for routine decryption, or you inherit both clouds' outages. Keep keys, owners and data classes in one inventory (Chapter 43), use the same rotation and deletion standards everywhere, and plan for **exit**: regulators, DORA among them, expect a credible strategy for leaving a provider.

> **At Meridian.** Meridian runs workloads on all three hyperscalers. The PKI and Cryptography Services team owns the key standard and the key broker; Platform Engineering owns each cloud's landing zone, where policy as code requires customer-managed keys in HSM-backed tiers. Most keys are generated in Meridian's HSMs and imported through the broker. One EU customer dataset in the insurance arm uses an external key store backed by the key managers in DC-East and DC-West, under a sovereignty commitment to a regulator, and GRC signed off the availability risk. The SOC receives alerts from every cloud whenever a key is disabled, scheduled for deletion or has its policy changed.

## 28.10 Sovereignty and data residency

Three ideas are often confused:

- **Data residency** is where data is stored and processed: "customer records stay in EU regions".
- **Data sovereignty** is whose laws apply to the data and who can be compelled to disclose it. A US-headquartered provider storing data in Frankfurt may still receive orders under US law, such as the CLOUD Act of 2018.
- **Operational and key sovereignty** is who operates the service and who controls the keys: whether foreign staff can access systems, and whether the provider can decrypt without the customer.

The EU Court of Justice's **Schrems II** judgment of July 2020 invalidated the EU-US Privacy Shield and required exporters to assess "supplementary measures" for transfers. The European Data Protection Board's recommendations identified strong encryption, with keys kept under the exporter's control, as effective for data that the importer stores but does not process in the clear. The EU-US Data Privacy Framework of July 2023 restored an adequacy route, but many European regulators and customers still ask for key control as a hedge.

Cryptography helps sovereignty in a precise and limited way. External key management or a customer-administered HSM can ensure the provider cannot decrypt **data at rest** without your cooperation, and gives you an independent log and a kill switch. It cannot protect data the cloud service **processes in plaintext**: a managed database answering queries has your data decrypted in memory, under the provider's control. For that, the options are confidential computing (Chapter 30), client-side encryption (Chapter 27), or sovereign offerings with local operation, such as the AWS European Sovereign Cloud, Microsoft's EU Data Boundary and sovereign cloud programmes, Google's partner-operated sovereign clouds and Oracle's EU Sovereign Cloud. National schemes such as France's SecNumCloud set requirements for such services.

> **Compliance hook.** GDPR Article 32 names encryption as an appropriate measure, and Chapter V governs transfers. DORA requires financial entities to manage ICT third-party risk, including exit strategies and data location. PCI DSS v4.0.1 Requirements 3.6 and 3.7 cover protection and lifecycle of keys for stored account data, and cloud CMKs are in scope when they protect cardholder data. NIST SP 800-57 Part 1 sets the key lifecycle expectations, and ISO/IEC 27001:2022 A.8.24 and the CSA Cloud Controls Matrix (its Cryptography, Encryption and Key Management domain) are the usual audit anchors for cloud key controls.

## 28.11 SaaS customer-managed keys

Much sensitive data lives in SaaS: email and collaboration suites, CRM and IT service management. Many vendors offer customer-managed keys, which differ greatly in what the key actually controls.

### Microsoft 365 Customer Key

**Microsoft Purview Customer Key** lets a tenant supply the root keys for Microsoft 365 service encryption. The customer creates keys in Azure Key Vault or Managed HSM (purge protection required) and builds **data encryption policies (DEPs)**: one type for Exchange mailboxes, one for SharePoint and OneDrive (one per geography in multi-geo tenants), and a multi-workload DEP covering Teams and other services. Each DEP uses two customer root keys, and Microsoft holds a third, the **availability key**, so that it can recover from the customer losing access to both. If the customer revokes its keys and starts the **data purge path**, the availability key is deleted and the data is cryptographically erased. Customer Key requires appropriate licensing (Microsoft 365 E5 or an add-on, as of 2026).

Customer Key protects at the service-encryption layer: Microsoft services still decrypt content to index, search and scan it. For a small number of documents that Microsoft must never be able to read, **Double Key Encryption** adds a second key held on customer infrastructure (Chapter 29).

### Salesforce Shield Platform Encryption

**Salesforce Shield Platform Encryption** encrypts selected fields, files and search indexes with AES-256. By default, Salesforce derives each data encryption key from a customer-controlled **tenant secret** combined with a Salesforce master secret, using PBKDF2. Customers can instead upload their own key material (BYOK), or use **Cache-Only Keys**, in which Salesforce fetches the key on demand from a customer-run key service, wrapped with JSON Web Encryption, holds it only in cache, and never persists it. Disconnecting the key service cuts off access once cached keys expire. Field encryption has functional costs: the **deterministic** scheme allows exact-match filtering, while the stronger **probabilistic** scheme blocks it, so design choices are made field by field.

### ServiceNow

ServiceNow groups its options in a Platform Encryption bundle, as of 2026. The **Key Management Framework (KMF)** manages keys on the instance. **Column Level Encryption Enterprise** encrypts chosen fields and attachments and supports **customer-supplied keys** and scheduled rotation. **Cloud Encryption** encrypts the instance database at block level, with a customer-managed key option in which ServiceNow holds the key on its infrastructure while the customer performs key operations, and an optional add-on that lets the customer **withdraw** the key, making the instance unreadable until it is resupplied.

### Other platforms

The same ideas recur elsewhere: Slack Enterprise Key Management uses a key in the customer's AWS KMS, Google Workspace client-side encryption uses a customer-run key service, and Snowflake Tri-Secret Secure requires both a customer key and a Snowflake key.

### Evaluating a SaaS key offering

For each platform, ask which data the key protects (all content, selected fields, backups, indexes, logs), where the key lives, whether you see every use in logs you control, what revocation does and how fast, whether the vendor can recover through an availability key, and which features stop working. The answers often show that a SaaS "customer key" protects against a narrow set of threats, such as a storage breach at the vendor or proof of deletion at exit, while the service still decrypts data to run. Describe it that way to risk committees.

> **At Meridian.** Meridian uses customer keys for its productivity suite, held in single-tenant HSM-backed vaults in two regions, mainly so it can evidence cryptographic deletion at exit. Its CRM platform encrypts customer identifiers at field level, and its IT service management platform encrypts security incident records with customer-supplied keys. The PKI and Cryptography Services team records each SaaS key and its revocation procedure in the key inventory, and GRC reviews them in the annual third-party risk cycle.

## 28.12 Lab: BYOK wrapping and least-privilege keys with Vault

This lab uses HashiCorp Vault in dev mode (in Docker) and OpenSSL. Vault's transit engine implements the same encryption context and BYOK import patterns as the cloud KMSs.

1. Start Vault in dev mode and define a helper that runs the CLI inside the container, using the token in `VT`:

    ```bash
    docker run -d --name vlab --cap-add=IPC_LOCK \
      -e VAULT_DEV_ROOT_TOKEN_ID=root \
      -e VAULT_ADDR=http://127.0.0.1:8200 hashicorp/vault:1.17
    v() { docker exec -i -e VAULT_TOKEN="${VT:-root}" vlab vault "$@"; }
    v secrets enable transit
    v audit enable file file_path=/tmp/audit.log
    ```

2. Create a key for an `orders` application with **derived** keys, so each encryption context yields a different key:

    ```bash
    v write -f transit/keys/orders derived=true
    ```

3. Create a writer policy that can only encrypt, and a reader policy that can only decrypt, then a token for each:

    ```bash
    echo 'path "transit/encrypt/orders" { capabilities = ["update"] }' \
      | v policy write orders-writer -
    echo 'path "transit/decrypt/orders" { capabilities = ["update"] }' \
      | v policy write orders-reader -
    W=$(v token create -policy=orders-writer -field=token)
    R=$(v token create -policy=orders-reader -field=token)
    ```

4. Encrypt as the writer with a context of `app=orders,env=prod`:

    ```bash
    PT=$(printf 'card-ref-1234' | base64)
    CTX=$(printf 'app=orders,env=prod' | base64)
    CT=$(VT=$W v write -field=ciphertext transit/encrypt/orders \
      plaintext=$PT context=$CTX)
    echo "$CT"
    ```

5. Try to decrypt as the writer (denied), as the reader with the same context (allowed), and as the reader with `env=test` (fails, because a different context derives a different key):

    ```bash
    VT=$W v write transit/decrypt/orders ciphertext=$CT context=$CTX
    VT=$R v write -field=plaintext transit/decrypt/orders \
      ciphertext=$CT context=$CTX | base64 -d; echo
    BAD=$(printf 'app=orders,env=test' | base64)
    VT=$R v write transit/decrypt/orders ciphertext=$CT context=$BAD
    ```

6. Now perform a BYOK import by hand. Fetch Vault's RSA wrapping key, then generate a target AES-256 key and an ephemeral key with OpenSSL, as your HSM would:

    ```bash
    v read -field=public_key transit/wrapping_key > wrap.pem
    openssl rand -out target.key 32
    openssl rand -out ephemeral.key 32
    ```

7. Wrap the ephemeral key with RSA-OAEP (SHA-256) and the target key with AES Key Wrap with Padding, concatenate them, and import:

    ```bash
    openssl pkeyutl -encrypt -pubin -inkey wrap.pem \
      -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 \
      -pkeyopt rsa_mgf1_md:sha256 -in ephemeral.key -out eph.wrapped
    EK=$(od -An -tx1 ephemeral.key | tr -d ' \n')
    openssl enc -id-aes256-wrap-pad -iv A65959A6 -K "$EK" \
      -in target.key -out tgt.wrapped
    cat eph.wrapped tgt.wrapped | base64 -w0 > payload.b64
    v write transit/keys/byok/import ciphertext="$(cat payload.b64)"
    v read transit/keys/byok
    ```

    You still hold `target.key`: that is your escrow copy, and also the reason crypto-shredding the Vault key alone would not prove deletion. Delete the local files with `shred -u` when you finish.

8. Crypto-shred the `orders` key and confirm the ciphertext is now unrecoverable, then read the audit log and find the denied and failed requests from step 5:

    ```bash
    v write transit/keys/orders/config deletion_allowed=true
    v delete transit/keys/orders
    VT=$R v write transit/decrypt/orders ciphertext=$CT context=$CTX
    docker exec vlab sh -c 'tail -n 20 /tmp/audit.log'
    ```

    Note that the audit log records request paths and identities but stores sensitive values as HMACs, the same balance cloud KMS logs strike.

9. Write down how you would detect, within minutes, that someone had scheduled a production key for deletion in each cloud you use.

**Optional cloud extension.** In an AWS account, create a KMS key with no key material (`--origin EXTERNAL`), call `get-parameters-for-import` with the `RSA_AES_KEY_WRAP_SHA_256` wrapping algorithm, and import key material built exactly as in step 7. Then find the import and encrypt events in CloudTrail. Azure Key Vault BYOK and Google Cloud KMS import jobs follow the same pattern with different tooling. *Cost warning:* cloud KMS keys carry a monthly charge per key and per-request charges, and Managed HSM and dedicated HSMs are billed by the hour at much higher rates; schedule deletion of lab keys and delete any HSM resources when you finish.

## 28.13 Failure story: encrypted, and decrypted for the attacker

In July 2019, a large US bank disclosed that an attacker had obtained data on about 100 million customers in the United States and 6 million in Canada from its cloud environment. According to the US Department of Justice's criminal complaint, the attacker exploited a misconfigured web application firewall to perform server-side request forgery against the cloud instance metadata service, and obtained temporary credentials for the role the firewall ran under. That role could list and read the storage buckets holding the data.

The data was encrypted at rest. It did not matter: the stolen role was authorised to read the objects, so the storage service called the KMS, unwrapped the DEKs, and returned plaintext, exactly as designed. In 2020 the US Office of the Comptroller of the Currency fined the bank 80 million dollars, citing failures in risk assessment for its cloud migration.

The lessons: encryption at rest only helps against principals who cannot use the key, so scope key policies so that a web-facing role cannot decrypt bulk customer data; treat the key permission as a second, independent control from the storage permission; alert on unusual decryption volume in KMS logs; and encrypt the most sensitive fields at a higher layer so that even a role with storage access sees only ciphertext (Chapter 27).

## 28.14 Chapter summary

- A cloud KMS holds non-exportable keys in HSMs and powers envelope encryption; its policy decides who can decrypt.
- Provider-managed keys answer stolen disks; customer-managed keys add policy, audit and revocation.
- BYOK proves key origin and gives escrow but does not stop the provider using the key; HYOK and external key management keep the key outside the cloud at a cost in availability.
- AWS, Azure, Google Cloud, Oracle and IBM all offer the same custody spectrum, with different trust details such as Managed HSM's customer-held security domain and Google's Key Access Justifications.
- Separate key administration from use, scope keys narrowly, bind encryption context, protect deletion and monitor the logs.
- Multi-cloud strategy usually means native KMS per cloud under one standard and inventory, BYOK through a broker, and HYOK only for a few datasets.
- Key control protects data at rest from the provider, not data the service processes in plaintext; sovereignty also involves jurisdiction and who operates the service.
- SaaS customer-managed keys vary widely in scope; establish what the key controls and what revocation does.
