## 18.1 Why integration decides whether automation works

Chapter 17 described a certificate lifecycle management (CLM) platform: the inventory, the policy engine, the connections to public and private certificate authorities (CAs) and the enrolment protocols. Every one of those pieces can work perfectly and a service can still go down at 03:00 on a Sunday, because the renewed certificate never reached the device that presents it, or reached one node of a pair but not the other, or was installed but never bound to the listener.

A **target** is any system that presents or uses a certificate: a CDN edge, a load balancer virtual server, a firewall decryption profile, a Kubernetes ingress, a Java application server, a RADIUS server. A **binding** is the configuration that tells the target which certificate to present for which name, port or service. An **integration** is the code and configuration that lets automation install a certificate on a target, bind it and confirm the result. Integrations are where certificate programmes spend most of their engineering effort, for a simple reason: there is one ACME protocol, but there are hundreds of ways to install a certificate.

Shrinking lifetimes turn this from an engineering nicety into a survival question. Under the CA/Browser Forum schedule adopted in 2025, public TLS certificates fall to a maximum of 200 days from March 2026, 100 days from March 2027 and 47 days from March 2029. A team that renews 4,000 public certificates once a year with a manual installation step will, by 2029, be renewing each of them roughly every month. If the installation step is still manual for even 5 percent of the estate, that is a couple of hundred hand-installed certificates every month, each a small chance of an outage.

For every integration in this chapter, ask the same four questions:

1. **Where do the certificate and private key live** on this platform: a file, a Windows certificate store, a Java keystore, a device's configuration database, a hardware security module (HSM), or a cloud service the platform reads from?
2. **How is it installed and bound**: which objects must be created or updated (a certificate object, a key object, an SSL profile, a listener, a route)?
3. **How does automation reach it**: a management API, an agent, a built-in ACME client, a plug-in, or a secret store the platform reads?
4. **What are the gotchas**: high-availability (HA) synchronisation, chain handling, service restarts, keys that cannot be exported, API limits?

> **At Meridian.** Meridian's PKI and Cryptography Services team owns the CLM platform, but it owns almost none of the targets. Network Engineering owns the ADCs, firewalls and VPN gateways; Platform Engineering owns Kubernetes and the cloud accounts; IAM owns AD CS and endpoint enrolment; application teams own Java and database servers; the edge team inside Network Engineering owns the CDN and WAF. Every integration in this chapter is therefore a negotiated agreement: the PKI team provides the connector and the policy, and the target's owner grants a scoped service account and agrees what "done" looks like. The team keeps an integration register that records, for each target type, the delivery pattern, the credential used, the owner and the verification check.

## 18.2 Delivery patterns and their trust implications

There are five ways a certificate gets from the issuing side to a target. Most estates use all five. The choice matters because each pattern answers differently the questions that auditors and attackers both care about: who holds credentials to what, which direction the network connection opens, and where the private key is created.

### API push from the platform

In **API push**, the CLM platform (or a connector it controls) logs in to the target's management interface and installs the certificate. This is the normal model for appliances that cannot run third-party software: load balancers, firewalls, CDNs and cloud certificate stores. The platform needs a credential for every target, stored in its vault, and network reachability from the connector to every management interface.

The trust implication is concentration. A CLM platform that can push certificates to every load balancer and firewall holds administrative credentials to the most exposed systems in the company. Scope those credentials as tightly as the target allows: F5 BIG-IP, NetScaler and Palo Alto firewalls all support role-based accounts that can manage certificates without full administrative rights, and cloud providers allow policies limited to certificate operations. Rotate the credentials, log every use and alert on use from anywhere other than the connector hosts.

Key generation is the second implication. Many appliances can generate a key and a **certificate signing request (CSR)** through their API, which keeps the key on the device; others only accept an uploaded key, which means the platform generates the key and the key travels. Prefer on-device generation when the API supports it, and record the exception when it does not.

### Agent pull

In **agent pull**, a small program on the target host connects outbound to the CLM platform, asks for work, generates keys locally, submits CSRs and installs the results. Agents suit general-purpose servers: Linux web servers, Windows servers running IIS, Java application hosts. The network connection opens from the target to the platform, so inbound firewall rules to thousands of servers are not needed, and the key never leaves the host.

The cost is software on every host: packaging, patching, a service account and a footprint that security teams must approve. Agents also need a bootstrap identity, usually a registration token or a machine certificate, so the platform knows which host is asking.

### Native ACME clients

Many targets now speak **ACME** (Automatic Certificate Management Environment, RFC 8555) themselves. Caddy and Apache's mod_md have done so for years; NGINX announced an official ACME module in August 2025, initially supporting the HTTP-01 challenge; FortiGate firewalls have had a built-in ACME client since FortiOS 7.0; cert-manager, Windows tools such as win-acme and Posh-ACME, and scripts like certbot and acme.sh cover most remaining hosts. A native client keeps the key on the target and needs only outbound access to the ACME server.

For enterprises, the key design choice is which ACME server the client talks to. Pointing thousands of clients directly at a public CA gives the CLM platform no control or visibility beyond Certificate Transparency logs. The common pattern is to point clients at an ACME endpoint the enterprise controls: a CLM platform's ACME service, a private CA's ACME interface (EJBCA, Vault PKI, step-ca and AWS Private CA via connectors all offer one), or a public CA account protected by **External Account Binding (EAB)**, which ties each client to an enterprise account and its policy.

### Secret-store sync

In **secret-store sync**, the certificate and key are written to a secret store, and the consuming platform reads from that store. Azure Application Gateway reads certificates from Azure Key Vault; Kubernetes workloads read TLS Secrets that the External Secrets Operator or the Secrets Store CSI Driver populates from Vault, AWS Secrets Manager or Key Vault; Vault Agent renders certificates to files on a host. The CLM platform's job becomes writing a new version to the store; the platform's job is noticing the new version.

The trust implication is that the store becomes the boundary. Anyone who can read the secret holds the key, so access policies on the store matter as much as those on the target. The gotcha is timing: consumers poll on their own schedule, and that schedule is rarely the one you would choose (section 18.9 gives examples).

### Infrastructure as code

**Infrastructure as code** (IaC) treats certificates as declared resources. Ansible collections exist for most targets (community.crypto for ACME and OpenSSL operations, vendor collections for BIG-IP, NetScaler, PAN-OS and FortiOS), and Terraform providers can request certificates (the ACME provider, aws_acm_certificate, the Google and Azure providers) and bind them to load balancers in the same plan. IaC fits teams that already deploy everything through pipelines.

Two cautions. First, IaC runs on a schedule set by humans: a Terraform plan that only runs when someone changes the application will not renew a certificate on time unless a scheduled pipeline exists. Second, Terraform writes resource attributes into its **state file**, and the documentation for the tls_private_key resource warns that the private key is stored unencrypted in state. Treat state as a secret, store it encrypted with restricted access, or avoid generating keys in Terraform at all.

### Choosing between them

| Pattern | Connection opens from | Key generated | Credential risk | Fits |
| --- | --- | --- | --- | --- |
| API push | Platform to target | Often central; on-device where the API allows | Platform holds admin credentials to many targets | Appliances, CDNs, cloud stores |
| Agent pull | Target to platform | On the host | One registration identity per host | General-purpose servers |
| Native ACME | Target to ACME server | On the target | ACME account key or EAB credentials per client | Web servers, firewalls, Kubernetes |
| Secret-store sync | Consumer to store | Central or in the store | Store access policy is the boundary | Cloud services, Kubernetes |
| Infrastructure as code | Pipeline runner to target | In the pipeline, often in state | Pipeline credentials and state file | Pipeline-driven teams |

Whatever the pattern, a deployment is complete only when four steps succeed: **install** the certificate, key and chain; **bind** it to the listener, profile or route; **synchronise** HA peers and caches; and **verify from outside** that clients receive the new certificate with the full chain and correct names. Chapter 19 covers verification in depth. This chapter shows where each step lives on each platform.

## 18.3 The public edge and CDNs

Customer-facing names usually terminate TLS first at a **content delivery network (CDN)** or cloud web application firewall, not in the data centre. The CDN presents the public certificate to browsers, then opens a second TLS connection to the **origin**, the enterprise's own load balancer or cloud service. That gives two certificates per name, with very different rules.

### Edge-managed versus customer-managed certificates

Every major CDN offers two models. In the **edge-managed** model, the CDN obtains and renews a certificate from a public CA itself, usually domain-validated, using a validation method you approve once (often a CNAME delegation for DNS-01, or HTTP-01 answered by the CDN). The private key is generated and held inside the CDN. Renewal is the CDN's problem, which is attractive as lifetimes shrink. The trade-offs are less control over the CA, the key type and validation level, and a certificate that the CLM platform discovers rather than issues.

In the **customer-managed** model, the enterprise supplies the certificate: either it uploads a certificate and key, or the CDN generates a CSR and the enterprise has it signed by the CA of its choice. This model allows organisation-validated (OV) or extended validation (EV) certificates, a specific CA, and centralised policy, at the cost of building and running the renewal integration.

### Akamai

Akamai's **Certificate Provisioning System (CPS)** manages edge certificates as **enrollments**. For Akamai-managed DV enrollments, Akamai handles issuance and renewal. For **third-party enrollments**, CPS generates the key pair (RSA, ECDSA or both, since dual-stacked keys are the default) and produces a CSR; you retrieve the CSR, have your CA sign it and upload the signed certificate and chain back to CPS. The key stays inside Akamai, which suits most enterprises but means the CLM platform automates CSR signing rather than key delivery. Both the CPS API and Akamai's Terraform provider support this flow.

**Property Manager** holds the delivery configuration, and it connects to certificates through **edge hostnames**: a property's hostnames map to an edge hostname that is tied to a CPS enrollment. A renewed certificate on an existing enrollment needs no property change; adding a new hostname means updating both the enrollment's SAN list and the property. CPS changes deploy to Akamai's network over time rather than instantly, so a renewal workflow must start well before expiry and must wait for deployment status before declaring success.

### Cloudflare

Cloudflare offers several distinct certificate types, and confusing them is a common mistake:

- **Edge certificates** issued and renewed by Cloudflare (Universal SSL and the paid Advanced Certificate Manager), with Cloudflare holding the key.
- **Custom certificates**, uploaded by the customer through the dashboard or the API (`POST /zones/{zone_id}/custom_certificates` with the certificate, private key and a bundle method), which the customer must renew.
- **Origin CA certificates**, issued by Cloudflare's own private CA for installation on origin servers. They are trusted by Cloudflare's edge but not by browsers, and can be issued for up to 15 years. That long life is convenient but is also a trap: a 15-year origin certificate is one nobody will remember.
- **Keyless SSL**, in which the customer keeps the private key on its own **key server**, optionally backed by an HSM through PKCS #11, and Cloudflare's edge sends the key operation to that server during each handshake. Keyless suits regulated firms that may not hand private keys to a third party, at the cost of running a highly available key server reachable from Cloudflare.

### AWS CloudFront with ACM

CloudFront uses certificates from **AWS Certificate Manager (ACM)**, and they must be in the US East (N. Virginia) Region, us-east-1, whatever Region the rest of the workload uses. ACM-issued public certificates renew automatically when DNS validation records remain in place. In February 2026 AWS reduced ACM's public certificate validity to 198 days to comply with the 200-day limit and said ACM begins automatic renewal 45 days before expiry. Imported certificates are never renewed by ACM. A CLM platform that issues from its own CA must re-import into the same certificate ARN (`aws acm import-certificate --certificate-arn ...`), which keeps every CloudFront association pointing at the new certificate.

### Fastly

Fastly's TLS service can manage certificates for you, with a choice of CA: Certainly (Fastly's own publicly trusted CA), Let's Encrypt or GlobalSign. Customers can also upload their own certificates and keys through the TLS API, which separates **private keys**, **certificates** and **activations** (which bind a certificate to a domain), and a bulk "Platform TLS" interface exists for very large numbers of certificates. The separation into objects is typical of edge APIs: rotation means uploading a new key and certificate, then updating the activation, then deleting the old objects.

### Origin certificates and mTLS to origin

The CDN-to-origin connection deserves the same care as the browser-facing one. Three rules apply:

- **Validate the origin.** Configure the CDN to require a valid certificate whose name matches the origin hostname (Cloudflare's "Full (strict)" mode, equivalent settings at other providers). CloudFront requires a custom origin's certificate to come from a publicly trusted CA.
- **Authenticate the CDN to the origin** with **mutual TLS (mTLS)**: the CDN presents a client certificate and the origin accepts only connections that present it. Cloudflare calls this Authenticated Origin Pulls; Akamai, Fastly and the cloud CDNs offer equivalents. This stops attackers from bypassing the CDN and WAF by connecting to the origin directly.
- **Inventory both sides.** Origin certificates and CDN client certificates are often private, long-lived and forgotten.

> **At Meridian.** Meridian uses one CDN and WAF at the edge for the customer website, mobile app APIs and open banking endpoints. For the public website it uses customer-managed OV certificates: the CDN generates the key and CSR, and the CLM platform's edge connector retrieves the CSR, signs it through Meridian's primary public CA account and uploads the result. For marketing microsites it allows edge-managed DV certificates, which the CLM platform discovers through the CDN's API and Certificate Transparency monitoring. Origins present certificates from Meridian's private CA, and every origin requires the CDN's client certificate; the origin load balancers trust only the CDN's client-certificate issuer on those virtual servers.

## 18.4 Load balancers and application delivery controllers

An **application delivery controller (ADC)** is a load balancer that also terminates TLS, rewrites traffic and often hosts a WAF. ADCs present a large share of an enterprise's certificates, both public and internal, and they are where HA synchronisation and HSM-held keys cause most trouble.

### F5 BIG-IP

On BIG-IP, certificates and keys are configuration objects in the `/sys/crypto` namespace (stored on disk under the device's file store), and a **client SSL profile** binds them to traffic: the profile's cert-key-chain lists the certificate, key and chain, and the profile is attached to a **virtual server**. A **server SSL profile** does the same for the BIG-IP-to-pool connection. Automation uses **iControl REST**: upload the file, install it as a crypto object, then patch the profile.

```bash
# Upload, install and bind a renewed certificate on BIG-IP
F5=https://bigip.example.net
curl -sku "$USER:$PASS" -H 'Content-Type: application/octet-stream' \
  -H "Content-Range: 0-$(($(stat -c%s app.crt)-1))/$(stat -c%s app.crt)" \
  --data-binary @app.crt \
  "$F5/mgmt/shared/file-transfer/uploads/app-2026.crt"
curl -sku "$USER:$PASS" -H 'Content-Type: application/json' \
  -d '{"command":"install","name":"app-2026",
       "from-local-file":"/var/config/rest/downloads/app-2026.crt"}' \
  "$F5/mgmt/tm/sys/crypto/cert"
curl -sku "$USER:$PASS" -X PATCH -H 'Content-Type: application/json' \
  -d '{"certKeyChain":[{"name":"default","cert":"/Common/app-2026",
       "key":"/Common/app-2026","chain":"/Common/issuing-ca"}]}' \
  "$F5/mgmt/tm/ltm/profile/client-ssl/~Common~app_clientssl"
```

The key is installed the same way through `/mgmt/tm/sys/crypto/key`, or generated on the device so it never travels. Gotchas:

- **HA device groups.** BIG-IP pairs and clusters share configuration through a **device group**. Changes on one device are not live on its peer until a config sync runs, either automatically or by an explicit `config-sync to-group` command. An integration that updates one unit and skips the sync works perfectly until the next failover.
- **Versioned names.** Install the new certificate under a new name and repoint the profile, rather than overwriting the object in place. That gives a clean rollback and avoids breaking every other profile that references the old object.
- **FIPS and network HSM keys.** BIG-IP models with an internal FIPS 140 module, and BIG-IP configured to use a network HSM (Thales Luna, Entrust nShield or a cloud HSM), store the key in the HSM and keep only a reference on the device. Such keys cannot be exported and must be generated through the device or HSM. HA peers need the key made available through the HSM's own mechanism, which an ordinary config sync does not do for an internal FIPS card. Design renewal around on-device CSR generation for these keys.
- **SNI.** One virtual server can host many client SSL profiles, selected by Server Name Indication, with one marked as the default for clients that send no SNI.

### Citrix NetScaler

NetScaler represents a certificate and key as a single **certkey** object (`sslcertkey`) that points to files under `/nsconfig/ssl/`. Intermediate CAs are separate certkey objects **linked** to the server certkey, and the server certkey is **bound** to an SSL virtual server. Automation uses the **NITRO** REST API: upload files through the `systemfile` resource, then update the existing certkey in place (`POST /nitro/v1/config/sslcertkey?action=update`), which instantly changes every virtual server bound to it. That in-place update is convenient and also the gotcha: if the new key does not match the new certificate, every binding fails at once. In an HA pair, configuration commands propagate to the secondary, but the certificate files themselves must also reach the secondary's file system, so check that file synchronisation has run before declaring success.

### NGINX and HAProxy

Open-source proxies keep certificates as **files**. NGINX reads PEM files named by `ssl_certificate` and `ssl_certificate_key`, where the certificate file holds the leaf followed by intermediates. A graceful reload (`nginx -s reload`, or `systemctl reload nginx`) starts new worker processes with the new files while old workers finish their connections, so renewal needs no downtime. Always run `nginx -t` first: a reload with a mismatched key fails, and the old workers keep serving the old certificate, which looks like success to a careless script. NGINX Plus can also load certificates from its key-value store, and the new ACME module lets NGINX obtain certificates itself.

HAProxy reads combined PEM files (certificate, chain and key in one file) from `crt` lines or a `crt-list`. Since version 2.0, its **Runtime API** can replace a certificate in the running process without a reload, in a two-step transaction: `set ssl cert` loads the new content into a pending transaction, and `commit ssl cert` makes it live. Runtime changes exist only in memory, so the integration must also write the file to disk, or the next restart brings the old certificate back. The lab in section 18.11 does exactly this.

### Cloud load balancers

- **AWS Application and Network Load Balancers** take certificates from ACM (or, for older setups, IAM server certificates). A listener has one default certificate and a list of additional certificates chosen by SNI. Using ACM-issued certificates gives automatic renewal; using imported ones means re-importing to the same ARN.
- **Azure Application Gateway** (v2) reads certificates from **Key Vault** through a managed identity. Its instances poll Key Vault every four hours for a newer version, and any change to the gateway forces a check. Rotation works only if the listener references a **versionless** secret identifier; a versioned URI pins the gateway to one version forever. Key Vault certificates used this way must have an exportable key.
- **Azure Front Door** offers Azure-managed certificates or bring-your-own from Key Vault. With the secret version set to "Latest", Microsoft documents that Front Door picks up a new version within three to four days and takes up to 24 hours to deploy it, so renew more than a week before expiry.
- **Google Cloud load balancers** use Google-managed certificates or self-managed ones, either as classic SSL certificate resources or through **Certificate Manager**, whose certificate maps attach many certificates to a load balancer and support DNS authorisation for managed issuance.

> **Watch out.** Cloud load balancers that read from a store on a schedule make "renewal succeeded" and "new certificate live" two different events, sometimes days apart. Record the expected propagation delay for each target type in the integration register, and make the verification check wait for it rather than reporting success at upload time.

## 18.5 Network and security devices

Firewalls, VPN gateways and network access control systems hold some of the least visible and most damaging certificates in an enterprise. When they expire, remote workers cannot connect, Wi-Fi stops authenticating or, worse, inspection silently stops.

### Two very different certificates for decryption

Firewalls that decrypt TLS use certificates in two distinct ways, and they must be managed differently.

- **Inbound inspection** decrypts traffic to the enterprise's own servers. The firewall needs a copy of each server's certificate **and private key**, so every renewal of the server certificate must also reach the firewall. Miss one and inspection fails or the firewall blocks the session. TLS 1.3 and forward-secret key exchange mean the firewall must actually proxy the connection rather than passively decrypt it, which makes the copy on the firewall the certificate clients see.
- **Forward proxy decryption** (outbound inspection) intercepts users' connections to external sites. The firewall generates a certificate for each site on the fly, signed by a **subordinate CA** certificate whose key lives on the firewall. Every managed endpoint must trust that CA. This is one of the most sensitive keys in the enterprise: anyone holding it can impersonate any website to every employee. Issue it from a dedicated private hierarchy, constrain it where the firewall supports constrained certificates, store the key in an HSM where the firewall supports one, and give it a long enough life that its renewal can be planned as a project with endpoint trust distribution.

### Palo Alto Networks

PAN-OS firewalls store certificates in their configuration, in a shared or virtual-system scope, and bind them through **SSL/TLS service profiles** (for the management interface, GlobalProtect portals and gateways, and captive portal) and through **decryption profiles and policies** (marking certificates as Forward Trust and Forward Untrust for forward proxy, or attaching server certificates for inbound inspection). The XML API imports a certificate with its key using `type=import&category=keypair` and a passphrase, and nothing takes effect until a **commit**. Under **Panorama**, certificates are typically defined in **templates** and reach firewalls only when Panorama pushes the template, so the automation must commit on Panorama and then push to the affected device groups and templates. PAN-OS also supports keys held in network HSMs (Thales Luna and Entrust nShield).

```bash
# Import a key pair, then commit (PAN-OS XML API)
curl -sk -F file=@gp-portal.pem \
  "https://fw.example.net/api/?key=$KEY&type=import&category=keypair\
&certificate-name=gp-portal-2026&format=pem&passphrase=$PASS"
curl -sk "https://fw.example.net/api/?key=$KEY&type=commit\
&cmd=<commit></commit>"
```

**GlobalProtect** portal and gateway certificates are public-facing for remote users, and some deployments also use machine certificates on endpoints for pre-logon authentication. A portal certificate change affects every remote worker at once, so verify against the external address after the commit.

### Fortinet, Cisco, Check Point and Zscaler

- **Fortinet FortiGate** stores local certificates in its configuration and binds them in SSL VPN settings, admin access and SSL inspection profiles. FortiOS has a built-in ACME client (from 7.0) for public names that resolve to the firewall, which requires HTTP-01 reachability on the chosen interface, and a REST API for importing certificates from a CLM platform. FortiManager can distribute certificates to managed firewalls.
- **Cisco ASA** organises certificates as **trustpoints**, each holding an identity certificate, its key and its issuing CA, and binds a trustpoint to an interface for AnyConnect or Secure Client VPN with `ssl trust-point`. ASA can enrol through SCEP or import PKCS #12 files. **Firepower Threat Defense (FTD)** devices are managed through Firewall Management Center, whose REST API manages certificate objects that are then deployed to devices.
- **Cisco ISE** assigns each **system certificate** one or more usages: Admin, EAP Authentication, RADIUS DTLS, pxGrid, Portal and SAML. Replacing the Admin certificate restarts application services on the node, so ISE renewals need a maintenance window per node and must be staggered across a deployment.
- **Check Point** gateways receive VPN and internal communication certificates from the management server's **Internal CA (ICA)**. HTTPS inspection uses an imported server certificate for inbound inspection and a CA certificate (generated by the management server or imported from the enterprise PKI) for outbound inspection. Changes reach gateways when policy is installed.
- **Zscaler** and other cloud security service edges perform forward-proxy inspection in the provider's cloud. By default they sign with the provider's own intermediate; enterprises that want their own trust anchor have the provider generate a CSR for a custom intermediate, sign it with their enterprise CA and upload the result, so the key stays in the provider's cloud.

### VPN gateways and 802.1X

Site-to-site IPsec gateways (strongSwan, cloud VPN gateways and the firewall vendors above) authenticate peers with certificates when pre-shared keys are not used. Each peer must trust the other's issuing CA and often checks a specific identity, so changing CA or subject naming needs coordination on both ends. Chapter 22 covers the protocols.

**802.1X** network access, used for corporate Wi-Fi and wired port authentication, relies on a **RADIUS server certificate** presented during EAP-TLS, PEAP or EAP-TTLS. Microsoft NPS, Cisco ISE, Aruba ClearPass and FreeRADIUS all present one. Supplicants are usually configured, through Group Policy or mobile device management (MDM) profiles, to trust a specific issuing CA and sometimes a specific server name. Renewing from the same issuing CA with the same name is invisible to users. Renewing from a different CA, or changing the name, breaks authentication for every device whose profile has not been updated first. Push new trust settings to endpoints weeks before the server certificate changes, and keep RADIUS server certificates on a private CA, because public CAs cannot vouch for an internal name and their roots change on schedules you do not control.

> **Compliance hook.** PCI DSS v4.0.1 Requirement 4.2.1.1 requires an inventory of the entity's trusted keys and certificates used to protect cardholder data in transit, and Requirement 4.2.1 requires certificates on those transmissions to be valid and not expired. Firewalls performing inbound inspection of cardholder traffic hold copies of those keys, so they belong in the inventory. ISO/IEC 27001:2022 Annex A control 8.24 (use of cryptography) and NIST SP 800-53 SC-12 and SC-17 (key and PKI certificate management) expect the same discipline across network devices.

## 18.6 Kubernetes, service meshes and platform PKI

Container platforms change how certificates are consumed: workloads come and go in minutes, and certificates are declared as Kubernetes objects rather than installed by hand.

### cert-manager

**cert-manager** is the de facto certificate controller for Kubernetes, a Cloud Native Computing Foundation project. It adds custom resources:

- An **Issuer** (namespaced) or **ClusterIssuer** (cluster-wide) describes how to obtain certificates. Built-in types include ACME, CA (signing with a key held in a Kubernetes Secret), SelfSigned, Vault and Venafi (which connects to CyberArk Certificate Manager, formerly Venafi). **External issuers** add more: AWS Private CA, Google CA Service, step-ca, and plug-ins from commercial CLM vendors.
- A **Certificate** declares what you want: the Secret name, DNS names, duration, renewal point (`renewBefore`) and private key settings. cert-manager generates the key inside the cluster, creates a **CertificateRequest**, gets it signed and writes `tls.crt`, `tls.key` and often `ca.crt` into the Secret.
- **Ingress annotations** (`cert-manager.io/cluster-issuer`) and Gateway API support create Certificates automatically for routes.

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: payments-api
  namespace: payments
spec:
  secretName: payments-api-tls
  dnsNames: ["payments-api.internal.example"]
  duration: 720h        # 30 days
  renewBefore: 240h     # renew with a third remaining
  privateKey:
    algorithm: ECDSA
    size: 256
    rotationPolicy: Always
  issuerRef:
    kind: ClusterIssuer
    name: enterprise-ca
```

Gotchas: since cert-manager 1.18 the default private key rotation policy is `Always`, so every renewal creates a new key, which is the right default but surprises teams that pinned keys. Applications must reload when the Secret changes; ingress controllers do so automatically, but many applications read files once at start-up and need a reloader or a restart. Trust distribution is a separate problem, which the companion **trust-manager** project addresses by publishing CA bundles to namespaces. Finally, cert-manager's own inventory lives in each cluster, so the CLM platform must discover Certificates across clusters through the Kubernetes API or the vendor's plug-in.

### OpenShift

Red Hat OpenShift adds three certificate mechanisms of its own. The **ingress controller** has a default wildcard certificate for the cluster's application domain, replaceable by setting `spec.defaultCertificate` on the IngressController to a Secret. **Routes** can carry their own certificates inline for edge or re-encrypt termination, or pass TLS through to the pod. The **service CA operator** issues certificates to internal services automatically: annotate a Service with `service.beta.openshift.io/serving-cert-secret-name` and the operator creates and renews a Secret signed by the cluster's service CA, whose bundle can be injected into ConfigMaps for clients. cert-manager also runs on OpenShift and is offered as a supported operator. The common enterprise design is to replace the default ingress certificate with one from the enterprise CA, use cert-manager for application routes, and leave the service CA for intra-cluster traffic.

### Istio and SPIFFE

A **service mesh** issues a certificate to every workload for mutual TLS between services. Istio's control plane (istiod) acts as a CA by default and issues short-lived certificates (24 hours by default) whose identity is a **SPIFFE ID** of the form `spiffe://<trust-domain>/ns/<namespace>/sa/<service-account>`. **SPIFFE** (Secure Production Identity Framework for Everyone) standardises that identity format and the **SVID** documents that carry it; **SPIRE** is its reference implementation, usable with or without a mesh.

Enterprises rarely want each cluster to invent its own root. Istio supports plugging in an intermediate CA from the enterprise hierarchy, and cert-manager's istio-csr project lets cert-manager sign mesh certificates through any configured issuer. The CLM platform's role is then to manage the mesh intermediates (a handful of certificates with months of life), not the millions of daily workload certificates, which it should count and monitor in aggregate. Chapter 24 covers meshes in depth.

### HashiCorp Vault PKI and CI/CD

Vault's **PKI secrets engine** is a private CA built for automation: **roles** constrain allowed names, key types and lifetimes, and clients call `pki/issue/<role>` to receive a key and certificate in one response, or `pki/sign/<role>` with their own CSR. Since Vault 1.14 the engine also offers ACME. Vault Agent can render certificates to files and run a command (such as an NGINX reload) when they change. Because Vault issues fast and cheaply, the usual pattern is short lifetimes, sometimes hours, with no revocation, and the CLM platform imports issuance records for visibility rather than approving each request.

**CI/CD pipelines** both consume and deploy certificates. A pipeline may request a certificate during deployment (through ACME, Vault or a CLM API), bake a truststore into an image, or run the Ansible or Terraform that binds certificates to load balancers. Give each pipeline its own narrowly scoped credential, never commit keys to repositories, and do not build private keys into container images, where they persist in every registry layer.

> **At Meridian.** Platform Engineering runs cert-manager on every cluster, on premises and in all three clouds. A ClusterIssuer on each cluster points at Meridian's CLM platform through its cert-manager plug-in, which applies policy and issues from the private issuing CA in the data centre; public names on cloud ingresses use an ACME ClusterIssuer bound to Meridian's public CA account through EAB. The meshes use intermediates issued from a dedicated mesh sub-CA, renewed by cert-manager and monitored by the PKI team. The PKI team does not try to inventory each 24-hour workload certificate; it tracks issuance rates per cluster and alerts when they stop.

## 18.7 Windows and endpoints

### AD CS and auto-enrolment

For domain-joined Windows machines and users, **Active Directory Certificate Services (AD CS)** with **auto-enrolment** remains the most automated certificate system most enterprises own. A **certificate template** defines the certificate's contents, key settings and who may enrol; Group Policy turns on auto-enrolment; and the Windows certificate services client on each machine enrols, renews and replaces certificates without anyone touching it. Keys live in the Windows certificate store, protected by the operating system or, where the template requires it, by the **Trusted Platform Module (TPM)** through the Microsoft Platform Crypto Provider.

Template security is part of integration. Templates that let the requester supply the subject, or that grant enrolment rights too widely, enabled the AD CS escalation techniques published in 2021 and covered in Chapter 15. A CLM platform typically integrates with AD CS in two ways: as an issuing CA (submitting CSRs to a template through DCOM or a gateway) and as a discovery source (importing the CA database so auto-enrolled certificates appear in the inventory).

### Intune and Jamf

Devices that are not domain-joined get certificates through MDM. Microsoft **Intune** offers two profile types. **SCEP** profiles make the device generate its own key and enrol through the Simple Certificate Enrollment Protocol, usually via Microsoft's Network Device Enrollment Service (NDES) with the **Intune Certificate Connector**, or through a third-party or cloud SCEP service. **PKCS** profiles have the connector request a certificate from the CA on the device's behalf and deliver it, key included, to the device; that supports scenarios such as S/MIME encryption keys that must be recoverable, but the key leaves the CA side. Microsoft's Cloud PKI, part of the Intune Suite, adds a hosted CA option.

**Jamf Pro** manages macOS and iOS certificates through configuration profiles with SCEP or certificate payloads, and connects to AD CS through its AD CS Connector or to commercial CAs through integrations. On Apple platforms, keys live in the keychain, and on devices with the Secure Enclave, hardware-bound keys can be requested through **ACME device attestation** payloads. Android Enterprise uses the same SCEP and PKCS patterns through its MDM. Chapter 36 covers endpoint certificates more fully.

### IIS, Exchange and RDP

- **IIS** reads certificates from the Windows store by thumbprint. A site's HTTPS binding records the thumbprint, so renewal means importing the new certificate and updating the binding, as below. IIS's **Centralized Certificate Store** alternatively reads PFX files from a share named by host name, which suits farms. Agents, win-acme and Posh-ACME all handle the rebind.
- **Exchange Server** certificates must be imported and then enabled for services (`Enable-ExchangeCertificate -Thumbprint ... -Services IIS,SMTP`), on every server in the organisation, and hybrid deployments also reference the certificate in the hybrid connector configuration. Missing one server is the classic Exchange failure.
- **Remote Desktop** uses a self-signed certificate by default. Enterprises replace it through an auto-enrolment template and the Group Policy setting for the RDP server authentication template, which removes the warning users learn to click through.

```powershell
# Rebind an IIS site to a renewed certificate (WebAdministration)
$cert = Get-ChildItem Cert:\LocalMachine\My |
  Where-Object { $_.Subject -like '*portal.example.com*' } |
  Sort-Object NotAfter -Descending | Select-Object -First 1
$b = Get-WebBinding -Name 'Portal' -Protocol https
$b.AddSslCertificate($cert.Thumbprint, 'My')
```

## 18.8 Applications and middleware

Behind the load balancers sit Java application servers, message brokers, databases and, in banks, mainframes. These hold thousands of certificates, often in formats that general-purpose tools do not handle, and often for TLS between internal services.

### Java keystores and truststores

Java applications read keys and certificates from a **keystore** (the identity: private key plus certificate chain) and decide whom to trust from a **truststore** (CA certificates only). Both are files, protected by passwords. The older **JKS** format is Java-specific; **PKCS #12** is the cross-platform standard and has been the JDK's default keystore type since Java 9. Prefer PKCS #12: OpenSSL, Windows and every CLM platform can produce it directly. `keytool` converts and inspects:

```bash
# Build a PKCS#12 keystore from PEM files, then inspect it
openssl pkcs12 -export -name app -inkey app.key -in app.crt \
  -certfile chain.pem -out app.p12 -passout pass:"$KS_PASS"
keytool -list -v -keystore app.p12 -storetype PKCS12 \
  -storepass "$KS_PASS" | grep -E 'Alias|Valid|Owner'
# Add an enterprise root to a truststore
keytool -importcert -noprompt -alias meridian-root \
  -file root.pem -keystore truststore.p12 -storepass "$TS_PASS"
```

Gotchas: the **alias** must match what the server expects; passwords end up in configuration files and need managing as secrets; and truststores drift. Old JDK cacerts files and appliance truststores missing a newer root are one of the most common causes of failures after a CA change, a problem Chapter 19 addresses in its failure modes.

### Tomcat, WebLogic and Kafka

- **Tomcat** binds certificates in an `SSLHostConfig` element of `server.xml`, pointing at a keystore or at PEM files. Since Tomcat 8.5 it can reload the TLS configuration without a restart through JMX, but many deployments simply restart.
- **WebLogic** uses an **identity keystore** and a **trust keystore** per server, configured in the console or through WLST, with a private key alias and passphrase. In a domain, each managed server has its own keystores, so automation must reach every machine, and changes take effect after the server's SSL configuration is restarted.
- **Apache Kafka** brokers read `ssl.keystore.*` and `ssl.truststore.*` properties per listener. Kafka supports dynamic updates of listener keystores without a broker restart, through `kafka-configs` against the broker, and newer versions accept PEM content directly. Clients have their own keystores when brokers require mTLS, which multiplies certificates quickly: a cluster with a hundred client applications may have a hundred client certificates to renew.

### IBM MQ, databases and the mainframe

- **IBM MQ** keeps keys in a **key repository** (a CMS key database managed with `runmqakm`) on each queue manager and client. The queue manager selects its certificate by **label**, either the default `ibmwebspheremq<qmgr>` form or the label set in the `CERTLABL` attribute. After changing the repository, `REFRESH SECURITY TYPE(SSL)` makes the queue manager reload it, briefly restarting channels.
- **Databases** each have their own mechanism. PostgreSQL reads `ssl_cert_file` and `ssl_key_file` and reloads them on a configuration reload; SQL Server uses a certificate from the Windows machine store, which its service account must be able to read, and typically needs a service restart to change; Oracle Database uses **wallets** managed with `orapki`. Database certificates are frequently forgotten because only applications, not users, see them.
- **Mainframes** running z/OS hold certificates in RACF (or ACF2 or Top Secret) **key rings**, managed with commands such as `RACDCERT`, with keys optionally protected by the cryptographic hardware through ICSF. **AT-TLS** (Application Transparent TLS) applies TLS policy to applications through the Policy Agent, which names the key ring and certificate label to use. Mainframe changes go through strict change control and are usually made by the systems programming team, so the practical integration is often the CLM platform generating the request and a scheduled job on the mainframe completing the import.

> **In practice.** For middleware, the hardest part is rarely the certificate. It is finding out how each application reloads it. Before onboarding an application, record three facts in the inventory: the file or store it reads, the reload command or restart it needs, and whether the restart needs a change window. With those three facts, almost any application can be automated with an agent and a post-install script.

## 18.9 Cloud certificate services and the CLM platform

Each hyperscaler offers a certificate service tightly integrated with its own load balancers and CDNs, and a private CA service. The architectural question is how these fit with a central CLM platform.

### The services

- **AWS Certificate Manager (ACM)** issues public certificates for use with integrated AWS services and renews them automatically; holds imported certificates; and, since June 2025, can issue **exportable** public certificates for use outside AWS. ACM-issued keys for integrated services cannot be exported, which is a strength rather than a limitation. **AWS Private CA** provides managed private CAs, with keys in AWS-managed HSMs, and integrates with ACM, with Kubernetes through an external cert-manager issuer and with IoT and Roles Anywhere.
- **Azure Key Vault certificates** combine a key, a secret (the exportable PFX or PEM) and a certificate policy. Key Vault can renew automatically from integrated public CAs (DigiCert and GlobalSign) or create CSRs for any other CA, and its lifetime actions can renew at a percentage of life. **App Service** imports certificates from Key Vault and syncs renewed versions automatically, though not instantly, and App Service Managed Certificates offer free DV certificates for simple cases.
- **Google Certificate Manager** issues Google-managed certificates (with DNS or load balancer authorisation) and holds self-managed ones, attaching them to load balancers through certificate maps. **Certificate Authority Service (CAS)** provides managed private CAs organised in **CA pools**, with DevOps and Enterprise tiers, and an external cert-manager issuer.

### Integration models with a central CLM platform

There are three workable models, and most enterprises mix them.

1. **Cloud-native issuance, central visibility.** Let ACM, Key Vault and Certificate Manager issue and renew, and have the CLM platform discover them through cloud APIs for inventory, policy checking and alerting. This is the simplest and most reliable model for workloads that live entirely in one cloud.
2. **Central issuance, cloud as store.** The CLM platform issues from the enterprise's chosen CAs and imports into ACM, writes new versions into Key Vault, or uploads to Certificate Manager. This gives one policy and one CA strategy across clouds, at the cost of running the renewal. Import to the same identifier (ACM ARN, Key Vault certificate name) so bindings follow automatically.
3. **Cloud private CA as an issuer of the CLM platform.** The CLM platform uses AWS Private CA, CAS or an Azure-hosted CA as one of its issuing CAs, so cloud workloads get certificates from a cloud-resident CA under central policy.

> **At Meridian.** Meridian uses model 1 for public certificates on cloud-only workloads, with the CLM platform discovering them every few hours from all three clouds and flagging any that break policy. It uses model 2 for anything that must chain to Meridian's private hierarchy or come from its contracted public CAs, such as open banking endpoints that partners pin to specific issuers. And it uses model 3 in the cloud where its Kubernetes platform runs, where a cloud private CA subordinate to Meridian's offline root issues to cert-manager. Whichever model applies, every certificate appears in the central inventory with an owner.

### Split-horizon DNS

Many enterprises use **split-horizon DNS**: the same name resolves to a public address for internet clients and a private address for internal ones. This affects certificate automation in three ways. ACME HTTP-01 validation happens from the CA's network, so it reaches whatever the public view says, which may not be the server requesting the certificate; DNS-01 validation through a delegated `_acme-challenge` CNAME avoids that. A certificate covering both views must be publicly issuable, so names that exist only internally (such as `.corp` or `.internal` names) must come from a private CA. And verification checks must test both views, because the internal and external paths often terminate on different devices with different copies of the certificate.

### Reaching devices behind firewalls and in DMZs

A **DMZ** (demilitarised zone) is a network segment between the internet and the internal network, holding internet-facing systems. Firewall policy normally allows connections from internal to DMZ but not the reverse, so a central platform can push to DMZ devices if a rule permits its connector to reach their management interfaces. Where even that is not allowed, a **satellite** or **proxy connector** deployed in the DMZ does the pushing locally and talks to the central platform through a narrow, authenticated channel. Every vendor in Chapter 17's comparison offers some form of distributed connector or gateway for this reason.

### Outbound-only connectors

An **outbound-only connector** opens connections to the platform and never accepts any. It polls for work (renewals to install, CSRs to generate), executes locally and reports results. This is how SaaS CLM platforms reach on-premises targets, and how a central platform reaches high-security segments whose firewall policy forbids inbound connections entirely. Treat connectors as privileged systems: harden the host, give each connector its own identity, restrict which targets each one may manage and monitor its activity.

### Air-gapped and OT segments

**Operational technology (OT)** networks, which run industrial and building control systems, and truly **air-gapped** networks may allow no automated path at all. Within such a segment, a local CA or registration authority can issue to devices through EST or SCEP, and only the CA's own certificate renewal and its issuance records cross the boundary, through a controlled offline transfer. Many OT devices cannot be automated at all and have long-lived certificates; inventory them, document the exception with an owner and an end date, and plan renewals as maintenance events. Keep OT issuing CAs separate from IT ones, so a compromise or emergency revocation in one does not spill into the other.

### Hybrid multi-cloud designs

In a hybrid estate, the CLM platform runs either on premises, in one cloud, or as SaaS, and reaches the others through connectors. Practical principles:

- Run **one inventory and one policy** across every environment, even when issuance is distributed.
- Place a **connector in each cloud and each data centre**, close to the targets it manages, so management traffic does not cross the internet.
- Use **cloud-native identities** (instance roles, managed identities, workload identity federation) for connectors in place of long-lived API keys.
- Make the **private CA hierarchy reachable** from every environment, or place a subordinate issuing CA in each, chained to the same offline root.
- Plan for **network partition**: a connector or cluster that loses contact with the central platform should keep serving the certificates it has and renew from a local issuer if one is configured, rather than failing closed.

> **At Meridian.** Meridian runs its CLM platform core in DC-East with a warm standby in DC-West. Connectors sit in each data centre's DMZ, in each of the three clouds and in the payments card-data environment, where Payments Security insisted on an outbound-only connector with its own credential vault and a target list limited to that segment. The SD-WAN branch devices use SCEP against a registration authority in DC-East. Branch building-management systems sit in an OT segment with long-lived certificates from a separate OT issuing CA, listed as named exceptions in the quarterly report to GRC.

## 18.11 Lab: cert-manager on a local cluster, then push renewals to NGINX and HAProxy

This lab builds a private CA inside a local Kubernetes cluster with cert-manager, issues a short-lived certificate, forces a renewal, then delivers the renewed certificate to NGINX by file and reload, and to HAProxy through its Runtime API without a reload. You need Docker, kind (or k3d), kubectl, Helm, OpenSSL and socat.

**1. Create a cluster and install cert-manager.** Use the current release from the cert-manager documentation; this lab was written against the 1.18 series.

```bash
kind create cluster --name certlab   # or: k3d cluster create certlab
helm repo add jetstack https://charts.jetstack.io && helm repo update
helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager --create-namespace --set crds.enabled=true
kubectl -n cert-manager rollout status deploy/cert-manager-webhook
```

**2. Bootstrap a private CA.** A SelfSigned issuer creates a root certificate, and a CA ClusterIssuer then signs with it. This mirrors a real hierarchy in miniature.

```yaml
# ca.yaml
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: selfsigned}
spec: {selfSigned: {}}
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: {name: lab-root, namespace: cert-manager}
spec:
  isCA: true
  commonName: Lab Root CA
  secretName: lab-root-ca
  privateKey: {algorithm: ECDSA, size: 256}
  issuerRef: {kind: ClusterIssuer, name: selfsigned}
---
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata: {name: lab-ca}
spec: {ca: {secretName: lab-root-ca}}
```

```bash
kubectl apply -f ca.yaml
kubectl get clusterissuer lab-ca   # READY should be True
```

**3. Issue a short-lived certificate.** One hour is the minimum duration cert-manager accepts.

```yaml
# app.yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata: {name: app, namespace: default}
spec:
  secretName: app-tls
  dnsNames: [app.lab.test]
  duration: 1h
  renewBefore: 20m
  privateKey: {algorithm: ECDSA, size: 256, rotationPolicy: Always}
  issuerRef: {kind: ClusterIssuer, name: lab-ca}
```

```bash
kubectl apply -f app.yaml
kubectl get certificate app -o wide
kubectl get secret app-tls -o jsonpath='{.data.tls\.crt}' | base64 -d \
  | openssl x509 -noout -serial -enddate -issuer
```

**4. Export the certificate as files.** This step stands in for a CLM connector or agent fetching the issued certificate.

```bash
mkdir -p certs
kubectl get secret app-tls -o jsonpath='{.data.tls\.crt}' \
  | base64 -d > certs/app.crt
kubectl get secret app-tls -o jsonpath='{.data.tls\.key}' \
  | base64 -d > certs/app.key
kubectl -n cert-manager get secret lab-root-ca \
  -o jsonpath='{.data.ca\.crt}' | base64 -d > certs/root.crt
cat certs/app.crt certs/app.key > certs/app.pem   # HAProxy format
```

**5. Run NGINX and HAProxy.** Create the two configuration files below, then start both containers.

```text
# nginx.conf
events {}
http {
  server {
    listen 8443 ssl;
    ssl_certificate     /certs/app.crt;
    ssl_certificate_key /certs/app.key;
    location / { return 200 "nginx ok\n"; }
  }
}
```

```text
# haproxy.cfg
global
  stats socket ipv4@0.0.0.0:9999 level admin
defaults
  mode http
  timeout connect 5s
  timeout client 30s
  timeout server 30s
frontend fe
  bind :9443 ssl crt /certs/app.pem
  http-request return status 200 content-type text/plain string "haproxy ok"
```

```bash
docker run -d --name ngx -p 8443:8443 -v "$PWD/certs:/certs:ro" \
  -v "$PWD/nginx.conf:/etc/nginx/nginx.conf:ro" nginx:stable
docker run -d --name hap -p 9443:9443 -p 127.0.0.1:9999:9999 \
  -v "$PWD/certs:/certs" \
  -v "$PWD/haproxy.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro" \
  haproxy:3.0
for p in 8443 9443; do
  openssl s_client -connect localhost:$p -servername app.lab.test \
    -CAfile certs/root.crt </dev/null 2>/dev/null \
    | openssl x509 -noout -serial
done
```

Both should print the same serial number, the one from step 3.

**6. Force a renewal.** Use the cmctl tool (`cmctl renew app`) or, without it, delete the Secret and let cert-manager reissue. Repeat step 4 and confirm the serial in `certs/app.crt` has changed. Run the `s_client` loop again: both proxies still serve the **old** serial, because a new file on disk changes nothing until the server reloads. This is the "successful renewal" outage in miniature.

**7. Push to NGINX by reload.**

```bash
docker exec ngx nginx -t && docker exec ngx nginx -s reload
```

**8. Push to HAProxy through the Runtime API.** The file path in the command must match the `crt` path HAProxy loaded. The payload ends at the first blank line.

```bash
( printf 'set ssl cert /certs/app.pem <<\n'; cat certs/app.pem
  printf '\n' ) | socat - TCP:127.0.0.1:9999
echo 'commit ssl cert /certs/app.pem' | socat - TCP:127.0.0.1:9999
echo 'show ssl cert /certs/app.pem' | socat - TCP:127.0.0.1:9999
```

Rerun the `s_client` loop: both now present the new serial, and HAProxy did so with no reload. Because the lab mounted the same `app.pem` that you regenerated, a restart would also pick up the new certificate; in production, always write the file to disk as well as calling the Runtime API.

**9. Break it on purpose.** Generate a fresh key with `openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256`, combine it with the current certificate into a mismatched PEM, and try steps 7 and 8. Note how `nginx -t` fails and HAProxy rejects the transaction, and that both keep serving the previous certificate. Write a check that would catch this before an alert did.

**10. Optional extension: step-ca as the issuer.** Run step-ca with ACME enabled (as in the Chapter 17 lab) and replace the CA ClusterIssuer with Smallstep's step-issuer or an ACME ClusterIssuer pointing at step-ca's directory URL. HTTP-01 needs the ACME server to reach the cluster's ingress, so on a laptop it is easier to run step-ca inside the cluster or use the step-issuer.

**Optional cloud extension.** Repeat step 8's idea against a cloud load balancer: import the renewed certificate into ACM in a test account with `aws acm import-certificate --certificate-arn` on an existing ARN and confirm an ALB listener picks it up, or write a new version to an Azure Key Vault certificate referenced by an Application Gateway and time how long rotation takes. Cost warning: load balancers and gateways bill by the hour (and Application Gateway v2 is not cheap), and an ACM exportable public certificate is charged per name. Delete everything when you finish.

## 18.12 Failure story: one wildcard certificate, hundreds of services

At 12:00 UTC on 6 April 2021, a wildcard TLS certificate used by Epic Games expired. Epic's own public post-incident report explains that the certificate covered an internal DNS zone and was used for a large amount of internal-only communication between back-end services across its platform, including core identity and authentication systems that many other services depend on. Traffic between back-end systems failed at the moment of expiry.

Epic stated that its monitoring did not cover every place the certificate was used, so the expiry was not caught in advance. The certificate itself was managed in AWS Certificate Manager, which let the team renew it and deploy the new one to hundreds of production services quickly once the problem was found, and Epic was explicit that the cause lay in how it managed its own certificate, not in the cloud service. Recovery was then prolonged by secondary effects: a surge of traffic to the Epic Games Launcher when services came back, and an incorrect version of the store website deployed during automatic scaling. Epic's actions included limiting the scope of each certificate, revising its certificate-use processes and completing a manual review of all its certificates.

Three lessons apply directly to integration work:

- **A certificate's blast radius is the number of places it is installed.** One wildcard deployed to hundreds of services means one expiry takes all of them down at once. Narrower certificates, issued per service through automation, fail one at a time.
- **Monitoring must follow deployment, not issuance.** Knowing that a certificate exists is not enough; the inventory must record every endpoint that presents it, which is exactly what install-bind-verify integrations produce as a by-product.
- **Recovery is an integration test.** Epic could redeploy quickly because the certificate already lived in a managed service connected to its platforms. An estate whose certificates are hand-installed would have had to visit each service in turn.

## 18.13 Chapter summary

- Issuance is the easy half; the integration that installs, binds, synchronises and verifies a certificate on each target is where automation succeeds or fails.
- Five delivery patterns cover nearly every target: API push, agent pull, native ACME, secret-store sync and infrastructure as code. Each moves credentials, network paths and key generation to a different place.
- CDNs offer edge-managed and customer-managed certificates; the CDN-to-origin connection needs strict validation, mTLS and its own inventory.
- ADCs bind certificates through profiles or certkey objects; HA synchronisation, versioned object names and HSM-held keys that cannot be exported are the common traps.
- Firewalls use certificates for inbound inspection (a copy of the server key) and forward proxy (a subordinate CA trusted by every endpoint); RADIUS and VPN certificates break clients when their issuer or name changes.
- Kubernetes uses cert-manager Issuers and Certificates; OpenShift adds routes, a default ingress certificate and a service CA; meshes issue short-lived SPIFFE certificates under an enterprise intermediate.
- Windows relies on AD CS auto-enrolment and MDM (SCEP and PKCS); middleware relies on keystores, key repositories, wallets and key rings, and each application's reload behaviour must be recorded.
- Cloud certificate services work best either as issuers with central visibility, as stores for centrally issued certificates, or as cloud-resident CAs under central policy.
- Reaching every zone needs DMZ and outbound-only connectors, DNS-01 for split-horizon names and documented offline processes for air-gapped and OT segments.
