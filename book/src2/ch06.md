## 6.1 Why modes exist

Chapter 5 ended with the encrypted penguin: encrypting each block independently (**ECB mode**, for electronic codebook) leaks every repetition in the data. A **mode of operation** is a recipe for using a block cipher on data of any length so that patterns disappear. Every mode does this by mixing in something that changes: a previous ciphertext block, a counter, a sector number or a random starting value.

That changing input has two names you must know:

- **Initialisation vector (IV):** a starting value for the mode. Some modes need it to be unpredictable.
- **Nonce:** short for "number used once". A value that must never repeat under the same key. It does not have to be secret or random, only unique.

Getting the IV or nonce wrong is the most common way modes fail in practice.

## 6.2 CBC and the padding oracle

**Cipher Block Chaining (CBC)** mode XORs each plaintext block with the previous ciphertext block before encrypting it. The first block is XOR-ed with the IV.

```text
C1 = Encrypt(K, P1 XOR IV)
C2 = Encrypt(K, P2 XOR C1)
C3 = Encrypt(K, P3 XOR C2) ...
```

Because each ciphertext block depends on all previous blocks, identical plaintext blocks now produce different ciphertext. CBC was the default for TLS and disk encryption for many years. It has two requirements and three weaknesses:

- The IV must be **unpredictable** for each message. Predictable IVs enabled the BEAST attack on TLS 1.0 in 2011.
- The plaintext must be **padded** to a multiple of 16 bytes, usually with PKCS#7 padding, where the last bytes all equal the number of padding bytes added.
- Encryption cannot run in parallel, because each block needs the previous one.
- **CBC provides no integrity.** Flipping a bit in ciphertext block C1 scrambles P1 but flips the same bit in P2. An attacker can make controlled changes without the key.
- Its padding becomes an attack surface.

### The padding oracle attack

Imagine a server that decrypts CBC data and responds differently when the padding is wrong ("padding error") than when the content is wrong ("invalid request"). That small difference is an **oracle**: a yes-or-no answer about a secret. In 2002, Serge Vaudenay showed that an attacker can use it to decrypt any ciphertext one byte at a time, by submitting up to 256 altered versions per byte and watching which ones produce valid padding. No key is recovered; the server decrypts the data for the attacker.

Padding oracles appeared in web frameworks, in TLS (the Lucky Thirteen attack in 2013 used timing differences instead of error messages, and POODLE in 2014 broke SSL 3.0) and in countless custom applications. The deeper lesson: **any encryption that can be modified without detection will eventually leak through the way systems react to the modified data.** The fix is not better error messages. It is integrity protection.

## 6.3 CTR: turning a block cipher into a stream cipher

**Counter (CTR)** mode encrypts a sequence of counter values and XORs the results with the plaintext:

```text
keystream block i = Encrypt(K, nonce || counter_i)
Ci = Pi XOR keystream block i
```

CTR needs no padding, runs in parallel, and uses the same operation to encrypt and decrypt. Its one rule is absolute:

> **Watch out.** Never reuse a nonce with the same key. Two messages encrypted with the same key and nonce share a keystream. XOR-ing the two ciphertexts cancels the keystream and gives the XOR of the two plaintexts, which is usually enough to recover both.

Like CBC, CTR alone provides no integrity, and it is even easier to tamper with: flipping a ciphertext bit flips exactly the same plaintext bit. An attacker who knows a message says "pay 100" can change it to "pay 900" without the key.

## 6.4 Authenticated encryption

The solution to tampering is to attach an integrity check that only key holders can create. For years, developers did this by hand: encrypt with one key, then compute a MAC (Chapter 7) over the ciphertext with another. The order matters. **Encrypt-then-MAC** is safe, because the receiver checks the MAC and rejects altered ciphertext before decrypting anything. The other orderings, used by older TLS and SSH versions, led to attacks.

Hand-assembled constructions proved fragile, so cryptographers created **authenticated encryption with associated data (AEAD)**: single algorithms that encrypt and authenticate together.

```text
ciphertext, tag = AEAD_Encrypt(key, nonce, plaintext, associated_data)
plaintext       = AEAD_Decrypt(key, nonce, ciphertext, tag,
                               associated_data)
                  # fails completely if anything was altered
```

**Associated data (AD)** is information that must be protected against tampering but need not be secret, such as a packet header, a database record ID or a key version. It is authenticated but not encrypted. Binding context this way stops an attacker from moving a valid ciphertext into a different context, for example swapping the encrypted salary fields of two employees' records.

The decryption rule is strict: if the tag does not verify, the function returns an error and **no plaintext at all**. Never use partially decrypted data from a failed check.

## 6.5 AES-GCM

**Galois/Counter Mode (GCM)** combines CTR encryption with a fast authenticator called GHASH, computed with multiplication in the finite field GF(2^128). It is the most widely used AEAD in the world: the default in TLS 1.3, IPsec, MACsec and most cloud storage encryption. It is fast with the processor instructions described in Chapter 5, uses a 96-bit nonce that must be unique per key, and produces a 128-bit tag.

GCM fails badly when a nonce repeats. Reuse exposes the XOR of the two plaintexts, as with CTR, and also leaks enough about the internal authentication key that an attacker can forge valid tags for any message from then on.

### Managing GCM nonces

You have two safe options:

1. **Counters.** Use a message counter as the nonce, one counter per key, stored reliably. Ideal when one process owns the key.
2. **Random nonces.** Generate 96 random bits per message. Because of the birthday bound (Chapter 4), NIST limits random-nonce GCM to 2^32 messages per key.

When many machines encrypt with one key, counters are hard to coordinate and random nonces reach the limit sooner. The usual fix is to give each machine or data object its own key, derived from or wrapped by a master key, so that no single key is used too much. This is the **envelope encryption** pattern that every cloud KMS uses (Chapter 28).

> **Watch out.** Nonce reuse happens in real systems: when a counter is restored from an old backup, when virtual machines are cloned with the same state, and when a developer hard-codes a nonce "for testing". A 2016 internet-wide study found 184 HTTPS servers repeating GCM nonces, exposing them to forgery.

## 6.6 ChaCha20-Poly1305 and misuse-resistant modes

**ChaCha20-Poly1305** pairs the ChaCha20 stream cipher with the Poly1305 authenticator. It is standardised in RFC 8439, supported by TLS 1.3, and used by WireGuard, SSH and many messaging apps.

| Property | AES-256-GCM | ChaCha20-Poly1305 |
| --- | --- | --- |
| Speed with AES hardware | Fastest | Fast |
| Speed without AES hardware | Slow, hard to make constant-time | Fast and constant-time |
| Nonce | 96 bits | 96 bits (XChaCha20: 192 bits) |
| Nonce reuse | Catastrophic | Catastrophic |
| FIPS status | Approved | Not approved |

Choose AES-GCM where FIPS validation is required, which in a regulated bank is most places. The extended-nonce variant **XChaCha20-Poly1305** uses a 192-bit nonce, large enough that random nonces never realistically collide.

Because nonce reuse is so damaging, cryptographers designed **nonce-misuse-resistant** AEADs. The best known is **AES-GCM-SIV** (RFC 8452). It computes the tag first and uses it as the effective IV. If a nonce is repeated, the only thing leaked is whether two messages were identical. The cost is a second pass over the data.

## 6.7 XTS: encrypting disks and volumes

Disk encryption has an unusual constraint: a 4,096-byte sector must encrypt to exactly 4,096 bytes, because the storage layout has no room for a nonce or a tag. Disk encryption therefore uses a **tweakable** mode, where the sector number acts as a public "tweak" that makes every sector's encryption different. The standard is **XTS-AES**, defined in IEEE 1619 and approved by NIST in SP 800-38E.

XTS uses two AES keys. The second key encrypts the sector number to produce a starting mask; for each 16-byte block within the sector, the mask is multiplied by a fixed value so that every block position gets a different one. Each block is XOR-ed with its mask, encrypted with the first key, and XOR-ed with the mask again. A final partial block, if any, is handled by **ciphertext stealing**, which borrows bytes from the previous block so that nothing grows. Because two keys are concatenated, "XTS-AES-256" uses 512 bits of key material, and "XTS-AES-128" uses 256 bits, a frequent source of confusion in configuration screens. FIPS 140-3 modules must also check that the two halves are different.

XTS is everywhere at rest. BitLocker on Windows uses XTS-AES (128-bit by default, with 256-bit selectable by policy), FileVault on macOS uses XTS-AES-128, and LUKS on Linux defaults to `aes-xts-plain64`. Self-encrypting drives and storage arrays use it internally too (Chapter 26).

What XTS does not do is just as important:

- **No integrity.** An attacker who changes ciphertext cannot make controlled edits, but they can randomise a 16-byte block or replay an older version of a sector, and nothing detects it.
- **Deterministic.** The same data written to the same sector produces the same ciphertext. An attacker who sees two snapshots of a disk learns exactly which 16-byte blocks changed between them.

So XTS fits its original threat: a lost laptop or a failed drive leaving the building. It is a weaker fit where an attacker can see many versions of the ciphertext over time, as with cloud volume snapshots, SAN replication streams or backup images. For those, layer authenticated encryption above it, at the file, database or application level (Chapter 27).

## 6.8 AES key wrap: encrypting keys with keys

Every key hierarchy needs a way to encrypt one key under another. A **key-encrypting key (KEK)** protects a **data-encrypting key (DEK)**, so the DEK can be stored next to the data while the KEK stays in an HSM or KMS. Here there is no natural place for a nonce, and the plaintext is itself random. What matters is that the wrapped key cannot be modified undetected.

**AES Key Wrap** (RFC 3394, also NIST's KW mode in SP 800-38F) was designed for this. It splits the key into 64-bit halves and runs six passes of AES over them, mixing in a fixed 64-bit **integrity check value**. The output is 8 bytes longer than the input: a 32-byte AES-256 key wraps to 40 bytes. On unwrap, the receiver checks the integrity value; any change to the wrapped key makes unwrapping fail. The original algorithm requires the key to be a multiple of 8 bytes and at least 16 bytes long. **AES Key Wrap with Padding** (RFC 5649, NIST's KWP) removes that limit by storing the real length in the integrity value and padding with zeros, so it can wrap an HMAC secret of any length or an encoded private key.

Key wrap is deterministic: wrapping the same key under the same KEK always gives the same output. That is acceptable because the payload is a random key, not a message with patterns. **AES-SIV** (RFC 5297) is a related deterministic AEAD sometimes used for the same job when associated data is needed.

You will meet key wrap constantly:

- **HSM interfaces.** PKCS#11, the standard HSM programming interface (Chapter 33), exposes AES key wrap as a mechanism, which is how keys move between HSM partitions and into backups.
- **Bring your own key (BYOK).** When you import key material into a cloud KMS, the cloud gives you an RSA public key. A combined scheme wraps your key with a fresh AES key using KWP, then wraps that AES key with RSA-OAEP (Chapter 8). AWS KMS, Azure Key Vault Managed HSM and Google Cloud KMS all document variants of this RSA plus AES key wrap method (as of 2026).
- **Protocols and formats.** JSON Web Encryption (`A256KW`), CMS and S/MIME, and KMIP key transfer all use AES key wrap.

> **At Meridian.** Meridian's application teams use envelope encryption. Each service gets DEKs from the cloud KMS or, on-premises, from the enterprise key manager, wrapped under a KEK that never leaves the HSM. When the PKI and Cryptography Services team imported an HSM-generated root key into one cloud KMS for a BYOK project, the transfer used the cloud's documented RSA plus AES-KWP method, with two custodians present and the ceremony recorded. Payment keys are different: Payments Security moves them as TR-31 key blocks between payment HSMs, a payments-specific format covered in Chapter 37.

## 6.9 Format-preserving encryption

Some data has to keep its shape. A legacy core-banking table may define the card number column as 16 decimal digits, or a test environment may need realistic-looking account numbers. Ordinary encryption turns 16 digits into 32 or more bytes of binary, which breaks all of these. **Format-preserving encryption (FPE)** produces ciphertext in the same format as the plaintext: 16 digits in, 16 digits out.

FPE works by building a **Feistel network**, a structure that splits the input into two halves and alternately modifies one half using a function of the other, using AES as the round function and arithmetic in the input's own alphabet (base 10 for digits, base 36 for alphanumerics). Like XTS, it accepts a **tweak**: extra public input, such as the first and last digits of a card number, that makes the encryption different for each context.

NIST SP 800-38G (2016) approved two methods, **FF1** and **FF3**. In 2017, Durak and Vaudenay published a practical attack on FF3 over small domains. NIST's 2019 draft revision proposed a repaired **FF3-1** with a shorter tweak and required the domain to contain at least one million possible values. Further cryptanalysis of FF3-1 followed, and in February 2025 NIST's second public draft of SP 800-38G Revision 1 removed FF3 altogether, leaving FF1 as the only specified method. As of 2026 that revision is still a draft, but the direction is clear: use FF1, treat FF3 and FF3-1 as withdrawn for new designs, and plan to migrate any existing FF3 deployments.

Small domains are FPE's main weakness. If you encrypt only the middle six digits of a card number, keeping the first six and last four in the clear, the domain is exactly one million values, the bare minimum, and an attacker with enough plaintext and ciphertext pairs gains real leverage. Use the visible digits as the tweak, keep domains as large as the format allows, and rate-limit any service that encrypts on request.

FPE products include OpenText Voltage SecureData, Thales CipherTrust tokenisation and Google Cloud Sensitive Data Protection, all of which document FF1-based options (as of 2026). Chapter 27 compares FPE with tokenisation, which replaces data with random surrogates and keeps the mapping in a vault.

> **Compliance hook.** FPE-encrypted card numbers are still encrypted account data under PCI DSS v4.0.1, so the systems holding them and the keys stay in scope (Requirement 3.5.1 and the key management controls in 3.6 and 3.7). Tokenisation designs can reduce scope in ways FPE usually cannot. ISO/IEC 27001 control A.8.24 and NIST SP 800-53 SC-13 both expect you to document which modes are approved, which is where an "FF1 only" rule belongs.

## 6.10 Choosing a mode

| Situation | Use | Avoid |
| --- | --- | --- |
| General application data | AES-256-GCM, or XChaCha20-Poly1305 via a high-level library | Hand-built CBC plus HMAC |
| High volume per key, or nonce risk | AES-GCM-SIV, or per-object keys | Random-nonce GCM beyond 2^32 messages |
| Encrypting keys with keys | AES-KW or AES-KWP | GCM with fixed nonces, ECB |
| Disks and volumes | AES-XTS, plus AEAD above it if snapshots are exposed | GCM, CBC |
| Data that must keep its format | FF1 with a tweak and a large domain | FF3, FF3-1, home-made schemes |
| Legacy interoperability | CBC with Encrypt-then-MAC, only if forced | ECB, CBC without a MAC |

## 6.11 Lab: nonces, tampering and key wrap

This Python lab uses the `cryptography` package (`pip install cryptography`).

**1. Break CTR mode with a reused nonce.**

```python
from cryptography.hazmat.primitives.ciphers import (
    Cipher, algorithms, modes)
import os
key, nonce = os.urandom(32), os.urandom(16)
def ctr(msg):
    e = Cipher(algorithms.AES(key), modes.CTR(nonce)).encryptor()
    return e.update(msg) + e.finalize()
p1 = b"Transfer 100 USD to account 1234"
p2 = b"Meeting moved to Thursday at 3pm"
c1, c2 = ctr(p1), ctr(p2)        # same key, same nonce: the mistake
x = bytes(a ^ b for a, b in zip(c1, c2))
print(bytes(a ^ b for a, b in zip(x, p1)))  # recovers p2
```

The attacker never touched the key. Knowing one plaintext reveals the other.

**2. Tamper with an unauthenticated message.**

```python
c = bytearray(ctr(p1))
c[9] ^= ord("1") ^ ord("9")      # turn "1" into "9"
d = Cipher(algorithms.AES(key), modes.CTR(nonce)).decryptor()
print(d.update(bytes(c)))         # b"Transfer 900 USD ..."
```

**3. See AEAD refuse the same trick.**

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
g, n = AESGCM(key), os.urandom(12)
c = bytearray(g.encrypt(n, p1, b"record-42"))
c[9] ^= ord("1") ^ ord("9")
g.decrypt(n, bytes(c), b"record-42")  # raises InvalidTag
```

**4. Wrap and unwrap a key.**

```python
from cryptography.hazmat.primitives import keywrap
kek, dek = os.urandom(32), os.urandom(32)
w = keywrap.aes_key_wrap(kek, dek)
print(len(dek), len(w))                      # 32 40
print(keywrap.aes_key_wrap(kek, dek) == w)   # True: deterministic
bad = bytearray(w); bad[5] ^= 1
try:
    keywrap.aes_key_unwrap(kek, bytes(bad))
except keywrap.InvalidUnwrap:
    print("unwrap refused: integrity check failed")
w2 = keywrap.aes_key_wrap_with_padding(kek, b"20-byte HMAC secret!")
print(keywrap.aes_key_unwrap_with_padding(kek, w2))   # RFC 5649
```

**5. Optional: XTS on Linux.** Run `cryptsetup benchmark -c aes-xts-plain64 -s 512` to see XTS-AES-256 throughput (note the 512-bit key size).

## 6.12 Failure story: Zerologon and the all-zero IV

In August 2020, Microsoft patched a vulnerability in the Netlogon protocol that Windows domain controllers use to authenticate machines. Researchers named it **Zerologon**, and it allowed an attacker on the internal network to take over a domain controller, and with it the entire Windows domain, in seconds.

The root cause was a mode of operation. Netlogon computed a login credential using AES in CFB8 mode with a **fixed IV of all zeros**. With an all-zero IV, there is a 1-in-256 chance, for any key, that encrypting an all-zero input produces an all-zero output. An attacker could send an all-zero credential repeatedly; on average, after 256 attempts, it was accepted. From there, the attacker could reset the domain controller's own machine password.

AES was never weakened. The designers broke the one rule of the mode: the IV must be unpredictable. The flaw went unnoticed for years in one of the most widely deployed authentication systems in the world, was rated at the maximum severity score, and was exploited by ransomware groups after disclosure. Cryptographic flaws in identity infrastructure are domain-wide incidents.

## 6.13 Chapter summary

- Modes turn a block cipher into practical encryption by mixing in changing values. IVs and nonces carry most of the risk.
- CBC needs unpredictable IVs and padding; CTR needs unique nonces. Neither provides integrity, and padding oracles show what that costs.
- AEAD combines encryption and integrity. AES-GCM and ChaCha20-Poly1305 are the standard choices; associated data binds ciphertext to its context.
- GCM fails catastrophically on nonce reuse. Use counters, cap messages per key, use per-object keys, or use AES-GCM-SIV.
- XTS protects disks against theft but offers no integrity and leaks change patterns across snapshots.
- AES key wrap (RFC 3394) and its padded form (RFC 5649) protect keys under keys, and underpin HSM backups and cloud BYOK.
- FF1 is the only format-preserving method NIST's current draft keeps. Treat FF3 and FF3-1 as withdrawn and keep domains large.
