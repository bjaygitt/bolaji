## 25.1 Why these channels matter

A database administrator restarting a cluster, a partner sending a payment file and a fraud analyst messaging a colleague are all moving sensitive data without a browser. They use **SSH**, **email** and **messaging apps**.

Each channel's original trust model breaks down at scale. SSH trusts whatever key a server presents the first time you connect. Email between servers was sent in plaintext, with no proof of who sent it. Messaging services encrypted only to their own servers. This chapter follows the same repair in all three: replace "trust whatever you saw" with keys vouched for by something the organisation controls and can audit.

## 25.2 How SSH works

**SSH** (Secure Shell) gives administrators encrypted remote access to servers and carries file transfer (SFTP, SCP), Git operations and a great deal of automation. Like TLS (Chapter 20), SSH negotiates algorithms, runs an ephemeral key exchange, and derives session keys. The server then signs the exchange with its **host key**, the client checks that it trusts that key, and finally the user authenticates inside the encrypted channel, usually with a key pair.

### Host keys and trust on first use

The host key check is where SSH differs from TLS: there is no certificate authority by default. The first time you connect, your client shows the host key's fingerprint and asks whether to trust it. If you accept, the key is stored in `~/.ssh/known_hosts`, and future connections warn loudly if it changes. This model is called **trust on first use (TOFU)**.

TOFU is weak in practice. Almost nobody verifies the fingerprint, and where servers are rebuilt constantly, engineers learn to delete the old entry whenever they see "host key has changed", which is exactly the warning that should stop a man-in-the-middle.

### User keys and their sprawl

Users usually authenticate with a key pair: the public key goes in `~/.ssh/authorized_keys` on each server, and the client signs a challenge with the private key. Ed25519 is the recommended key type.

At organisational scale static keys become a liability. They are copied to many servers and rarely removed when people leave, private keys sit unencrypted on laptops and build servers, and nobody can answer "who can log in to this server?", because the answer is spread across thousands of `authorized_keys` files.

### Protocol hygiene

SSH negotiates algorithms, so old ones linger. OpenSSH 8.8 disabled RSA signatures using SHA-1 (`ssh-rsa`) by default in 2021, and DSA keys have since been removed altogether. In late 2023, researchers disclosed the **Terrapin attack**, which manipulated sequence numbers to silently delete messages at the start of the encrypted channel under ChaCha20-Poly1305 and some encrypt-then-MAC modes. Vendors responded with a "strict key exchange" countermeasure that both ends must support. Keep an approved-algorithm list for SSH, scan for it, and patch both ends, because embedded SSH implementations in network devices often lag years behind OpenSSH.

> **Current development.** OpenSSH 9.0 (April 2022) made the hybrid sntrup761x25519-sha512 key exchange the default, and version 10.0 in April 2025 made **mlkem768x25519-sha256** the default. OpenSSH 10.1 added a client warning, controlled by the `WarnWeakCrypto` option, when a connection does not use a post-quantum key exchange. Up-to-date SSH sessions are therefore protected against harvest-now-decrypt-later. Host and user signature keys remain classical; migrating them is a later, separate step (Chapter 46).

## 25.3 SSH certificates at scale

OpenSSH has its own simple **certificate** format, which is not X.509. An SSH certificate is a public key plus a small set of fields, signed by an **SSH certificate authority** key:

- a **key ID**, a free-text identifier that appears in server logs
- **principals**: the usernames or host names the certificate is valid for
- a **validity period** and a serial number
- **critical options** such as `force-command` and `source-address`, and **extensions** such as `permit-pty`

### User certificates

On each server, one line in `sshd_config` replaces every `authorized_keys` entry:

```text
TrustedUserCAKeys /etc/ssh/user_ca.pub
AuthorizedPrincipalsFile /etc/ssh/principals/%u
```

The first line accepts any user certificate signed by this CA. The second maps local accounts to allowed principals: the `postgres` account might accept `dba-prod` and `breakglass`, so access is granted by group, not person. A user who signs in to the identity provider with phishing-resistant MFA (Chapter 16) receives a certificate valid for a working day or less. When they leave, it expires within hours and there are no keys to hunt down: **short lifetimes replace revocation.**

### Host certificates

The CA also signs host keys. Clients then trust the host CA with one line in `known_hosts`:

```text
@cert-authority *.meridian.example ssh-ed25519 AAAAC3Nza...
```

TOFU prompts disappear, a rebuilt server presents a new certificate without any warning, and a genuine "host key changed" warning becomes rare enough to be taken seriously. Host certificates usually live for weeks to a year and are issued at build time by the provisioning pipeline.

### Revocation

When waiting for expiry is not enough, OpenSSH supports **key revocation lists (KRLs)**: compact files listing revoked keys, serials or key IDs, referenced by `RevokedKeys` in `sshd_config`. KRLs must reach every server, so they are a backstop; short lifetimes do most of the work.

### Designing the SSH CA

The CA private key can log in to every server, so it is among the most sensitive keys an organisation holds. Design rules:

- **Separate CAs** for users and hosts, and for production and non-production.
- **Keep CA keys in an HSM or a cloud KMS** (Chapter 33), and issue through a service, never from a laptop.
- **Tie issuance to identity and context**: the identity provider decides who you are; the issuer decides which principals you get, for how long, and whether approval (such as a change ticket) is needed.
- **Plan CA rotation**: servers can trust two CA keys at once, so publish the new key, then switch issuance, then retire the old one.
- **Log every issuance** and send it to the SOC with the servers' login logs.

### How the products do it

Several approaches exist side by side, as of 2026:

| Approach | Examples | How certificates are issued |
| --- | --- | --- |
| Secrets manager engine | HashiCorp Vault and OpenBao SSH secrets engine | Clients call an API with a Vault token; roles define allowed principals and TTLs |
| Dedicated access platforms | Smallstep, Teleport | SSO login on the client issues a short-lived certificate; often adds session recording and approval workflows |
| Cloud-native access | AWS EC2 Instance Connect, Google Cloud OS Login, Microsoft Entra ID login for Linux VMs | The cloud IAM system authorises access and pushes a short-lived key or certificate, or maps cloud identities to accounts |
| PAM platforms | CyberArk, BeyondTrust, Delinea | A privileged-access proxy brokers the session, holds or issues credentials, and records the session |

The approaches are often combined, all fed by one identity provider. The risk is ending up with three unconnected answers to "who can log in where".

> **At Meridian.** The PKI and Cryptography Services team runs separate host and user SSH CAs for Meridian's 9,000 servers, with keys in its general-purpose HSM cluster. IAM owns the mapping from identity-provider groups to principals. Engineers receive 8-hour certificates after SSO with a security key; root on production needs a change ticket and yields a 1-hour certificate. Platform Engineering's build pipeline requests a host certificate for every new server. The remaining static keys, mostly for partner file transfer, sit in the PAM vault with named owners and rotation dates.

### STARTTLS and its weakness

SMTP began in plaintext. **STARTTLS** lets a client upgrade an existing plaintext SMTP connection to TLS: the server advertises the `STARTTLS` capability, the client sends the command, and the two run a TLS handshake. Between servers this is **opportunistic**: if the receiving server does not offer STARTTLS, or the certificate does not validate, the sender delivers in plaintext anyway, because refusing would lose mail.

Opportunistic encryption defeats passive eavesdroppers but not active attackers. An attacker on the path can delete the `STARTTLS` line from the server's capabilities (a **stripping** attack), or present any certificate at all, since senders historically did not check. Measurements published in 2015 found STARTTLS being stripped on real traffic in several countries. Two standards let a receiving domain declare in advance that TLS with a valid certificate is required.

### MTA-STS

**SMTP MTA Strict Transport Security (MTA-STS)** borrows the idea of HSTS from the web. The receiving domain publishes:

- a DNS TXT record at `_mta-sts.example.com` containing a policy ID, which changes whenever the policy changes
- a policy file at `https://mta-sts.example.com/.well-known/mta-sts.txt`, served over HTTPS with a publicly trusted certificate

```text
version: STSv1
mode: enforce
mx: mx1.example.com
mx: *.mail.example.com
max_age: 1209600
```

A sending server that supports MTA-STS fetches and caches the policy. In `enforce` mode it delivers only to the listed MX hosts, only over TLS, and only if the certificate is valid for the MX name under the Web PKI; in `testing` mode it delivers anyway but reports failures. The `max_age` (here 14 days) keeps the policy cached even if an attacker later blocks the lookup. The weakness is first contact: a sender with no cached policy can still be fooled by an attacker who controls its DNS and HTTPS path.

Its companion, **SMTP TLS Reporting (TLS-RPT)**, is a TXT record at `_smtp._tls.example.com` naming an address for daily JSON reports of TLS failures. Deploy TLS-RPT first, run MTA-STS in `testing` until the reports are clean, then `enforce`.

### DANE for SMTP

**DANE** (DNS-Based Authentication of Named Entities) takes a different route. The receiving domain publishes a **TLSA record** for each MX host, for example at `_25._tcp.mx1.example.com`, saying which certificate or public key the server will present. A typical record is `3 1 1 <SHA-256 hash>`: usage 3 (match the server's own key, ignoring CAs), selector 1 (the public key rather than the whole certificate), matching type 1 (SHA-256).

DANE needs unforgeable TLSA records, so the zone must be signed with **DNSSEC** (Chapter 23) and the sender must validate it. In exchange there is no first-contact gap and no dependence on any public CA. The cost is that every key change needs the new hash published alongside the old one before rotation, and a mismatch makes mail queue rather than deliver.

| | Opportunistic STARTTLS | MTA-STS | DANE |
| --- | --- | --- | --- |
| Trust anchor | None | Web PKI and HTTPS | DNSSEC |
| Defeats passive eavesdropping | Yes | Yes | Yes |
| Defeats active downgrade | No | Yes, after first fetch | Yes |
| Prerequisites | TLS on the MX | Policy web host, public certificate | Signed zone, validating resolver at sender |
| Failure mode | Silent plaintext | Mail held if policy not met | Mail held if TLSA does not match |

Many domains publish both. As of 2026, large mailbox providers honour MTA-STS, Postfix and other open-source MTAs have long supported DANE, and Microsoft Exchange Online supports DANE with DNSSEC; check each provider's documentation for current coverage.

> **Watch out.** MTA-STS and DANE protect mail *to* your domain. Much mail *from* your domain is sent by marketing, ticketing and payroll platforms whose TLS behaviour you do not control; it belongs in third-party risk reviews.

## 25.5 Proving who sent it: SPF, DKIM and DMARC

SMTP lets any sender write any `From:` address. Three mechanisms, layered over the years, let a receiver check whether mail claiming to come from a domain really did.

### SPF: an authorised sender list

**Sender Policy Framework (SPF)** is not cryptography at all. The domain publishes a TXT record listing the IP addresses and services allowed to send mail for it:

```text
v=spf1 ip4:192.0.2.0/24 include:_spf.mailprovider.example -all
```

The receiver checks the connecting IP address against the list for the envelope sender domain (the "return path"), not the visible `From:` header. SPF breaks when mail is forwarded and allows only ten DNS lookups per evaluation, which large organisations exceed easily.

### DKIM: signatures on the message

**DomainKeys Identified Mail (DKIM)** is the cryptographic piece. The sending server hashes the message body and a chosen set of headers (always including `From:`), signs the result, and adds a `DKIM-Signature` header:

```text
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed;
  d=meridian.example; s=sel2026a; h=from:to:subject:date;
  bh=2jUSOH9NhtVGCQWNr9BrIAPreKQjO6Sn7XIkfJVOzv8=;
  b=dzdVyOfAKCdLXdJOc9G2q8LoXSlEniSb...
```

The `d=` tag names the signing domain and `s=` the **selector**. The receiver fetches the public key from DNS at `sel2026a._domainkey.meridian.example`, recomputes the body hash (`bh=`), and verifies the signature (`b=`). The `c=` tag sets **canonicalisation**, the rules for normalising whitespace and header case so that harmless changes in transit do not break the signature.

Cryptographic points that matter in operations:

- **Key size and algorithm.** RFC 8301 forbids SHA-1 and requires RSA keys of at least 1024 bits, recommending 2048. Ed25519 for DKIM is standardised, but since many receivers cannot verify it, senders sign with both Ed25519 and RSA.
- **Selectors make rotation possible.** Publish a new selector, switch signing, and keep the old key in DNS for a few days. Give every third-party sender its own selector so you can revoke one alone.
- **DKIM signs content, not delivery.** A signed message can be replayed to millions of recipients and still verify; short expiry (`x=`) limits this.
- **DKIM gives authenticity, not confidentiality.** Nothing is encrypted.

### DMARC: tying it to the visible From

**Domain-based Message Authentication, Reporting and Conformance (DMARC)** connects these checks to the address a human actually sees. A message passes DMARC if SPF or DKIM passes **and** the domain that passed is **aligned** with the `From:` domain. The domain publishes its policy at `_dmarc.meridian.example`:

```text
v=DMARC1; p=reject; rua=mailto:dmarc@meridian.example; adkim=s
```

The policy `p=` tells receivers what to do with failures: `none` (monitor only), `quarantine` or `reject`. The `rua=` address receives aggregate reports listing every source sending as your domain, which is how organisations find forgotten senders before tightening the policy. **ARC** (Authenticated Received Chain) lets intermediaries such as mailing lists record the results they saw before modifying a message.

> **Current development.** Since February 2024, Google and Yahoo have required bulk senders (Google's threshold is about 5,000 messages a day) to use SPF, DKIM and a DMARC policy, and Microsoft announced similar requirements for its consumer mail in 2025. DMARC is now a condition of reaching customers' inboxes.

> **Watch out.** DKIM keys are long-lived private keys that often sit in software on mail gateways and in dozens of SaaS platforms. Inventory them like certificates: selector, owner, platform, key size, creation date. In 2012 a researcher found that Google and other large companies were signing with DKIM keys as short as 512 bits, which he could factor cheaply, allowing forged mail that passed DKIM.

## 25.6 S/MIME: end-to-end email

Everything in sections 25.4 and 25.5 protects mail between servers. The message sits in plaintext on every server along the way. **S/MIME** (Secure/Multipurpose Internet Mail Extensions) protects the message itself, from the sender's mail client to the recipient's, using X.509 certificates (Chapter 12) and the Cryptographic Message Syntax:

- **Signing**: the sender signs with their private key, and the recipient verifies against the sender's certificate, which travels with the message. This gives authenticity and integrity that survive forwarding and storage.
- **Encryption**: the sender generates a content-encryption key, encrypts the message with it (AES-GCM in S/MIME 4.0), and wraps the key for each recipient's public key, plus the sender's own so they can read their sent items.

Encryption is the hard part. You need the recipient's certificate before you send, which across organisations means exchanging signed messages first. Encrypted mail also blinds malware scanning, data loss prevention and e-discovery, so enterprises **escrow** encryption keys (never signing keys) or decrypt at a gateway.

Publicly trusted S/MIME certificates have been governed since September 2023 by the CA/Browser Forum's S/MIME Baseline Requirements. Enterprises usually issue staff certificates from their own PKI and buy public ones only where outsiders must validate signatures. **OpenPGP** offers similar features with a web-of-trust model, common in file transfer. Gateway **email encryption services** (from Microsoft Purview, Proofpoint and others) send recipients without keys a link to an encrypted portal; Chapter 29 covers them.

## 25.7 Signal-style secure messaging

In TLS and in server-to-server email, the service can read your data. **End-to-end encryption (E2EE)** means that only the communicating users can read messages and the relaying service cannot. The **Signal protocol**, designed by Moxie Marlinspike and Trevor Perrin, underlies E2EE in Signal, WhatsApp, Google Messages and others.

Messaging adds two problems: the recipient may be offline when a conversation starts, and conversations last for years on phones that may be compromised.

### Starting a conversation offline: X3DH and PQXDH

Each user uploads a bundle of public keys to the server: a long-term **identity key**, a signed medium-term **prekey**, and a batch of **one-time prekeys**. Alice downloads Bob's bundle and combines several Diffie-Hellman exchanges between her keys and his into one shared secret, without Bob being online. This is **X3DH** (Extended Triple Diffie-Hellman).

In 2023, Signal upgraded this to **PQXDH**, which adds a post-quantum KEM encapsulation (CRYSTALS-Kyber, since standardised as ML-KEM) to the exchange. The resulting secret is safe if either the elliptic-curve or the lattice part holds, so a recording of today's conversation start cannot be decrypted by a future quantum computer.

### Healing after compromise: the Double Ratchet

Once a conversation begins, the **Double Ratchet** derives a new key for every message:

- A **symmetric ratchet** runs the chain key through a KDF to produce each message key and the next chain key, deleting the old ones, so stealing today's key does not reveal yesterday's messages (**forward secrecy**).
- A **Diffie-Hellman ratchet** mixes a fresh DH exchange in whenever the conversation changes direction, so an attacker who steals a device's state is locked out again by the next exchange (**post-compromise security**, or self-healing).

> **Current development.** PQXDH protects only the start of a conversation. In October 2025, Signal announced a "triple ratchet" that runs a post-quantum ratchet called SPQR (Sparse Post-Quantum Ratchet) alongside the Double Ratchet, so that ongoing conversations also gain quantum resistance and post-compromise security. Apple's iMessage moved to a comparable design, PQ3, in 2024, which also re-keys with a post-quantum KEM during the conversation.

### Groups: MLS

Pairwise encryption is expensive for groups: a message to 1,000 members needs 1,000 encryptions. **Messaging Layer Security (MLS)**, standardised as RFC 9420 in 2023, arranges members in a tree of keys (**TreeKEM**) so that membership changes cost work proportional to the logarithm of the group size, with forward secrecy and post-compromise security intact. Its cipher suites allow post-quantum options to be added later. The GSMA's RCS Universal Profile 3.0, published in March 2025, adopted MLS for interoperable end-to-end encryption in carrier messaging.

### Trusting the keys: safety numbers and key transparency

The server distributes the public keys, so a malicious or compelled server could hand Alice its own key instead of Bob's. Users can compare **safety numbers** (fingerprints of both identity keys), but few do. **Key transparency** automates the check: the service publishes every user's key in an append-only, auditable log, and clients verify against it, much as Certificate Transparency works for the Web PKI (Chapter 13). WhatsApp announced key transparency in 2023, and Apple offers Contact Key Verification for iMessage.

E2EE still does not hide **metadata** (who talks to whom, and when), and offers nothing once a device is compromised.

## 25.8 Messaging in a regulated enterprise

Banks must retain, supervise and produce business communications. From 2022 onwards, US regulators fined many large financial firms for staff using personal messaging apps for business, the "off-channel communications" cases. The answer is to choose deliberately where plaintext exists. **Enterprise collaboration platforms** (Microsoft Teams, Slack, Zoom, Webex, Google Chat) encrypt in transit and at rest while letting the tenant retain and search content, and several offer customer-managed keys (Chapter 28). **Archiving tools** capture messages from managed apps on corporate devices. **Managed E2EE apps** built on Signal or MLS let the organisation hold archive copies for its own staff. Document, per channel, who can read content, where retention happens, and which keys an investigation would need.

> **At Meridian.** Internal chat lives on Meridian's collaboration platform under customer-managed keys; personal messaging apps are banned for business. Secure messages in the mobile banking app are encrypted in transit and at rest with keys in Meridian's KMS, not end-to-end, because complaints and fraud teams must read them. Inbound email uses MTA-STS in `enforce` mode and DANE; DMARC is at `p=reject`, with a separate DKIM selector for each SaaS platform that sends as Meridian, tracked in the same inventory as certificates.

> **Compliance hook.** PCI DSS v4.0.1 Requirement 4.2.1 requires strong cryptography for cardholder data over open, public networks, including email and messaging if they carry PAN, and Requirement 8 covers authentication for SSH access to systems in scope. NIST IR 7966 covers SSH access management, NIST SP 800-177 Rev. 1 covers trustworthy email, and ISO/IEC 27001:2022 control A.8.24 requires managed use of cryptography.

## 25.9 Lab: an SSH certificate authority and an email security check

You need OpenSSH (for `ssh-keygen`), Docker for a test server, and `dig` and `curl` for the email checks.

1. Create separate user and host CAs, a user key, and a user certificate valid for 8 hours for the principal `alice`:

    ```bash
    ssh-keygen -t ed25519 -f user_ca -C "lab user CA" -N ""
    ssh-keygen -t ed25519 -f host_ca -C "lab host CA" -N ""
    ssh-keygen -t ed25519 -f alice -N ""
    ssh-keygen -s user_ca -I alice@lab -n alice -V +8h \
      -z 1001 alice.pub
    ssh-keygen -L -f alice-cert.pub
    ```

2. Start a test server in a container and install OpenSSH inside it:

    ```bash
    docker run -d --name sshlab -p 2222:22 ubuntu:24.04 sleep infinity
    docker exec sshlab bash -c \
      "apt-get update -qq && apt-get install -y -qq openssh-server"
    docker exec sshlab useradd -m alice
    ```

3. Sign the container's host key with the host CA, and configure the server to trust the user CA:

    ```bash
    docker cp sshlab:/etc/ssh/ssh_host_ed25519_key.pub .
    ssh-keygen -s host_ca -I sshlab -h -n localhost -V +52w \
      ssh_host_ed25519_key.pub
    docker cp ssh_host_ed25519_key-cert.pub sshlab:/etc/ssh/
    docker cp user_ca.pub sshlab:/etc/ssh/
    docker exec sshlab bash -c 'cat >> /etc/ssh/sshd_config <<EOF
    HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
    TrustedUserCAKeys /etc/ssh/user_ca.pub
    EOF'
    docker exec sshlab bash -c "mkdir -p /run/sshd && /usr/sbin/sshd"
    ```

4. Trust the host CA on the client and log in. There should be no TOFU prompt and no `authorized_keys` file:

    ```bash
    echo "@cert-authority [localhost]:2222 $(cat host_ca.pub)" \
      > lab_known_hosts
    ssh -p 2222 -i alice -o UserKnownHostsFile=lab_known_hosts \
      alice@localhost 'echo logged in as $(whoami)'
    ```

5. Issue a certificate valid for one minute with `-V +1m`, log in, wait two minutes, and try again. Then revoke the 8-hour certificate by serial with a KRL and confirm it is refused:

    ```bash
    echo "serial: 1001" > krl.txt
    ssh-keygen -k -f revoked.krl -s user_ca.pub krl.txt
    ssh-keygen -Q -f revoked.krl alice-cert.pub
    ```

    Copy `revoked.krl` into the container, add `RevokedKeys /etc/ssh/revoked.krl` to `sshd_config`, restart `sshd`, and retry the login.

6. Check which key exchange was negotiated. With OpenSSH 10 at both ends you should see `mlkem768x25519-sha256`. Ubuntu 24.04 ships an OpenSSH 9 release, so against this container expect the older hybrid `sntrup761x25519-sha512`, which is still post-quantum:

    ```bash
    ssh -v -p 2222 -i alice -o UserKnownHostsFile=lab_known_hosts \
      alice@localhost true 2>&1 | grep "kex: algorithm"
    ```

7. Inspect a large mail domain's email security records. Try `gmail.com`, then your own organisation's domain:

    ```bash
    D=gmail.com
    dig +short MX $D
    dig +short TXT _mta-sts.$D
    curl -s https://mta-sts.$D/.well-known/mta-sts.txt
    dig +short TXT _smtp._tls.$D
    dig +short TXT _dmarc.$D
    dig +short TXT $D | grep spf1
    ```

8. In the headers of an email from that domain, find the `DKIM-Signature` tags `d=` and `s=`, and fetch the key with `dig +short TXT <s>._domainkey.<d>`. For an MX host that uses DANE, run `dig +dnssec TLSA _25._tcp.<mx-host>` and look for the `ad` (validated) flag.

**Optional cloud extension.** Use a cloud-native access service (AWS EC2 Instance Connect, Google Cloud OS Login or Entra ID login for a Linux VM) to log in to a small VM without any static key, and find the corresponding entries in the cloud audit log. *Cost warning:* VMs and public IP addresses are charged by the hour; delete them when you finish.

## 25.10 Failure story: the SSH keys nobody owned

From around 2013, Tatu Ylönen, the inventor of SSH, and other researchers published findings from SSH key audits at large banks, governments and enterprises, and the work fed into NIST IR 7966. The pattern was consistent. Organisations held hundreds of thousands to millions of SSH keys, most of them unused or of unknown purpose, and a significant share granted privileged access, including keys belonging to people who had left years before. Nobody had designed this sprawl. It accumulated one convenient copy at a time, and no system of record could say which key opened which door.

Attackers exploit exactly this. Intrusion groups routinely harvest private keys from compromised machines and read `known_hosts` and `authorized_keys` files as maps for lateral movement. A stolen SSH key bypasses MFA and is rarely rotated. SSH's value as a target was shown again in March 2024, when an engineer investigating slow SSH logins discovered a backdoor in the xz compression library, which some Linux distributions linked into the OpenSSH server; it was caught shortly before reaching stable releases.

The lessons: treat every SSH key as a credential with an owner, a purpose and an expiry, in the same inventory as certificates (Chapter 43); replace static keys with short-lived certificates issued after strong authentication; put the remaining static keys behind a PAM platform; and watch the SSH supply chain.

## 25.11 Chapter summary

- SSH's defaults, trust on first use and static user keys, fail in large, fast-changing fleets.
- SSH certificates with separate host and user CAs, group-based principals and lifetimes of hours replace `authorized_keys` and TOFU; KRLs are only a backstop.
- Keep SSH CA keys in an HSM or KMS, tie issuance to the identity provider, and log every issuance.
- OpenSSH defaults to hybrid ML-KEM key exchange; keep embedded SSH implementations patched.
- Opportunistic STARTTLS stops only passive eavesdroppers; MTA-STS (Web PKI) and DANE (DNSSEC) let a domain require authenticated TLS, with TLS-RPT for visibility.
- SPF lists sending IPs, DKIM signs messages with keys under DNS selectors, and DMARC demands alignment with the visible From address.
- S/MIME gives end-to-end email signing and encryption, at the cost of key distribution and conflicts with scanning and retention.
- Signal combines PQXDH with the Double Ratchet, now plus a post-quantum ratchet; MLS scales the same properties to groups, and key transparency closes the server man-in-the-middle gap.
