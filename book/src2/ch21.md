## 21.1 "We use TLS" is the start of the question

Chapter 20 explained how one TLS 1.3 connection works. In a real enterprise there is rarely only one. A customer opening a banking app might be served through five separate TLS connections before the request reaches a database, and each connection ends somewhere. The place where a TLS connection ends, decrypting the traffic, is its **termination point**. Every termination point holds a private key, has a cipher configuration, sees the traffic in clear text, and belongs to some team.

So the most useful question about any service is: "Where does TLS terminate, and what protects the next hop?" The answer decides who can read customer data, where keys live and what an auditor needs to see.

Most real TLS failures are deployment failures: an expired certificate on a forgotten load balancer, a backend connection that skips verification, a legacy cipher left on for one old client. This chapter works through them in the order a request meets them.

The layers, from the outside in:

- **CDN.** A **content delivery network** (Akamai, Cloudflare, Fastly, Amazon CloudFront and others) terminates the customer's TLS connection at an edge server close to the user, caches content, and opens a new connection back to the **origin** (your servers). The public certificate's private key therefore lives with the provider (Chapter 23 covers edge key custody).
- **WAF.** A **web application firewall** inspects HTTP requests for attacks such as SQL injection. It must see clear text, so it either runs inside the CDN (Akamai App and API Protector, Cloudflare WAF, AWS WAF on CloudFront) or as its own termination point (F5 Advanced WAF, Imperva, or a WAF module on a load balancer).
- **Load balancer or ADC.** An **application delivery controller (ADC)** such as F5 BIG-IP, Citrix NetScaler, HAProxy or NGINX, or a cloud load balancer (AWS ALB and NLB, Azure Application Gateway and Front Door, Google Cloud load balancers), spreads traffic across servers.
- **Ingress.** In Kubernetes, an **ingress controller** or **Gateway API** implementation (for example Envoy Gateway, Istio, Contour, Traefik, or a vendor ingress) routes traffic into the cluster, terminating TLS with a certificate usually issued by cert-manager (Chapter 18).
- **Sidecar or mesh proxy.** In a **service mesh** such as Istio or Linkerd, a proxy beside each workload terminates **mutual TLS** from other services using short-lived workload certificates (Chapter 24).
- **Application.** Some applications terminate TLS themselves (a Java service with its own keystore, a database, a message broker). Behind a sidecar, the application often speaks plain HTTP over the pod's local interface.

| Termination point | Typical owner | Where the key lives | What goes wrong |
| --- | --- | --- | --- |
| CDN and WAF | Network or edge team | With the provider, or a customer HSM through keyless TLS | Origin connection left unencrypted or unverified |
| Load balancer or ADC | Network Engineering | ADC file system, FIPS module or network HSM | One HA node updated, the other forgotten |
| Ingress or gateway | Platform Engineering | Kubernetes secret, ideally encrypted at rest | Wildcard certificate shared by every team |
| Mesh sidecar | Platform Engineering | Memory of the proxy, issued by the mesh CA | Mesh CA root never rotated |
| Application | Application team | Keystore or file on the host | Unmanaged self-signed certificates |

> **At Meridian.** Meridian's customer website and mobile API cross all five hops. Network Engineering owns the CDN and WAF contract and the data-centre ADCs; Platform Engineering owns the ingress gateways and mesh on both its on-premises and cloud Kubernetes platforms; application teams own anything that terminates inside a container. The PKI and Cryptography Services team owns none of these devices but owns the TLS standard, the certificates on all of them, and a quarterly "termination map" for every customer-facing service that names each hop, its key location and its owner. Auditors for PCI DSS start with that map.

## 21.3 Offload, re-encryption and passthrough

At every intermediate device you choose what happens to TLS. There are three options.

**TLS offload** (also called termination or bridging to clear text) decrypts at the device and sends plain HTTP to the next hop. It was popular when TLS was expensive for servers; today it leaves everything behind the device in clear text on a shared network. Treat offload as an exception that needs a written justification, such as a sidecar talking to its own application over the pod's loopback interface.

**Re-encryption** (also called TLS bridging or end-to-end TLS) decrypts at the device, applies layer 7 logic such as routing, WAF rules or header insertion, then opens a new TLS connection to the backend. This is the normal enterprise pattern. It gives full visibility at the device and encryption on every wire. Its cost is that every hop needs a certificate, and the device must **verify** the backend's certificate. Many products allow re-encryption without verification, and some cloud load balancers accept any backend certificate by design, so check your provider's documentation. A connection that encrypts but does not verify is protected against passive eavesdroppers only: anyone who can redirect the traffic can present their own certificate.

**Passthrough** forwards the encrypted bytes untouched. The device routes on layer 4 information and on the **Server Name Indication (SNI)** in the ClientHello, which is still visible in TLS 1.3 unless Encrypted Client Hello is used (Chapter 20). The backend holds the only private key, and the device never sees clear text. The cost is losing everything that needs clear text: no WAF, no cookie-based persistence, no URL routing, no header insertion. Passthrough suits services where end-to-end key custody matters more than inspection, such as an HSM-backed payment endpoint, or mutual TLS where the backend must see the client's certificate itself.

| Mode | Device sees clear text | Keys on device | Backend verified | Typical use |
| --- | --- | --- | --- | --- |
| Offload | Yes | Front-end key | Not applicable | Sidecar to local app only |
| Re-encryption | Yes | Front-end key and a trust store | Must be configured | Default for web and APIs |
| Passthrough | No | None | Client does it | End-to-end key custody, client certificates |

Products name these choices differently. Kubernetes Gateway API listeners have a TLS mode of `Terminate` or `Passthrough`, and a separate BackendTLSPolicy describes how a gateway verifies the backend when re-encrypting. On AWS, an Application Load Balancer with an HTTPS listener and HTTPS target group re-encrypts, while a Network Load Balancer with a TCP listener passes through. F5 BIG-IP uses a **client SSL profile** for the front side and a **server SSL profile** for the backend, and leaving out the server profile means offload.

> **Watch out.** When a device re-encrypts, the client's certificate and the original TLS details do not travel to the backend. Devices pass them in HTTP headers instead, such as `X-Forwarded-Client-Cert` in Envoy. The backend must accept those headers only from the device, and the device must strip any copy the client sent, or an attacker can claim any identity by adding the header themselves.

## 21.4 A boring, modern configuration

A good TLS configuration is boring. It offers a small set of modern options, has no legacy fallbacks, and changes rarely. Most organisations should adopt a published profile rather than invent their own. The Mozilla Server Side TLS guidelines are the most widely used, with three levels:

| Profile | Protocols | Who it serves | When to use |
| --- | --- | --- | --- |
| **Modern** | TLS 1.3 only | Clients from roughly the last five years | New services, APIs, internal systems |
| **Intermediate** | TLS 1.2 and 1.3, AEAD ciphers with forward secrecy | Almost all clients | The default for public websites |
| **Old** | Down to TLS 1.0 | Very old clients | Only with a documented, time-limited exception |

For TLS 1.2 under the intermediate profile, every cipher suite should use **ephemeral key exchange** (ECDHE) for forward secrecy and an **AEAD** cipher (AES-GCM or ChaCha20-Poly1305). Remove RSA key transport, CBC suites, 3DES, RC4 and anything export, NULL or anonymous. TLS 1.3 suites need no tuning. Offer the hybrid post-quantum group `X25519MLKEM768` first where your software supports it, then `X25519` and `secp256r1`.

```text
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:
  ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:
  ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
ssl_ecdh_curve X25519MLKEM768:X25519:prime256v1:secp384r1;
ssl_session_tickets off;   # or rotate ticket keys at least daily
ssl_certificate     /etc/tls/fullchain.pem;   # leaf + intermediates
ssl_certificate_key /etc/tls/privkey.pem;
```

(In a real NGINX file the cipher list is one line.) Session tickets are disabled here because a ticket key that is never rotated undermines forward secrecy: whoever steals it can decrypt resumed sessions. On a load balancer fleet, ticket keys must also be shared across nodes, so rotation needs to be automated.

On the certificate side, configure the **full chain** (leaf plus intermediates): browsers often hide a missing intermediate, while mobile apps, Java clients and appliances fail. Make sure every hostname is in the Subject Alternative Name list (a wildcard covers one label only), automate renewal (Chapters 17 to 19), and serve an ECDSA certificate with an RSA fallback where old clients need it.

Almost every historical TLS attack exploited an option kept "for compatibility". The single best rule in TLS deployment is to **remove what you do not need**.

| Year | Attack | What it exploited | Rule it taught |
| --- | --- | --- | --- |
| 2009 | SSL stripping | First request over plain HTTP | Use HSTS and preloading |
| 2011 | BEAST | Predictable CBC IVs in TLS 1.0 | Retire TLS 1.0; prefer AEAD |
| 2012 | CRIME, later BREACH | Compression leaking secret lengths | Disable TLS compression |
| 2014 | Heartbleed | A memory-read bug in OpenSSL's heartbeat feature | Patch fast; rotate keys after memory disclosure |
| 2014 | POODLE | SSL 3.0 padding | Disable SSL 3.0 everywhere |
| 2015 | FREAK, Logjam | Downgrade to export-grade crypto | Remove legacy options entirely |
| 2016 | Sweet32 | 64-bit block ciphers (3DES) | Remove 3DES |
| 2017 | ROBOT | Bleichenbacher oracles in RSA key exchange | Remove RSA key transport |

## 21.5 Cipher policy as code

An enterprise has hundreds of TLS configurations: CDN settings, ADC profiles, cloud policies, ingress annotations, Java properties, database parameters. A standard in a PDF that each team copies by hand does not survive that. **Cipher policy as code** means expressing the standard once, in machine-readable form, then generating each platform's configuration from it and testing every endpoint against it automatically.

### Named policies on managed platforms

Cloud and CDN platforms do not let you type an OpenSSL cipher string. They offer named policies, so the standard becomes a list of approved names. As of 2026, for example:

- **AWS** Elastic Load Balancing offers predefined security policies such as `ELBSecurityPolicy-TLS13-1-2-2021-06` (TLS 1.3 and 1.2 with strong suites).
- **Azure** Application Gateway offers predefined policies such as `AppGwSslPolicy20220101`, or a custom policy that lists suites and a minimum version.
- **Google Cloud** load balancers use SSL policies with a profile (`COMPATIBLE`, `MODERN`, `RESTRICTED` or `CUSTOM`) and a minimum TLS version.
- **Cloudflare** and **Akamai** expose a minimum TLS version and cipher settings per zone or property.
- **F5 BIG-IP** uses cipher rules and cipher groups attached to SSL profiles; **NetScaler** uses cipher groups bound to virtual servers.

### Enforcing the policy

Policy as code works in three layers:

1. **Define.** Keep the standard in a version-controlled file: allowed protocol versions, cipher suites, groups, key types and the approved named policy for each platform.
2. **Prevent.** Check infrastructure code before it is applied. A policy engine such as Open Policy Agent (through Conftest), HashiCorp Sentinel or a cloud-native policy service rejects a Terraform plan that uses an unapproved policy.
3. **Detect.** Scan every endpoint continuously, because not everything is deployed through code. Scanners such as testssl.sh and sslyze in pipelines and on a schedule catch drift; Qualys SSL Labs gives an external view of public sites.

A small Conftest rule for AWS listeners looks like this:

```text
package main

approved := {"ELBSecurityPolicy-TLS13-1-2-2021-06"}

deny contains msg if {
  r := input.resource_changes[_]
  r.type == "aws_lb_listener"
  p := r.change.after.ssl_policy
  p != null
  not approved[p]
  msg := sprintf("%s uses TLS policy %s", [r.address, p])
}
```

The same pattern applies to Azure Policy definitions for Application Gateway, Kubernetes admission policies for ingress annotations, and configuration templates pushed to ADCs by the certificate platform (Chapter 18).

> **In practice.** Track one number: the share of endpoints that meet the standard, by owner. A dashboard that shows Network Engineering at 98 per cent and one application team at 60 per cent starts better conversations than any policy document.

## 21.6 Mutual TLS

In ordinary TLS only the server proves its identity. In **mutual TLS (mTLS)**, the client also presents a certificate and proves possession of its private key, using the client authentication messages described in Chapter 20. There is no shared secret to leak in a log or configuration file.

Enterprises use mTLS in four places:

- **Partner and open-banking APIs**, where regulations and the FAPI profile require certificate-bound clients (Chapter 39).
- **Service-to-service traffic** inside a mesh, where the mesh issues and rotates workload certificates automatically (Chapter 24).
- **CDN to origin**, so the origin accepts connections only from the CDN. Most CDNs can present a client certificate to your origin.
- **Devices and administrators**, such as VPN clients, Wi-Fi supplicants and privileged consoles (Chapters 16 and 22).

Every mTLS deployment has to answer three questions:

1. **Which CAs are trusted?** The server's client trust store should contain only the private CA, or the specific issuing CA, that issues these client certificates. Never trust the public root store for client authentication, or any public certificate would pass.
2. **How is the certificate mapped to an identity?** A rule must map its subject, SAN or SPIFFE ID to a specific client and its permissions.
3. **How is revocation handled?** Short-lived certificates (hours or days) avoid most revocation questions. Longer-lived client certificates need CRL or OCSP checking at the terminating device.

Products support this side by side. NGINX uses `ssl_verify_client` with a trusted CA file; F5 BIG-IP sets client certificate mode in the client SSL profile; AWS Application Load Balancer has an mTLS verify mode with a trust store; Cloudflare offers mTLS for API endpoints at its edge; Azure Application Gateway supports mutual authentication with uploaded trusted client CAs. A terminating device passes the verified identity to the backend in a header, with the precautions in section 21.3.

## 21.7 HTTPS beyond the handshake

TLS protects the connection, but web applications can still undo that protection. Four mechanisms matter.

**HTTP Strict Transport Security (HSTS).** A response header, `Strict-Transport-Security`, tells the browser to use only HTTPS for this site for a set period (`max-age`). It stops **SSL stripping**, where an attacker on the network intercepts the first plain-HTTP request and keeps the user on HTTP. With `includeSubDomains` and a long `max-age`, a site can apply to be **preloaded** into browsers, so even the first visit is protected. Roll it out in stages: start with a short `max-age` on the main site, add `includeSubDomains` only after you have confirmed that every subdomain, including forgotten internal ones that share the parent domain, supports HTTPS, then lengthen it and preload. Removal from the preload list takes months.

**Secure cookies.** Session cookies must carry the `Secure` flag, `HttpOnly` and an appropriate `SameSite` value. The `__Host-` name prefix enforces these properties.

**Mixed content.** An HTTPS page that loads scripts over plain HTTP gives an attacker a way to inject code. Browsers block active mixed content, and `Content-Security-Policy: upgrade-insecure-requests` helps migrate old pages.

**Certificate Authority Authorization (CAA).** A DNS record listing which CAs may issue certificates for your domain (Chapter 13).

In a multi-hop design, add these headers at one layer, usually the CDN, so that every origin gets the same policy.

## 21.8 TLS inspection

Everything so far concerned traffic coming **in** to the enterprise. **TLS inspection** (also called SSL decryption or break-and-inspect) concerns traffic going **out**: employees' browsers and corporate applications connecting to the internet. Most malware delivery and data exfiltration now travels over HTTPS, so a gateway that cannot see inside TLS sees very little.

### How forward-proxy inspection works

A **forward proxy** performs a deliberate, authorised man-in-the-middle:

1. The enterprise creates an **inspection CA** (often an intermediate under its private root) and installs the root in the trust store of every managed device, using MDM or group policy.
2. When an employee connects to `news.example`, the proxy intercepts the connection and opens its own TLS connection to the real site, validating the real certificate.
3. The proxy generates a certificate for `news.example` on the fly, signed by the inspection CA, and completes the employee's handshake with it. The browser trusts it because it trusts the inspection CA.
4. The proxy now sees clear text in the middle, applies malware scanning, DLP and URL policy, and relays traffic between the two connections.

**Inbound inspection** is different: a firewall or IPS in front of your own servers is given copies of their private keys so it can decrypt incoming traffic. With TLS 1.3 and forward secrecy, passive decryption with a copied key no longer works (Chapter 20), so inbound inspection must also terminate the connection.

### How the products do it

| Product | Model | Inspection CA options | Bypass and pinning handling |
| --- | --- | --- | --- |
| Palo Alto Networks NGFW and Prisma Access | On-premises or cloud firewall; "SSL Forward Proxy" outbound and "SSL Inbound Inspection" inbound | Enterprise-issued forward trust certificate; key can be stored in an HSM | Decryption policy rules by category, with a predefined exclusion list for applications that break |
| Zscaler Internet Access | Cloud proxy reached by agent or tunnel | Zscaler's intermediate CA, or a customer-supplied intermediate under the enterprise root | SSL inspection policy with "do not inspect" rules by category, application or destination |
| Netskope | Cloud security service steered by the Netskope client | Netskope-generated or customer-supplied CA | Decryption policies, plus settings that bypass or block applications known to pin certificates |
| F5 SSL Orchestrator | On-premises appliance that decrypts once and passes clear text through a chain of security tools | Enterprise CA held on the BIG-IP, optionally in an HSM | Policy-based bypass; re-encrypts after the service chain |

Fortinet, Check Point and Cisco firewalls offer comparable deep inspection. The architectural choice is mainly between a **cloud proxy**, which follows users anywhere, and an **on-premises appliance**, which keeps decrypted traffic inside your own data centre. Table entries reflect public documentation as of 2026.

### The inspection CA is a master key

The inspection CA can mint a trusted certificate for any website in the world, for every managed device. Whoever steals its key can intercept employees' banking, email and SaaS sessions without a warning. Protect it like an issuing CA (Chapter 15): non-exportable in an HSM where the product supports it, constrained by policy to its purpose, monitored, and rotated on a schedule. Never reuse it for anything else.

The proxy also takes over validating the real site's certificate, which the browser can no longer check. Research in 2017 found that many interception products and middleboxes did this job worse than browsers did: accepting expired or invalid certificates, offering weak ciphers to the server, or hiding validation errors from the user. US-CERT issued an alert the same year warning that HTTPS inspection could weaken TLS security. Test your proxy against deliberately broken sites such as badssl.com, and require it to block invalid upstream certificates.

### Legal and privacy limits

Decrypting employees' traffic means processing personal data, sometimes of special categories such as health, religion or trade-union membership. In the EU, GDPR requires a lawful basis, necessity and proportionality, transparency to employees, and usually a **data protection impact assessment**. European regulators have said such monitoring must be targeted and disclosed to staff. In several countries, including Germany, works councils have co-determination rights over systems that can monitor staff, so inspection cannot start without their agreement. In the United States, employer monitoring generally relies on consent through acceptable-use policies, but sector rules and state laws still apply.

The practical result is a **do-not-decrypt list** agreed with legal, privacy and HR: categories such as health, personal banking and government services are bypassed, the policy is published to staff, decrypted content is logged minimally, and access to logs is controlled and audited.

### Technical limits: pinning, client certificates and new protocols

Inspection breaks some connections by design:

- **Certificate pinning.** An application that **pins** expects a specific certificate or public key (or a specific CA) and refuses any other, including the proxy's. Many mobile apps, software updaters and some desktop applications pin. The only options are to bypass them or block them.
- **Client certificates.** A proxy cannot forward the employee's client certificate authentication, because it does not hold the client's private key. Partner portals and mTLS APIs must be bypassed.
- **Unmanaged devices.** Devices without the inspection root installed see certificate errors. That is a feature: it proves the proxy cannot silently intercept devices the enterprise does not manage.
- **QUIC and ECH.** HTTP/3 runs over QUIC on UDP, which many proxies cannot inspect, so enterprises commonly block UDP 443 to force fallback to TCP. Encrypted Client Hello hides the destination name and weakens category-based bypass decisions (Chapter 20).

ETSI's Enterprise Transport Security restores passive visibility by reusing a static Diffie-Hellman key, which deliberately removes forward secrecy; browsers do not support it. For most enterprises, active inspection on managed devices with a narrow bypass list remains the realistic option.

> **At Meridian.** Meridian decrypts outbound web traffic from managed laptops and servers through its secure web gateway. The inspection CA is an intermediate under Meridian's private root, generated in the general-purpose HSM cluster and owned by the PKI and Cryptography Services team, not the network team. The do-not-decrypt list was agreed with GRC, the EU works councils and the data protection officer, and is reviewed every year. Payments Security insisted that connections from Meridian Pay's processing environment to card networks are excluded entirely: those links use mutual TLS with network-issued certificates, and inspection would break them.

> **Compliance hook.** PCI DSS v4.0.1 requirement 4.2.1 requires strong cryptography and valid, unexpired and unrevoked certificates for cardholder data over open, public networks, and 4.2.1.1 requires an inventory of the trusted keys and certificates used. NIST SP 800-52 Rev. 2 sets TLS configuration rules for US federal systems. ISO/IEC 27001:2022 control A.8.24 expects a cryptography policy, and A.8.16 (monitoring activities) together with GDPR Article 35 shapes how inspection is justified. DORA requires financial entities to protect data in transit within their ICT risk framework. A termination map, a policy-as-code standard and scan reports are the evidence.

| openssl s_client | Manual inspection of handshakes and chains |
| Certificate Transparency monitors | Alert when certificates are issued for your domains (Chapter 13) |

An SSL Labs A+ requires TLS 1.2 and 1.3 only, forward-secret AEAD suites, a complete chain, adequate key sizes, no known vulnerabilities and HSTS with a long `max-age`. Treat it as a floor: it never sees the backend hops in Figure 21.1, so scan private ranges with testssl.sh or sslyze too and feed the results into the certificate inventory (Chapter 17).

## 21.10 Lab: termination, re-encryption, passthrough and mTLS

You need Docker, OpenSSL and curl. Everything runs locally.

**1. Build a lab CA and three certificates.**

```bash
mkdir tlslab && cd tlslab
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -nodes -keyout ca.key -out ca.crt -days 30 -subj "/CN=Lab Root"
for n in edge backend client; do
  openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
    -keyout $n.key -out $n.csr -subj "/CN=$n.lab"
  openssl x509 -req -in $n.csr -CA ca.crt -CAkey ca.key \
    -CAcreateserial -days 7 -out $n.crt \
    -extfile <(printf "subjectAltName=DNS:$n.lab")
done
```

**2. Start a backend that terminates TLS.** Save as `backend.conf`:

```text
server {
  listen 8443 ssl;
  server_name backend.lab;
  ssl_certificate     /lab/backend.crt;
  ssl_certificate_key /lab/backend.key;
  return 200 "hello from backend\n";
}
```

**3. Start an edge proxy that re-encrypts and verifies.** Save as `edge.conf`:

```text
server {
  listen 443 ssl;
  server_name edge.lab;
  ssl_certificate     /lab/edge.crt;
  ssl_certificate_key /lab/edge.key;
  ssl_protocols TLSv1.2 TLSv1.3;
  location / {
    proxy_pass https://backend:8443;
    proxy_ssl_server_name on;
    proxy_ssl_name backend.lab;
    proxy_ssl_verify on;
    proxy_ssl_trusted_certificate /lab/ca.crt;
  }
}
```

```bash
docker network create tlslab
docker run -d --name backend --network tlslab -v "$PWD":/lab:ro \
  -v "$PWD/backend.conf":/etc/nginx/conf.d/default.conf:ro nginx:1.27
docker run -d --name edge --network tlslab -p 8443:443 \
  -v "$PWD":/lab:ro \
  -v "$PWD/edge.conf":/etc/nginx/conf.d/default.conf:ro nginx:1.27
curl --cacert ca.crt --resolve edge.lab:8443:127.0.0.1 \
  https://edge.lab:8443/
```

**4. Prove that backend verification is working.** Change `proxy_ssl_name` to `wrong.lab`, run `docker exec edge nginx -s reload`, and repeat the curl. You get a 502 error, and `docker logs edge` shows the verification failure. Then set `proxy_ssl_verify off` and reload: the request succeeds, which is the silent failure mode of section 21.3. Restore both settings.

**5. Require client certificates.** Add these lines to the `server` block in `edge.conf` and reload:

```text
  ssl_client_certificate /lab/ca.crt;
  ssl_verify_client on;
```

Repeat the curl: it fails with a 400 error. Add `--cert client.crt --key client.key` and it succeeds.

**6. Pass through instead.** Save as `haproxy.cfg` and start HAProxy, which routes on SNI without any key:

```text
defaults
  mode tcp
  timeout connect 5s
  timeout client 30s
  timeout server 30s
frontend tls_in
  bind :9443
  tcp-request inspect-delay 5s
  tcp-request content accept if { req_ssl_hello_type 1 }
  use_backend be_backend if { req_ssl_sni -i backend.lab }
backend be_backend
  server b1 backend:8443
```

```bash
docker run -d --name pt --network tlslab -p 9443:9443 \
  -v "$PWD/haproxy.cfg":/usr/local/etc/haproxy/haproxy.cfg:ro \
  haproxy:3.0
openssl s_client -connect 127.0.0.1:9443 -servername backend.lab \
  -CAfile ca.crt < /dev/null 2>/dev/null | grep -E "subject|Verify"
```

The certificate you see is the backend's: HAProxy forwarded the handshake without decrypting it.

**7. Scan the edge.** Run `docker run --rm --network tlslab drwetter/testssl.sh edge:443` and compare the findings with section 21.4. Clean up with `docker rm -f edge backend pt` and `docker network rm tlslab`.

## 21.11 Failure story: Heartbleed

In April 2014, a flaw named **Heartbleed** was disclosed in OpenSSL, the library behind a large share of the web's HTTPS servers, and inside many load balancers, VPN gateways and appliances. The TLS heartbeat extension let one side send a message and ask for it to be echoed back, stating the message's length. OpenSSL trusted the stated length without checking it. An attacker could send one byte, claim 64 kilobytes, and receive 64 kilobytes of whatever was in the server's memory: session cookies, passwords, and in some cases the private TLS key.

Some doubted at first that keys could really be extracted. Cloudflare set up a deliberately vulnerable server and challenged the public to steal its key; independent researchers did so within a day. Real harm followed quickly: the Canada Revenue Agency reported that attackers had used the flaw to extract about 900 social insurance numbers from its systems before it took its services offline.

The cryptography was never involved. A missing bounds check in a rarely used feature exposed everything the cryptography protected, and the attack left no trace in normal logs. Recovery required patching, then **replacing private keys and certificates** and revoking the old ones, because nobody could prove their keys had not been read. Many enterprises had no inventory of where their certificates were installed, and the vulnerable OpenSSL might be in the web server, the ADC, the VPN concentrator or an appliance whose vendor had no patch yet. Measurements in the following weeks found many sites patched but slow to replace and revoke their certificates.

Heartbleed also exposed how underfunded OpenSSL was, with a handful of part-time maintainers. The response led to the Core Infrastructure Initiative, later the Open Source Security Foundation, and to BoringSSL and LibreSSL.

The enterprise lessons remain current. Know every termination point and which TLS library it uses. Be able to rotate every key and certificate quickly, which is exactly what certificate automation provides (Chapters 17 to 19). Keep the highest-value keys in HSMs, where a memory-disclosure bug in the TLS library cannot read them.

## 21.12 Chapter summary

- An enterprise request crosses several TLS connections; map every termination point, its key location and its owner.
- Re-encryption with backend certificate verification is the default; offload needs a written exception; passthrough keeps keys end to end at the cost of layer 7 features.
- Adopt a published profile such as Mozilla intermediate or modern, with forward-secret AEAD suites, hybrid post-quantum groups where supported, full chains and rotated ticket keys.
- Express cipher policy as code: approved named policies per platform, checks on infrastructure code before deployment, and continuous scanning for drift.
- Mutual TLS needs a narrow client trust store, an identity mapping rule and a revocation or short-lifetime strategy.
- HSTS, secure cookies, mixed-content controls and CAA protect what TLS alone cannot; roll out HSTS in stages before preloading.
- TLS inspection is an authorised man-in-the-middle; its CA is a master key, its validation must be tested, and its scope is limited by privacy law, works councils, pinning, client certificates and new protocols.
- Heartbleed showed that the ability to replace every key and certificate quickly is a core security control.
