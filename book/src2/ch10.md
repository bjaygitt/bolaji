## 10.1 What a signature guarantees

A **digital signature** scheme has three operations:

```text
keypair   = KeyGen()
signature = Sign(private_key, message)
valid     = Verify(public_key, message, signature)   # true or false
```

A valid signature proves three things:

1. **Authenticity.** It was produced by someone holding the private key.
2. **Integrity.** The message has not changed since it was signed. Changing a single bit makes verification fail.
3. **Non-repudiation.** Because only the private key holder could have produced it, the signer cannot plausibly deny it later, provided the key was properly protected.

Signatures differ from MACs (Chapter 7) in one essential way. A MAC uses a shared secret, so either party could have created the tag. A signature uses a private key held by one party, and anyone with the public key can verify it. This makes signatures suitable for publishing: one signature on a software update can be verified by a billion devices that hold only the public key.

### What a signature does not guarantee

- **That the public key belongs to who you think.** A signature proves that the holder of *some* key signed. Linking that key to an identity requires a certificate (Chapter 12) or another trusted source.
- **That the signer understood or intended the content.** Systems that show users one thing and sign another have been abused. Section 10.6 returns to this.
- **When the signature was made.** Without a trusted timestamp, a signature does not prove it was created before a key was compromised or its certificate expired.
- **Confidentiality.** Signed messages are readable by anyone.

## 10.2 Hash-then-sign

Signature algorithms work on short, fixed-size values. Every practical scheme first hashes the message, then signs the hash. Two consequences follow:

- The signature is only as strong as the hash. If an attacker can find two messages with the same hash, a signature on one is a signature on the other. This is how MD5 collisions produced a rogue CA certificate (Chapter 7).
- Large files can be signed cheaply. Signing a 4-gigabyte disk image costs the same as signing a sentence, plus the time to hash it.

Hash-then-sign also enables **remote signing**: the client hashes a large file locally and sends only the 32-byte digest to an HSM or signing service. The document never leaves the client, and the key never leaves the HSM.

## 10.3 The major signature schemes

### RSA signatures

Chapter 8 covered RSA signatures: pad the hash with PKCS#1 v1.5 or PSS, then exponentiate with the private key. RSA signatures are large (384 bytes for a 3072-bit key) and slow to create, but very fast to verify. They remain the most common signature in the web PKI and in code signing.

### ECDSA

The **Elliptic Curve Digital Signature Algorithm (ECDSA)** is the elliptic curve version of the older DSA standard. It gives 128-bit security with 64-byte signatures on P-256, and is used in TLS certificates, smart cards, payment terminals and countless devices.

Signing works like this, with private key d and public key Q = dG:

1. Hash the message to get z.
2. Choose a secret, single-use random number k, called the **nonce**.
3. Compute the point kG and take its x-coordinate, mod the curve order n, as r.
4. Compute `s = k^(-1)(z + r*d) mod n`.
5. The signature is the pair (r, s).

Step 2 is the dangerous one. The nonce k must be:

- **Secret.** If k is ever revealed, the private key follows immediately: `d = (s*k - z)/r`.
- **Never repeated.** If the same k signs two different messages, the two equations can be solved together to find k, and then d. This is how the PlayStation 3 master key was recovered (Chapter 4).
- **Unbiased.** Even if a few bits of k are predictable, or leak through timing, lattice techniques combine many signatures to recover the key. The 2019 **Minerva** and **TPM-Fail** attacks recovered keys from smart cards and trusted platform modules this way.

> **Watch out.** With ECDSA, a small flaw in one signature, not in the key, can reveal the long-term private key. Any implementation that draws k from a random number generator inherits that generator's every weakness.

**RFC 6979** removes the dependence on randomness by deriving k from the private key and the message hash using HMAC. A broken random number generator can no longer leak the key. Many libraries now use "hedged" nonces: deterministic plus some fresh randomness, which also helps against fault attacks.

### EdDSA and Ed25519

**EdDSA**, and its most common instance **Ed25519** (RFC 8032), was designed to avoid ECDSA's sharp edges. It is deterministic by design, uses complete constant-time formulas with no special cases for an attacker to trigger, and is fast and small: 32-byte public keys and 64-byte signatures. Ed25519 is the default for SSH keys, is used by Signal, Tor and many software signing systems, and was added to FIPS 186-5 in 2023, making it acceptable in US federal systems.

| Scheme | Signature size | Security | Nonce risk | Typical use |
| --- | --- | --- | --- | --- |
| RSA-3072 PSS | 384 bytes | 128 bits | None | Certificates, code signing, documents |
| ECDSA P-256 | 64 bytes | 128 bits | Severe unless deterministic | TLS certificates, smart cards, devices |
| Ed25519 | 64 bytes | About 128 bits | None by design | SSH, modern protocols, software signing |
| ML-DSA-65 | 3,309 bytes | Category 3 (post-quantum) | Hedged by design | Post-quantum signatures (Chapter 45) |

## 10.4 Code signing

**Code signing** attaches a signature to software so that an operating system, package manager or container platform can check who published it and that nobody altered it. Code signing keys are among the most valuable keys an organisation holds: a stolen key lets malware run as trusted software on every machine that trusts the publisher.

### How the ecosystems do it

Each platform has its own format, and an enterprise usually needs several:

| Ecosystem | Format and tool | Trust anchor |
| --- | --- | --- |
| Windows | Authenticode, applied with signtool or open-source jsign | Publicly trusted code signing certificates, or an enterprise CA for internal software |
| Apple platforms | codesign with a Developer ID certificate, then Apple notarisation | Apple's developer CA |
| Java | jarsigner | Certificates in the JVM truststore |
| Linux packages | GPG signatures on RPM packages and APT repository metadata | Repository keys installed on each host |
| Containers | Sigstore cosign, or Notary Project Notation | Keys, certificates or keyless identities, enforced by admission policy |
| Firmware and devices | Vendor-specific signed images | Keys burned into boot ROM or a TPM (Chapter 36) |

For publicly trusted code signing certificates, the CA/Browser Forum's code signing requirements have demanded since June 2023 that private keys live in hardware: an HSM, a hardware token, or a cloud signing service backed by one. Internal code signing keys deserve the same treatment.

### Timestamps make signatures outlive certificates

A code signing certificate expires after a year or so, but signed software stays installed for many years. A **timestamping authority (TSA)** solves this. After signing, the tool sends the signature's hash to a TSA, which returns a signed token, defined in RFC 3161, saying "this signature existed at this time". Verifiers then accept the signature as long as it was made while the certificate was valid, even after the certificate expires. Without a timestamp, signed software stops verifying the day its certificate expires.

### Signing services and keyless signing

Enterprises centralise signing in a **signing service**: build pipelines submit hashes, the service checks policy (which project, which key, which approver), signs in an HSM and logs every operation. Options as of 2026 include open-source Keyfactor SignServer, commercial services from CLM and CA vendors such as DigiCert, Keyfactor and CyberArk, and cloud KMS keys driven by tools such as jsign. AWS Signer covers some AWS-specific artefacts.

**Sigstore**, an open-source project launched in 2021, popularised **keyless signing**: a developer or pipeline proves its identity through an existing OpenID Connect login, receives a certificate valid for about ten minutes, signs, and the signature is recorded in a public transparency log. There is no long-lived signing key to steal. Major open-source package ecosystems have adopted it for publishing provenance.

A signature only proves what the build system produced, not that the build was clean. The 2020 compromise of a network monitoring vendor's build system, which inserted a backdoor into signed updates delivered to about 18,000 customers, made that painfully clear. Modern supply-chain practice adds **reproducible builds**, signed build provenance and transparency logs, so you can check how an artefact was made as well as who signed it.

## 10.5 Document signing

Contracts, loan agreements, insurance policies and board minutes are now signed electronically. Two quite different things share the name "electronic signature":

- A **click-to-sign** record: the platform logs that a user clicked a button after logging in, and seals the document with the platform's own key. The evidence is the platform's audit trail.
- A **cryptographic signature by the signer**: the document carries a signature made with a key and certificate bound to that person.

### PAdES and long-term validation

PDFs carry signatures in the format called **PAdES** (PDF Advanced Electronic Signatures), standardised by ETSI. XML and generic binary data have sibling formats, XAdES and CAdES. PAdES defines baseline levels that add evidence step by step:

- **B-B:** the basic signature and signing certificate.
- **B-T:** adds a trusted timestamp.
- **B-LT:** embeds the certificate chain and revocation data (OCSP responses or CRLs), so the signature can be validated after the CA's services disappear.
- **B-LTA:** adds archive timestamps that are renewed periodically, so the whole bundle stays protected by a current algorithm even after the original one weakens.

A mortgage signed today may need verifying in 2050, which only B-LTA with renewed archive timestamps makes realistic.

### eIDAS: simple, advanced and qualified

In the EU, the **eIDAS Regulation** gives electronic signatures legal effect and defines three levels:

- A **simple electronic signature** is any data in electronic form attached to other data and used to sign, including a typed name or a click. It is admissible in court but carries little presumption.
- An **advanced electronic signature (AdES)** is uniquely linked to and capable of identifying the signer, created with data under the signer's sole control, and linked to the document so that any change is detectable.
- A **qualified electronic signature (QES)** is an advanced signature created by a **qualified signature creation device (QSCD)** and based on a **qualified certificate** issued by a **qualified trust service provider (QTSP)** on the EU trusted lists. A QES has the equivalent legal effect of a handwritten signature in every member state.

Early QES deployments used smart cards. Most today use **remote QSCDs**: the QTSP holds the signer's key in a certified HSM, and the signer authorises each signature with strong authentication. The Cloud Signature Consortium publishes a common API for this. The 2024 amendment, often called **eIDAS 2.0**, adds European Digital Identity Wallets, which are expected to let citizens create qualified signatures from their phones. Electronic seals are the organisational equivalent: a company, not a person, signs.

E-signature platforms such as DocuSign and Adobe Acrobat Sign, and QTSPs such as those listed on the EU trusted lists, offer all three levels, typically by integrating with a QTSP for qualified signatures. Choose the level from the legal requirement of each document type, not from the product's default.

## 10.6 Transaction signing

**Transaction signing** binds a user's approval to the exact details of one transaction: amount, payee and date. It defends against malware in the browser or a compromised session, where the attacker cannot steal the password but can change what the user approves.

The core principle is **what you see is what you sign**. The device that displays the details must be the device that holds the key, and it must sign exactly what it displays.

In the EU, the PSD2 rules on strong customer authentication require **dynamic linking**: the authentication code must be specific to the amount and payee the payer agreed to. Common designs are:

- **Mobile app signing.** The banking app holds a key pair generated in the phone's secure hardware (Secure Enclave or Android StrongBox). The app displays the transaction, the user confirms with a biometric, and the hardware signs a canonical encoding of the details.
- **Hardware tokens and card readers** that display the amount and compute a code over it.
- **FIDO2 and passkeys,** whose signed challenge can include a hash of the transaction details (Chapter 16).

Machine-to-machine transactions are signed too. Open banking APIs sign requests and responses with **JSON Web Signature (JWS)** or the newer **HTTP Message Signatures** standard, and FAPI profiles specify how (Chapter 39). Card payments mostly use symmetric MACs and cryptograms instead of signatures, because the issuer and card already share keys (Chapter 37).

> **At Meridian.** Meridian runs three signing services, all owned by the PKI and Cryptography Services team. The code signing service fronts a general-purpose HSM cluster and signs Windows, Java and container artefacts for Platform Engineering pipelines, with a second approver required for release keys. The document signing service integrates the group's e-signature platform with an EU QTSP, because some insurance contracts and loan agreements in EU markets require qualified signatures. The mobile app's transaction signing keys live in customers' phones; the Payments Security team owns the server that verifies them and stores the signed payloads as evidence for disputes. GRC maps each service to its regulatory driver.

## 10.7 Signatures in protocols and tokens

In TLS 1.3, the server signs a hash of the entire handshake transcript with its certificate key, binding the key exchange to its identity (Chapter 9). In SSH, the server signs the exchange with its host key. Identity providers sign SAML assertions and OpenID Connect tokens (JWTs), and every application that accepts them trusts that signing key completely (Chapter 16). Token signing keys deserve the same protection as code signing keys: a stolen identity provider key lets an attacker mint tokens for any user, as section 10.10 shows.

## 10.8 Operating signature keys

Signature keys need different handling from encryption keys:

- **Value scales with what trusts them.** A root CA key, a firmware signing key or a token signing key may be trusted by millions of devices or every application. Protect such keys in HSMs, with multi-person controls (Chapter 33).
- **Separate keys by purpose.** Never use one key for both signing and encryption, and never reuse a TLS server key for code signing.
- **Scope narrowly, verify strictly.** A key should sign one kind of thing for one audience, and verifiers should reject anything outside that scope.
- **Plan for rotation.** Devices that trust a single hard-coded signing key cannot be fixed if that key leaks. Ship them able to trust new keys, signed by the old ones.
- **Log every use.** For high-value keys, every signature should be recorded and reviewable, so misuse is detected.
- **Use timestamps** for signatures that must outlive the signing certificate.

> **Compliance hook.** NIST SP 800-57 Part 1 sets crypto-periods for signing keys, and FIPS 186-5 lists approved signature algorithms. In PCI DSS v4.0.1, requirement 6 (secure systems and software) is where assessors look for evidence that only authorised, unaltered code reaches the cardholder data environment. ISO/IEC 27001:2022 control A.8.24 covers signature use, and A.8.32 (change management) is where code signing evidence usually lands. In the EU, eIDAS defines the legal effect of signatures, and DORA's ICT risk management rules expect integrity controls over software changes.

## 10.9 Lab: sign, verify and break ECDSA

You need OpenSSL 3.x and Python 3 with the `ecdsa` package (`pip install ecdsa`).

**Step 1. Sign and verify with Ed25519.**

```bash
openssl genpkey -algorithm ED25519 -out ed.key
openssl pkey -in ed.key -pubout -out ed.pub
echo "firmware v7" > fw.bin
openssl pkeyutl -sign -inkey ed.key -rawin -in fw.bin -out fw.sig
openssl pkeyutl -verify -pubin -inkey ed.pub -rawin -in fw.bin \
  -sigfile fw.sig
```

Change one character in `fw.bin` and verify again: it fails.

**Step 2. Add a trusted timestamp.** Create an RFC 3161 request for the signature, send it to a free public TSA (FreeTSA is used here; several CAs also run public ones), and read the reply.

```bash
openssl ts -query -data fw.sig -sha256 -cert -out fw.tsq
curl -s -H "Content-Type: application/timestamp-query" \
  --data-binary @fw.tsq https://freetsa.org/tsr -o fw.tsr
openssl ts -reply -in fw.tsr -text
```

The reply shows the TSA's name, the time and the hash of your signature.

**Step 3. Recover an ECDSA key from a repeated nonce.**

```python
from ecdsa import SigningKey, NIST256p
from ecdsa.util import sigdecode_string
import hashlib
sk = SigningKey.generate(curve=NIST256p); n = NIST256p.order
k = 123456789                       # the fatal mistake: a fixed nonce
def sign(m):
    sig = sk.sign(m, k=k, hashfunc=hashlib.sha256)
    z = int.from_bytes(hashlib.sha256(m).digest(), "big")
    return sigdecode_string(sig, n), z
(r, s1), z1 = sign(b"message one")
(_, s2), z2 = sign(b"message two")
k_found = ((z1 - z2) * pow(s1 - s2, -1, n)) % n
d = ((s1 * k_found - z1) * pow(r, -1, n)) % n
print(d == sk.privkey.secret_multiplier)   # True: key recovered
```

Two signatures, a few lines of algebra, and the private key is gone. This is why deterministic nonces matter.

**Optional cloud extension.** Create an asymmetric signing key in a cloud KMS and sign a file's digest with the provider's CLI, so the private key never exists outside the service. Keys are billed monthly until deleted, so schedule deletion when you finish.

## 10.10 Failure story: a stolen signing key and a crash dump

In July 2023, Microsoft disclosed that a threat actor it named Storm-0558 had accessed the email accounts of about 25 organisations, including US government agencies. The attackers forged authentication tokens accepted by Microsoft's cloud email service. They could do this because they had obtained a **consumer account signing key**, created in 2016, that should only have been able to sign tokens for personal accounts.

Two failures combined. First, the private signing key left its protected environment: Microsoft's investigation suggested it ended up in a crash dump that was moved into a less-protected debugging environment and later reached a compromised engineer's account, although Microsoft later said it could not confirm this path with certainty. Second, a validation flaw meant enterprise email systems accepted tokens signed by the consumer key, so one key could forge access far beyond its intended scope.

The US Cyber Safety Review Board's 2024 report called the intrusion preventable and criticised the long-lived key, which should have been rotated years earlier. The lessons map directly onto section 10.8: keep signing keys in hardware where they cannot be copied into dumps, scope keys narrowly and verify scope strictly, rotate keys on a schedule, and keep an inventory of which keys are trusted by what.

## 10.11 Chapter summary

- Signatures provide authenticity, integrity and non-repudiation, verifiable by anyone with the public key. They do not provide confidentiality, identity binding or timing on their own.
- All practical schemes hash then sign, so signatures are only as strong as their hash, and signing services need only the digest.
- ECDSA leaks its private key if a nonce is repeated, revealed or slightly biased. Use deterministic or hedged nonces, or Ed25519.
- Code signing needs hardware-protected keys, a central signing service, RFC 3161 timestamps and, increasingly, build provenance and transparency logs.
- Document signatures need long-term validation (PAdES B-LT and B-LTA). Under eIDAS, only a qualified electronic signature has the legal effect of a handwritten one.
- Transaction signing binds approval to the exact amount and payee, on a device that shows what it signs.
- Signing keys are among the most valuable secrets an organisation holds: protect them in hardware, scope them narrowly, rotate them and log their use.
