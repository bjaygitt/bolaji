## 4.1 Why randomness is the foundation

A 128-bit key is strong only if an attacker has to try all 2^128 possibilities. If the key was generated by a process that can only produce a million different values, the attacker only has to try a million, and the 128 bits on paper mean nothing. The Debian incident in Chapter 1 is exactly this: keys that looked long but came from a pool of about 32,000 values.

Cryptography consumes randomness in several roles:

| Item | What it is | What goes wrong if it is predictable |
| --- | --- | --- |
| **Key** | The secret that protects everything | Attacker guesses the key |
| **Nonce** ("number used once") | A value that must never repeat under the same key | Encryption leaks data; signatures leak the private key |
| **Initialisation vector (IV)** | A starting value for some encryption modes | Patterns in data become visible |
| **Salt** | A random value mixed into password hashing | Precomputed tables crack many passwords at once |
| **Session ID or token** | An identifier that grants access | Attacker guesses a valid session and takes it over |

Randomness failures are dangerous because they are silent. A predictable key works perfectly: it encrypts, decrypts, signs and verifies. Nothing in a log or a test suite looks wrong. The failure only shows when an attacker exploits it.

## 4.2 Entropy: measuring unpredictability

**Entropy** is the measure of how unpredictable something is, counted in bits. A fair coin flip has 1 bit of entropy. A fair six-sided die has about 2.6 bits. A truly random 128-bit key has 128 bits.

Two traps catch people:

- **Length is not entropy.** A password made from a dictionary word plus a year, such as "Summer2026!", has far less entropy than its length suggests, because attackers guess common patterns first.
- **Average is not worst case.** Cryptographers care about **min-entropy**: how likely the single most likely value is. A source that produces a fixed value 1 percent of the time is dangerous even if its other outputs look random, because an attacker simply guesses the common value first.

## 4.3 Where computers get randomness

Computers are built to be predictable, so randomness has to be harvested from the physical world and then stretched.

1. **Entropy sources.** Unpredictable physical events: timing jitter between hardware interrupts, electrical noise inside dedicated hardware random number generators (such as the RDRAND and RDSEED instructions in modern x86 processors), and similar sources.
2. **The operating system's pool.** The kernel mixes many sources together, so that one weak or compromised source cannot ruin the result.
3. **A cryptographically secure pseudo-random number generator (CSPRNG).** A deterministic algorithm, seeded from the pool, that produces an endless stream of output that nobody can predict without knowing the seed. NIST calls this a **deterministic random bit generator (DRBG)**.

A CSPRNG differs from an ordinary pseudo-random generator in one essential property: even an attacker who sees millions of outputs cannot predict the next one or work out earlier ones. Ordinary generators, such as those used for simulations and games, do not have this property. Their output can often be predicted after seeing a few values.

NIST describes this structure in three documents that you will see cited in HSM and module certificates: SP 800-90A for the DRBG algorithms, SP 800-90B for testing and validating entropy sources, and SP 800-90C for combining the two into a complete generator.

### The rule: always use the operating system's CSPRNG

In almost every situation, the correct answer is to ask the operating system or your language's dedicated cryptographic API:

| Language or platform | Use this | Never use this for secrets |
| --- | --- | --- |
| Linux | `getrandom()` system call, or `/dev/urandom` | Custom generators |
| Windows | `BCryptGenRandom` | `rand()` |
| Python | `secrets` module, `os.urandom` | `random` module |
| Java | `java.security.SecureRandom` | `java.util.Random` |
| JavaScript (browser and Node.js) | `crypto.getRandomValues`, `crypto.randomBytes` | `Math.random()` |
| Go | `crypto/rand` | `math/rand` |

A widely repeated myth says `/dev/random` is better than `/dev/urandom` on Linux because it "blocks when entropy runs out". On modern Linux kernels, both are fed by the same CSPRNG, and since Linux 5.6 (2020) `/dev/random` blocks only until the pool is first initialised. `/dev/urandom` is the right choice once the system has been seeded at boot. The `getrandom()` call handles the one genuinely risky moment, very early boot before seeding, by waiting until the pool is ready.

## 4.4 Enterprise entropy: VMs, images and containers

On a physical laptop, the kernel has plenty of entropy: keystrokes, disk timings, network interrupts and a hardware generator. The riskiest places for randomness in an enterprise are elsewhere.

### Headless devices and first boot

A network appliance, printer or embedded controller often generates its keys the first time it boots, before it has seen much unpredictable input, with no keyboard, no disk and identical firmware to thousands of siblings. In 2012, researchers scanned the internet's TLS and SSH hosts and found that they could factor the RSA private keys of 0.50% of TLS hosts and obtain DSA private keys for 1.03% of SSH hosts. Most of the weak keys came from headless network devices that generated keys at first boot with too little entropy. Many devices had produced RSA keys that shared one prime with another device, so a single gcd calculation, the tool from Chapter 3, revealed both private keys.

### Cloned virtual machines and snapshots

A virtual machine has no keyboard and virtualised hardware, so its early-boot entropy can be thin. Worse, its whole memory state can be copied. If you snapshot a running VM and restore the snapshot twice, both copies resume with the **same CSPRNG state** and will produce the same "random" numbers until something reseeds them. Researchers demonstrated in 2010 that VM reset attacks of this kind could cause real TLS implementations to reuse randomness.

Three enterprise patterns create this risk:

- **Golden images.** A template VM image with SSH host keys, TLS keys or a seeded random state already inside. Every VM built from it shares those secrets.
- **Snapshot and restore.** Backup tools, VDI pools and test environments that resume from memory snapshots.
- **Fast-start serverless.** Some serverless platforms speed up cold starts by restoring an initialised memory snapshot. AWS documents this risk for Lambda SnapStart and advises generating unique values after restore, not during initialisation.

The controls are well understood:

- Generate long-term keys after first boot, never inside the image. Tools such as cloud-init delete and regenerate SSH host keys on first boot by default; check that your image pipeline does the same for every key it might contain.
- Give VMs a good entropy source. Hypervisors can pass a **virtio-rng** device to guests, and modern CPUs expose RDRAND and RDSEED inside VMs.
- Use **VM Generation ID**, a value the hypervisor changes whenever a VM is restored from a snapshot or cloned. Hyper-V, VMware and QEMU/KVM can expose it; Windows reseeds its generator when it changes, and Linux gained a driver for the same purpose in 2022.

### Containers

Containers share the host's kernel, so `getrandom()` inside a container draws from the host's well-seeded pool. That is good news. The risks are in user space: a process that seeds its own generator once and then forks, a container image built with a pre-generated key or keystore, or checkpoint-and-restore tools that freeze and copy a running process. Modern libraries such as OpenSSL detect forks and reseed, but home-grown code may not. The rule is the same as for VMs: no secrets in images, and generate keys at runtime from the operating system's CSPRNG.

> **At Meridian.** Platform Engineering's image pipeline builds about 9,000 servers from a few dozen golden images. In 2024 a scan by the PKI and Cryptography Services team found 140 Linux VMs in DC-West sharing four SSH host keys, all cloned from an image built before the pipeline added a first-boot cleanup step. The fix was a pipeline test that fails any image containing a private key, plus a weekly job that compares public key fingerprints across the estate and raises a ticket for any duplicate. Kubernetes workloads receive their certificates at runtime from the platform's issuer, never from the container image.

## 4.5 HSM and cloud random number generators

A **hardware security module (HSM)** is a tamper-resistant device that generates, stores and uses keys without letting them leave in plaintext (Chapter 33). Every HSM contains its own entropy source, typically a physical noise source, feeding an approved DRBG. Under FIPS 140-3, the entropy source itself must now be validated against SP 800-90B, and the module's security policy states how much entropy it claims.

This matters in three ways:

- **Keys generated inside an HSM never touch a general-purpose operating system.** For CA keys, payment master keys and code signing keys, generation inside the HSM is normally a requirement, not an option. Payment standards expect it for the most sensitive payment keys.
- **Applications can borrow the HSM's generator.** PKCS#11, the standard HSM programming interface, offers `C_GenerateRandom`. Cloud KMS services offer the same idea as an API call: AWS KMS has `GenerateRandom`, Google Cloud KMS has `GenerateRandomBytes`, and Azure Managed HSM exposes a random bytes operation (all as of 2026). These are useful for seeding or for high-value secrets, but they add network latency and cost per call, so they suit occasional use, not every nonce.
- **Hardware can fail too.** In 2013, researchers factored over a hundred RSA keys from Taiwan's certified citizen smart cards, because the cards' hardware generator sometimes produced poor output and the card software did not catch it. Certification is evidence, not proof. Defence in depth means mixing sources and scanning generated public keys for duplicates and shared primes.

Products differ in how they expose and document their generators. General-purpose HSMs such as Thales Luna, Entrust nShield and Utimaco publish their DRBG and entropy details in their FIPS security policies; cloud HSM and KMS services describe theirs in their own compliance documentation. When you compare products, read those documents rather than marketing pages.

> **Compliance hook.** FIPS 140-3 requires validated entropy sources and approved DRBGs inside a module. NIST SP 800-133 describes how cryptographic keys must be generated from approved random bit generators. PCI DSS requires strong key generation as part of documented key-management procedures (requirement 3.6 and 3.7), and PCI PIN Security requires the most sensitive payment keys to be generated in a secure cryptographic device such as a payment HSM. ISO/IEC 27001:2022 control A.8.24 covers key generation within its key management rules.

## 4.6 Probability that every engineer should know: the birthday bound

How many people must be in a room before there is a 50 percent chance that two share a birthday? Most people guess around 180. The answer is 23.

This **birthday paradox** happens because you are not comparing everyone with one person; you are comparing every pair, and the number of pairs grows much faster than the number of people. The general rule, called the **birthday bound**, is:

> If values are drawn at random from N possibilities, a repeat becomes likely after about the square root of N draws.

For bit strings, the square root of 2^n is 2^(n/2). So among random 64-bit values, you expect a repeat after about 2^32, roughly 4 billion, draws. That sounds like a lot until you remember that a busy enterprise service can generate 4 billion values in days.

The birthday bound sets the safe size of many things:

| Item | Size | Repeat expected after about | Consequence |
| --- | --- | --- | --- |
| Random 64-bit IDs | 64 bits | 4 billion | Too small for large systems |
| AES-GCM random nonces | 96 bits | 2^48 messages | NIST limits random-nonce use to 2^32 messages per key, for a large safety margin |
| Block cipher output blocks | 128 bits (AES block) | 2^64 blocks | Rekey well before this; old 64-bit block ciphers fell to attacks like Sweet32 |
| Hash outputs | 256 bits (SHA-256) | 2^128 hashes | Collisions infeasible: this is why hash security is "half the output size" |
| UUID version 4 | 122 random bits | 2^61 | Fine as an identifier; not a substitute for a secret token |

The hash outputs row explains why a hash function with an n-bit output gives only n/2 bits of security against collisions. SHA-256 gives 128-bit collision resistance.

> **At Meridian.** Meridian Pay's tokenisation service issues random surrogate values for card numbers. When the service was designed, Payments Security used the birthday bound to size the token space: with a few hundred million tokens drawn from about a billion possible values (16 digits, less a fixed prefix and a check digit), collisions were certain, so the service checks every new token for uniqueness before issuing it. The same reasoning set the limit on how many messages a single AES-GCM key encrypts in the payments platform before it rotates.

## 4.7 What "hard" means

Security claims say things like "breaking this requires solving a hard problem". In cryptography, **hard** has a specific meaning: no algorithm running in a practical amount of time succeeds with more than a tiny probability.

Three terms make this precise:

- **Polynomial time** describes algorithms whose running time grows reasonably with input size, such as doubling when the input doubles. Honest users must be able to do their part in polynomial time.
- **Superpolynomial or exponential time** describes algorithms whose running time explodes, such as doubling every time the input grows by one bit. Attackers should face this.
- **Negligible** describes a success probability so small that it shrinks faster than any polynomial. In practice, below about one in 2^80 to 2^128.

Two cautions keep these claims honest:

1. **Hardness is believed, not proved.** No one has proved that factoring or lattice problems are hard. Confidence comes from decades of failed attacks.
2. **Hardness is relative to a computer model.** Factoring is hard for classical computers and easy for large quantum ones. A problem's hardness can change when technology changes, which is exactly what is happening now (Chapter 44).

## 4.8 Security in practice: work factors

Engineers translate abstract hardness into concrete **work factors**, the expected number of operations to break a system. Some reference points help calibrate:

| Operations | Roughly equals |
| --- | --- |
| 2^40 | A laptop for a few hours |
| 2^64 | A large cluster for months; feasible for well-funded attackers (SHA-1 collisions were found with about 2^63) |
| 2^80 | Beyond any single organisation today; considered the old minimum |
| 2^112 | NIST's current minimum security level |
| 2^128 | The standard target; far beyond all computing on Earth |
| 2^256 | Approaches the number of atoms in the observable universe (about 2^266) |

Choose 128-bit security for almost everything. Choose 256-bit symmetric keys where data must stay secret for decades, as a margin against both unknown advances and quantum search (Chapter 44). Remember that a work factor only holds if the key was generated with at least that much entropy.

## 4.9 Lab: see weak randomness fail, and find shared keys

This lab uses Python 3, OpenSSL and, optionally, SoftHSM with OpenSC's `pkcs11-tool`.

1. Predict a non-cryptographic generator. Python's `random` module uses the Mersenne Twister, which is designed for simulations. Seed it with a time value and watch it repeat.

```python
import random, time
seed = int(time.time())
random.seed(seed); a = [random.getrandbits(32) for _ in range(3)]
random.seed(seed); b = [random.getrandbits(32) for _ in range(3)]
print(a == b)   # True: same seed, same "random" numbers
```

An attacker who knows roughly when a token was created can try every second in that window.

2. Use the right source.

```python
import secrets
print(secrets.token_hex(32))     # 256 bits, suitable for keys
print(secrets.token_urlsafe(32)) # for URLs and reset links
```

3. Watch the birthday bound in action. Draw random 24-bit values until one repeats.

```python
import secrets
seen, n = set(), 0
while True:
    v = secrets.randbits(24); n += 1
    if v in seen: break
    seen.add(v)
print(n)   # usually a few thousand, near sqrt(2^24) = 4096
```

Run it several times. The answer clusters around a few thousand, not millions.

4. Simulate the shared-prime failure from section 4.4 with two toy RSA moduli that share a prime, and recover both keys with one gcd.

```python
from math import gcd
p, q1, q2 = 1000003, 1000033, 1000037
n1, n2 = p * q1, p * q2      # two "devices", same weak prime
g = gcd(n1, n2)
print(g, n1 // g, n2 // g)   # both moduli fully factored
```

5. Check for duplicate SSH host keys across machines you control by collecting fingerprints and looking for repeats.

```bash
for h in host1 host2 host3; do
  ssh-keyscan -t ed25519 "$h" 2>/dev/null | ssh-keygen -lf -
done | awk '{print $2}' | sort | uniq -d
```

Any fingerprint printed is a duplicated key, the sign of a cloned image.

6. Optionally, ask an HSM for random bytes. Initialise a SoftHSM token and call `C_GenerateRandom` through `pkcs11-tool`. The module path varies by distribution.

```bash
softhsm2-util --init-token --free --label lab --so-pin 1234 --pin 1234
pkcs11-tool --module /usr/lib/softhsm/libsofthsm2.so \
  --generate-random 32 | xxd
```

**Optional cloud extension.** Call `aws kms generate-random --number-of-bytes 32`, or the equivalent in Google Cloud KMS or Azure Managed HSM, and find the call in the provider's audit log. Cost warning: each call is billed as an API request, and an Azure Managed HSM is billed by the hour, so do not leave one running.

## 4.10 Failure story: the console that signed with a constant

In 2010, a group of researchers presented a complete break of the code-signing system protecting the PlayStation 3. The console accepted only software signed with the manufacturer's private key, using the ECDSA signature algorithm (Chapter 10). ECDSA requires a fresh random number for every signature. The implementation used the **same** number every time.

With two signatures made using the same random value, simple algebra reveals the private key. The researchers recovered the master signing key, and from then on anyone could sign software the console would trust. The key could not be changed in devices already sold.

Nothing was wrong with ECDSA or with the curve. One value that had to be random was constant. Modern implementations avoid this whole class of failure by deriving the per-signature value deterministically from the key and message (RFC 6979, and the design of EdDSA), so a broken random generator cannot leak the key. For an enterprise, the lesson extends to every signing service: code signing, document signing and token signing keys should live in HSMs whose signing implementations are validated, and the libraries that call them should use deterministic or hedged signature schemes where available.

## 4.11 Chapter summary

- Every key, nonce, IV, salt and token depends on unpredictable randomness. Predictable randomness silently destroys security.
- Entropy measures unpredictability; length and appearance do not. Min-entropy is what attackers exploit.
- Always use the operating system's CSPRNG through your language's cryptographic API. NIST SP 800-90A, B and C describe the generators and entropy sources behind them.
- Headless devices, golden images, VM snapshots and fast-start serverless platforms are the main enterprise entropy risks. Generate keys at runtime, reseed on restore, and scan for duplicate keys.
- HSMs provide validated entropy sources and should generate high-value keys, but hardware generators can fail too, so test outputs and inventories.
- The birthday bound says repeats become likely after about the square root of the number of possibilities. It sets safe sizes for nonces, identifiers, tokens and hash outputs.
- "Hard" means infeasible for practical computers, as far as we know, and can change with technology.
