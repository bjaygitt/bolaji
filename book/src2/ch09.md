## 9.1 The problem Diffie-Hellman solved

Before 1976, two parties could communicate securely only if they had already shared a secret key, delivered by courier or in person. Some payment systems still work this way (Chapter 38). For billions of devices that meet each other for the first time every second, that model cannot work.

Whitfield Diffie and Martin Hellman published a method that lets two parties create a shared secret over a public channel. (It later emerged that researchers at the UK's GCHQ had discovered the same idea secretly a few years earlier.) Their method is called **Diffie-Hellman (DH) key exchange**. A version of it runs every time a browser opens an HTTPS connection or two VPN gateways set up a tunnel.

The technical term for what DH does is **key agreement**: both parties contribute to the key, and neither one chooses it alone. Compare this with **key transport**, where one party picks a key and sends it to the other encrypted, as RSA key transport did in older TLS (Chapter 8). The difference decides whether recorded traffic can be decrypted years later (section 9.4).

## 9.2 The exchange, step by step

Both parties agree on public parameters: a large prime p and a generator g. Then:

| Step | Alice | Public channel | Bob |
| --- | --- | --- | --- |
| 1 | Picks secret a | | Picks secret b |
| 2 | Computes A = g^a mod p | A and B are exchanged | Computes B = g^b mod p |
| 3 | Computes B^a = g^(ab) | | Computes A^b = g^(ab) |

Both arrive at the same value, `g^(ab) mod p`, called the **shared secret**. An eavesdropper sees p, g, A and B. To compute the shared secret, they would need a or b, which means solving a **discrete logarithm**: given g and g^a mod p, find a. For well-chosen parameters of 2048 bits or more, nobody knows how to do this with classical computers in any useful time (Chapter 3).

A famous analogy uses paint. Alice and Bob each mix a secret colour into a shared public colour and swap the mixtures. Each then adds their own secret colour to the other's mixture, and both end up with the same final colour. An observer who sees the two mixtures cannot "unmix" them to find the secret colours.

The shared secret is never used directly as a key. It is fed into a **key derivation function (KDF)** such as HKDF (Chapter 7), together with context such as the handshake transcript, to produce the actual encryption and integrity keys.

## 9.3 Elliptic curve Diffie-Hellman

The same exchange works in any mathematical group where the discrete logarithm is hard. Using elliptic curves (Chapter 3) gives **Elliptic Curve Diffie-Hellman (ECDH)**:

- The public parameters are a curve and a base point G.
- Alice picks a secret number a and publishes the point `A = aG`. Bob publishes `B = bG`.
- Both compute the point `abG`, and use its x-coordinate as the shared secret.

The best known attacks on the elliptic curve discrete logarithm are far slower than those on the finite-field version, so ECDH achieves 128-bit security with 256-bit keys, compared with 3072-bit values for finite-field DH. Exchanges are smaller and much faster.

### X25519: the modern default

**X25519**, defined in RFC 7748, is ECDH on Curve25519, a curve designed by Daniel Bernstein in 2005. It has become the default key exchange in TLS 1.3, SSH, WireGuard, Signal and most modern protocols, for reasons that are about safety as much as speed:

- **Every 32-byte string is a valid public key.** There is no need to validate points, which removes a whole class of attacks (section 9.7).
- **Constant-time by design.** The recommended implementation, called the Montgomery ladder, performs the same operations for every key bit, so timing does not leak the secret.
- **Transparent parameters.** The curve's constants were chosen by a documented, minimal process, which answers suspicions about how some older curves were generated.

The NIST curves **P-256** and **P-384** remain widely used, are approved for US federal use, and are required by some government and payment profiles. They are secure when implemented carefully, but they demand more care: every incoming point must be validated.

| Option | Public value size | Security | Strengths | Cautions |
| --- | --- | --- | --- | --- |
| Finite-field DH (3072-bit) | 384 bytes | 128 bits | Simple mathematics, universal support | Large and slow; old parameters were weak |
| ECDH P-256 | 65 bytes (33 compressed) | 128 bits | FIPS-approved, universal hardware support | Must validate points |
| X25519 | 32 bytes | About 128 bits | Fast, misuse-resistant, default in TLS 1.3 | Not in older FIPS profiles (now allowed under SP 800-186) |
| ECDH P-384 | 97 bytes | 192 bits | Required by CNSA 1.0 | Slower |

## 9.4 Ephemeral keys and forward secrecy

If Alice and Bob use the same DH secrets for every session, anyone who later steals Alice's secret can decrypt every recorded past session. If instead they generate fresh secrets for each session and delete them afterwards, a later theft reveals nothing about the past. These one-time secrets are called **ephemeral keys**, and the resulting protection is called **forward secrecy** (sometimes "perfect forward secrecy").

- **TLS 1.2 with RSA key transport had no forward secrecy.** The browser encrypted the session key with the server's long-term RSA key. Anyone who recorded traffic and later obtained that private key could decrypt everything ever recorded.
- **TLS 1.3 requires ephemeral (EC)DH** for every full handshake. The server's long-term key is used only to sign the handshake, proving identity, never to protect the session key.

### What forward secrecy means for traffic inspection

Many security teams once gave copies of server private keys to passive monitoring appliances on a network tap. With RSA key transport, the appliance could decrypt each recorded session. With ephemeral ECDH, the private key no longer helps, because the session key never travelled under it.

Most enterprises responded by moving inspection inline, terminating TLS at a load balancer, proxy or firewall and re-encrypting behind it (Chapter 21). Some export per-session keys to the analytics tool. A few adopted ETSI's **Enterprise Transport Security**, which uses a static server DH key so that passive decryption works again, and so deliberately gives up forward secrecy. That trade-off deserves an explicit risk decision.

> **Watch out.** Forward secrecy protects past sessions from future theft of long-term keys. It does not protect against a quantum computer that can break the recorded ephemeral exchange itself. That is why "harvest now, decrypt later" drives the move to hybrid post-quantum key exchange (Chapter 46).

## 9.5 The missing piece: authentication

Diffie-Hellman alone has a fatal weakness: it does not tell Alice who she is talking to. An attacker in the middle can run one exchange with Alice and a separate exchange with Bob, relaying and reading everything. This is a **man-in-the-middle (MITM) attack**, and plain DH has no defence against it.

Real protocols therefore **authenticate** the exchange. One or both parties sign their DH public value, or the whole handshake transcript, with a long-term signing key whose public half is vouched for by a certificate (Chapter 12) or known in advance (as with SSH host keys). The combination is called **authenticated key exchange**:

- Ephemeral DH provides a fresh shared secret and forward secrecy.
- Signatures with long-term keys prove identity (Chapter 10).

Keeping these two roles separate is the design principle behind TLS 1.3, SSH, IKEv2, Noise and Signal. It also means that in TLS 1.3 the certificate key on your load balancer is a *signing* key: if it leaks, an attacker can impersonate the server, but cannot decrypt sessions already recorded.

## 9.6 Where key agreement lives in the enterprise

Every encrypted channel in an enterprise starts with a key agreement, and each one is configured in a different place by a different team.

| Where | Protocol | Typical groups | Who usually owns the setting |
| --- | --- | --- | --- |
| Websites, APIs, load balancers | TLS 1.3 and 1.2 | X25519, P-256, hybrid X25519MLKEM768 | Network or Platform Engineering |
| Administrator and automation access | SSH | curve25519-sha256, hybrid post-quantum methods | Platform Engineering, IAM |
| Site-to-site and remote access VPN | IKEv2/IPsec | DH group 14 (2048-bit), 19 (P-256), 20 (P-384), 31 (Curve25519) | Network Engineering |
| Modern tunnels | WireGuard | X25519 only, fixed by the protocol | Network or Platform Engineering |
| Service mesh and Kubernetes | mTLS | Whatever the mesh's TLS library negotiates | Platform Engineering |
| Envelope encryption to a public key | ECIES, HPKE | X25519, P-256 | Application teams |
| Messaging apps | Signal protocol | X25519 | Vendor-controlled |

### How the major platforms configure it

Products expose the choice of groups in different ways, as of 2026:

- **Libraries and web servers.** OpenSSL calls them "groups"; NGINX sets them with `ssl_ecdh_curve`, HAProxy with its `curves` bind option, and Java with the `jdk.tls.namedGroups` system property.
- **Windows.** Schannel reads its curve order from Group Policy, and the PowerShell TLS module can list and enable curves.
- **Appliances.** F5 BIG-IP, Citrix NetScaler and the major firewalls set groups inside SSL or VPN profiles. Map each vendor's names back to the standard group names in your policy.
- **HSMs and cloud KMS.** General-purpose HSMs expose ECDH through PKCS#11 derive mechanisms, so the private key never leaves the hardware (Chapter 33). Among cloud KMS services, AWS KMS offers a derive-shared-secret operation for elliptic curve keys; check each provider's documentation for current support.

> **At Meridian.** The PKI and Cryptography Services team publishes a single approved list of key agreement groups: hybrid X25519MLKEM768 preferred, then X25519, then P-256, with P-384 for the payments zone. Network Engineering owns the IKEv2 profiles on the SD-WAN and the inter-DC links, and was the last team to remove DH group 2 (1024-bit) from a handful of partner VPNs. When the SOC lost passive visibility after the move to TLS 1.3, Meridian chose to inspect at the WAF and forward proxy instead of copying keys, and GRC recorded the decision.

## 9.7 How Diffie-Hellman fails

### Weak and shared parameters

In 2015, the **Logjam** research showed that many servers still accepted 512-bit "export-grade" DH parameters, a leftover from 1990s US export controls, and that an attacker in the middle could force connections down to them. Worse, millions of servers used the same handful of 1024-bit primes. Because the expensive part of breaking DH can be precomputed once per prime, the researchers estimated that a nation-state could break a single common 1024-bit prime and then passively decrypt a large fraction of VPN and HTTPS traffic. TLS 1.3 now allows only standard, large, well-studied groups (RFC 7919 for finite fields), and only modern curves.

### Small-subgroup and invalid-curve attacks

If an implementation does not check that a received public value is valid, an attacker can send a value that lies in a tiny subgroup, or, for elliptic curves, a point that is not on the agreed curve at all. Combining the victim's secret with such a value leaks a few bits of the secret each time, and repeated exchanges reveal it entirely. In 2015, researchers demonstrated invalid-curve attacks that extracted private keys from TLS servers built on several popular libraries.

The defences:

- **Validate every received public key** (on the curve, correct subgroup, not the identity point) for NIST curves and finite-field groups. NIST SP 800-56A specifies these checks.
- Prefer **X25519**, where every input is safe by construction.
- Use **ephemeral keys**, so that leaked bits relate to a key that is about to be thrown away.

### Reused "ephemeral" keys and missing authentication

Some implementations generate one "ephemeral" key at start-up and reuse it for hours to save CPU, silently weakening forward secrecy and turning small leaks into key recovery. Others, often internal tools and IoT devices, run an exchange but never check a signature or certificate, leaving them open to the attack of section 9.5. When you review a vendor's "encrypted" protocol, ask what authenticates the exchange.

## 9.8 Design decisions

An architect makes a small number of key agreement choices, and each one needs a defensible reason:

- **Which groups, in which order.** Prefer hybrid post-quantum where both ends support it, then X25519, then P-256. Keep P-384 where a regulator or the NSA's CNSA profile requires it.
- **Minimum finite-field size.** Where finite-field DH survives (older IKEv2 peers, some Java and mainframe stacks), set 2048 bits as the floor and use the RFC 7919 or RFC 3526 groups rather than locally generated primes.
- **FIPS mode.** If you must run FIPS 140-3 validated modules, check that X25519 is inside the module's approved boundary in your version; support arrived after SP 800-186 and varies by vendor (Chapter 40).
- **Where the private key lives.** Static ECDH keys used for decryption (in ECIES or HPKE) belong in an HSM or KMS.

> **Compliance hook.** PCI DSS v4.0.1 requirement 4.2.1 asks for strong cryptography on cardholder data sent over open, public networks. NIST SP 800-52 Rev. 2 sets TLS group choices for US federal systems, and SP 800-56A Rev. 3 defines approved DH and ECDH schemes. ISO/IEC 27001:2022 control A.8.24 (use of cryptography) expects a documented rule such as the group list in section 9.6.

## 9.9 Diffie-Hellman as a building block

Beyond simple key exchange, DH appears inside many other constructions:

- **ECIES and HPKE.** Public-key encryption built from ECDH plus symmetric encryption. **HPKE** (Hybrid Public Key Encryption, RFC 9180) is the modern standard, used by Encrypted Client Hello and Messaging Layer Security.
- **Signal's X3DH and Double Ratchet** combine several DH exchanges to give messaging both forward secrecy and recovery after compromise (Chapter 25).
- **Key Encapsulation Mechanisms (KEMs).** A **KEM** is an interface where one party "encapsulates" a fresh random key to another's public key and sends the resulting ciphertext. DH can be framed as a KEM, and the post-quantum ML-KEM is one (Chapter 45). This shared interface is what makes hybrid classical plus post-quantum key exchange straightforward: run both, and feed both secrets into the KDF.

## 9.10 Lab: exchange keys yourself

You need Python 3 and OpenSSL 3.x. All steps run locally.

**Step 1. Run a toy exchange in Python.** The prime is far too small for real use, but the arithmetic is the real thing.

```python
import secrets
p = 2**127 - 1          # a prime (far too small for real use)
g = 3
a, b = secrets.randbelow(p), secrets.randbelow(p)
A, B = pow(g, a, p), pow(g, b, p)
print(pow(B, a, p) == pow(A, b, p))   # True: same shared secret
```

**Step 2. Perform X25519 with OpenSSL.**

```bash
openssl genpkey -algorithm X25519 -out alice.key
openssl genpkey -algorithm X25519 -out bob.key
openssl pkey -in alice.key -pubout -out alice.pub
openssl pkey -in bob.key   -pubout -out bob.pub
openssl pkeyutl -derive -inkey alice.key -peerkey bob.pub | xxd -p
openssl pkeyutl -derive -inkey bob.key   -peerkey alice.pub | xxd -p
```

The two outputs are identical: both sides derived the same 32-byte secret without ever sending it.

**Step 3. Restrict the groups a local TLS server accepts.**

```bash
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -nodes -keyout srv.key -out srv.crt -subj "/CN=localhost" -days 7
openssl s_server -accept 8443 -key srv.key -cert srv.crt \
  -groups X25519 -www &
openssl s_client -connect localhost:8443 -groups P-256 -brief
openssl s_client -connect localhost:8443 -groups X25519 -brief
```

The first client fails the handshake; the second reports the negotiated group. Stop the server with `kill %1`.

**Step 4. See what your browser negotiates.** Visit any major website, open the browser's developer tools, choose the Security tab, and look at the key exchange. Since late 2024, Chrome, Edge and Firefox negotiate **X25519MLKEM768** with most large sites: classic X25519 combined with a post-quantum KEM. Chapter 46 explains this hybrid.

**Optional cloud extension.** Create an elliptic curve key pair with key-agreement usage in a cloud KMS that supports it, and derive a shared secret against a locally generated public key. Cloud keys incur a monthly charge for as long as they exist, so schedule the key for deletion when you finish.

## 9.11 Failure story: Logjam and the shared primes

In May 2015, a team of 14 researchers published "Imperfect Forward Secrecy: How Diffie-Hellman Fails in Practice". They found two problems.

First, 8.4 percent of the top one million HTTPS websites still supported 512-bit export-grade DH, and a flaw in TLS 1.2 let an attacker in the middle downgrade normal connections to it. The researchers broke 512-bit groups in about 90 seconds per connection after a week of precomputation per prime.

Second, and more troubling, the expensive precomputation for the number field sieve depends only on the prime, not on individual keys. Because a few standard 1024-bit primes were hard-coded into widely used software, the researchers estimated that breaking a single common prime, at a cost of hundreds of millions of US dollars in custom hardware, would allow passive decryption of connections to about 18 percent of the top one million HTTPS sites and a large share of VPN servers. They noted that this matched descriptions in leaked intelligence documents of large-scale VPN decryption capabilities.

Browsers raised minimum DH sizes immediately, and TLS 1.3 later removed custom DH groups altogether. The lesson reaches beyond DH: shared parameters concentrate risk, "nobody would spend that much" is not a threat model when the prize is everyone's traffic, and old settings survive longest in the places nobody inventories.

## 9.12 Chapter summary

- Diffie-Hellman lets two parties create a shared secret over a public channel, based on the hardness of discrete logarithms. The secret is always turned into keys with a KDF.
- ECDH gives the same exchange with much smaller, faster keys. X25519 is the modern default because it is fast and hard to misuse; P-256 and P-384 remain for FIPS and government profiles.
- Ephemeral keys give forward secrecy: stealing a long-term key later does not expose past sessions. TLS 1.3 requires it, which ended passive decryption with copied server keys.
- DH alone is open to man-in-the-middle attacks. Authenticated key exchange adds signatures, keeping secrecy and identity in separate keys.
- Key agreement is configured in many places (web servers, Windows, appliances, VPNs, meshes), so a central approved group list is the only way to keep it consistent.
- Weak or shared parameters (Logjam), unvalidated public keys (invalid-curve attacks) and reused ephemeral keys have broken real deployments.
- DH is also a building block for HPKE, Signal and the KEM interface that makes hybrid post-quantum migration practical.
