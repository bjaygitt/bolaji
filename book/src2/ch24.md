## 24.1 Why internal traffic needs its own cryptography

Chapter 22 encrypted the links between sites and data centres. That protects packets on the wire but says nothing about which service sent them. Inside a data centre or cloud region, a payment API calls a fraud service, which reads from Kafka, which feeds a database, all across a flat, shared network. An attacker who compromises one container can reach the others unless each connection proves who is calling and who is answering.

Three facts shape the design:

- **Scale and churn.** A Kubernetes platform may run thousands of pods that live for minutes. Certificates for them must be issued and rotated by machines, not by tickets.
- **Identity matters more than secrecy.** An encrypted connection from an unknown caller is still a breach. The goal is **mutual authentication**: both ends prove an identity that policy can reason about.
- **Defaults fail open.** Database drivers that encrypt without checking certificates, meshes in "permissive" mode and Kafka listeners left on plaintext are the norm, not the exception. Much of this chapter is about finding and closing those gaps.

## 24.2 The internal PKI of a Kubernetes cluster

A Kubernetes cluster is itself a distributed system whose components talk over mutual TLS. Built with **kubeadm**, the reference installer, a cluster has three private CAs and one signing key pair, kept under `/etc/kubernetes/pki` on each control-plane node:

| Trust anchor | Signs | Used for |
| --- | --- | --- |
| Cluster CA (`ca.crt`) | API server serving certificate, API server's client certificate to kubelets, kubelet client certificates, administrator certificates | Authenticating everything that talks to or from the API server |
| etcd CA (`etcd/ca.crt`) | etcd server and peer certificates, the API server's etcd client certificate | Protecting the datastore, which holds every Secret |
| Front-proxy CA | The aggregator's client certificate | Extension API servers |
| Service account key pair (`sa.key`, `sa.pub`) | Not a CA: signs service account tokens (JWTs) | Pod identity to the API server and, via OIDC discovery, to clouds and vaults (Chapter 35) |

kubeadm issues leaf certificates valid for one year and CAs for ten. It renews leaf certificates during a control-plane upgrade, and `kubeadm certs check-expiration` and `kubeadm certs renew` handle the rest. A cluster that is never upgraded will stop working on its first anniversary, which is a common outage in on-premises clusters.

**Kubelet certificates** need particular care. Each node's kubelet has a client certificate to talk to the API server, obtained at join time through **TLS bootstrapping** (a short-lived bootstrap token lets the kubelet submit a certificate signing request through the Kubernetes CSR API). Client certificate rotation is on by default in kubeadm clusters: the kubelet requests a new certificate as expiry approaches. The kubelet's **serving** certificate, used when the API server connects to it for logs and exec, is self-signed by default, so the API server cannot verify it. Setting `serverTLSBootstrap: true` makes kubelets request serving certificates from the cluster CA, but those CSRs are not approved automatically; you need an approver controller or a policy that does it safely.

The **service account signing key** has no expiry date, so it is easily forgotten. Rotating it means configuring the API server to verify tokens with both old and new public keys, switching signing to the new key, waiting for old tokens to expire, then removing the old key.

### Managed clusters and OpenShift

On managed services the provider runs the control plane and its PKI. Amazon EKS, Azure Kubernetes Service and Google Kubernetes Engine all rotate control-plane certificates for you, with documented procedures for rotating the cluster CA (AKS's `rotate-certs` operation and GKE's credential rotation, for example), which force clients to fetch new credentials. You still own the worker-side details: node images, workload certificates and anything you added.

**Red Hat OpenShift** goes furthest. Its operators manage dozens of internal certificates and rotate them automatically. The **service CA operator** issues a serving certificate to any service annotated to request one, and injects the service CA bundle into ConfigMaps for clients; the service CA itself is rotated automatically before expiry. You can supply your own certificates for the API server and the default ingress, which is where enterprise CA integration happens (Chapter 18). The documented caveat is that a cluster shut down for long enough may come back with expired kubelet certificates and pending CSRs that an administrator must approve.

> **At Meridian.** Platform Engineering runs on-premises Kubernetes and OpenShift alongside managed clusters in each cloud. The PKI and Cryptography Services team does not issue control-plane certificates (the platforms do that themselves), but it requires that every self-built cluster report `kubeadm certs check-expiration` output to the certificate inventory weekly, and it holds the escrowed backup of each cluster CA key in an HSM-protected vault. Cluster CAs are never chained to Meridian's enterprise root: compromise of one cluster must not create certificates that other systems trust.

## 24.3 Encrypting Secrets at rest

Kubernetes stores Secrets in etcd, by default only base64-encoded. Anyone with an etcd backup or disk image has every database password and API key in the cluster. **Encryption at rest** is configured on the API server with an `EncryptionConfiguration` file listing **providers** in order: the first encrypts new writes; all are tried on reads, which is how rotation works.

| Provider | How it works | Assessment |
| --- | --- | --- |
| `identity` | No encryption | The default; acceptable only as the last entry during migration |
| `aescbc` | AES-CBC with a key in the config file | Not recommended by the Kubernetes documentation (padding oracle risk) |
| `aesgcm` | AES-GCM with a key in the config file | Fast, but the key must be rotated frequently because of nonce limits |
| `secretbox` | XSalsa20-Poly1305 with a key in the config file | Sound cipher, same key-on-disk problem |
| `kms` (v2) | Envelope encryption with a key encryption key in an external KMS | The recommended option |

The local-key providers protect a stolen etcd backup, but the key sits in a file on the control-plane node, next to the data. **KMS v2**, generally available since Kubernetes 1.29, uses **envelope encryption** (Chapter 28). The API server encrypts each Secret with a data encryption key (DEK) derived from a seed it generates; the seed is encrypted by a **key encryption key (KEK)** that never leaves the external KMS, through a **KMS plugin** that the API server reaches over a local gRPC socket. Because the API server caches the DEK seed, it calls the KMS rarely, and the plugin reports a key ID so that the API server notices when the KEK has been rotated. The older KMS v1 API is deprecated.

Providers: EKS integrates with AWS KMS, GKE offers application-layer secrets encryption with Cloud KMS, and AKS offers KMS etcd encryption with Azure Key Vault. On premises, HashiCorp Vault and HSM or key-manager vendors (Chapter 34) publish KMS plugins. OpenShift can encrypt etcd with AES-CBC or AES-GCM and rotates the encryption keys automatically.

Two operational points follow. Enabling encryption affects only new writes, so you must rewrite existing Secrets afterwards (the lab does this). And the KMS becomes a dependency of the control plane: if the plugin cannot reach the KMS when the cache is cold, the API server cannot read Secrets. Treat the KMS key's availability and deletion protection like a tier-zero dependency.

> **Watch out.** Encryption at rest protects etcd and its backups. It does nothing against anyone who can `kubectl get secret` through the API, which returns plaintext. RBAC on Secrets, and keeping high-value secrets in a dedicated secrets manager (Chapter 35), matter at least as much.

## 24.4 Service meshes: mTLS and workload identity

A **service mesh** moves service-to-service security out of application code into a proxy that sits beside each workload (a **sidecar**) or on each node. The mesh's control plane runs a CA, issues each workload a short-lived certificate encoding its identity, and configures the proxies to use mutual TLS for every connection. Application code speaks plain HTTP to localhost; the proxies encrypt, authenticate and enforce policy. The approach is described in NIST's guidance on service-mesh security for microservices.

The identity in the certificate is usually a **SPIFFE ID** (Section 24.5), a URI such as `spiffe://cluster.local/ns/payments/sa/api`, derived from the pod's namespace and Kubernetes service account. Authorisation policy is then written in terms of identities ("only `payments/api` may call `fraud/score`"), not IP addresses, which change constantly.

| Mesh (as of 2026) | CA and issuance | Defaults and notes |
| --- | --- | --- |
| Istio | `istiod` acts as CA; the node or sidecar agent requests certificates and delivers them to Envoy over SDS; workload certificates live about 24 hours by default | mTLS starts in PERMISSIVE mode; STRICT is set with PeerAuthentication. An enterprise intermediate can be plugged in through the `cacerts` Secret or cert-manager's istio-csr. Ambient mode (generally available since 1.24) replaces sidecars with per-node ztunnel proxies |
| Linkerd | An identity controller signs proxy CSRs with an issuer certificate under a trust anchor you supply; proxy certificates live about 24 hours | mTLS is automatic for TCP between meshed pods. Trust anchor and issuer rotation are your job, commonly automated with cert-manager |
| HashiCorp Consul | Built-in CA, or Vault or AWS Private CA as CA providers; SPIFFE-format leaf certificates | Runs across Kubernetes, virtual machines and multiple data centres; "intentions" express which services may connect |
| Cilium | Node-to-node transparent encryption with WireGuard or IPsec; optional mutual authentication using SPIRE identities | Encryption at the network layer without sidecars; identity-based policy from Cilium's own identities |

### Design decisions for a mesh

- **Who is the root?** Every mesh can generate its own self-signed root, which is fine for a lab and wrong for an enterprise. Plug in an intermediate issued from a dedicated mesh root (not the enterprise root that end-user devices trust), with the CA key in an HSM or a secrets manager. Use one trust domain per environment, and federate deliberately between them.
- **PERMISSIVE versus STRICT.** Permissive mode accepts both mTLS and plaintext so that migration does not break callers. It also means an attacker can simply skip mTLS. Measure plaintext traffic, then move each namespace to STRICT with a deadline.
- **Trust anchor rotation.** A mesh root that expires takes down every service at once. Rotation requires distributing a bundle containing old and new roots, reissuing intermediates, and only then removing the old root. Rehearse it.
- **Headers from the mesh.** Proxies can forward the caller's identity to the application in a header such as Envoy's `x-forwarded-client-cert`. Applications must accept it only from their own proxy, or any caller can forge an identity.

> **In practice.** A mesh does not replace TLS to things outside it. Calls to managed databases, SaaS APIs and the mainframe leave the mesh, and need their own TLS with certificate validation, configured in the mesh's egress rules or the application.

## 24.5 SPIFFE and SPIRE beyond the mesh

Chapter 35 introduced **SPIFFE** (Secure Production Identity Framework for Everyone) as a workload identity standard. Here its importance is that it gives every workload, on any platform, a certificate-based identity in one format:

- A **SPIFFE ID** names the workload inside a **trust domain**: `spiffe://meridian.example/payments/api`.
- An **X.509-SVID** is a short-lived certificate whose URI SAN carries that ID, used for mTLS. A **JWT-SVID** carries it as a token for cases where TLS cannot be end to end.
- The **Workload API** is a local Unix socket from which a workload fetches its SVID and the **trust bundle** (the CA certificates for its own and federated trust domains). The workload needs no bootstrap secret; the agent identifies the caller from the kernel.

**SPIRE**, the reference implementation and a graduated CNCF project, splits the job between a **server**, which signs SVIDs, and an **agent** on each node. The agent proves its node's identity through **node attestation** (cloud instance identity documents, Kubernetes projected tokens or a TPM), then identifies each local process through **workload attestation** (Kubernetes namespace and service account, container image, Unix user). Registration entries map those selectors to SPIFFE IDs. SPIRE's upstream authority plugins let it sit under an enterprise CA, Vault or a cloud private CA.

SPIFFE matters for an enterprise because it spans what a single mesh cannot: virtual machines, several Kubernetes distributions, batch jobs and multiple clouds can all present identities that the same policy understands, and Istio, Consul and Cilium either use SPIFFE-format identities or can consume SPIRE's. **Federation** exchanges trust bundles between trust domains, so `payments.meridian.example` can verify `cards.meridian.example` without sharing a root.

## 24.6 API gateways

An **API gateway** sits in front of services and handles routing, authentication, rate limiting and transformation. It is also a cryptographic hub: it terminates TLS for many API hostnames, validates client certificates and tokens, and opens new TLS connections to backends.

| Gateway (as of 2026) | Client mTLS | Notes from public documentation |
| --- | --- | --- |
| AWS API Gateway | Mutual TLS on custom domain names, with a truststore uploaded to S3 | Backend calls to private integrations use TLS; client certificates for backend authentication are supported |
| Azure API Management | Client certificate negotiation and a `validate-client-certificate` policy | Can present client certificates to backends from Key Vault |
| Google Apigee | Mutual TLS through configured keystores and truststores | Separate truststores northbound and southbound |
| Kong Gateway | mTLS authentication plugin (enterprise) and upstream client certificates | Open-source core, often deployed on Kubernetes |
| Others: MuleSoft, Tyk, NGINX, Envoy-based gateways | Varies | Kubernetes Gateway API adds a BackendTLSPolicy resource for backend TLS |

Three design points recur:

- **Client authentication.** For partner and open banking APIs, mTLS with client certificates from a known CA is common, often combined with **certificate-bound access tokens**, where the OAuth token is valid only with the client certificate it was issued to. Chapter 39 covers the FAPI profile that requires this.
- **Token validation.** Gateways validate JWT access tokens with keys from the identity provider's JWKS endpoint (Chapter 16). Cache keys, but refresh on an unknown key ID, and reject unsigned or `none`-algorithm tokens.
- **Backend trust.** The gateway should use TLS to backends and validate their certificates, and backends should accept calls only from the gateway, by mTLS or by verifying a token the gateway signs. A backend that also accepts direct calls lets attackers bypass every gateway policy.

## 24.7 Kafka and message queues

### Apache Kafka

Kafka brokers accept connections on **listeners**, each with a security protocol: `PLAINTEXT`, `SSL` (TLS, optionally with client certificates), `SASL_PLAINTEXT` or `SASL_SSL` (SASL authentication, with or without TLS). The only acceptable production choices are `SSL` and `SASL_SSL`, on client listeners and on inter-broker and controller listeners alike. Since Kafka 4.0 (2025) clusters run on KRaft controllers without ZooKeeper, so the controller quorum's listener is one more channel to secure.

Authentication options:

| Mechanism | How the client proves identity | Considerations |
| --- | --- | --- |
| mTLS | Client certificate; the principal is mapped from the DN by `ssl.principal.mapping.rules` | Strong and simple; certificate sprawl across client applications |
| SASL/SCRAM-SHA-256 or 512 | Salted challenge-response password | No password on the wire; credentials still need rotation |
| SASL/GSSAPI | Kerberos (Chapter 16) | Natural in Active Directory estates; keytabs to manage |
| SASL/OAUTHBEARER | OAuth access token from an identity provider | Short-lived tokens, central identity; needs a reachable IdP |
| SASL/PLAIN | Username and password sent inside TLS | Acceptable only over TLS; common in managed services as API keys |

Clients verify the broker's hostname by default (`ssl.endpoint.identification.algorithm=https`); never set it to empty to "fix" a certificate error. Managed services follow the same pattern: Amazon MSK offers TLS with IAM authentication, mTLS with AWS Private CA, or SCRAM with secrets in Secrets Manager; Confluent Cloud uses `SASL_SSL` with API keys or OAuth; Azure Event Hubs exposes a Kafka endpoint over `SASL_SSL` with Entra ID tokens or connection strings.

Kafka does not encrypt data at rest itself, and brokers see every message. Where messages carry card data or personal data, encrypt fields in the producer and decrypt in consumers with keys from a KMS (Chapter 27), so that brokers, their disks and their operators handle ciphertext only.

### RabbitMQ and others

**RabbitMQ** serves AMQP over TLS on port 5671. Set `verify_peer` and `fail_if_no_peer_cert` for client certificates, and remember that inter-node clustering traffic is separate and needs its own TLS configuration. **ActiveMQ**, **NATS** (TLS plus NKey or JWT credentials) and cloud queues (Amazon SQS, Azure Service Bus, Google Pub/Sub, all TLS with IAM or token authentication) round out the field. The questions are the same everywhere: TLS on every listener, certificate validation on every client, authentication tied to a real identity, and payload encryption where the broker should not see content.

## 24.8 Database connections

Database drivers are where "encrypted" most often means "unauthenticated". Many encrypt opportunistically but do not validate the server certificate, so an attacker on the path can present any certificate and read everything.

| Database | Insecure default or common setting | Secure setting |
| --- | --- | --- |
| PostgreSQL (libpq) | `sslmode=prefer`: TLS if offered, no certificate check | `sslmode=verify-full` with `sslrootcert`; `channel_binding=require` with SCRAM |
| MySQL | `ssl-mode=PREFERRED`: no certificate check | `ssl-mode=VERIFY_IDENTITY`; server `require_secure_transport=ON` |
| SQL Server | `TrustServerCertificate=true` skips validation | `Encrypt=Strict` (TDS 8.0, SQL Server 2022) or `Encrypt=Mandatory` with validation |
| Oracle | Native network encryption without server authentication | TLS (TCPS) with wallet-based server verification, or native encryption set to required with integrity |
| MongoDB | `tlsAllowInvalidCertificates=true` in connection strings | `tls=true` with a CA file; x.509 or SCRAM authentication |

PostgreSQL's **channel binding** is worth explaining. With SCRAM authentication, `channel_binding=require` mixes a hash of the server's TLS certificate into the authentication exchange. A man in the middle who terminates TLS with his own certificate cannot complete the login, even if the client does not otherwise validate certificates.

Managed databases add one more lesson. Cloud database services sign server certificates from provider CAs that clients must trust, and those CAs rotate. In August 2024 the original Amazon RDS certificate authority (`rds-ca-2019`) expired, and AWS asked customers to move databases to newer CAs and update client trust stores beforehand. Applications that pinned the old CA, or had validation switched off, were the ones that either broke or never noticed. Track provider CA rotations in the certificate inventory like any other expiry.

Encrypting database files is covered in Chapter 27. The connection is a separate control: TDE does nothing for credentials and query results on the network.

## 24.9 Mainframe and legacy protocols

A bank's core ledger often lives on an IBM Z mainframe running z/OS, reached by terminal emulators, message queues and file transfer. These protocols predate TLS-everywhere and are often the last clear-text traffic in the data centre.

### TN3270 over TLS

**TN3270** carries 3270 terminal sessions (the green screens) over Telnet. Plain TN3270 sends user IDs and passwords in clear. The z/OS TN3270E server supports TLS, usually configured through **AT-TLS** (Application Transparent TLS): the z/OS Communications Server's Policy Agent applies TLS policy to the connection by port and application, using a certificate in a **RACF key ring** (or ACF2 or Top Secret equivalents), with keys optionally protected by the Crypto Express hardware through **ICSF**. Port 992 is the conventional port for Telnet over TLS. Emulators that support TLS include IBM Personal Communications and Host On-Demand, Rocket BlueZone, OpenText Reflection and the open-source x3270 family. Client certificates can strengthen authentication to the host. The migration work is mostly operational: distributing the right CA to every emulator profile and finding the scripts and robotic process automation bots that still connect in clear.

### IBM MQ

**IBM MQ** secures each **channel** separately. The `SSLCIPH` attribute selects the protocol and cipher (for example `ANY_TLS13_OR_HIGHER` on current versions), `SSLCAUTH(REQUIRED)` demands a client certificate, and `SSLPEER` or channel authentication records (`CHLAUTH` with `SSLPEERMAP`) map certificate distinguished names to permitted identities. Keys live in the queue manager's key repository, which on z/OS is a RACF key ring. TLS protects messages only between queue managers and clients; messages rest in queues in clear. **MQ Advanced Message Security (AMS)** adds end-to-end protection by signing or encrypting each message at the putting application, so it stays protected on intermediate queue managers and in logs.

### Other legacy protocols

| Clear-text protocol | Encrypted replacement |
| --- | --- |
| FTP | FTPS (FTP over TLS) or SFTP (Chapter 25); IBM Sterling Connect:Direct with Secure Plus for scheduled transfers |
| LDAP on port 389 with simple binds | LDAPS or StartTLS, plus LDAP signing and channel binding on Active Directory |
| SMB 1 and 2 | SMB 3 with encryption required on sensitive shares |
| SNMP v1 and v2c | SNMPv3 with authentication and privacy |
| Syslog over UDP | Syslog over TLS |
| NFS with system authentication | NFS with Kerberos privacy (`krb5p`) or an encrypted network path |

z/OS also supports **pervasive encryption** of data sets with keys held in the Crypto Express hardware, a data-at-rest control discussed with storage encryption in Chapter 26.

> **At Meridian.** Meridian's core banking mainframe accepts TN3270 only over TLS through AT-TLS policies, with server certificates in a RACF key ring issued by a mainframe-specific intermediate under Meridian's private root. IBM MQ channels between the mainframe and the payments platform require TLS 1.3 cipher specifications and client certificates, mapped with CHLAUTH rules; Meridian Pay's settlement queues also use AMS encryption, because Payments Security wants card data protected while it rests in transmission queues. The systems programming team owns the key rings; the PKI and Cryptography Services team owns the issuing CA and tracks every mainframe certificate in the inventory.

## 24.10 Design decisions, operations and compliance

The decisions an architect needs to make and defend:

- **One identity model across platforms.** Prefer SPIFFE-format identities from a small number of mesh or SPIRE CAs, each under a dedicated root, over ad hoc certificates per team.
- **Strict by default.** Meshes in STRICT mode, Kafka with no plaintext listeners, database drivers with full verification, MQ channels with `SSLCAUTH(REQUIRED)`. Exceptions are recorded with an owner and an end date.
- **Secrets encrypted with KMS v2** on every cluster, with the KMS key treated as tier-zero.
- **Platform CAs isolated** from the enterprise root, so that one cluster's compromise stays inside that cluster.

Operationally, the failures are predictable: kubeadm certificates reaching their first anniversary, mesh trust anchors expiring, kubelet serving CSRs left unapproved, provider database CAs rotating, and MQ key repositories updated on one queue manager but not its partner. Monitor certificate expiry on every platform CA, count workload certificates in aggregate rather than individually (Chapter 18), alert on plaintext connections reported by meshes and brokers, and scan connection strings in code repositories for `TrustServerCertificate=true`, `sslmode=disable` and similar settings.

> **Compliance hook.** PCI DSS v4.0.1 requirement 4.2.1 mandates strong cryptography only over open, public networks, but requirements 3.5 and 3.6 (protecting stored account data and its keys) apply to Kubernetes Secrets and Kafka payloads that hold card data, and requirement 8.6 governs system and application account credentials such as database and broker passwords. NIST SP 800-204A gives security guidance for service-mesh architectures, NIST SP 800-190 covers container security, and the NSA and CISA Kubernetes Hardening Guide recommends encrypting Secrets at rest and using TLS between components. NIST SP 800-53 controls SC-8 (transmission confidentiality and integrity), SC-12 (cryptographic key establishment), SC-28 (protection of information at rest) and IA-9 (service identification and authentication) map to this chapter, as do ISO/IEC 27001:2022 Annex A controls 8.24 (use of cryptography) and 8.26 (application security requirements).

## 24.11 Lab: Kubernetes PKI, Secrets encryption and mesh mTLS

You need Docker, `kind`, `kubectl`, `jq` and OpenSSL. You will inspect a cluster's PKI, encrypt Secrets in etcd, and watch Istio issue and enforce workload certificates.

**1. Create a cluster and inspect its PKI.**

```bash
kind create cluster --name lab24
N=lab24-control-plane
docker exec $N kubeadm certs check-expiration
docker exec $N ls /etc/kubernetes/pki /etc/kubernetes/pki/etcd
docker cp $N:/etc/kubernetes/pki/apiserver.crt .
openssl x509 -in apiserver.crt -noout -subject -issuer -enddate \
  -ext subjectAltName
```

Note the one-year leaf lifetimes against the ten-year CAs, and the API server's SANs (service IP, DNS names and node address).

**2. Look at kubelet certificate requests.**

```bash
kubectl get csr
docker exec $N ls -l /var/lib/kubelet/pki
```

The rotating client certificate appears as `kubelet-client-current.pem`, a symlink to the latest issued certificate.

**3. Prove that Secrets are stored in clear.** Create a Secret and read it straight from etcd.

```bash
kubectl create secret generic before --from-literal=pin=1234
etcd_get() {
  kubectl -n kube-system exec etcd-$N -- etcdctl \
    --cacert /etc/kubernetes/pki/etcd/ca.crt \
    --cert /etc/kubernetes/pki/etcd/server.crt \
    --key /etc/kubernetes/pki/etcd/server.key \
    get "/registry/secrets/default/$1" \
    | tr -c '[:print:]' '.' | head -c 300; echo
}
etcd_get before
```

You will see `pin` and `1234` in the output.

**4. Enable encryption at rest.** Write an `EncryptionConfiguration` with a random AES-GCM key, copy it into the control-plane node and add the flag to the API server's static pod manifest.

```bash
KEY=$(head -c 32 /dev/urandom | base64)
cat > enc.yaml <<EOF
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]
    providers:
      - aesgcm:
          keys:
            - name: key1
              secret: ${KEY}
      - identity: {}
EOF
docker cp enc.yaml $N:/etc/kubernetes/pki/enc.yaml
F=--encryption-provider-config=/etc/kubernetes/pki/enc.yaml
docker exec $N sed -i \
  "s|^    - kube-apiserver\$|&\n    - $F|" \
  /etc/kubernetes/manifests/kube-apiserver.yaml
```

The kubelet restarts the API server. Wait until `kubectl get nodes` answers again (about a minute).

**5. Compare old and new Secrets, then rewrite.**

```bash
kubectl create secret generic after --from-literal=pin=1234
etcd_get after
etcd_get before
kubectl get secrets -A -o json | kubectl replace -f -
etcd_get before
```

The new Secret begins with `k8s:enc:aesgcm:v1:key1:` followed by ciphertext. The old one stays in clear until it is rewritten. In production you would use the `kms` provider so that the key is not in a file beside the data.

**6. Install Istio and look at a workload certificate.**

```bash
curl -L https://istio.io/downloadIstio | sh -
export PATH="$PWD/$(ls -d istio-* | head -n 1)/bin:$PATH"
istioctl install --set profile=minimal -y
kubectl create namespace demo
kubectl label namespace demo istio-injection=enabled
kubectl -n demo create deployment web --image=nginx:1.27
kubectl -n demo expose deployment web --port 80
kubectl -n demo run client --image=curlimages/curl:8.10.1 \
  --command -- sleep 86400
kubectl -n demo wait --for=condition=Ready pod --all --timeout=180s
istioctl proxy-config secret -n demo deployment/web -o json \
  | jq -r '.dynamicActiveSecrets[0].secret.tlsCertificate
           .certificateChain.inlineBytes' \
  | base64 -d | openssl x509 -noout -subject -dates \
      -ext subjectAltName
```

The subject is empty; the identity is in the URI SAN, `spiffe://cluster.local/ns/demo/sa/default`. The validity is about 24 hours.

**7. Enforce STRICT mTLS and test from outside the mesh.**

```bash
kubectl -n demo apply -f - <<'EOF'
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
spec:
  mtls:
    mode: STRICT
EOF
kubectl -n demo exec client -c client -- \
  curl -s -o /dev/null -w '%{http_code}\n' http://web.demo
kubectl create namespace outside
kubectl -n outside run probe --rm -it --restart=Never \
  --image=curlimages/curl:8.10.1 -- curl -sS -m 5 http://web.demo
```

The meshed client gets `200`; the probe outside the mesh is refused, because it cannot present a certificate from the mesh CA. Delete the PeerAuthentication and try again to see how PERMISSIVE mode silently accepts plaintext. Clean up with `kind delete cluster --name lab24`.

**Optional cloud extension.** Create a small managed cluster (for example EKS with a customer managed AWS KMS key for Secrets encryption, or GKE with application-layer secrets encryption) and inspect the KMS key's usage logs as you create Secrets. Managed control planes, nodes and KMS keys are all billed while they exist, typically several dollars a day; delete the cluster and schedule the key for deletion when you finish.

## 24.12 Failure story: the Azure leap-day certificate outage

On 29 February 2012, Microsoft's Windows Azure suffered a widespread outage caused by a platform-internal certificate. Microsoft published a detailed root cause analysis.

When a new virtual machine started, a guest agent inside it created a **transfer certificate**, which the platform used to protect secrets sent to the VM. The code set the certificate's expiry by taking the current date and adding one to the year. On 29 February 2012 that produced 29 February 2013, a date that does not exist, so certificate creation failed. The guest agent exited, and the host agent, after repeated failures, concluded that the server hardware was faulty and marked it for human investigation. As new VMs were deployed and existing ones were moved, the failure spread across clusters. To stop the spread, Microsoft disabled service management worldwide, so customers could not deploy or change services for many hours. During recovery, a hotfix rolled out with a mismatched component took down running VMs in several clusters, extending the outage. Microsoft gave affected customers a service credit of 33%.

The lessons apply to every platform PKI in this chapter:

- **Internal certificates are production dependencies**, even when no human ever sees them. Kubelet, etcd, mesh and transfer certificates fail the same way public ones do.
- **Validity arithmetic is code**, and code has bugs. Compute expiry as a duration from issuance using a tested date library, never by editing calendar fields.
- **Automatic remediation can amplify a certificate failure.** The host agent's "bad hardware" logic turned one bug into a fleet-wide incident. Make health checks distinguish certificate errors from infrastructure faults.
- **Test date boundaries**: leap days, year ends, time zones and the first anniversary of a cluster.

## 24.13 Chapter summary

- Internal service traffic needs mutual authentication, not only encryption, and most internal protocols default to failing open.
- A kubeadm cluster runs three private CAs plus a service account signing key; leaf certificates last a year and are renewed on upgrade, so unmaintained clusters fail on their anniversary.
- Kubelet client certificates rotate automatically, but serving certificates need `serverTLSBootstrap` and a safe approval process; OpenShift and managed services automate most control-plane rotation.
- Kubernetes Secrets are plaintext in etcd until encryption at rest is configured; KMS v2 envelope encryption keeps the KEK in an external KMS, and existing Secrets must be rewritten.
- Service meshes issue short-lived SPIFFE-format certificates and enforce mTLS; plug in an enterprise-controlled intermediate, move from PERMISSIVE to STRICT, and rehearse trust anchor rotation.
- SPIFFE and SPIRE give attested workload identities across clusters, virtual machines and clouds, with federation between trust domains.
- API gateways must validate clients, tokens and backends, and backends must accept only the gateway.
- Kafka, message queues and database drivers need TLS on every listener and full certificate verification; field-level encryption keeps sensitive payloads from brokers.
- Mainframe protocols such as TN3270 and IBM MQ support TLS through AT-TLS, RACF key rings and channel cipher specifications, and MQ AMS protects messages at rest in queues.
